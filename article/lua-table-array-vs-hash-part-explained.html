Lua Table Array vs Hash Part Explained

In the Lua programming language, tables are the sole data structuring mechanism, serving as arrays, dictionaries, sets, and objects through a single unified interface. Internally, the standard Lua C runtime splits this single abstraction into two distinct physical representations: the array part and the hash part. This hybrid implementation allows Lua to optimize memory consumption and execution speed automatically, using flat, contiguous memory for sequential integer keys and a collision-handled hash table for arbitrary or sparse keys without requiring any explicit configuration from the programmer.

The Internal Dual Architecture

Under the hood, a Lua table is represented as a C structure containing two primary memory segments:

  • TValue *array: A pointer to a contiguous block of values representing the array part.
  • Node *node: A pointer to an array of nodes representing the hash part, where each node stores a key, a value, and a pointer to the next element in a collision chain.

When a value is read from or written to a table, Lua inspects the key to decide whether to query the array segment or the hash segment.

The Array Part

The array part is designed for dense, 1-based sequential integer keys (1, 2, ..., n).

  • Memory Efficiency: The array part only stores values. The keys are implicit based on their offset in memory, requiring zero overhead for key storage.
  • Access Performance: Lookups and assignments run in constant time (\(O(1)\)) through direct pointer arithmetic (e.g., array[key - 1]), making it significantly faster than the hash part.
  • Boundary Operations: The length operator (#) operates most predictably when keys form an unbroken sequence inside this contiguous segment.

The Hash Part

The hash part is a generic associative array capable of storing values indexed by any valid Lua value, except nil and NaN.

  • Key Types: It holds non-integer keys (such as strings, functions, and nested tables), floating-point numbers, negative integers, zero, and integer keys that are too sparse to justify array storage.
  • Memory Overhead: Each entry in the hash part requires a Node structure that holds the explicit key, the stored value, and a link field to manage collisions. Consequently, elements in the hash part consume substantially more memory than elements in the array part.
  • Lookup Mechanism: Key access requires running the key through a hash function, mapping it to a main position in the node buffer, and potentially traversing a linked collision list (resolved via an internal open-addressing variation known as Brent’s method). While average access time is still \(O(1)\), it incurs higher CPU overhead than direct array indexing.

Automatic Allocation and Rehashing

Lua dynamically determines the division between the array and hash parts during table creation and resizing via an internal routine called rehashing.

When a table grows and requires more space:

  1. Lua counts all existing keys, identifying integer keys and arbitrary keys.
  2. It calculates the optimal power-of-two size for the array part such that more than half of the allocated array slots will be populated (ensuring at least 50% density).
  3. Integer keys that fit within this dense range are allocated to the array part.
  4. Any remaining keys—including integers outside the dense boundary and all non-integer keys—are allocated to the hash part.

This dynamic division allows Lua tables to provide the simplicity of a universal mapping type while retaining the raw execution performance of native C arrays for list-based data.
