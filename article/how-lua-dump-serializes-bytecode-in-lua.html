How lua_dump Serializes Bytecode in Lua

The lua_dump function in the Lua C API serializes a compiled Lua function into a binary byte stream, allowing code to be saved, transmitted, and reloaded without recompilation. This process works by traversing the internal function prototype (Proto) and emitting its constituent elements—including binary headers, virtual machine instructions, constants, upvalue references, and debug metadata—sequentially through a user-defined writer callback. This article details the internal mechanics of lua_dump, how the serialization pipeline is structured, and how each component of a compiled chunk is represented in binary format.

The C API Interface and lua_Writer

At the API level, lua_dump is defined with the following signature:

int lua_dump (lua_State *L, lua_Writer writer, void *data, int strip);

The function expects a compiled Lua function at the top of the stack. It does not output a monolithic memory buffer directly; instead, it delegates output handling to a callback function of type lua_Writer:

typedef int (*lua_Writer) (lua_State *L, const void* p, size_t sz, void* ud);

Whenever the serialization engine prepares a block of bytes, it calls writer, passing the byte buffer pointer p, the buffer size sz, and the user-supplied pointer data. This streaming model allows Lua to stream bytecode directly to files, memory buffers (such as in string.dump), or network sockets without allocating large intermediate strings. The strip parameter instructs the engine whether to discard debug metadata (line numbers, local variable names) to produce smaller payloads.

The Serialization Pipeline (ldump.c)

Internally, lua_dump extracts the underlying Proto struct from the closure on the stack and hands control to internal dumping logic, implemented primarily in ldump.c via the function luaU_dump.

The process is managed using an internal state structure (DumpState), which wraps the target lua_State, the writer callback, user data, error status, and the stripping flag. The dumper serializes data in strict order:

  1. The Binary Header: Validates compatibility when reloading.
  2. The Main Prototype: The top-level function representing the chunk.
  3. Closing Signatures: Endianness and floating-point format checks.

Structure of the Binary Stream

1. The Chunk Header

Before writing executable bytecode, Lua writes a standardized header to ensure that the virtual machine loading the binary matches the environment in which it was compiled. The header consists of:

  • Signature (Magic Bytes): The four-byte sequence \x1bLua (0x1B, 0x4C, 0x75, 0x61), identifying the stream as precompiled Lua bytecode.
  • Version Number: A single byte encoding the Lua version (e.g., 0x54 for Lua 5.4).
  • Format Flag: A byte indicating the bytecode format (0 indicates official standard Lua).
  • Environment Validation Data: Conversion constants that verify system architecture:
    • Sizes of native types (int, size_t, Instruction, lua_Integer, lua_Number).
    • Endianness test integer (typically 0x5678 or a defined format integer).
    • Floating-point format validation number (typically 370.5 or PI).

If any byte in this header does not match the parameters of the loading environment, lua_load rejects the chunk immediately to prevent memory corruption or execution errors caused by mismatched data representations.

2. Function Prototype Serialization

A Lua function is represented in memory by a Proto object. In luaU_dump, functions are serialized through a dedicated internal routine that writes each field of the Proto sequentially:

  • Source Name: The string identifying the source file or chunk (omitted if strip is enabled).
  • Line Defined and Last Line Defined: Integers representing the beginning and ending lines of the function definition in the original source code.
  • Parameter Count: The number of fixed parameters accepted by the function.
  • Vararg Flag: A byte specifying whether the function takes variable arguments (...).
  • Max Stack Size: The maximum number of virtual registers required by the execution frame.
  • Code (Bytecode Instructions): The array of VM instructions (Instruction), each written as fixed-size integers (typically 32-bit unsigned values) containing the opcode and register operands.
  • Constants: The literal values used in the function. The dumper first writes the number of constants, followed by each constant:
    • A tag byte indicating the type (LUA_TNIL, LUA_TBOOLEAN, LUA_TNUMFLT, LUA_TNUMINT, LUA_TSHRSTR, LUA_TLNGSTR).
    • The actual value according to the type (strings are prefixed by their length).
  • Upvalues: A list of descriptors for external variables captured in lexical scopes. Each descriptor identifies whether the upvalue resides in the immediate parent stack or in the parent's upvalue table, along with its index.
  • Nested Prototypes: Functions defined inside the current function. The serialization function calls itself recursively for each child prototype, embedding nested closures into the byte stream.
  • Debug Information: If strip is zero, the dumper writes the line mapping array (connecting each bytecode instruction to a source line), local variable names with their active instruction ranges, and upvalue variable names. If strip is non-zero, these fields are written as empty arrays.

Low-Level Type Serialization

To ensure the byte stream remains compact, ldump.c employs specific binary encoders for basic types:

  • Integers and Floats: Native numeric values are copied directly as their raw memory bytes using low-level block writes (memcpy equivalents).
  • Variable-Length Integers: In modern Lua versions (such as Lua 5.4), size markers and line offsets are often encoded using variable-length quantities (7 bits per byte, with the eighth bit indicating continuation), minimizing storage space for small numerical values.
  • Strings: Serialized by first writing their length (as a size indicator or variable-length integer) followed by the raw byte buffer. Nil strings are indicated by a dedicated size value (typically 0).

Once the root prototype and all its child components have been processed through the lua_Writer callback, the stream is terminated, completing the serialization lifecycle.
