Converting Lua Sparse Tables to JSON Arrays

Converting Lua tables to JSON arrays presents significant challenges when dealing with sparse structures. Because Lua unifies arrays and hash maps into a single table type, serializing a table with non-contiguous integer keys (holes) introduces severe ambiguity. Standard serialization libraries struggle to determine whether such data should be treated as a JSON array or an object, how to represent missing indices, and how to safely compute table bounds without causing memory bloat or performance degradation.

The Ambiguity of the Length Operator

Lua calculates sequence length using the # operator, which is designed to return a boundary—an index n where t[n] ~= nil and t[n+1] == nil. When a table is sparse, multiple boundaries can exist simultaneously.

For instance, a table defined as t = { [1] = "a", [3] = "c" } lacks a value at index 2. Depending on internal table reallocation and the specific Lua runtime (such as PUC-Rio Lua versus LuaJIT), #t may evaluate to 1 or 3. If a JSON serializer relies on the # operator to determine the array boundary, it can prematurely truncate data, completely ignoring valid elements located after the first detected hole.

Array vs. Object Heuristics

JSON separates indexed lists ([]) from key-value maps ({}). Because Lua lacks native distinct array and map types, JSON encoders use heuristics to deduce the intended format. Typically, a library iterates through keys to confirm if they form a contiguous 1-to-N integer range.

When a sparse table fails this contiguous check, encoders generally react in one of two ways:

  1. Fallback to JSON Objects: The encoder converts the table into a JSON object with stringified numeric keys (e.g., {"1": "a", "3": "c"}). This violates data schemas when consuming applications expect a valid JSON array.
  2. Strict Failure: Some strict serializers throw runtime errors upon encountering missing indices, halting execution.

Memory Exhaustion from Gap Filling

If an encoder forces a sparse table into a JSON array, it must reconcile Lua's nil with JSON's requirement that every array index contains an explicit token. The standard solution is inserting null for every missing index.

While functional for small gaps, this approach fails dramatically with wide intervals. A table with keys t[1] = true and t[1000000] = true will compel the encoder to allocate and serialize 999,998 JSON null values. This causes massive memory spikes, extensive garbage collection pressure, and large network payloads that degrade performance across the entire application stack.

Handling 0-Based and Negative Indices

Standard Lua sequences start at index 1, whereas JSON arrays are 0-indexed by position. Lua permits 0 and negative numbers as valid table keys. If a sparse table contains t[0] or t[-5], it cannot map directly to a standard sequence without transforming or discarding keys. Serializers either drop these keys, shift index positions (breaking downstream contract logic), or abandon array encoding entirely to represent them as object keys.

Strategies for Reliable Serialization

To safely handle sparse data intended for JSON arrays, systems typically adopt the following patterns:

  • Explicit Metatable Tagging: Using libraries that support metatables (like cjson.empty_array) to explicitly mark a table as an array regardless of key distribution.
  • Pre-serialization Normalization: Writing a preprocessing step that maps sparse data into a dense list of objects (e.g., [{ "index": 1, "value": "a" }, { "index": 3, "value": "c" }]).
  • Iterative Key Scanning: Manually computing the absolute maximum integer key using pairs() instead of #, while setting an upper threshold on allowable gap sizes to prevent runaway null padding.
