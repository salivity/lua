OpenResty Lua Execution Lifecycle Explained

This article provides an overview of the OpenResty execution lifecycle, detailing how embedded Lua code executes sequentially within Nginx request-processing phases. By understanding the execution order of key directives such as rewrite_by_lua, access_by_lua, and content_by_lua, developers can properly architect routing rules, authentication mechanisms, proxying, and response generation without introducing race conditions or unintended side effects.

The OpenResty Phase Model

OpenResty integrates LuaJIT directly into the Nginx event loop. Instead of executing Lua code in a single generic block, it exposes specific phases of Nginx's internal request-processing lifecycle as configurable directives. Each phase serves a distinct architectural purpose and executes in a deterministic order.

Below is the chronological execution order for an HTTP request handled by OpenResty.

1. Initialization Phases (Server Startup)

These phases execute outside the context of individual client requests:

  • init_by_lua*: Runs when the Nginx master process loads or reloads the configuration file. It is used to initialize global Lua modules, pre-load libraries, and set up read-only shared state.
  • init_worker_by_lua*: Runs immediately after a worker process is created. It is commonly used to establish background timers (via ngx.timer.at) for periodic tasks like health checking or metric scraping.

2. Request Handling Phases (Per Request)

When a client initiates an HTTP request, OpenResty processes it through the following operational phases:

ssl_certificate_by_lua*

Executes during the SSL/TLS handshake before any HTTP data is parsed. It allows dynamic loading of SSL certificates and private keys based on Server Name Indication (SNI).

set_by_lua*

Executes alongside standard Nginx rewrite module directives. It is designed to compute dynamic values and assign them directly to standard Nginx variables. It executes synchronously and does not support non-blocking I/O operations (cosockets).

rewrite_by_lua*

Executes early in the request processing pipeline, directly after URI matching.

  • Primary Use Cases: Rewriting URIs, internal redirects, manipulating request headers, or short-circuiting requests early.
  • Characteristics: Supports non-blocking I/O (cosockets). Calling ngx.redirect() or ngx.exit(status) here terminates further phase execution and immediately sends the response to the client.

access_by_lua*

Executes after the rewrite phase has determined the final URI and location block, but before the response payload is produced.

  • Primary Use Cases: Authentication, authorization, rate limiting, and IP blacklisting/whitelisting.
  • Characteristics: Acts as a security gatekeeper. If access checks pass, execution proceeds to the content generation phase. If an access check fails, an ngx.exit(ngx.HTTP_FORBIDDEN) or ngx.exit(ngx.HTTP_UNAUTHORIZED) call terminates the request cleanly.

content_by_lua*

Acts as the primary content generation handler. In Nginx, only one content handler can run per location.

  • Primary Use Cases: Generating dynamic HTTP responses, querying upstream databases/caches directly using Lua cosockets, and serving API payloads.
  • Characteristics: If content_by_lua* is specified in a location, standard content handlers (such as proxy_pass or root) in the same location are bypassed. The response body is typically produced here using ngx.say() or ngx.print().

3. Upstream and Response Processing Phases

Once the content handler finishes or delegates work to an upstream server, the response enters the downstream delivery pipeline:

balancer_by_lua*

Executes when proxy_pass, fastcgi_pass, or similar upstream modules require an endpoint address. It enables programmable, dynamic load-balancing logic (e.g., consistent hashing, round-robin) per request.

header_filter_by_lua*

Executes as soon as all response status codes and headers are assembled, but before any part of the response body is streamed to the client.

  • Primary Use Cases: Adding, removing, or modifying HTTP response headers (e.g., adding security headers like Content-Security-Policy).
  • Characteristics: Cosocket operations are disabled in this phase.

body_filter_by_lua*

Executes iteratively for each chunk of the response body as it streams through Nginx.

  • Primary Use Cases: Data transformations on the fly, streaming compression, or response truncation.
  • Characteristics: Operates as a streaming filter. It can be invoked multiple times per request as data buffers are flushed to the client.

4. Post-Request Phase

log_by_lua*

Executes after the request has completely finished sending data to the client.

  • Primary Use Cases: Structured access logging, custom metric reporting (e.g., Prometheus counters), and latency tracking.
  • Characteristics: Occurs asynchronously relative to client latency; failures here do not affect the client response. Cosocket operations are not supported, though operations on shared memory dictionaries (ngx.shared.DICT) are permitted.

By mapping logic strictly according to this execution path—rewriting parameters in rewrite_by_lua, validating tokens in access_by_lua, and producing payloads in content_by_lua—applications running on OpenResty maintain high throughput and predictable execution behavior.
