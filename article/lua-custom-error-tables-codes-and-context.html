Lua Custom Error Tables: Codes and Context

Handling errors in Lua often relies on simple strings, which makes parsing failure details brittle and inefficient. By passing custom tables to the built-in error() function instead of plain text, developers can attach structured error codes, debugging context, dynamic variables, and stack traces. This approach allows calling code wrapped in pcall or xpcall to inspect machine-readable metadata directly, decoupling error diagnosis from human-readable text formatting.

The Limitation of String-Based Errors

The conventional approach in Lua uses error("File not found: " .. filename) to signal issues. While readable in a console log, this pattern forces calling functions to parse strings via regex or string.find to determine programmatic actions. String parsing is fragile, susceptible to minor message changes, and lacks standard fields for conveying critical diagnostic data like HTTP status codes, missing parameters, or timestamps.

Creating and Raising Structured Error Tables

Because Lua's error() function accepts any Lua value—not just strings—you can pass a fully formed table. A structured error table typically contains:

  • code: A unique string or integer identifying the error type (e.g., "ERR_NOT_FOUND", 404).
  • message: A human-readable description of what failed.
  • context: A table containing runtime values that contributed to the error (e.g., user IDs, payloads, paths).
local function readFile(path)
    local file = io.open(path, "r")
    if not file then
        error({
            code = "FILE_NOT_FOUND",
            message = "Unable to open target file for reading.",
            context = {
                path = path,
                timestamp = os.time()
            }
        }, 2)
    end
    local content = file:read("*a")
    file:close()
    return content
end

The second argument to error() defines the stack level, ensuring stack-trace attribution points to the caller rather than the utility function itself.

Handling Structured Errors with pcall

When an operation wrapped in pcall() fails, the second return value contains the error object. If a table was passed to error(), that table is returned directly, allowing the caller to switch execution based on the error code.

local success, result = pcall(readFile, "nonexistent.txt")

if not success then
    if type(result) == "table" and result.code then
        if result.code == "FILE_NOT_FOUND" then
            print("Handled missing file at path: " .. result.context.path)
        else
            print("Generic error: " .. result.message)
        end
    else
        -- Fallback for standard string errors or external runtime errors
        print("Standard Lua error: " .. tostring(result))
    end
end

Implementing __tostring for Compatibility

Third-party libraries or logging utilities may attempt to treat error objects as plain strings. To maintain compatibility without sacrificing structure, assign a metatable containing a __tostring metamethod to the error table:

local ErrorMetatable = {
    __tostring = function(self)
        return string.format("[%s] %s (Path: %s)", 
            self.code, 
            self.message, 
            self.context and self.context.path or "N/A"
        )
    end
}

local function createError(code, message, context)
    local err = {
        code = code,
        message = message,
        context = context or {}
    }
    return setmetatable(err, ErrorMetatable)
end

Using this factory function, the error table can be printed directly by logging layers via tostring(err) while downstream recovery routines retain direct access to err.code and err.context.
