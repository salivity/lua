How Pegasus.lua Handles HTTP and WebSockets

This article provides an overview of how the Pegasus.lua web server processes incoming network traffic in Lua environments. It details the server's lifecycle management for standard HTTP transactions via structured request and response objects, as well as the transition mechanisms required to support persistent, bidirectional WebSocket communication over raw TCP sockets.

Architecture and Standard Request Processing

Pegasus.lua is a lightweight, non-blocking HTTP server built natively for Lua, relying on the LuaSocket library to manage low-level network I/O. Its primary execution model centers around an event loop that listens for incoming TCP connections on a configured host and port.

When a client initiates a standard HTTP request, Pegasus.lua handles the transaction through the following sequence:

  1. Connection Acceptance: The server accepts the incoming client socket and initializes a buffered reader to read the raw HTTP stream.

  2. Parsing Request Headers: Pegasus.lua reads the request line to extract the HTTP method (GET, POST, PUT, DELETE, etc.), the request target path, and the HTTP version. It then parses incoming headers line by line into a key-value Lua table, normalizes paths, and extracts query parameters.

  3. Payload Ingestion: If headers such as Content-Length or Transfer-Encoding: chunked are present, Pegasus reads the specified bytes from the socket to assemble the request body.

  4. Context Creation: The server constructs two primary objects:

    • Request: Exposes client data, including path, headers, query parameters, method, and raw payload data.
    • Response: Exposes methods to construct and write HTTP response headers, set cookies, define status codes, and stream or write the response body.

  5. Handler Invocation: Pegasus.lua invokes the user-defined callback function, passing the Request and Response objects as arguments:

    local Pegasus = require('pegasus')

local server = Pegasus:new({
    port = 9090,
    location = './public'
})

server:start(function(req, rep)
    local path = req:path()
    if path == "/api/status" then
        rep:addHeader("Content-Type", "application/json")
        rep:write('{"status": "ok"}')
    else
        rep:status(404)
        rep:write("Not Found")
    end
end)

  6. Connection Termination: Once the handler execution finishes and the response buffer flushes to the client, the server closes the TCP socket or prepares it for subsequent requests if HTTP Keep-Alive is negotiated.

WebSocket Handshake and Socket Hijacking

Standard HTTP transactions are stateless and transient, while WebSockets require a persistent, full-duplex communication channel. Pegasus.lua does not implement a monolithic, built-in WebSocket framing protocol parser by default; instead, it relies on protocol upgrades and underlying socket access to facilitate WebSocket communication.

The WebSocket lifecycle in Pegasus.lua works through the following phases:

1. Upgrade Detection

A WebSocket connection begins as a standard HTTP GET request containing specific headers:

  • Upgrade: websocket
  • Connection: Upgrade
  • Sec-WebSocket-Key: <base64-nonce>
  • Sec-WebSocket-Version: 13

The Pegasus.lua request handler inspects incoming headers to detect whether the client is requesting an upgrade:

local function is_websocket_request(req)
    local headers = req:headers()
    return headers["upgrade"] and headers["upgrade"]:lower() == "websocket"
end

2. The Upgrade Handshake

To complete the handshake, the server must compute the Sec-WebSocket-Accept header. This requires concatenating the incoming Sec-WebSocket-Key with the standard globally unique identifier 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, computing the SHA-1 hash of the result, and encoding that hash in Base64.

Pegasus.lua responds with an HTTP/1.1 101 Switching Protocols status code:

rep:status(101)
rep:addHeader("Upgrade", "websocket")
rep:addHeader("Connection", "Upgrade")
rep:addHeader("Sec-WebSocket-Accept", computed_key)
rep:sendHeader()

3. Bypassing HTTP Lifecycle

Once the 101 Switching Protocols response is sent, the standard HTTP cycle terminates without closing the client socket. At this point, the underlying raw client socket (managed by LuaSocket) is handed over directly to a dedicated WebSocket implementation or framing library (such as lua-websockets).

4. Frame Processing and Event Dispatching

Once the socket is detached from HTTP handling:

  • Framing Protocol: Data is no longer formatted as plain-text HTTP messages. Pegasus hands data reading over to logic that parses RFC 6455 data frames, handling masking keys, opcodes (text, binary, ping, pong, close), and payload lengths.
  • Bi-directional Flow: The Lua server can independently write frames to the raw client socket without waiting for a new request, allowing real-time event pushing.
  • Connection Closure: The socket remains open until either endpoint transmits an explicit close frame (opcode 0x8) or the underlying TCP connection breaks.
