Lua Registry Guide: Storing C References Safely

This article provides an overview of the Lua registry and its role in C and Lua interoperability. You will learn what the registry is, why standard Lua globals are unsuitable for C modules, and how to utilize the registry alongside the auxiliary reference system (luaL_ref and luaL_unref) to safely anchor Lua objects against garbage collection.

What Is the Lua Registry?

The Lua registry is a regular Lua table that is accessible only to C code via the C API. It resides at a pseudo-index defined by the constant LUA_REGISTRYINDEX.

Because pure Lua scripts cannot directly access LUA_REGISTRYINDEX, the registry serves as a private storage area. It allows C libraries to store values, share state across different C functions, and anchor Lua values in memory without polluting or conflicting with the global variable table (_G).

Why Use the Registry Instead of Global Variables?

When interacting with Lua from C, developers often need to keep references to Lua objects (such as callbacks, tables, or coroutines) alive across multiple API calls. Storing these objects in the global environment (_G) introduces two major issues:

  1. Name Collisions: Different third-party C libraries might overwrite each other's global keys.
  2. Accidental Modification: Lua scripts can alter, overwrite, or delete global variables, leading to crashes or undefined behavior in the C runtime.

Additionally, keeping a raw C pointer to a Lua object is unsafe because Lua’s garbage collector (GC) cannot trace references stored in native C memory. If an object is not referenced anywhere inside Lua, the GC will collect it, leaving dangling pointers in your C code. The registry solves this by keeping the object rooted inside Lua's GC graph.

Storing References with luaL_ref and luaL_unref

The recommended and most common way to store values in the registry is using the reference system provided by Lua’s auxiliary library. This system creates unique integer keys for values, eliminating key-collision issues completely.

1. Creating a Reference (luaL_ref)

To anchor an object:

  1. Push the target Lua object onto the stack.
  2. Call luaL_ref(L, LUA_REGISTRYINDEX).

luaL_ref pops the top value from the stack, assigns it an integer key inside the registry, and returns that integer reference.

// Assume a Lua callback function is at the top of the stack
int callback_ref = luaL_ref(L, LUA_REGISTRYINDEX);

// The callback is now safely stored in the registry, 
// protected from garbage collection.

2. Retrieving a Reference (lua_rawgeti)

To retrieve the object later and push it back onto the Lua stack, use lua_rawgeti with the stored integer reference:

// Push the referenced object onto the stack
lua_rawgeti(L, LUA_REGISTRYINDEX, callback_ref);

// Verify and call the function if needed
if (lua_isfunction(L, -1)) {
    lua_pcall(L, 0, 0, 0);
} else {
    lua_pop(L, 1);
}

3. Releasing a Reference (luaL_unref)

When the reference is no longer needed, it must be freed to prevent memory leaks and allow the garbage collector to reclaim the object:

luaL_unref(L, LUA_REGISTRYINDEX, callback_ref);
callback_ref = LUA_NOREF; // Good practice to reset the variable

luaL_unref frees the integer key in the registry and marks it for reuse by future luaL_ref calls.

Alternative: Using Static Memory Addresses as Keys

If you need to associate a single C library instance with registry data rather than dynamic references, you can use the address of a static C variable as a unique key:

static const char my_unique_key = 'k';

// Storing a value:
lua_pushlightuserdata(L, (void*)&my_unique_key);
lua_pushvalue(L, -2); // The value you want to store
lua_rawset(L, LUA_REGISTRYINDEX);

// Retrieving the value:
lua_pushlightuserdata(L, (void*)&my_unique_key);
lua_rawget(L, LUA_REGISTRYINDEX);

Because the memory address of my_unique_key is unique across the entire process address space, no other module can accidentally collide with your registry key.
