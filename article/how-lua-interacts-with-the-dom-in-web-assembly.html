How Lua Interacts with the DOM in WebAssembly

Running the Lua programming language inside a WebAssembly (Wasm) browser context requires a dedicated interop bridge, as WebAssembly cannot directly manipulate the Document Object Model (DOM). Because WebAssembly execution remains sandboxed with access restricted to linear memory and host imports, Lua code compiled to Wasm must route all DOM operations through an intermediate JavaScript abstraction layer. This article breaks down the architectural pipeline, object reference handling, and event system that make Lua-to-DOM communication possible.

The WebAssembly Architectural Boundary

WebAssembly currently lacks direct access to web APIs and the DOM. Any language targeting Wasm—including standard C implementations of Lua (PUC-Rio Lua) compiled via toolchains like Emscripten—inherits this limitation.

To bridge this gap, the environment uses a two-tier execution pipeline:

  1. Lua interacts with host-bound C functions via the standard Lua C API (lua_pushcfunction, lua_CFunction).
  2. The compiled C code invokes imported JavaScript functions provided by the host runtime (such as Emscripten's EM_JS or WebAssembly System Interface host bindings).
  3. The JavaScript host function performs the requested DOM mutation (e.g., document.createElement, element.appendChild) and returns data back across the boundary.

Object Marshalling and Handle Management

Because JavaScript DOM objects live in the browser's garbage-collected heap and cannot reside directly inside Lua's or WebAssembly's linear memory, the runtime manages them using opaque handles or object tables.

  1. Handle Allocation: When a Lua script requests a DOM node (e.g., window.document:getElementById("app")), JavaScript fetches the node and assigns it a unique integer key or symbol in a host-side registry map.
  2. Userdata Wrapping: The integer handle is passed into WebAssembly, where the Lua C API wraps it as a Lua userdata object. Metatables are assigned to this userdata to overload operators and method indexing (__index, __newindex).
  3. Property and Method Resolution: When Lua reads a property or calls a method on the userdata, the metamethod forwards the handle and the requested attribute name back through to JavaScript via an imported function. JavaScript looks up the actual DOM node in the registry, performs the operation, and serializes the result back to Lua.
  4. Garbage Collection Synchronization: To prevent memory leaks, Lua's __gc metamethod notifies the JavaScript registry to delete its reference when the Lua userdata is collected, allowing the browser's engine to reclaim the DOM element.

Bidirectional Event Handling

DOM interaction requires handling asynchronous user inputs, such as clicks and keyboard inputs. The Lua-Wasm bridge achieves this through callback registries:

  1. Listener Registration: When Lua registers an event listener (button:addEventListener("click", callback)), the Lua engine stores the Lua function in the Lua registry to protect it from garbage collection and passes an assigned callback ID to the JavaScript bridge.
  2. Event Triggering: JavaScript attaches a native listener to the target DOM element. When fired, the listener executes an exported WebAssembly function, supplying the callback ID along with relevant event payload data.
  3. Lua Invocation: The exported Wasm function locates the corresponding Lua function using the callback ID and executes it via lua_pcall, delivering the event context back to the Lua runtime.

Performance Considerations

Bridging Lua and the DOM through WebAssembly incurs boundary-crossing overhead. Every DOM read or write traverses three layers: the Lua virtual machine, the WebAssembly linear memory boundary, and the JavaScript runtime. High-performance implementations mitigate this overhead by batching DOM updates, caching frequently accessed properties within Lua, or using specialized memory-shared buffers for large data transfers rather than granular property-by-property manipulation.
