Can Multiple lua_State Run in Different OS Threads?

Yes, multiple independent lua_State instances can run simultaneously across different operating system (OS) threads in the Lua programming language. Because core Lua is designed to be fully reentrant and maintains no internal global mutable state across distinct master runtimes, each completely isolated lua_State operates independently within its own memory space. This article explains the architectural reasons why this is possible, distinguishes independent states from Lua coroutines, and covers key caveats regarding C libraries and data sharing.

Complete State Isolation

When you create a Lua state using luaL_newstate() or lua_newstate(), Lua allocates an entirely self-contained environment. This state includes its own:

  • Garbage collector and memory allocator
  • Global environment table (_G)
  • Registry table
  • Call stack and execution mechanisms

Because distinct states share no memory, pointers, or global locks at the C level, two or more OS threads can execute Lua bytecode inside their respective states simultaneously without data races or the need for a Global Interpreter Lock (GIL).

luaL_newstate() vs. lua_newthread()

A frequent source of confusion is the distinction between creating a new state and creating a new thread via the Lua C API:

  1. Independent States (luaL_newstate): Creates an entirely new runtime. These can be executed concurrently on separate OS threads without synchronization.
  2. Coroutines (lua_newthread): Despite the naming, lua_newthread allocates a coroutine (a new execution thread within the same overall state). Coroutines share the global state, string table, and garbage collector with the parent state. Running multiple coroutines from the same master state across different OS threads simultaneously is not thread-safe and requires external mutual exclusion (mutexes).

Reentrancy of the Lua Core

Standard Lua is written in ANSI C and deliberately avoids writable global or static variables. All state-specific data is encapsulated within the global_State struct, which is accessed strictly through the lua_State pointer passed into API calls. As long as a specific lua_State pointer is accessed by only one OS thread at any given moment, the core engine remains completely thread-safe.

Caveats: C Modules and Static Memory

While core Lua is thread-safe across independent states, issues can arise from external C libraries loaded into those states:

  • Static/Global C Variables: If a compiled C module uses non-thread-safe static or global variables, loading that module into multiple independent states across different threads can result in race conditions.
  • Third-Party C Dependencies: External C libraries bound to Lua must themselves be thread-safe and reentrant.
  • Non-Thread-Safe Standard C Functions: Certain platform-specific C standard library functions (e.g., standard setlocale) modify global process state and can cause side effects across threads.

Inter-Thread Communication

Because independent lua_State instances share no memory, they cannot directly access each other's variables. Communication between threads must be handled explicitly through:

  • Message Passing: Serializing data (such as JSON or bytecode strings) and passing it via thread-safe queues or pipes.
  • Shared Memory Buffers: Using C-level mutexes to guard shared buffers accessed by custom C functions exposed to each state.
  • Dedicated Multithreading Libraries: Libraries such as LuaLanes provide pre-built abstractions that manage independent states, channel-based communication, and data deep-copying across OS threads.
