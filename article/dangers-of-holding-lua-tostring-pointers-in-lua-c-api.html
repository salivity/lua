Dangers of Holding lua_tostring Pointers in Lua C API

Holding raw char pointers returned by lua_tostring across subsequent Lua C API calls is a frequent source of undefined behavior, memory corruption, and unpredictable crashes. When developers use lua_tostring, the returned pointer directly references an internal memory buffer managed entirely by Lua's garbage collector rather than an independent, static C-string. If subsequent API calls manipulate the Lua stack or trigger garbage collection, that underlying memory can be collected, reallocated, or overwritten, immediately turning the stored pointer into a dangling reference.

How Lua Manages String Memory

In the Lua runtime, strings are immutable, garbage-collected objects. When you invoke lua_tostring(L, index), Lua returns a const char* pointing directly to the internal character array of the string object stored on the Lua stack.

Lua does not duplicate this buffer for C. The pointer remains valid only as long as:

  1. The corresponding string object remains reachable on the Lua stack or within another referenceable Lua structure.
  2. The garbage collector does not sweep the object.
  3. The stack slot holding the object is not modified or popped.

Garbage Collection and Subsequent API Calls

Almost any subsequent call to the Lua C API has the potential to trigger a garbage collection cycle. Functions such as lua_pcall, lua_newtable, lua_pushstring, or any call that allocates memory can invoke the garbage collector.

If a developer extracts a pointer using lua_tostring and then executes another Lua API call that pops or replaces the original stack element, the string loses its reference anchor. If that subsequent call initiates an allocation, the garbage collector may identify the unanchored string as unreachable and free its memory. Accessing the raw pointer afterward reads from deallocated memory.

Stack Mutation Caused by lua_tostring

A subtle risk arises when calling lua_tostring on a value that is a number rather than an actual string. To convert the number, lua_tostring modifies the value directly on the stack, transforming the number into a string in place.

If subsequent code assumes the original stack layout or executes functions like lua_pop, lua_remove, or lua_settop, the converted string object can be removed from the stack unintentionally. Once removed, the pointer returned prior to the stack adjustment is no longer anchored, leaving it exposed to immediate collection.

Safe Alternatives and Best Practices

To safely handle strings extracted from Lua, developers should apply one of two standard approaches:

  • Copy the Data Immediately: If the string is required across multiple operations or outlives the immediate scope of the function, copy the contents into C-managed memory right away using functions such as strdup, memcpy, or a C++ container like std::string.
  • Anchor the Value on the Stack: If copying is unnecessary due to performance considerations, developers must guarantee that the string's index on the stack remains untouched and valid throughout the entire duration of the pointer's usage. The pointer must be completely discarded before any stack manipulation or API call that could disturb that anchor.
