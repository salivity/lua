How LuaRocks Handles Semantic Versioning Constraints

This article explains how LuaRocks, the package manager for Lua, parses and resolves semantic version constraints within its ecosystem. It details the constraint operators supported in rockspec manifests—focusing on the pessimistic version constraint (~>)—how the version comparison algorithm evaluates version strings, and the dependency resolution mechanism used to settle diamond dependencies and conflicting version requirements.

Version Constraints in Rockspec Files

LuaRocks defines package metadata and dependencies in .rockspec files. Within the dependencies table, packages specify external requirements alongside optional version constraints. Multiple constraints for a single package can be combined using commas, representing a logical AND condition.

LuaRocks supports the following relational operators:

  • ==: Exact version match (e.g., "lua == 5.1").
  • ~=: Not equal to.
  • > and >=: Strictly greater than, or greater than or equal to.
  • < and <=: Strictly less than, or less than or equal to.
  • ~>: The pessimistic version operator, specifically designed for Semantic Versioning (SemVer).

The Pessimistic Operator (~>)

To follow Semantic Versioning principles—where patch and minor updates preserve backward compatibility while major updates introduce breaking changes—LuaRocks implements the pessimistic constraint operator (~>).

The behavior of ~> depends on the precision of the specified version:

  • Two-part version (~> X.Y): Matches >= X.Y and < (X+1).0. For example, ~> 1.2 allows 1.2, 1.3, and 1.9.9, but excludes 2.0.0. This is suitable for libraries where minor releases are backward-compatible.
  • Three-part version (~> X.Y.Z): Matches >= X.Y.Z and < X.(Y+1).0. For example, ~> 1.2.3 permits 1.2.3 and 1.2.4, but excludes 1.3.0. This restricts updates purely to patch-level bug fixes.

Version String Parsing and Comparison

LuaRocks does not strictly enforce that authors follow SemVer, but its comparison algorithm accommodates semantic numbering schemes. Version strings are parsed into sequences of alphanumeric segments.

The comparison logic processes version strings by:

  1. Splitting strings by periods (.) and hyphens (-).
  2. Distinguishing between numeric components and textual suffixes (such as rc, beta, or scm).
  3. Comparing components sequentially from left to right. Numeric components are compared numerically (10 > 2), while text components are compared lexicographically (rc2 > rc1).
  4. Treating the package revision (the integer following the hyphen, such as 1.0.0-1) as the final discriminator to resolve updates to the rockspec packaging itself.

The Dependency Resolution Algorithm

When executing luarocks install, the package manager queries configured manifests (such as the default repository at luarocks.org or local mirrors) to fetch available versions of requested modules.

  1. Candidate Gathering: LuaRocks gathers all available releases matching the package name and filters out versions that do not satisfy the constraint query.
  2. Top-Down Evaluation: Candidate versions are evaluated in descending order (highest version number first) to install the most up-to-date compatible release.
  3. Recursive Resolution: Once a candidate version is selected, its own dependencies list is fetched and resolved recursively.
  4. Conflict Handling: If two packages depend on incompatible version constraints of a shared library (a diamond dependency conflict), standard LuaRocks installation aborts with an error indicating an unsatisfiable constraint. LuaRocks does not employ deep backtracking SAT solvers by default; it evaluates dependencies greedily based on the requested top-level targets.

Local Trees vs. System Deployments

LuaRocks supports parallel installations of multiple versions of the same rock within the file system (/lib/luarocks/rocks-5.x/), but runtime loading via standard require calls resolves only one active version per environment. To ensure strict isolation and avoid version mismatches across shared environments, modern Lua workflows often utilize project-local rocks trees (--tree flag) or tools like LuaRocks lockfiles to fix resolved versions immutably.
