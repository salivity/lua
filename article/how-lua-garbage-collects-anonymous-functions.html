How Lua Garbage Collects Anonymous Functions

In the Lua programming language, anonymous functions are first-class values represented internally as closures and managed entirely by Lua's automatic memory management system. When an anonymous function is created, memory is allocated on the heap to store its prototype and associated upvalues. Once all active references—such as local variables, global tables, or callbacks—are removed or go out of scope, the function becomes unreachable. Lua's garbage collector identifies these unreferenced closures during its mark-and-sweep cycles, deallocates their internal data structures, and safely reclaims the occupied memory.

Functions as First-Class Closures

Lua makes no internal distinction between a named function and an anonymous function; both are compiled into closure objects (LClosure). A closure consists of a reference to a function prototype (the compiled bytecode) and an array of upvalues (references to external local variables captured from enclosing scopes).

Because closures are dynamically allocated on the heap, their lifecycle is decoupled from the lexical scope where they are declared. An anonymous function remains alive as long as a reference path exists from a root object.

The Reachability Cycle

Lua's garbage collector operates on the principle of reachability. The collector starts scanning from a root set, which includes:

  • The global environment (_G)
  • The Lua registry
  • The current execution thread's stack (active local variables and temporary values)
  • Active coroutines

During execution, if an anonymous function is assigned to a variable or passed as an argument, a reference to that closure exists on the stack or within a table. When that variable goes out of scope, is reassigned, or is explicitly set to nil, the reference count drops conceptually, though Lua does not use reference counting. Instead, the pointer to the closure simply disappears from the root-accessible graph.

Mark-and-Sweep Execution

Lua employs an incremental mark-and-sweep garbage collector (with an optional generational mode in Lua 5.4). When references to an anonymous function are dropped, reclamation occurs across distinct phases:

  1. Mark Phase: The collector traverses all objects accessible from the root set. If an anonymous function can no longer be reached through any path of active variables, tables, or environments, its GC color flag is left uncolored (white).
  2. Atomic Phase: Any pending references and upvalues are finalized to ensure no boundary objects were missed during incremental mutations.
  3. Sweep Phase: The collector iterates through the linked list of all allocated objects. Any object still marked as unreachable (white) is freed. For an anonymous function, Lua deallocates the LClosure structure and unbinds its upvalue pointers. The shared function prototype (Proto) remains in memory only if other closures still use the same underlying bytecode.

Handling Upvalues and Closures

Anonymous functions often capture variables from their outer lexical scope. The lifecycle of these upvalues directly impacts garbage collection:

  • Open Upvalues: While the outer function is executing, upvalues point directly to the outer function’s stack frame. If the anonymous function becomes unreachable while the outer function is still running, the closure is swept without affecting the stack.
  • Closed Upvalues: When the outer function exits, any upvalues captured by an active anonymous function are moved from the stack to the heap ("closed"). The anonymous function then holds a reference to this heap-allocated upvalue.
  • Mutual Reachability: If the anonymous function is discarded, the closed upvalue loses a reference. If no other closure shares that upvalue, the upvalue itself becomes unreachable and is collected alongside the function.

Cyclic References

Anonymous functions frequently participate in cycles, such as an object method stored in a table capturing the table itself inside an upvalue. Because Lua utilizes a tracing mark-and-sweep algorithm rather than reference counting, cyclic references between tables and anonymous functions do not prevent collection. Once the entire cycle becomes isolated from the root set, the garbage collector sweeps both the table and the anonymous function simultaneously.
