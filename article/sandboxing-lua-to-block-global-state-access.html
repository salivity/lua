Sandboxing Lua to Block Global State Access

Executing untrusted Lua code introduces severe security risks if the host application's global state is left exposed. This article explains how to build a robust sandbox in Lua by manipulating environment tables, stripping dangerous base functions, protecting shared metatables, and enforcing resource limits to ensure untrusted scripts execute without compromising the host environment.

The Mechanics of Lua Environments

By default, any Lua script reads and writes variables within a single shared global environment table known as _G. In modern Lua (5.2 through 5.4), global variables are syntactic sugar for accessing a special upvalue named _ENV. Whenever a variable is referenced without a local declaration, Lua implicitly resolves it as _ENV.variable.

To prevent an untrusted script from reading or mutating the host environment, you must replace _ENV with an isolated table before the code runs.

In Lua 5.2+, the standard load function accepts an optional fourth parameter representing the environment:

local untrusted_code = "x = 10; os.execute('rm -rf /')"
local sandbox_env = {}

-- Load the chunk using an empty table as its _ENV
local chunk, err = load(untrusted_code, "untrusted", "t", sandbox_env)
if not chunk then
    error("Syntax error: " .. err)
end

chunk() -- Executes safely without access to _G or standard libraries

In Lua 5.1 and LuaJIT, this isolation is achieved using setfenv on the loaded function:

local chunk = loadstring(untrusted_code)
setfenv(chunk, sandbox_env)
chunk()

Setting sandbox_env to an empty table completely denies access to all global functions, including basic utilities like print, math, and string.

Establishing a Safe Whitelist

An empty sandbox renders most code non-functional. Instead of attempting to blacklist dangerous libraries (an approach prone to bypasses), use an explicit whitelist.

Expose only deterministic, stateless libraries:

  • Safe to include: Safe subsets of math, table, and string.
  • Dangerous to exclude: io (filesystem access), os (process execution and system clock), package (module loading), and debug (introspection and memory manipulation).

Construct the environment by copying allowed functions into the isolated table:

local safe_env = {
    ipairs = ipairs,
    pairs = pairs,
    next = next,
    pcall = pcall,
    tonumber = tonumber,
    tostring = tostring,
    type = type,
    math = {
        abs = math.abs,
        floor = math.floor,
        max = math.max,
        min = math.min,
        random = math.random,
    },
    string = {
        byte = string.byte,
        char = string.char,
        find = string.find,
        format = string.format,
        len = string.len,
        sub = string.sub,
    },
    table = {
        insert = table.insert,
        remove = table.remove,
        sort = table.sort,
    }
}

Mitigating Metatable and String Metatable Leaks

Even with a whitelisted environment, shared metatables can allow untrusted code to escape the sandbox. In Lua, all string literals share a single underlying metatable. If untrusted code accesses this metatable, it can modify behaviors globally or retrieve hidden functions.

-- How an attacker might leak standard libraries through strings:
local str_meta = getmetatable("")
str_meta.__index.evil = function() ... end

To close this hole:

  1. Do not expose debug.setmetatable or standard getmetatable to untrusted scripts, or replace getmetatable with a version that returns nil for strings.
  2. Freeze or protect the string metatable using the __metatable field so scripts cannot inspect or modify it.

Completely Eliminating the Debug Library

The debug library provides complete introspection into the Lua runtime. Functions like debug.getupvalue, debug.setupvalue, and debug.getregistry permit arbitrary traversal of the call stack, enabling an attacker to extract the host _G from enclosing functions. The debug library must never be accessible within a sandboxed environment.

Enforcing Execution Quotas

Blocking access to the global environment does not prevent an attacker from executing denial-of-service attacks using infinite loops (while true do end) or memory exhaustion attacks (local s = "x"; while true do s = s .. s end).

To handle these scenarios, configure execution limits:

  • CPU Hook Limits: In the host context, use debug.sethook to intercept long-running execution. By attaching an instruction-count hook to the execution thread, you can abort the script if it exceeds a predetermined threshold of operations.
  • Memory Allocator Limits: If running Lua via its C API, pass a custom memory allocator via lua_newstate. This allows the host application to enforce an absolute memory ceiling, terminating scripts that attempt allocation-based denial of service.
