How to Add Custom package.searchers in Lua

In the Lua programming language, the require function locates and loads modules using a sequence of loader functions stored in the package.searchers table. This article provides a concise guide on how module resolution works in Lua, the required interface for a searcher function, and how to inject your own custom searchers into package.searchers to load modules from unconventional sources like databases, memory, or encrypted files.

Understanding package.searchers

When you call require("module_name"), Lua iterates through the functions stored in the package.searchers array (named package.loaders in Lua 5.1). Each searcher is invoked with the requested module name as its only argument.

Lua provides four standard searchers by default:

  1. Preload searcher: Checks the package.preload table for existing loaders.
  2. Lua loader: Searches standard paths defined in package.path for .lua files.
  3. C loader: Searches standard paths defined in package.cpath for compiled dynamic libraries (.so or .dll).
  4. All-in-one C loader: Looks for C libraries that export multiple submodules.

Implementing a Searcher Function

A custom searcher must follow a specific contract:

  • Input: Receives a single string argument, the module name passed to require.
  • Success: Returns a loader function that will actually execute or return the module, along with an optional extra value that Lua passes as an argument to that loader.
  • Failure: Returns a string describing why or where the module was not found. Lua appends this message to the final error output if no subsequent searchers can locate the module.

Here is an example of a simple custom searcher that loads modules from an in-memory string table:

local virtual_filesystem = {
    ["virtual.config"] = "return { version = '1.0.0', debug = true }",
    ["virtual.math"] = "return { add = function(a, b) return a + b end }"
}

local function virtual_searcher(modname)
    local code = virtual_filesystem[modname]
    
    if code then
        -- Return a loader function that compiles and runs the code
        local loader, err = load(code, modname)
        if not loader then
            error("Error loading virtual module '" .. modname .. "': " .. err)
        end
        return loader
    end

    -- Return an error message if the module was not found
    return string.format("\n\tno virtual file '%s'", modname)
end

Adding the Searcher to package.searchers

Because package.searchers is a standard Lua table acting as an ordered array, you can use table.insert to register your custom function.

Appending as a Fallback Searcher

To let standard Lua and C files take precedence and only fall back to your custom searcher if standard lookups fail, append it to the end:

table.insert(package.searchers, virtual_searcher)

Prepending for Higher Precedence

To check your custom searcher before standard files are searched, insert it earlier in the list. For example, to give it precedence over disk-based .lua files while still respecting package.preload, insert it at index 2:

table.insert(package.searchers, 2, virtual_searcher)

Testing the Custom Searcher

Once added, the new search mechanism integrates natively with Lua's module caching system.

-- Adding the searcher
table.insert(package.searchers, virtual_searcher)

-- Successfully requiring the virtual module
local config = require("virtual.config")
print(config.version) -- Outputs: 1.0.0

-- Subsequent calls use the package.loaded cache, bypassing searchers
local cached_config = require("virtual.config")
assert(config == cached_config)

Version Compatibility

If supporting Lua 5.1 alongside newer versions (Lua 5.2, 5.3, 5.4, and LuaJIT), use conditional assignment to select the appropriate table:

local searchers = package.searchers or package.loaders
table.insert(searchers, custom_searcher)
