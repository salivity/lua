Lua C Modules and Dynamic Linking Explained

This article explores C modules in Lua and details how the built-in require function locates, dynamically links, and initializes native shared libraries at runtime. You will learn what constitutes a Lua C module, how Lua communicates with the operating system’s dynamic linker, and the exact sequence of events that takes place when loading compiled code into a Lua runtime environment.

What Are C Modules in Lua?

A Lua C module is a shared library—such as a .so file on Linux, a .dylib on macOS, or a .dll on Windows—compiled from C or C++ that exposes functions and data structures to Lua. Unlike standard Lua scripts that interpret source code directly, C modules run as compiled native machine code. They are typically used to achieve high computational performance, interact directly with hardware or low-level operating system APIs, or integrate existing third-party C libraries into Lua programs.

To function as a valid module, the library must conform to the Lua C API. Specifically, it must define and export an entry-point function with a name matching the convention luaopen_<modulename>. This initialization function receives the Lua state pointer (lua_State*), creates a table containing the module's functions, and returns that table onto the Lua stack.

How require Locates Shared Libraries

When a script calls require("modname"), Lua delegates the search process to a list of loader functions stored in the package.searchers table (known as package.loaders in Lua 5.1).

  1. Cache Verification: Lua first checks the package.loaded table to verify if "modname" is already loaded. If found, require returns the cached value immediately.
  2. Lua Searcher: If not cached, the default Lua searcher examines the paths in package.path for pure Lua files.
  3. C Library Searcher: If no matching Lua file is found, the C searcher inspects the templates defined in package.cpath. This path string contains patterns with question marks, such as ./?.so or /usr/local/lib/lua/5.4/?.so. Lua substitutes the question mark with the requested module name to look for the file on disk.

For submodules using dot notation (e.g., require("parent.child")), the C searcher replaces the dot with a directory separator to locate the binary (e.g., ./parent/child.so).

The Dynamic Linking Process

Once Lua finds the shared object on the filesystem, it relies on the operating system’s dynamic linker to load the code into the host process's address space.

Lua abstracts this system-level interaction through its internal dynamic linking interface, defined in loadlib.c:

  • On POSIX-compliant systems (Linux and macOS), Lua calls dlopen() with the path to the library and the RTLD_NOW flag.
  • On Windows systems, Lua calls LoadLibraryEx().

Once the shared library is mapped into memory, Lua constructs the expected entry-point symbol name. For require("mymodule"), it expects an exported symbol named luaopen_mymodule. If dots or hyphens are present in the module name, Lua adjusts the symbol name to adhere to valid C identifier rules (dots are converted to underscores, and any characters prior to an initial hyphen are ignored).

Lua then queries the symbol table of the opened library using dlsym() on POSIX or GetProcAddress() on Windows:

lua_CFunction f = (lua_CFunction)dlsym(handle, "luaopen_mymodule");

Module Initialization and Finalization

If the dynamic linker successfully resolves the luaopen_* symbol, Lua packages the returned function pointer as a native Lua C function and executes it.

During this invocation:

  1. Lua passes the module's name as a string argument to the function.
  2. The luaopen_* function registers C functions via functions like luaL_newlib or luaL_setfuncs and leaves the resulting module table at the top of the stack.
  3. Lua captures the returned value from the stack, stores it into package.loaded["mymodule"], and returns it to the caller of require.

If either the dynamic linking step fails (for example, due to missing shared dependencies) or the required entry symbol cannot be found, require raises an error detailing the paths and symbols that were attempted.
