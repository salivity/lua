Lua Garbage Collector Tri-Color Marking Scheme

The Lua garbage collector relies on an incremental tri-color mark-and-sweep algorithm to manage memory automatically without causing perceptible execution pauses. By categorizing allocated objects into white, gray, and black states, the Lua runtime can interleave garbage collection steps directly with standard program execution. This article examines the definition and role of each color state, how the collector traverses object graphs, and how write barriers preserve memory consistency during execution.

The Tri-Color Abstraction

In standard mark-and-sweep collectors, the runtime stops program execution to trace all reachable objects and delete unreachable ones. Lua avoids long "stop-the-world" pauses by dividing the collection work into small, incremental steps.

To track progress across these steps, every collectable object (such as tables, strings, functions, threads, and userdata) is tagged with a color representing its state in the collection cycle:

  • White (Unvisited / Candidate for Collection): Indicates that the object has not been reached by the collector. At the start of a cycle, almost all objects are white. If an object remains white after the traversal phase concludes, it is unreachable garbage and will be collected during the sweep phase.
  • Gray (Visited, Children Pending): Indicates that the collector has reached this object, but has not yet inspected the objects it references. Gray objects constitute the collector’s traversal worklist.
  • Black (Visited and Fully Scanned): Indicates that the object is reachable, and all objects it directly references have been inspected and marked (pushed to the gray list or already marked). Black objects are completely safe from collection in the current cycle.

The Double-White Optimization

Lua refines the white state into two variants: currentwhite and otherwhite. Because Lua collects memory incrementally, new objects may be allocated while a sweep phase is underway.

Using two alternating shades of white prevents newly allocated objects from being accidentally collected in the active cycle. One shade represents objects eligible for deletion in the current sweep, while the other represents fresh allocations that will only be considered in the subsequent cycle.

The Collection Process

The tri-color marking process proceeds through distinct phases:

  1. Root Initialization: The collector starts by marking root objects—such as the global table (_G), the main thread, and the registry. These roots are turned gray.
  2. Propagation: The collector pulls an object from the gray list, marks all white objects it points to as gray, and transitions the original object to black. This step repeats incrementally as the program runs.
  3. Atomic Phase: A brief, non-interruptible step finishes scanning remaining volatile structures, such as weak tables and upvalues, ensuring no references were missed.
  4. Sweep Phase: The collector walks through all allocated objects. Any object still marked with the active white color is freed. Objects marked black or non-candidate white have their colors reset to the next cycle's white.

The Write Barrier

The integrity of an incremental collector depends on a strict invariant: a black object must never directly reference a white object. If a black object points to a white object unnoticed, the collector assumes the branch is fully explored, skipping the white object and inadvertently deleting live data during the sweep phase.

Because the main program continues executing during collection, mutator operations can introduce this illegal state (for example, assigning a newly created white table to an existing black table). Lua solves this using a write barrier.

Whenever a table or object mutation occurs, the write barrier detects if a black object is about to hold a reference to a white object. It resolves the conflict using one of two strategies:

  • Barrier Forward: Moves the referenced white object to gray immediately, ensuring it will be scanned.
  • Barrier Back: Reverts the parent black object back to gray, re-adding it to the traversal worklist so its new references are re-scanned later. This is often used for tables receiving multiple writes, reducing repetitive barrier triggers.
