How Lua Global Variables Persist Across Modules

In Lua, global environment modifications made within a module persist globally because all modules loaded within a given runtime state share a single, central global environment table, traditionally referenced as _G. When a module modifies an un-scoped variable, it directly alters this shared table rather than a localized copy. Consequently, any subsequent code running in that same Lua state accesses the updated table, ensuring that changes made by one module are immediately visible to all other modules.

The Shared Global Table (_G)

At the core of a Lua instance is the lua_State. When a Lua state is initialized, the runtime creates a single master table called _G to hold all standard libraries (such as math, string, and table) and any user-defined global variables.

Because Lua manages memory and state within this single lua_State, every chunk or file executed within it has direct access to this master table by default. There is no automatic memory partitioning or namespace isolation between different script files.

How Module Loading Works with require

When a module is loaded via the require function, Lua performs the following steps:

  1. Cache Inspection: It checks package.loaded[modname] to see if the module has already been run. If so, it returns the cached result.
  2. Chunk Loading: If the module has not been loaded, Lua locates the file and compiles it into a chunk.
  3. Execution in Context: Lua executes the chunk within the current lua_State.

Because the module executes within the active runtime context, its default environment points to the global table. If the module creates a variable without the local keyword, that variable is assigned directly to _G.

Environment Resolution: _ENV and Defaults

In modern Lua (versions 5.2 and later), lexical environments are governed by the upvalue _ENV:

  • Any free name lookup (such as x = 10 or print(x)) is syntactic sugar for _ENV.x = 10 or _ENV.print(_ENV.x).
  • When a module file is compiled by load or require, Lua automatically sets the chunk's upvalue _ENV to reference the global table _G.
  • Unless the module explicitly changes its _ENV to a local or isolated table (e.g., local _ENV = {}), any write to an undeclared variable mutates the shared _G table directly.

In Lua 5.1, the mechanism functions similarly using functions like setfenv and getfenv, where each function has an associated environment table that defaults to the global table.

Inter-Module Visibility

Once a module assigns a value to a global variable, the key-value pair resides in _G. When another module is executed subsequently, any global read resolves against _G. Because tables in Lua are reference types passed throughout the runtime state, any mutation made by the first module is instantly retrievable by any other module running in the same thread or state.

To prevent this automatic persistence, Lua developers explicitly use the local keyword for internal module variables or sandbox the module's execution by rebinding _ENV to an isolated environment.
