Lua 5.1 to 5.2 Module System Breaking Changes

The transition from Lua 5.1 to Lua 5.2 introduced significant architectural revisions to how code is packaged, isolated, and loaded. This article details the breaking changes made to Lua's module system between these two versions, focusing on the deprecation of the standard module() function, the replacement of package.loaders with package.searchers, the elimination of setfenv in favor of lexical _ENV, and the enforcement of explicit table-return conventions.

Deprecation of the module() Function

In Lua 5.1, modules were typically defined using the built-in module() function (often with package.seeall):

-- Lua 5.1 style
module("mymodule", package.seeall)

function hello()
    print("Hello World")
end

The module() function automatically registered the module table into the global environment, assigned it to package.loaded["mymodule"], and mutated the calling function’s global environment.

In Lua 5.2, module() was deprecated (and disabled by default in standard builds) because altering the environment implicitly was considered bad practice and created global namespace pollution. Instead, Lua 5.2 modules must be created as standard local tables and explicitly returned:

-- Lua 5.2 idiomatic style
local mymodule = {}

function mymodule.hello()
    print("Hello World")
end

return mymodule

Renaming package.loaders to package.searchers

Lua uses an array of search functions to determine how to locate and load modules invoked by require(). In Lua 5.1, this table was named package.loaders.

In Lua 5.2, this table was renamed to package.searchers to more accurately describe its role: searching for a loader rather than actually loading the chunk itself. Any legacy code or custom package managers that manipulated package.loaders directly fail with a nil indexing error in Lua 5.2 unless compatibility flags are compiled into the binary.

Overhaul of Environments: Removal of setfenv and Introduction of _ENV

The underlying mechanism used by Lua 5.1 modules to maintain private scopes relied on setfenv and getfenv. A module could isolate its internal functions and variables by reassigning its environment table at runtime.

Lua 5.2 completely removed setfenv and getfenv. Instead, Lua 5.2 introduced lexical scoping for environments through the pseudo-variable _ENV. Any code written for Lua 5.1 that relied on dynamically manipulating module environments via setfenv breaks in Lua 5.2. In 5.2, custom environments must be set lexically:

local _ENV = {} -- module scope is now bound to this local table

Obsolescence of package.seeall

Because module() was deprecated and setfenv was removed, the package.seeall function—which allowed a module’s environment to fall back to the global environment via a metatable—became obsolete and deprecated in Lua 5.2. Code relying on accessing standard libraries (print, math, etc.) through package.seeall inheritance fails in 5.2 unless those libraries are explicitly localized or accessed via the global _G table.

Return Value Requirement for require()

While Lua 5.1's require() returned package.loaded[modname] if a module did not explicitly return a value, it heavily encouraged reliance on the side effects of module(). In Lua 5.2, because modules no longer set global variables or implicitly alter package.loaded, scripts consuming modules are expected to assign the return value of require() directly:

local mymodule = require("mymodule")

If a module in Lua 5.2 does not explicitly return a value, require() returns true (indicating success) rather than the module table itself, breaking code that relies on the old implicit table creation.
