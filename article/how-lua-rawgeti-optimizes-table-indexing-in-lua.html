How lua_rawgeti Optimizes Table Indexing in Lua

In the Lua C API, retrieving table values efficiently is critical for performance-sensitive applications. Using lua_rawgeti optimizes table indexing over general key lookup mechanisms like lua_gettable or lua_getfield by bypassing the Lua C virtual stack for the key parameter, skipping metatable checks, and leveraging direct C-array access within Lua's internal table implementation. This approach avoids key-hashing overhead and reduces C-Lua interface stack manipulation, allowing integer-indexed elements to be read with minimal CPU cycles.

Internal Table Architecture: Array vs. Hash Part

Internally, a Lua table is implemented as a hybrid data structure containing two components:

  1. The Array Part: A contiguous C array of TValue structs indexed from 1 up to a dynamically sized boundary.
  2. The Hash Part: A hash table storing key-value pairs for non-integer keys or sparse/out-of-bounds integer keys.

When an operation accesses an integer key within the range of the array part, Lua avoids the hash table entirely.

Direct Array-Part Access

General lookup functions must determine the type of the key and decide whether to search the array part or compute a hash for the hash part.

When you call lua_rawgeti(L, index, n), the function accepts the index directly as a native C integer (lua_Integer). Lua performs a fast bounds check against the size of the internal array part:

if ((l_castS2U(n) - 1u) < cast_uint(t->alimit)) {
    setobj2s(L, L->top.p, &t->array[n - 1]);
    L->top.p++;
}

If the key n falls within bounds, the value is retrieved via direct pointer offset (t->array[n - 1]). This is an \(O(1)\) pointer dereference that involves zero hash computation, zero collision chaining, and no node traversal.

Elimination of Metamethod Overhead

The "raw" prefix in lua_rawgeti indicates that the operation bypasses metamethods.

A general lookup via lua_gettable monitors for the presence of an __index metamethod. If a key evaluates to nil, or if the target is not strictly a table, Lua traverses the metatable hierarchy to resolve the key. Checking and calling these metamethods incurs branching and execution overhead. lua_rawgeti skips metatable resolution entirely, guaranteeing that the operation operates strictly on the raw table data.

Virtual Stack Reduction

Under lua_gettable, passing a key requires managing Lua's virtual stack:

  1. Pushing the key onto the stack (e.g., lua_pushinteger(L, n)).
  2. Invoking lua_gettable(L, table_index), which reads the key, replaces it with the result, and shifts internal stack pointers.

This approach requires multiple C API calls and manipulates the virtual stack pointer twice. lua_rawgeti passes the integer directly as a native C parameter. The key is never pushed to the stack, cutting the required C API invocations in half and reducing stack frame management overhead.

Hash Fallback Efficiency

If the integer key falls outside the bounds of the array part, lua_rawgeti falls back to the hash part. Even in this fallback path, it retains advantages over generic lookups:

  • The key is treated as an integer primitive immediately, avoiding type-checking switches.
  • Metamethod resolution remains bypassed.
  • No stack allocation occurs for the key.
