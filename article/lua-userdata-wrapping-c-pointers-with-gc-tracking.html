Lua Userdata: Wrapping C Pointers with GC Tracking

In the Lua programming language, interfacing with external C libraries requires a mechanism to manage external memory allocations safely across two distinct runtime environments. Full userdata is the only native Lua data type engineered to encapsulate arbitrary C pointers within a garbage-collected object while binding them to automatic finalizers. By providing internal storage on the Lua heap, support for individual metatables, and the invocation of the __gc metamethod upon collection, userdata ensures that external C resources are freed deterministically without creating memory leaks or dangling pointers.

The Separation Between Lua and C Memory

Lua operates on an automatic, trace-based garbage collector that tracks the lifecycle of all internal objects such as strings, tables, and functions. In contrast, C relies on manual memory management, requiring explicit calls to functions like malloc() and free().

When bridging C and Lua, an application needs a way to pass a pointer to a C-managed struct into the Lua state. If that pointer were represented simply as a primitive value, Lua's garbage collector would have no visibility into the allocation size, origin, or destruction requirements of the underlying memory. Userdata resolves this fundamental disconnect by acting as a bridge managed by the Lua garbage collector.

Full Userdata vs. Light Userdata

Lua provides two variants of userdata: light userdata and full userdata. Understanding the distinction clarifies why only full userdata can track lifecycles automatically:

  • Light Userdata: A light userdata is simply a raw C void* pointer pushed onto the Lua stack. It is treated as a value type, similar to a number or a boolean. It does not possess its own metatable, is not managed by the garbage collector, and cannot trigger finalizer code. If the pointer points to dynamically allocated memory, Lua cannot know when scripts stop referencing it.
  • Full Userdata: A full userdata represents a block of raw memory allocated directly through Lua via lua_newuserdata() (or lua_newuserdatauv() in Lua 5.4). Lua treats this memory block as a fully managed garbage-collection object. It allocates, tracks, and frees the block alongside native Lua objects.

The Role of the __gc Metamethod

The primary mechanism enabling automatic lifecycle tracking is the __gc metamethod. When an object managed by the Lua garbage collector has no remaining references, the collector flags it for destruction.

For a full userdata, developers can assign a metatable containing a __gc field that points to a C function. When the garbage collector sweeps the unreachable userdata, it executes this function before reclaiming the memory block. Inside this finalizer, the developer can cleanly release associated external C resources—such as closing file descriptors, terminating network handles, or calling free() on secondary allocations.

Because light userdata cannot have individual metatables, it cannot define a __gc metamethod, rendering automatic finalization impossible without full userdata.

Memory Encapsulation and Type Safety

Beyond lifecycle tracking, userdata provides encapsulation. The internal byte array of a full userdata is opaque to Lua code; scripts cannot directly read, write, or forge arbitrary memory addresses inside it unless explicitly exposed via functions or accessors in its metatable.

The Lua C API enforces type safety through utility functions like luaL_checkudata(). This function verifies that an argument passed from Lua is not only a full userdata, but specifically one sharing the expected metatable associated with that C type. This prevents accidental type confusion or intentional exploits that could pass invalid pointers into the C runtime.

Why Tables Cannot Replace Userdata

Lua 5.2 introduced support for the __gc metamethod on tables, leading to the question of why tables cannot simply be used instead of userdata.

While a table can have a finalizer, it cannot natively hold an unboxed C pointer as an internal payload. Storing a pointer inside a table requires either encoding the address into a string, casting it to an integer, or storing it as a light userdata. In all these cases, the pointer itself is decoupled from the container's integrity:

  1. Tampering Risk: Table fields can be reassigned, deleted, or overwritten by Lua scripts, creating scenarios where the pointer is lost or replaced with an invalid value before the finalizer runs.
  2. Safety Guarantees: A table does not offer the native type-checking guarantees provided by luaL_checkudata.
  3. Atomic Lifetime: A full userdata holds the pointer (or the entire C struct) directly inside its own contiguous memory allocation on the Lua heap. The data and its garbage-collection wrapper are bound atomically; the pointer cannot be detached from its metadata or finalizer.

Full userdata remains the sole mechanism in Lua that simultaneously provides garbage-collector integration, non-forgeable memory encapsulation, distinct C-level type safety, and guaranteed execution of cleanup hooks.
