How Lua Prevents Garbage Collection Spikes in Games

Lua maintains stable frame rates in continuous, real-time video game environments by pairing an incremental and generational garbage collector (GC) with deep programmatic control exposed through its C API. Rather than halting execution for massive stop-the-world memory sweeps, Lua allows game engines to interleave memory cleanup directly into the frame loop, divide collection work into micro-steps, and leverage memory pooling patterns that eliminate mid-game allocation churn.

Incremental Garbage Collection

Historically, garbage collectors performed "stop-the-world" mark-and-sweep phases, pausing game logic for several milliseconds—or even seconds—when memory thresholds were reached. To solve this, Lua introduced an incremental collector based on Dijkstra’s three-color marking algorithm.

Instead of completing a full cycle at once, Lua executes the collection process in tiny, discrete slices interleaved with script execution. The engine marks a subset of objects, tracks object reference mutations using write barriers, and resumes game execution. Because the overhead is distributed smoothly across many frames, sudden frame drops and visual stuttering are avoided.

Lua 5.4 Generational Collector

Starting with Lua 5.4, the runtime introduced an optional generational garbage collection mode. This design builds on the weak generational hypothesis: most allocated objects in game scripts (such as temporary vector calculations, transient tables, and formatted strings) become unreachable shortly after creation.

In generational mode, Lua limits frequent collection passes to "young" objects. Minor cycles collect short-lived allocations rapidly with minimal traversal overhead. "Old" objects that survive multiple passes are inspected only during infrequent major cycles. This drastically lowers CPU cache thrashing and reduces the per-frame cost of scanning memory.

Fine-Grained Pacing via the C API

Game engines do not have to rely on Lua's automated trigger thresholds. Lua exposes its collector directly to engine developers through the lua_gc C function and the Lua-side collectgarbage() interface.

Engines typically tune or control execution using two parameters:

  • Garbage Collector Pause (LUA_GCSETPAUSE): Controls how long the collector waits before starting a new cycle after completing the previous one. Setting this value appropriately prevents premature cycles while keeping total memory bloat in check.
  • Garbage Collector Step Multiplier (LUA_GCSETSTEPMUL): Configures the speed of the collector relative to memory allocation speed.

Many commercial engines disable automatic GC pacing entirely during active gameplay. Instead, the engine manually invokes lua_gc(L, LUA_GCSTEP, step_size) at the end of each frame, granting Lua a fixed time budget (e.g., 1 millisecond) to clean memory before presenting the frame.

Strategic Scripting and Zero-Allocation Idioms

While the runtime facilitates smooth garbage collection, game developers utilize specific architectural patterns in Lua to minimize GC pressure:

  • Object and Table Pooling: Instead of creating new tables inside tight per-frame update loops, scripts recycle existing tables using clear functions or predefined object pools.
  • Light Userdata Usage: Complex assets (transforms, meshes, physics bodies) are stored in native C/C++ memory. Lua interacts with them via lightuserdata (raw pointers) or thin proxies, keeping heavyweight structures entirely outside the Lua GC tracking graph.
  • String Caching: Because Lua interns all strings, creating unique concatenated strings dynamically inside frame loops generates memory overhead. Games pre-hash strings or reuse string identifiers to avoid GC churn.
  • State-Based Forced Collections: Games execute full, non-incremental collection sweeps during controlled non-interactive moments, such as loading screens, level transitions, or pause menus, ensuring that memory headroom is cleared before active gameplay resumes.
