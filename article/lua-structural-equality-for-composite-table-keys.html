Lua Structural Equality for Composite Table Keys

Lua compares tables by reference rather than by structural value, meaning two separate tables containing identical keys and values will not match when used as lookup keys. Because Lua's __eq metamethod only affects equality operators (==) and does not modify the internal hashing mechanism used for table indexing, developers must simulate structural equality for composite keys. This article explores three direct methods to achieve value-based composite table indexing: string serialization, nested dimension lookup, and canonical key interning using weak tables.

The Limitation of Native Table Keys

In Lua, attempting to use composite tables as keys yields reference-based behavior:

local cache = {}
local key1 = { x = 10, y = 20 }
local key2 = { x = 10, y = 20 }

cache[key1] = "player_data"
print(cache[key2]) -- Output: nil

Even if key1 and key2 share a metatable with an __eq metamethod, cache[key2] remains nil. Lua relies on raw pointer identity to index tables via hash lookups.

Method 1: String Serialization (Composite String Keys)

The simplest way to achieve value-based equality is serializing composite keys into unique, deterministic string identifiers. Lua automatically interns strings, meaning identical strings share the exact same hash and memory address.

local function make_key(a, b)
    -- Use a delimiter that cannot occur in the underlying values
    return tostring(a) .. "\0" .. tostring(b)
end

local cache = {}
local key1 = make_key(10, 20)
local key2 = make_key(10, 20)

cache[key1] = "player_data"
print(cache[key2]) -- Output: player_data

For complex or arbitrarily nested tables, serialize keys into formats like JSON or custom deterministic byte sequences.

  • Advantages: Fast, straightforward, and works with standard table syntax.
  • Disadvantages: High string allocation overhead in tight loops; delimiter collisions can occur if input data is not sanitized.

Method 2: Nested Table Indexing (Trie Approach)

Instead of combining keys into a single object, split the composite key into multiple lookup levels. Each component of the key acts as an index into a successive nested table.

local NestedMap = {}
NestedMap.__index = NestedMap

function NestedMap.new()
    return setmetatable({ root = {} }, NestedMap)
end

function NestedMap:set(k1, k2, value)
    self.root[k1] = self.root[k1] or {}
    self.root[k1][k2] = value
end

function NestedMap:get(k1, k2)
    local sub = self.root[k1]
    return sub and sub[k2] or nil
end

-- Usage
local map = NestedMap.new()
map:set(10, 20, "player_data")
print(map:get(10, 20)) -- Output: player_data
  • Advantages: Avoids string creation entirely and leverages primitive hashing natively.
  • Disadvantages: Slower for deep lookups due to multiple table accesses, requires boilerplate helper functions, and creates intermediate tables that require garbage collection.

Method 3: Canonical Key Interning (Tuple Pattern)

Canonical interning ensures that any two tables representing identical values resolve to the exact same reference in memory. By passing composite values through a factory function backed by weak tables, Lua reuses an existing table reference if the combination of values has been seen before.

local tuple_registry = setmetatable({}, { __mode = "k" })

local function tuple(...)
    local n = select("#", ...)
    local node = tuple_registry
    
    for i = 1, n do
        local val = select(i, ...)
        if not node[val] then
            -- Use weak-valued child tables to allow unused nodes to be GC-collected
            node[val] = setmetatable({}, { __mode = "v" })
        end
        node = node[val]
    end
    
    if not node._leaf then
        node._leaf = { ... }
    end
    
    return node._leaf
end

-- Usage
local cache = {}
local key1 = tuple(10, 20)
local key2 = tuple(10, 20)

print(key1 == key2) -- Output: true (identical reference)

cache[key1] = "player_data"
print(cache[key2])  -- Output: player_data
  • Advantages: Allows clean table syntax (cache[key]), works with any number of elements, and supports non-string data types natively.
  • Disadvantages: Requires a specialized factory layer and introduces minor overhead on tuple creation.

Choosing the Right Strategy

  • Use String Serialization when composite keys consist strictly of primitive types (numbers, booleans, fixed strings) and write operations are infrequent.
  • Use Nested Table Indexing when building multidimensional matrices or spatial grids where lookups follow a fixed hierarchy.
  • Use Canonical Key Interning when composite keys must be passed around as first-class objects across your codebase and evaluated with standard Lua reference equality.
