How NaN Tagging Works in 64-Bit Lua

This article explains NaN tagging, an optimization technique prominently used in runtimes like LuaJIT to store dynamically typed values inside a single 64-bit word. By exploiting the IEEE 754 floating-point representation of "Not a Number" (NaN), the runtime packs floating-point doubles, 48-bit pointers, primitive types, and type tags into the width of a standard 64-bit pointer. This eliminates the memory bloat of traditional tagged unions, dramatically improves CPU cache locality, and minimizes register pressure during execution.

The Anatomy of IEEE 754 Floating-Point Numbers

Under the IEEE 754 double-precision standard, a 64-bit float is structured into three distinct segments:

  • 1 sign bit (bit 63)
  • 11 exponent bits (bits 62–52)
  • 52 mantissa (or fraction) bits (bits 51–0)

A value is defined as a NaN when all 11 exponent bits are set to 1 (binary 11111111111) and the mantissa is non-zero. Within this definition, standard hardware differentiates between "signaling" NaNs and "quiet" NaNs (qNaNs). A quiet NaN sets the most significant bit of the mantissa (bit 51) to 1.

Because a quiet NaN only requires the exponent to be all ones and bit 51 to be 1, the remaining 51 bits (bits 50 through 0) and the sign bit are ignored by floating-point hardware. These unused bits represent a payload space that dynamic language runtimes can repurpose.

Exploiting the 48-Bit Architecture Limit

Modern 64-bit computing architectures (such as x86-64 and ARM64) do not actually use all 64 bits for addressing memory. Instead, canonical virtual address spaces use only the lower 48 bits (or occasionally 52 bits in newer hardware extensions), sign-extended to 64 bits. In standard user-space allocations, the upper 16 bits of a valid pointer are zeros.

Because a pointer only requires 48 bits, it can easily fit inside the 51-bit payload of an IEEE 754 quiet NaN.

Packing Types and Values in Lua

In a standard C implementation of a dynamically typed language (like standard PUC-Rio Lua 5.1–5.3), a generic value is represented as a tagged union:

struct Value {
    int type;      // 4 or 8 bytes
    union {        // 8 bytes
        void *gc_object;
        double number;
        int boolean;
    } value;
};

Due to struct alignment, this structure consumes 16 bytes (128 bits) per value on a 64-bit machine.

LuaJIT replaces this 16-byte struct with an 8-byte (64-bit) primitive through NaN tagging:

  1. Floating-Point Numbers: Any valid 64-bit float that is not a masked qNaN is stored directly as its raw IEEE 754 double value. When the CPU processes standard arithmetic, it operates on the value without unpacking.
  2. Pointers (GC Objects): When storing a reference to an allocated object (such as a Lua table, string, or function), the runtime sets the 11 exponent bits and the qNaN bit to form a NaN envelope. The lower 48 bits are populated with the target's memory address.
  3. Primitives and Type Tags: The upper bits of the payload (bits 48 to 50) and the sign bit serve as an internal type tag. This tag designates whether the value is nil, boolean, lightuserdata, an integer, or an object reference. For simple primitives like boolean, the payload simply contains 0 (false) or 1 (true).

Detection and Unpacking

Checking a value's type requires only basic bitwise operations and integer comparisons:

  • If the upper 16 bits match the NaN mask, the runtime treats the value as a tagged entity. It reads the specific tag bits to invoke the correct branch or unwraps the lower 48 bits to dereference the pointer.
  • If the upper bits do not match the designated NaN mask, the CPU treats the entire 64-bit register directly as a normal floating-point double.

Performance Implications

NaN tagging cuts memory consumption for Lua values by exactly 50%—from 16 bytes down to 8 bytes. Because Lua tables (arrays and hash maps) store numerous dynamically typed slots, this halving of size allows twice as many values to fit within L1 and L2 CPU caches. Furthermore, values can be moved between CPU registers and stack frames using single 64-bit register instructions instead of multi-step memory copies, drastically lowering execution overhead.
