How Lua Manages String Hashes and Collisions

In the Lua programming language, string handling is optimized for rapid table lookups and minimal memory consumption through string interning, randomized hashing, and separate chaining. Lua categorizes strings into short and long types, ensuring that short strings—which frequently serve as identifiers and table keys—are stored uniquely inside a global hash table. This article explains how the Lua virtual machine (VM) calculates string hashes, resolves collisions using singly linked lists, and dynamically scales its internal string table to sustain constant-time operations.

Short vs. Long Strings

Lua (since version 5.2 and refined in 5.3 and 5.4) differentiates between two internal string representations based on length, defined by the constant LUAI_MAXSHORTSTR (defaulting to 40 bytes):

  • Short Strings (LUA_VSHRSTR): Any string of 40 bytes or fewer is automatically interned. The Lua VM guarantees that only one instance of any given short string exists in memory. This allows string equality comparisons to execute in \(O(1)\) time via pointer comparison rather than \(O(n)\) byte-by-byte inspection.
  • Long Strings (LUA_VLNGSTR): Strings exceeding 40 bytes bypass interning to prevent expensive rehashing and memory reallocation overhead. Their hashes are not calculated at creation time; instead, they are computed lazily only when the string is used as a table key.

Hash Generation and Randomization

Lua generates hashes using a seeded hash function to defend against collision-based Denial of Service (HashDoS) attacks. When a Lua state initializes, it generates a pseudo-random seed stored in global_State->seed.

For short strings, Lua computes the hash immediately upon creation by iterating over each byte:

unsigned int luaS_hash (lua_State *L, const char *str, size_t l, unsigned int seed) {
  unsigned int h = seed ^ cast_uint(l);
  for (; l > 0; l--)
    h ^= ((h << 5) + (h >> 2) + cast_byte(str[l - 1]));
  return h;
}

The algorithm uses bitwise shifts and XOR operations across all bytes of the short string, combining the seed, string length, and byte values to produce a uniform distribution across hash buckets.

The Global String Table and Collision Chains

All interned short strings reside in a centralized hash table located in the global state: global_State->strt (defined as stringtable). The stringtable structure consists of an array of bucket pointers (TString **hash), the current number of allocated buckets (size), and the count of stored strings (nuse).

Collision handling in the stringtable relies on separate chaining using singly linked lists:

  1. Bucket Selection: The bucket index for a string is computed using a bitwise AND between its precomputed hash and the table mask: bucket = hash & (size - 1). Lua ensures the table size is always a power of two.
  2. Chain Traversal: Lua traverses the singly linked list stored at strt->hash[bucket]. Each TString header contains a pointer named hnext, which points to the next TString in the same collision chain.
  3. Lookup and Insertion: Lua checks each node in the chain. Because hash values are cached in each TString, Lua first compares the 32-bit hash integers. If the hashes match, it verifies string length, followed by a raw memory comparison (memcmp). If a match is found, the existing string pointer is returned. If the end of the chain is reached without a match, a new TString is allocated, prepended to the head of the bucket’s linked list, and nuse is incremented.

Dynamic Resizing of Collision Chains

To prevent collision chains from growing too long—which degrades lookup performance from \(O(1)\) toward \(O(n)\)—Lua dynamically resizes the stringtable:

  • Growing: When the number of interned strings (nuse) exceeds the number of buckets (size) and size is below the maximum capacity, Lua doubles the table size.
  • Shrinking: During garbage collection cycles, if nuse drops below size / 4, Lua halves the bucket array to reclaim unused memory.

During a resize operation, Lua allocates a new bucket array and re-indexes every short string across all collision chains. Because the hash value is already stored in each TString->hash, Lua does not need to recompute byte hashes; it simply recalculates the bucket index using the updated bitmask (hash & (new_size - 1)) and re-links the hnext pointers into the new chains.
