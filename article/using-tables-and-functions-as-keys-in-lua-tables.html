Using Tables and Functions as Keys in Lua Tables

In the Lua programming language, tables are associative arrays capable of using virtually any value as an index, including complex types such as tables and functions. When non-string reference types are used as keys, Lua performs lookups strictly based on reference identity rather than structural or content equality. This article explains the core mechanics of non-string key lookups, detailing how pointer-based equality works, how Lua hashes reference types, the deliberate bypass of equality metamethods during indexing, and the memory management implications involving garbage collection and weak tables.

Reference Identity and Pointer Equality

Lua treats tables, functions, threads, and full userdata as reference types (objects). When using a table or a function as a key in another table, the associative lookup evaluates the object's specific memory address.

Two tables with identical key-value contents do not resolve to the same entry because they occupy different locations in memory:

local map = {}
local keyA = { id = 1 }
local keyB = { id = 1 }

map[keyA] = "Alpha"
map[keyB] = "Beta"

print(map[keyA]) -- Outputs: Alpha
print(map[keyB]) -- Outputs: Beta
print(map[{ id = 1 }]) -- Outputs: nil

Because { id = 1 } creates a new table instance in memory upon execution, accessing the array with an anonymous table literal results in nil. A lookup succeeds only if the exact same reference is supplied.

Functions follow the exact same rule. Assigning an entry to a function reference requires that precise reference for subsequent retrieval. If a function is defined inside a loop or closure generator, each generated closure is a distinct instance with its own reference:

local handlers = {}

local function createHandler()
    return function() end
end

local fn1 = createHandler()
local fn2 = createHandler()

handlers[fn1] = "Active"
print(handlers[fn1]) -- Outputs: Active
print(handlers[fn2]) -- Outputs: nil

Bypass of the __eq Metamethod

In Lua, developers can customize equality checks between two tables by defining the __eq metamethod. However, Lua completely bypasses __eq during internal table indexing and associative lookups.

The hash table implementation relies entirely on raw equality (rawequal). Even if two distinct tables implement a metatable where __eq returns true, Lua treats them as separate keys in an associative array. This design choice ensures internal consistency and avoids performance degradation, as invoking Lua-level metamethods during low-level hash collisions would introduce significant overhead and recursive complexity.

Hashing Mechanics and Lookup Performance

Internally, Lua tables consist of an array part and a hash part. Lookups for non-string objects occur within the hash part.

When a table or function serves as a key, Lua hashes the internal pointer address of that object. Because pointers are fixed integers representing memory locations, computing the hash of a table or function is instantaneous and requires no traversal of elements or bytecode analysis. Consequently, lookups using tables or functions as keys operate at constant amortized time, \(O(1)\), matching the performance of integer and string key operations.

Garbage Collection and Weak Tables

Using objects as keys directly impacts the Lua garbage collector. Under standard behavior, storing an object as a key creates a strong reference to that object, preventing it from being collected even if all other references to it elsewhere in the program have gone out of scope.

To associate metadata with tables or functions without preventing their destruction, Lua provides weak tables. By configuring the __mode field in a metatable to "k", the table is marked to have weak keys:

local metadata = setmetatable({}, { __mode = "k" })

do
    local obj = { data = "sensitive" }
    metadata[obj] = "additional info"
    -- obj is valid here
end

-- At this point, obj has no strong references outside 'metadata'.
collectgarbage()

-- metadata[obj] has been automatically removed by the collector

In a table with weak keys, if the only remaining reference to a table or function is its role as a key, the garbage collector reclaims the object and automatically purges the corresponding key-value pair from the associative array.
