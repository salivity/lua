Lua error Function: Setting Error Levels for Callers

In the Lua programming language, the built-in error function terminates the protected call currently running and returns an error message. When developing libraries, throwing an error from an internal implementation detail can confuse users by pointing to the library's internal line numbers rather than the offending call in their own code. This article explains how to use the optional level parameter in Lua's error function to shift the reported error location directly to the caller, making debugging significantly easier for consumers of your library.

The Syntax of error

The standard Lua error function accepts two arguments:

error(message [, level])
  • message: A string (or other value) describing the failure.
  • level: An optional integer that specifies how the error location (file name and line number) should be reported. The default value is 1.

How Error Levels Work

The level parameter tells Lua where to look in the call stack to attribute the source of the error:

  • Level 1 (Default): Attributes the error to the function calling error(). This means the error message will display the file and line number inside your library function where error() was executed.
  • Level 2: Attributes the error to the caller of the function that called error(). This points the error message directly to the line of user code that invoked your library function.
  • Level 3+: Attributes the error higher up the call stack, skipping intermediate functions.
  • Level 0: Removes all position information. The error message will not include any file name or line number prefix.

Practical Example: Level 1 vs. Level 2

Consider a library function that expects a positive number:

-- Inside mylibrary.lua
local mylibrary = {}

function mylibrary.calculate(value)
    if type(value) ~= "number" or value <= 0 then
        -- Default level (Level 1)
        error("value must be a positive number")
    end
    return value * 2
end

return mylibrary

If a user calls mylibrary.calculate(-5) from main.lua at line 10, the output with Level 1 will look like this:

mylibrary.lua:5: value must be a positive number

This points to line 5 of mylibrary.lua. The user sees an error inside the library code rather than identifying where they misused the API.

To attribute the fault to the user, supply 2 as the error level:

-- Inside mylibrary.lua
local mylibrary = {}

function mylibrary.calculate(value)
    if type(value) ~= "number" or value <= 0 then
        -- Level 2 attributes the error to the caller
        error("value must be a positive number", 2)
    end
    return value * 2
end

return mylibrary

Running the same invalid call now produces:

main.lua:10: value must be a positive number

The error now points directly to line 10 in main.lua, immediately showing the caller where the mistake occurred.

Accounting for Internal Helper Functions

If your library validates arguments using internal helper functions, you must increase the level to match the depth of your internal call stack:

local function assert_positive(value)
    if type(value) ~= "number" or value <= 0 then
        -- Level 1 is assert_positive
        -- Level 2 is mylibrary.calculate
        -- Level 3 is the external caller
        error("argument must be a positive number", 3)
    end
end

function mylibrary.calculate(value)
    assert_positive(value)
    return value * 2
end

Using level = 3 skips both the assert_positive helper and the public calculate wrapper, correctly pointing to the caller in main.lua.

Best Practices

  • Use Level 2 for API Boundaries: Standard public API entry points should use level 2 when checking inputs, ensuring errors are reported on the consumer's line of code.
  • Use Level 0 for Non-Location Errors: If the error is not tied to a specific location in code (such as a lost network connection), set the level to 0 to omit misleading line numbers.
  • Avoid Hardcoding Deep Levels: Avoid using levels greater than 3 when possible. Refactoring internal helper functions can easily misalign stack depths, causing errors to point to unexpected layers of code.
