How lua_yieldk Provides Continuations in Lua

In the Lua C API, lua_yieldk enables coroutines to yield execution inside C functions and resume seamlessly through the use of continuation functions. Introduced in Lua 5.2, this mechanism circumvents the limitation of standard C where the native call stack cannot be preserved across yields. By decoupling the resumption logic from the original C execution frame, lua_yieldk allows developers to specify a fallback function and context that Lua invokes once the coroutine is resumed, effectively solving the classic "attempt to yield across a C-call boundary" error.

The C Stack Limitation

Standard C relies on an operating system-managed execution stack. In earlier versions of Lua (such as Lua 5.1), if a C function yielded, Lua could not easily pause and restore the C stack frame without non-portable assembly or platform-specific thread mechanics. If a C function called another function or needed to perform operations after a yield, returning control to Lua would discard the local C variables and the execution pointer. Consequently, yielding was only permitted if the C function directly returned the yield result with no pending C operations.

The Structure of lua_yieldk

The lua_yieldk function extends the basic lua_yield macro by accepting additional parameters for continuation management:

int lua_yieldk (lua_State *L, int nresults, lua_KContext ctx, lua_KFunction k);
  • L: The execution state of the coroutine.
  • nresults: The number of values on the Lua stack to return to coroutine.resume.
  • ctx: An arbitrary integer-sized context value (lua_KContext) used to track state across yields.
  • k: A pointer to the continuation function of type lua_KFunction.

A continuation function follows this signature:

typedef int (*lua_KFunction) (lua_State *L, int status, lua_KContext ctx);

How the Continuation Cycle Works

The execution flow using lua_yieldk operates in three distinct phases:

  1. Suspending Execution: Inside the original C function, instead of performing a simple return or standard yield, the program invokes lua_yieldk. It passes the continuation function k, any needed state packed into ctx, and the count of return values. Lua records this metadata inside the internal call frame for that thread and immediately suspends the coroutine.
  2. Re-entering via the Continuation: When Lua code resumes the coroutine using coroutine.resume, the Lua runtime detects the pending continuation on the thread's call stack. Instead of trying to jump back into the middle of the original C function, it directly calls the function pointer k.
  3. Handling the Resumption State: The continuation function receives the Lua state, the yield status (typically LUA_YIELD), and the stored ctx. Any arguments passed to coroutine.resume are placed on the Lua stack and can be read by k.

Inside the continuation function, the developer can process the new parameters, use ctx to determine what step of the operation was pending, and either return final results to Lua or invoke lua_yieldk again to chain further continuations.

Practical Advantages

  • Yielding Across Metamethods: Continuations permit yields inside metamethods (such as __index or __newindex) and iterator functions written in C.
  • State Machine Emulation: Complex asynchronous I/O loops can be structured as C state machines where ctx represents the current state ID, allowing clean, non-blocking C extensions without requiring native OS threads.
