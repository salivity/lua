Lua Memory Management and Garbage Collection Explained

Lua utilizes an automatic memory management system centered around an efficient mark-and-sweep garbage collector, removing the burden of manual memory deallocation from the programmer. This article examines the mechanics of how Lua allocates memory, tracks object references, manages cleanup cycles incrementally and generationally, and provides developers with controls to tune performance in resource-constrained environments.

The Allocation Architecture

Lua does not manage raw system memory directly. Instead, the Lua runtime handles all memory allocation and deallocation through a single allocator function defined in C, typically conforming to the lua_Alloc type signature:

typedef void * (*lua_Alloc) (void *ud, void *ptr, size_t osize, size_t nsize);

By default, the standard C realloc function handles these requests, but developers embedding Lua can supply custom allocators to implement custom arenas, track usage, or enforce hard memory limits. Every dynamic resource in Lua—including tables, strings, functions, threads, and full userdata—is allocated through this interface.

The Mark-and-Sweep Core

At the heart of Lua's garbage collector (GC) is a tracing mark-and-sweep algorithm. The collector identifies which objects are reachable from "root" references (such as the global table, the registry, and active coroutine call stacks) and discards the rest.

Lua tracks the state of each object using a tri-color marking abstraction:

  • White: Objects that are candidates for collection. Lua uses two shades of white (current white and other white) to distinguish newly created objects during an active collection cycle.
  • Gray: Objects visited by the collector, but whose referenced children have not yet been evaluated.
  • Black: Objects visited along with all of their immediate references. Black objects can never point directly to white objects without triggering a write barrier.

During collection, roots are initially marked gray. The collector pops gray objects, visits their fields, marks those children gray, and colors the original object black. Once no gray objects remain, any objects that remain white are unreachable and are reclaimed during the sweep phase.

Incremental Collection and Write Barriers

Prior to Lua 5.1, the engine relied on a "stop-the-world" strategy, freezing program execution during the entire mark-and-sweep cycle. Modern Lua uses an incremental collector that executes interleaved with normal program instructions.

Because the program can mutate references while the collector is running, an invariant violation could occur: a black object might be modified to reference a newly allocated white object, hiding it from traversal. Lua prevents this using write barriers. When a table or reference is mutated, the write barrier detects if a black object points to a white object, either by shifting the black object back to gray (barrier back) or immediately marking the white object gray (barrier forward).

Generational Collection (Lua 5.4)

Lua 5.4 introduced a generational garbage collection mode based on the weak generational hypothesis: most dynamically allocated objects die young.

In generational mode, objects are segregated into distinct categories:

  • Minor collections: Frequent, rapid sweeps that only traverse and collect recently allocated (young) objects.
  • Major collections: Infrequent full mark-and-sweep cycles triggered when memory growth persists or young objects are promoted to old objects.

Generational mode drastically reduces GC overhead in workloads with high allocation turnover, such as tight loops creating short-lived tables.

Weak References and Finalizers

Lua provides tools to modify garbage collection semantics for advanced resource management:

  • Weak Tables: Configured via the __mode field of a metatable ("k" for weak keys, "v" for weak values, or "kv" for both). Weak references do not prevent the collector from reclaiming an object, making them useful for caches and memoization.
  • Finalizers (__gc Metamethod): When an object associated with a __gc metamethod becomes unreachable, the collector does not reclaim it immediately. Instead, it marks the object for finalization, revives it temporarily to execute its cleanup routine, and reclaims it in the subsequent cycle.

Manual Control and Parameter Tuning

Developers can inspect and adjust collector behavior using the collectgarbage() function. Key control parameters include:

  • gc-pause: Controls the delay between the end of one collection cycle and the start of the next. Lower values start cycles sooner, reducing memory footprint at the expense of CPU cycles.
  • gc-stepmul: Controls the speed of the collector relative to memory allocation during incremental mode. Higher values make the collector more aggressive.
  • gc-stepsize: Determines the size of each incremental pause step in bytes.

Through this combination of an abstract allocator, tri-color incremental sweeping, optional generational sorting, and developer-facing tuning levers, Lua maintains a predictable footprint suitable for everything from microcontrollers to large-scale game engines.
