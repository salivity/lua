Lua Closures vs Metatables: Memory Trade-Offs

When implementing object-oriented programming patterns in Lua, developers typically choose between closure-based objects and metatable prototype objects. This article analyzes the memory trade-offs between these two paradigms, examining per-instance overhead, shared prototype mechanics, garbage collection pressure, and scaling characteristics to help you select the most memory-efficient approach for your workload.

Closure-Based Objects

In a closure-based (factory) approach, an object is constructed by returning a table containing functions that enclose local variables as private state (upvalues).

local function createCounter()
    local count = 0
    return {
        increment = function() count = count + 1 end,
        get = function() return count end
    }
end

The primary memory cost of closure-based objects stems from method duplication:

  • Function Allocations: Every single instance allocates its own distinct set of function closures. If an object defines ten methods, creating one thousand instances allocates ten thousand separate closure objects.
  • Upvalue Storage: Each closure maintains internal structures pointing to the captured local variables.
  • Method Table Overhead: Each instance carries its own table containing keys for every method, contributing substantial hash table overhead per instance.

The sole memory advantage is that the object's instance state is held within stack/upvalue structures rather than table fields, but this savings is heavily eclipsed by the cost of duplicate function allocations.

Metatable Prototype Objects

In the metatable prototype approach, instances are lightweight tables whose __index metamethod directs property and method lookups to a shared class table.

local Counter = {}
Counter.__index = Counter

function Counter:new()
    return setmetatable({ count = 0 }, Counter)
end

function Counter:increment()
    self.count = self.count + 1
end

function Counter:get()
    return self.count
end

The memory profile of metatable-based objects is significantly more compact:

  • Shared Method Definitions: Functions are allocated exactly once inside the prototype table. Thousands of instances share the exact same function pointers in memory.
  • Minimal Instance Footprint: Each instance table only stores its unique instance variables (state fields) and a pointer to its metatable.
  • Efficient Hash Sizing: Instance tables require fewer hash slots or array elements because methods are not stored inside the instance table itself.

Garbage Collection and Scaling

The architecture you choose directly affects Lua's garbage collector (GC):

  1. GC Object Count: Closures introduce a large number of discrete collectible objects (the instance table plus each method closure). Because Lua's garbage collector operates proportionally to the total number of live objects, closure-based designs result in longer mark-and-sweep phases. Metatable objects create far fewer GC references.
  2. Allocation Churn: Creating and destroying temporary closure-based objects causes rapid memory fragmentation and frequent GC cycles due to the sheer volume of transient function allocations.
  3. Memory Footprint at Scale: For a single instance, memory differences are negligible (a few dozen to hundreds of bytes). However, as instance counts reach the thousands—such as game entities, particle systems, or network buffers—closure-based implementations consume megabytes of redundant function overhead where metatables consume only kilobytes.

Architectural Trade-Off Summary

  • Use Closure-Based Objects when you require strict encapsulation (private fields inaccessible from the outside) and only ever instantiate a small, bounded number of objects (such as singletons, modules, or services).
  • Use Metatable Prototypes when memory efficiency, low GC latency, and high scalability are paramount. For high-volume object creation, metatables provide the lowest possible memory overhead in standard Lua and LuaJIT.
