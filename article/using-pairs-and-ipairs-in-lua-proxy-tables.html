Using __pairs and __ipairs in Lua Proxy Tables

In the Lua programming language, proxy tables are commonly used to intercept read and write operations for data validation, read-only protection, or state tracking. However, because proxy tables are deliberately kept empty to trigger __index and __newindex metamethods, standard iterative functions like pairs() and ipairs() fail to expose the underlying data by default. The __pairs and __ipairs metamethods solve this problem by allowing developers to define custom iteration logic, ensuring that external code can seamlessly traverse proxy tables using standard for loops without exposing internal storage mechanisms.

The Problem with Default Traversal in Proxy Tables

A basic proxy pattern delegates access from an empty proxy table to an internal, hidden table:

local function create_proxy(target)
    local proxy = {}
    local mt = {
        __index = target,
        __newindex = function(_, k, v)
            target[k] = v
        end
    }
    setmetatable(proxy, mt)
    return proxy
end

If a developer executes for k, v in pairs(proxy) do on this structure, the loop terminates immediately. The native pairs() function traditionally inspects the table passed to it directly via next(). Since the proxy table itself contains no keys, it appears empty, breaking standard idioms of the language and forcing consumers of the API to know about and access the private target directly.

The Role of the __pairs Metamethod

Introduced in Lua 5.2, the __pairs metamethod intercepts calls to the global pairs() function. When pairs(t) is executed, Lua checks whether t has a metatable containing a __pairs key. If present, Lua invokes this metamethod instead of running its default traversal.

The __pairs metamethod is expected to return three values, mirroring the requirements of a generic for loop:

  1. An iterator function (such as next).
  2. The invariant state (usually the internal target table).
  3. The initial key (usually nil).
local mt = {
    __index = target,
    __newindex = function(_, k, v) target[k] = v end,
    __pairs = function(_)
        return next, target, nil
    end
}

With __pairs defined, invoking pairs(proxy) delegates traversal directly to the underlying target table. The consumer can write natural Lua code while the proxy maintains total control over element access.

The Role of the __ipairs Metamethod

The __ipairs metamethod functions identically in concept to __pairs, but it specifically customizes the behavior of the ipairs() function for sequential, integer-indexed arrays.

When implemented, __ipairs must return an iterator function, the state table, and the starting index (typically 0):

local function ipairs_iterator(t, i)
    i = i + 1
    local v = t[i]
    if v ~= nil then
        return i, v
    end
end

mt.__ipairs = function(_)
    return ipairs_iterator, target, 0
end

Note on Lua Versions: While __ipairs was introduced in Lua 5.2, Lua 5.3 deprecated __ipairs and changed the native ipairs() implementation to honor the __index metamethod directly until it encounters a nil value. However, __ipairs remains relevant in Lua 5.2 environments and specific LuaJIT configurations.

Key Benefits

  • Encapsulation: Internal storage remains completely private, hiding implementation details from the caller.
  • Idiomatic Code: Callers do not need specialized methods like proxy:iterate() or direct access to hidden references; standard Lua for loops work as expected.
  • Filtering and Transformation: Metamethods allow the iteration process itself to be customized, enabling on-the-fly transformations, key filtering, or sorting before values reach the loop body.
