How Lua Handles Coroutine Stack Resizing

This article explains how the Lua runtime dynamically manages and resizes coroutine stacks as function call depth and value allocations increase. Unlike operating system threads that rely on large, fixed virtual memory allocations, Lua treats coroutine stacks as dynamically resizable heap structures. By examining the allocation strategy, the relocation of pointers, and the mechanisms used to prevent stack overflows, you will understand how Lua maintains high memory efficiency and execution performance across deeply nested coroutine workflows.

Heap-Allocated Stacks

In Lua, every coroutine is represented internally as a separate thread state structure (lua_State). Instead of binding each coroutine to an operating system thread stack, Lua allocates the coroutine's data stack on the heap as a contiguous array of TValue structures.

When a new coroutine is instantiated using coroutine.create or the C API function lua_newthread, Lua assigns it a minimal initial stack capacity—typically defined by BASIC_STACK_SIZE (usually 40 or 45 slots in standard Lua 5.x implementations). This small initial footprint allows Lua applications to instantiate hundreds of thousands of concurrent coroutines without exhausting system memory.

Detecting Stack Exhaustion

As a coroutine executes, it pushes operands, function arguments, and return values onto its stack. Function calls also push execution frames represented by CallInfo structures. Before executing operations that require additional stack space, Lua performs boundary checks using internal macros like luaD_checkstack.

If the current top of the stack (L->top) plus the requested number of slots exceeds the allocated stack boundary (L->stack_last), the engine immediately pauses execution to trigger a stack growth routine, typically named luaD_growstack.

The Resizing Mechanism

Stack resizing is handled through the following sequence:

  1. Calculating the New Size: Lua attempts to double the current stack size to amortize reallocation costs. If doubling the size is not sufficient to satisfy the requested space, Lua allocates precisely the amount needed plus safety padding.
  2. Reallocation: The memory block is reallocated using luaM_realloc_ or standard heap reallocation routines. This operation may retain the original memory address or move the stack entirely to a new memory location.
  3. Correcting Pointers (Stack Fixup): Because the stack may move to a new base address, raw memory pointers into the old stack become invalid. Lua loops through active execution references and shifts them by the offset between the old and new base pointers. These adjustments include:
    • Base pointers and return targets stored in the active CallInfo chain.
    • Pointers to open upvalues that reference local variables still living on the stack.
    • The global stack top and reference boundaries in the lua_State.

Hard Limits and Overflow Handling

To protect the host process from unbounded memory consumption caused by infinite recursion, Lua enforces a compile-time upper limit defined by LUAI_MAXSTACK (typically set to 1,000,000 slots in standard configurations).

When luaD_growstack calculates that the requested stack depth exceeds this limit, Lua checks whether the limit has already been breached:

  • If the stack is approaching the limit, Lua raises a non-fatal "stack overflow" error using standard Lua error-handling routines (luaG_runerror), unwinding the coroutine to the nearest protected call boundary (pcall).
  • If stack expansion fails inside an error handler or during critical low-level reallocations, Lua converts the condition into an unrecoverable panic.

Stack Shrinking

Stack management in Lua is bidirectional. When execution unwinds and a coroutine's usage falls significantly below its allocated capacity, Lua avoids holding onto unused memory.

During garbage collection cycles or explicitly during execution unwinding, Lua calls luaD_shrinkstack. If the currently used stack space is substantially smaller than the allocated capacity, Lua reallocates the stack downward, shifting pointers again to reclaim heap memory for the host system.
