LuaRocks builtin vs make: Cross-Platform Builds

When packaging C extensions and libraries for the Lua ecosystem, choosing the right build type in a rockspec file directly dictates how portable and maintainable your package will be. This article breaks down the technical differences between the builtin and make build types in LuaRocks, comparing how each manages the compilation pipeline, handles platform-specific toolchains, and affects cross-platform distribution across Linux, macOS, and Windows.

The builtin Build Type

The builtin build type is the native, Lua-driven compiler backend integrated directly into LuaRocks. Instead of relying on external build tools, LuaRocks itself parses the build instructions in the rockspec and invokes the host system's C compiler and linker directly.

Key Characteristics

  • Zero External Build Dependencies: It only requires a C compiler (such as GCC, Clang, or MSVC). Users do not need GNU Make, CMake, or shell utilities installed.
  • Native Cross-Platform Translation: LuaRocks abstracts compiler flags, include paths, library paths, and output file extensions (.so, .dylib, .dll). A single rockspec definition compiles cleanly on Linux, macOS, and Windows.
  • Declarative Structure: Sources, include directories, and link libraries are declared directly inside the rockspec table using standard Lua syntax:
build = {
   type = "builtin",
   modules = {
      my_module = {
         sources = { "src/my_module.c", "src/helper.c" },
         incdirs = { "include" },
         libraries = { "m" }
      }
   }
}

The make Build Type

The make build type delegates the entire compilation process to an external build automation tool, typically GNU Make. LuaRocks invokes the specified makefile and passes relevant environment variables (like compiler flags and include paths for Lua headers) directly to the sub-process.

Key Characteristics

  • External Toolchain Reliance: The target machine must have make (or an equivalent like nmake on Windows) and a POSIX-compatible shell environment present in the system path.
  • Full Process Control: It allows arbitrary shell execution, custom pre-compilation steps, file generation, and complex dependency graphs that builtin cannot express.
  • Manual Cross-Platform Handling: You must write Makefiles that manually detect the target operating system to set correct linker flags, library extensions, and Lua header directories:
build = {
   type = "make",
   build_variables = {
      CFLAGS = "$(CFLAGS)",
      LIBFLAG = "$(LIBFLAG)",
      LUA_INCDIR = "$(LUA_INCDIR)"
   },
   install_variables = {
      INST_LIBDIR = "$(INST_LIBDIR)"
   }
}

Direct Comparison for Cross-Platform Compiling

Feature builtin make
Windows Support Works out-of-the-box with MSVC or MinGW without extra tools. Often fails unless MinGW/MSYS, Cygwin, or complex nmake files are provided.
Tool Requirements C/C++ Compiler only. Make utility + Shell environment + Compiler.
Configuration Pure Lua inside .rockspec. External Makefile + variables passed from .rockspec.
Build Complexity Limited to standard C/C++ compilation and linking. Capable of executing complex, multi-stage build systems.
Portability Risk Low; handled internally by LuaRocks. High; dependent on system-specific Make dialects and commands.

Which Build Type Should You Choose?

Choose builtin if you are writing a standard Lua C extension or wrapping a self-contained C library. Because Windows environments natively lack make and standard POSIX shell utilities, using builtin ensures your package can be compiled seamlessly by users on any supported operating system without setup friction.

Choose make primarily when wrapping large, existing legacy C libraries that already possess an established, non-trivial Makefile that would be impractical to rewrite into a rockspec format, or when code generation tools (such as Lex/Yacc or custom scripts) must run prior to compilation.
