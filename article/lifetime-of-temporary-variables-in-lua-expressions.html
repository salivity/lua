Lifetime of Temporary Variables in Lua Expressions

This article explores the lifetime of temporary variables and intermediate values generated during expression evaluation in the Lua programming language. It details how the Lua virtual machine (VM) allocates temporary registers on its internal stack, when these values lose their references, and how Lua's automatic garbage collection system reclaims the associated memory once expression evaluation concludes.

Virtual Machine Registers and Allocation

Lua (version 5.0 and later) utilizes a register-based virtual machine. When the Lua compiler processes an expression containing nested operations—such as arithmetic, string concatenation, or nested function calls—it allocates temporary internal registers to store intermediate results.

For example, evaluating the expression local result = (a + b) .. c generates an intermediate value for (a + b) before executing the concatenation. This intermediate value is assigned a temporary register on the execution stack for the current function activation frame.

Logical Lifetime vs. Garbage Collection

The lifetime of a temporary variable in Lua operates on two distinct levels: logical lifetime and physical memory reclamation.

1. Logical Lifetime

A temporary variable's logical lifetime is strictly bounded by the execution of the statement containing the expression. A temporary register remains valid only as long as downstream bytecode instructions within that statement require it.

Once the final operation of the statement finishes—such as assigning the final value to a local variable or passing it as an argument to a function—the temporary registers allocated for that statement are marked as free. The Lua compiler can immediately reuse these register slots for subsequent statements in the same scope.

2. Physical Memory Reclamation

Primitive values, such as booleans, light userdata, and numbers, are stored directly within Lua's TValue stack slots and require no heap deallocation.

Collectable objects, such as tables, closures, and strings created during intermediate steps (e.g., string.sub(str, 1, 3) .. "ext"), are allocated on the heap and referenced by the temporary register. These objects remain protected from garbage collection as long as the register holds a valid reference. Once the statement finishes and the register is either overwritten, cleared, or the stack frame unwinds, the reference to the heap object is broken. The object then becomes eligible for reclamation during the next cycle of Lua's incremental or generational garbage collector.

Temporary Values in Chained Calls

When expressions chain function calls or table indexing, such as get_table().method(), the return value of get_table() is held in a temporary register on the stack just long enough to resolve the .method lookup and perform the call. If the returned object is not anchored to a persistent variable, it becomes collectible as soon as the invocation resolves and the temporary register is cleared.

Temporary Lifetime in the C API

When evaluating expressions using the Lua C API, temporary lifetimes are controlled manually via the Lua stack. Any intermediate value pushed to the stack remains alive and protected from garbage collection indefinitely until it is explicitly popped using functions like lua_pop, replaced, or until the invoking C function returns to Lua, automatically collapsing the local stack frame.
