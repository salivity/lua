Lua Supported Character Sets and Source Encodings

The Lua programming language uses an 8-bit clean parser designed to interpret source files as raw sequences of bytes rather than abstract Unicode code points. Consequently, the parser officially supports ASCII and any ASCII-compatible encoding—most notably UTF-8—for source code execution. While language keywords, operators, and identifiers are strictly limited to the basic ASCII set, arbitrary encodings can safely reside inside string literals and source comments.

The 8-Bit Clean Parser Model

Lua’s parser relies on standard C char types, making it intrinsically 8-bit clean. It does not perform internal character-set decoding or normalization during compilation. Instead, the parser scans single bytes sequentially. As long as an encoding preserves the numeric values of standard 7-bit ASCII characters (0x00 to 0x7F) and does not use these byte values to represent parts of multibyte characters, the Lua parser can process the file without syntax conflicts.

Supported Encodings

  • ASCII: The fundamental baseline for all Lua source code. All syntactic elements, including keywords (if, then, function), operators, and structural tokens, must match standard ASCII values.
  • UTF-8: The primary modern encoding supported by Lua. Because UTF-8 is fully backwards-compatible with 7-bit ASCII, it is the standard encoding for Lua scripts. Starting with Lua 5.3, the parser explicitly recognizes and ignores a UTF-8 Byte Order Mark (BOM) (0xEF, 0xBB, 0xBF) if present at the very beginning of a source file.
  • ASCII-Compatible 8-Bit Encodings (ISO-8859 / Windows-1252): Single-byte encodings where codes 0–127 correspond exactly to ASCII are structurally supported in comments and string literals.

Unsupported Encodings

Encodings that alter or reassign ASCII byte ranges are not supported natively by the Lua parser:

  • UTF-16 and UTF-32 (LE and BE): These encodings use multiple bytes for all characters, introducing 0x00 bytes (null characters) for standard ASCII ranges. Because the parser expects individual ASCII-valued bytes for grammar tokens, UTF-16 and UTF-32 source files will cause immediate parsing errors unless converted to UTF-8 prior to compilation.
  • EBCDIC: Systems using EBCDIC cannot run standard Lua source code directly without compiling Lua specifically for that host system's native character mapping.
  • Non-ASCII-Compatible Multibyte Sets (e.g., Shift-JIS): Encodings where trailing bytes of multibyte characters can fall into the ASCII range (0x20–0x7E) can inadvertently match syntactic delimiters like quotes or brackets, potentially breaking the parser.

Identifiers vs. Literals

The Lua grammar enforces distinct rules depending on where characters appear:

  • Identifiers: In standard Lua, variable and function names must begin with an ASCII letter or underscore, followed by ASCII letters, digits, or underscores ([a-zA-Z_][a-zA-Z0-9_]*). Multibyte UTF-8 characters are invalid in identifiers unless Lua is specifically built with locale-dependent identifier support enabled.
  • Strings and Comments: Lua allows any byte sequence inside string literals ("...", '...', or [[...]]) and comments (--...). Any binary sequence—including UTF-8 payloads, extended ASCII bytes, and embedded null characters (\0)—is accepted and stored verbatim by the parser.
