How Lua Closures Share and Mutate Upvalues

In the Lua programming language, multiple closures observe and mutate shared external local variables accurately through a specialized reference mechanism called an upvalue. By using an internal UpVal structure that transitions between an "open" state on the execution stack and a "closed" state on the garbage-collected heap, the Lua virtual machine (VM) ensures that every closure accessing the same local variable points to the exact same reference. This architecture avoids value desynchronization and maintains lexical scoping integrity across the life cycle of any function.

The UpVal Structure: Open vs. Closed States

An upvalue is represented internally in the Lua runtime by the UpVal object. This structure contains a pointer, typically named v, which points to the actual data value (TValue). The upvalue exists in one of two distinct states:

  1. Open State: While the enclosing function that created the local variable is still running, the variable lives on Lua’s call stack. In this state, the upvalue’s pointer v points directly to that variable’s slot on the stack.
  2. Closed State: When the enclosing function terminates and its stack frame is cleared, the variable can no longer reside on the stack. The VM copies the data into a storage field within the UpVal structure itself and repoints v to this internal field. The UpVal object then lives on the garbage-collected heap.

De-duplication via the Open Upvalue List

When a closure is instantiated, the Lua VM must determine how to bind each captured variable. To prevent creating multiple redundant upvalues for the same stack address, Lua maintains a per-thread singly linked list of all currently open upvalues, ordered by stack level.

When a new closure captures a local variable:

  • Lua traverses the openupval list looking for an existing open UpVal whose pointer v matches the stack address of that variable.
  • If a match is found, the VM assigns the existing UpVal reference directly to the new closure's upvalue array, incrementing its reference count.
  • If no match is found, Lua instantiates a new UpVal, sets its pointer v to the stack slot, and inserts it into the sorted list.

Because every closure capturing the same variable receives a reference to the exact same UpVal object, any read or write operation resolves to the identical memory location.

Preserving State When Exiting Scope

When an enclosing function returns, or when a block ends where local variables go out of scope, the VM executes an internal operation (specifically luaF_close).

This operation:

  1. Traverses the openupval list down to the stack level being closed.
  2. Unlinks each relevant UpVal from the open list.
  3. Copies the current value from the stack slot into the UpVal’s own memory.
  4. Updates the internal pointer v to point to this embedded copy.

Because the closures hold references to the UpVal container rather than directly to the stack, this transition from open to closed is completely transparent to them. Subsequent reads or writes from any closure mutate the value held directly inside the shared UpVal container on the heap, ensuring that state changes remain synchronized across all referencing functions for the remainder of their lifecycles.
