How the Lua VM Executes Register-Based Bytecode

This article explores the execution mechanics of the Lua programming language virtual machine (VM), focusing on its register-based bytecode architecture introduced in Lua 5.0. It covers the structure of Lua bytecode instructions, how virtual registers map to the runtime execution stack, and the internal fetch-decode-execute loop that interprets these instructions with high performance.

Virtual Registers and Stack Mapping

Unlike traditional virtual machines that utilize an evaluation stack (where operands are pushed and popped), the Lua VM uses a register-based architecture. However, Lua’s "registers" are not physical hardware CPU registers. Instead, they are virtual registers that map directly to contiguous slots in Lua’s call stack for the current function call frame.

When a function is called, the VM allocates an activation record on the stack. The base of this frame serves as the reference point: register 0 (or R(0)) corresponds to the memory location at base + 0, register 1 to base + 1, and so on. Local variables and temporary expression values inhabit these register slots directly.

Bytecode Instruction Formats

Lua instructions are fixed-width 32-bit integers. Using fixed-width instructions simplifies fetching and decoding. Every instruction contains an opcode (typically 6 to 7 bits, depending on the Lua version) and several fields representing register indices or constant table indices.

The instructions primarily fall into a few formats:

  • iABC: Contains an 8-bit operand A, and two 9-bit operands B and C.
  • iABx: Contains an 8-bit operand A and an unsigned 18-bit operand Bx.
  • iAsBx: Contains an 8-bit operand A and a signed 18-bit operand sBx (commonly used for jumps).
  • iAx: Contains an expanded 26-bit operand Ax for operations needing larger indices.

Operand A almost always specifies the destination register for an operation, while operands B and C denote the source values. Lua uses a special bit flag in operands B and C (in the iABC format) to indicate whether the operand refers to a register on the stack or a value in the function's constant pool (K). This enables instructions to blend local variables and literals seamlessly without dedicated load instructions.

The Fetch-Decode-Execute Cycle

The VM executes bytecode inside a central loop located in the function luaV_execute in the Lua runtime source (lvm.c).

  1. Fetch: The VM maintains a program counter (pc) pointing to the current instruction array. The VM fetches the 32-bit instruction and increments the program counter:

    Instruction i = *pc++;

  2. Decode: The VM extracts the opcode and operands using bitwise masks and shifts:

    OpCode op = GET_OPCODE(i);
int a = GETARG_A(i);
int b = GETARG_B(i);
int c = GETARG_C(i);

  3. Execute: The VM branches to the appropriate instruction logic, typically via a C switch statement or computed goto statements (direct threaded code) when supported by the compiler (such as GCC).

Instruction Execution Example

Consider the Lua expression local a = b + c. In a stack-based VM, this requires three to four separate instructions:

  1. Push b
  2. Push c
  3. Add
  4. Pop into a

In the Lua register VM, this compiles into a single instruction:

ADD R(A) R(B) R(C)

During execution, the VM resolves the memory locations for R(B) and R(C) using the stack pointer base, performs the addition, and writes the result directly to the stack location corresponding to R(A):

TValue *rb = RKB(b); // Resolves to base + b, or constant table
TValue *rc = RKC(c); // Resolves to base + c, or constant table
setobjs2s(L, base + a, luaV_arith(L, rb, rc, TM_ADD));

Advantages of the Approach

By using register-based bytecode, the Lua VM significantly reduces the total instruction count required to execute a script compared to stack-based alternatives. Although decoding fixed-size 32-bit instructions requires bitwise manipulation, the reduced instruction dispatch overhead and the elimination of redundant push/pop stack operations provide substantial execution speed gains and keep memory traversal cache-friendly.
