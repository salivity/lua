How to Build a Lua Profiler Using Debug Hooks

This article explores how developers can utilize the hook functions provided by Lua's native debug library to build custom performance profilers. By leveraging debug.sethook, developers can intercept runtime events such as function calls, returns, and executed lines of code. This guide covers the operational mechanics of Lua hooks, how to gather timing and call-frequency metrics, a concrete implementation example of a basic profiler, and critical performance caveats to keep in mind.

The Foundation: debug.sethook

The core mechanism for building a profiler in Lua is the debug.sethook function. It allows you to register a callback function that executes whenever specific interpreter events occur.

The syntax is defined as:

debug.sethook([thread,] hook_function, mask [, count])

The mask string dictates which runtime events trigger the hook_function:

  • "c" (Call): Triggers whenever Lua calls a function.
  • "r" (Return): Triggers whenever a function returns.
  • "l" (Line): Triggers whenever Lua executes a new line of code.
  • Count: An optional integer specifying that the hook should trigger every count instructions, useful for sampling profilers.

Choosing a Profiling Strategy

Using hooks, you can implement two primary profiling paradigms:

  1. Deterministic (Instrumentation) Profiling: By setting the mask to "cr", your hook intercepts every function call and return. This allows you to compute exact execution counts and elapsed time per function using a high-resolution clock like os.clock().
  2. Statistical (Sampling) Profiling: By configuring an instruction count hook without "c" or "r", you periodically inspect the current call stack. This drastically reduces the overhead introduced by the hook function, making it suitable for production environments.

Extracting Metadata with debug.getinfo

Inside the hook function, the event type (such as "call" or "return") is passed as the first argument. To identify which function triggered the event, use debug.getinfo:

local function hook(event)
    -- Level 2 inspects the function that triggered the hook
    local info = debug.getinfo(2, "nS")
    local name = info.name or "[anonymous]"
    local source = info.short_src or "[unknown]"
    local line = info.linedefined
end

The "nS" parameter restricts data collection to function names (n) and source definitions (S), minimizing introspection overhead.

Building a Simple Call-Count and Timing Profiler

Below is a minimal, functional implementation of a deterministic profiler that records invocation counts and execution durations:

local profiler = {}
local call_data = {}
local call_stack = {}

local function hook(event)
    local info = debug.getinfo(2, "nS")
    local func_id = string.format("%s:%d (%s)", info.short_src, info.linedefined, info.name or "anon")

    if event == "call" then
        table.insert(call_stack, { id = func_id, start_time = os.clock() })
        if not call_data[func_id] then
            call_data[func_id] = { count = 0, total_time = 0 }
        end
        call_data[func_id].count = call_data[func_id].count + 1

    elseif event == "return" then
        local entry = table.remove(call_stack)
        if entry and entry.id == func_id then
            local duration = os.clock() - entry.start_time
            call_data[func_id].total_time = call_data[func_id].total_time + duration
        end
    end
end

function profiler.start()
    call_data = {}
    call_stack = {}
    debug.sethook(hook, "cr")
end

function profiler.stop()
    debug.sethook() -- Clears the hook
    return call_data
end

Caveats and Technical Limitations

While debug hooks provide a straightforward profiling mechanism, developers must account for several structural limitations:

  • Overhead (The Observer Effect): Triggering a Lua function on every call, return, or line adds significant CPU overhead. The profiling code itself can alter the timing profile of the host program.
  • Tail Calls: When Lua performs a tail call optimization, the calling function's stack frame is reused. This can cause unbalanced "call" and "return" events. In newer Lua versions, Lua generates a "tail call" event instead of a standard "call", which must be handled explicitly.
  • LuaJIT Disabling: If using LuaJIT, registering a debug hook typically forces the JIT compiler to abort traces and fall back to the slower interpreter mode, producing metrics that do not reflect fully compiled execution. For LuaJIT, using its dedicated low-overhead C-level sampling profiler API is generally preferred.
