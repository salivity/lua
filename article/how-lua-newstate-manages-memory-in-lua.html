How lua_newstate Manages Memory in Lua

The Lua runtime delegates all dynamic memory management to a single user-defined callback function passed during state initialization via lua_newstate. This article explains the signature and operational mechanics of the lua_Alloc allocator function, how it consolidates allocation, reallocation, and deallocation into a single interface, and how Lua interacts with it during regular execution and garbage collection cycles.

The lua_Alloc Callback Function

When creating a new Lua state with lua_newstate(lua_Alloc f, void *ud), the host program provides an allocation function f and an opaque pointer ud (user data). The function signature required by Lua is:

void * (*lua_Alloc) (void *ud, void *ptr, size_t osize, size_t nsize);

Lua does not call system-level allocation primitives such as malloc, realloc, or free directly within its core engine. Instead, every string, table, closure, thread, and internal data structure is allocated, resized, and freed exclusively through this supplied callback.

Parameter Semantics

The behavior expected from the allocator depends entirely on the combination of ptr, osize, and nsize:

  • ud: The user data pointer passed to lua_newstate. Lua never modifies this pointer; it simply forwards it back to the allocator on every invocation. This allows developers to pass custom context, such as memory arenas, pools, or tracking structures.
  • ptr: The address of the memory block being manipulated. It is NULL when allocating new memory.
  • osize: The original size of the block. If ptr is NULL, osize encodes the Lua type of the object being allocated (in some internal optimizations) or is zero. When freeing or resizing, osize contains the exact byte count previously allocated.
  • nsize: The requested new size of the memory block in bytes.

The Three Operational Modes

Because lua_Alloc unifies all memory operations, it acts as three distinct functions based on the values of ptr and nsize:

1. Allocation (ptr == NULL, nsize > 0)

When Lua needs new memory, it calls the allocator with ptr set to NULL and osize set to zero (or an object type tag). The allocator must return a pointer to a newly allocated block of at least nsize bytes, aligned appropriately for any basic C type. If memory cannot be allocated, it must return NULL.

2. Deallocation (ptr != NULL, nsize == 0)

When Lua's garbage collector reclaims an object, it calls the allocator with the target address in ptr and nsize set to 0. The allocator frees the block. Because Lua explicitly provides the original byte count in osize, custom allocators do not need to store allocation size headers alongside each memory block, allowing for lower memory overhead in pool or slab allocators. The function must return NULL when nsize is zero.

3. Reallocation (ptr != NULL, nsize > 0)

When expanding or shrinking existing structures (such as dynamic arrays or hash tables), Lua passes the current pointer in ptr, its current size in osize, and the new target size in nsize. The allocator must resize the block, preserving the original contents up to the minimum of osize and nsize, and return the address of the resized block (which may or may not match ptr).

Handling Out-of-Memory Conditions

If lua_Alloc returns NULL when nsize > 0, an allocation or reallocation request has failed. Lua responds through a two-step recovery process:

  1. Emergency Garbage Collection: Lua immediately triggers a full, non-reentrant garbage collection cycle to reclaim unreferenced memory and relieve pressure.
  2. Retry and Error Handling: Lua retries the allocation call once more. If the allocator returns NULL a second time, Lua raises a runtime error (LUA_ERRMEM), interrupting the current execution flow and jumping to the nearest protected call boundary (pcall).

Sandboxing and Custom Implementations

Because all memory passes through this single function, embedding applications can enforce deterministic constraints:

  • Memory Quotas: By tracking bytes allocated in the ud context, an application can reject allocations that exceed a hard limit, preventing malicious or runaway scripts from exhausting system resources.
  • Arena and Pool Allocators: Fast, contiguous memory arenas can be used for short-lived Lua states, avoiding global heap contention in multi-threaded systems.
  • Default Allocator: Standard Lua distributions provide luaL_newstate, a helper wrapper around lua_newstate that passes a standard implementation based directly on the C standard library's realloc and free.
