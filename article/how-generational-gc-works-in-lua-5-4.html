How Generational GC Works in Lua 5.4

Lua 5.4 introduces an optional generational garbage collection (GC) mode alongside its default incremental collector. Generational GC operates on the weak generational hypothesis: most newly allocated objects have very short lifespans, while older objects tend to persist. By focusing memory reclamation efforts primarily on recently created objects rather than traversing the entire memory graph, Lua 5.4 achieves significantly lower latency and reduced CPU overhead in programs with high allocation and deallocation churn.

Core Concepts and Object Generations

Under generational mode, Lua categorizes heap-allocated objects into two primary states based on their survival across collection cycles:

  • Young Objects: Objects allocated since the last garbage collection cycle. These represent the primary target of reclamation efforts.
  • Old Objects: Objects that have survived at least one collection cycle. These objects are presumed stable and are excluded from frequent scans.

To handle object progression, Lua internally manages state transitions: a newly allocated object starts in the nursery (young). If it survives a minor collection, it is promoted to an intermediate or old state.

Minor vs. Major Collection Cycles

Lua 5.4 separates reclamation into two types of cycles:

Minor Collections

Minor collections run frequently and only inspect young objects. Because the scan avoids traversing the vast majority of older objects, it finishes in a fraction of the time required by an incremental step or full cycle. Young objects that are unreachable are freed immediately. Surviving objects are promoted to old status.

Major Collections

If minor collections fail to free sufficient memory, or if the memory footprint grows past defined thresholds, Lua falls back to a major collection. A major collection performs a complete mark-and-sweep cycle across all objects in memory, young and old alike. After a major cycle completes, all surviving objects are marked as old, and the generational tracking resets.

The Write Barrier

Generational collection requires tracking instances where an old object is modified to reference a newly created young object. Without this, a minor collection would incorrectly assume the young object is unreachable and free it prematurely.

Lua 5.4 handles this using a write barrier. Whenever a table or object in the old generation is modified to reference a young object:

  1. The write barrier detects the old-to-young pointer.
  2. The old object is placed into a "gray-again" or modified list.
  3. During the next minor collection, Lua traverses only these specific modified old objects rather than scanning the entire old generation, ensuring young objects remain reachable without costly global traversals.

Enabling and Tuning Generational GC

Generational mode is not enabled by default in Lua 5.4; the incremental collector remains the default. To activate generational mode, run:

collectgarbage("generational")

The generational collector can be fine-tuned using two parameters:

  • Minor Multiplier (minor_mul): Controls the frequency of minor collections based on memory growth from newly allocated objects.
  • Major Multiplier (major_mul): Controls the threshold of memory growth that triggers a fallback to a major collection.

Adjusting these values allows developers to tailor the collection process to specific workload profiles, minimizing peak pause times in allocation-heavy environments.
