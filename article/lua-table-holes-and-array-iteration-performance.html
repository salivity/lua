Lua Table Holes and Array Iteration Performance

In the Lua programming language, tables are versatile structures that serve as both sequential arrays and associative hash maps. When an array contains "holes"—meaning nil values are interspersed between numeric indices—the internal representation and iteration mechanics change significantly. This article examines how table holes compromise the behavior of Lua's length operator, degrade traversal performance across different loop constructs, and affect CPU cache efficiency.

Lua's Dual Internal Representation

Lua tables are implemented internally in C as two distinct segments:

  1. The Array Part: A contiguous memory buffer that stores values for sequential integer keys starting at index 1.
  2. The Hash Part: A hash map that handles non-integer keys, negative or zero indices, and large or non-contiguous integer keys that would waste space if stored in an array.

When an array is strictly sequential (no nil values between index 1 and N), the Lua virtual machine stores all values inside the flat C array. Accessing elements by integer index maps directly to contiguous memory offsets.

How Holes Alter Table Structure

A table hole occurs when an element within an integer range is set to nil (for example, keys 1, 2, and 4 exist, but key 3 is missing). When keys become non-contiguous, Lua's internal resizing heuristic may decide that keeping a large array part is inefficient. Consequently, elements past the hole may be reallocated to the hash part of the table.

This reallocation introduces immediate performance costs:

  • Lookup Overhead: Retrieving an element from the hash part requires calculating a hash code, finding the main bucket, and potentially following collision node chains.
  • Cache Misses: Contiguous array indexing benefits from hardware-level CPU cache prefetching. Moving elements to the hash part leads to pointer chasing across non-contiguous memory, sharply increasing CPU cache misses.

Impact on Iteration Constructs

Table holes disrupt the three standard methods of traversing sequential data in Lua.

1. Numeric for Loops and the Length Operator (#)

The Lua length operator (#t) is mathematically defined only for proper sequences—tables without holes. If a table has holes, the Lua VM employs a binary search over the array and hash parts to find any index n where t[n] ~= nil and t[n+1] == nil.

  • Behavioral Issue: The loop for i = 1, #t do will often terminate prematurely because #t can stop at the boundary created by an internal hole rather than the true maximum index.
  • Performance Issue: Calculating #t on a sparse array involves a logarithmic binary search rather than reading a static size field, adding overhead to every evaluation if computed inside a loop condition.

2. ipairs Iteration

The ipairs iterator sequentially checks indices starting at 1 and stops at the very first nil it encounters.

local t = {10, 20, nil, 40}
for i, v in ipairs(t) do
    -- This loop only processes indices 1 and 2, entirely skipping 4.
end

Because ipairs halts at the first hole, it cannot be used to iterate across sparse arrays. Attempting to work around this by writing a custom iterator that checks up to a manual maximum index forces explicit nil handling and branch prediction penalties inside the loop body.

3. pairs Iteration

To guarantee that all elements in a table with holes are visited, developers often resort to pairs:

for k, v in pairs(t) do
    -- Traverses all existing keys, including those after holes.
end

While functional, pairs is substantially slower than array iteration:

  • It must iterate through the entire allocated array segment and all buckets in the hash segment, including empty slots.
  • It does not guarantee index order, necessitating an external sorting step if ordered processing is required.
  • In high-performance benchmarks, a continuous array traversal via numeric for is typically 2x to 5x faster than a pairs traversal due to Lua VM optimizations (such as the specialized OP_GETI instruction available in Lua 5.3+).

Strategies to Maintain Performance

To prevent performance degradation caused by table holes:

  • Use Sentinel Values: Replace nil with a lightweight placeholder, such as a dedicated sentinel table (local NONE = {}) or false, to keep the integer sequence contiguous.
  • Track Length Manually: If sparse keys are unavoidable, maintain an explicit count or max_index variable instead of relying on #.
  • Separate Dense and Sparse Data: Store sequential data in one flat table and sparse metadata or optional attributes in a dedicated key-value hash table.
