How Lua Avoids Hash Overhead on Long Strings

This article explains the internal mechanisms the Lua programming language uses to eliminate hash computation overhead when instantiating long strings. By distinguishing between short and long strings, Lua avoids the expensive process of immediate hashing and string interning for larger payloads. Instead, Lua employs a lazy-evaluation strategy, deferring hash calculations until they are strictly necessary, thereby ensuring fast allocation and optimal runtime performance.

The String Size Threshold

Starting in Lua 5.2 and refined in Lua 5.3 and 5.4, Lua splits string representations into two distinct types: short strings and long strings. This division is controlled internally by the compile-time constant LUAI_MAXSHORTLEN, which is typically set to 40 bytes.

  • Short Strings (≤ 40 bytes): Handled via string interning. They are hashed immediately upon creation and stored in a global string table to guarantee that only one copy of any given short string exists in memory.
  • Long Strings (> 40 bytes): Bypass the global string table entirely. Each creation of a long string produces a new, independent object in memory without checking for duplicates.

Lazy Hash Calculation

Because long strings are not interned, Lua does not need an immediate hash value to place them into a global hash map during creation. Lua exploits this by applying lazy evaluation to the hash generation process.

When a long string is instantiated, Lua sets an internal flag or initializes the cached hash field within the string's header structure (TString) to an uncalculated state (indicated by setting the extra byte flag). The memory allocation completes simply by copying the bytes and tracking the string length, keeping allocation overhead minimal regardless of the string's size.

On-Demand Hashing and Caching

Lua computes the hash of a long string only when the string is explicitly used in an operation that requires a hash value—primarily when the long string serves as a key in a Lua table.

When a table lookup or insertion occurs:

  1. Lua checks the string's header to determine if the hash has already been computed.
  2. If uncomputed, Lua runs the hash algorithm over the string data.
  3. The resulting hash is saved in the string's header, and the flag is updated to indicate the hash is valid.
  4. Subsequent lookups using the same string object reuse the cached hash, eliminating repetitive calculations.

Equality Comparisons Without Hashing

Lua also optimizes equality checks between long strings without relying on their hash values:

  1. Pointer Comparison: Lua first checks if the two string pointers point to the exact same memory address. If they do, they are equal.
  2. Length Comparison: If the pointers differ, Lua compares the length values stored directly in the string headers. If the lengths differ, the strings cannot be equal.
  3. Byte-by-Byte Comparison: Only if both the pointers differ and the lengths match does Lua perform a block memory comparison (memcmp).

At no point during standard equality checks is a hash required, allowing long strings to be compared and processed throughout a program lifecycle without ever triggering hash computation.
