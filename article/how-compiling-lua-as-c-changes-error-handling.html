How Compiling Lua as C++ Changes Error Handling

Compiling the Lua interpreter with a C++ compiler rather than a standard C compiler fundamentally alters its internal control-flow architecture by replacing traditional C jump mechanisms with native C++ exception handling. This switch enables proper stack unwinding and ensures the execution of C++ destructors (RAII) when runtime errors occur, preventing memory and resource leaks in hybrid C++/Lua applications.

The Default C Mechanism: setjmp and longjmp

By default, Lua is written in ANSI C and implements its error handling using the standard C library primitives: setjmp and longjmp.

When a protected call like lua_pcall or lua_cpcall is executed, Lua sets a recovery point using setjmp. If an error is raised anywhere down the call stack via lua_error, Lua executes a longjmp back to that recovery point.

While efficient, longjmp restores the CPU register state and resets the stack pointer directly. It has no awareness of the call frames it bypasses. If C++ code is executing between the setjmp call and the longjmp call, any local stack-allocated objects will be discarded instantly without their destructors ever being invoked. This breaks the Resource Acquisition Is Initialization (RAII) pattern, causing dangling pointers, unreleased locks, and memory leaks.

The C++ Alteration: try, catch, and throw

When Lua source files are compiled using a C++ compiler, configuration macros within luaconf.h automatically change Lua's internal error-handling primitives. Specifically, Lua adjusts the definition of LUAI_THROW, LUAI_TRY, and LUAI_CATCH.

Instead of setjmp and longjmp, Lua defines these operations using native C++ keywords:

  • LUAI_TRY: Wraps protected blocks in a C++ try block.
  • LUAI_THROW: Triggers errors using a native throw statement, typically throwing an internal exception object or pointer.
  • LUAI_CATCH: Catches the specific Lua exception using a catch (...) or typed catch block to handle the error payload and resume execution.

Preservation of RAII and Stack Unwinding

The primary technical consequence of compiling Lua as C++ is the activation of the C++ runtime's stack unwinder during error states.

When lua_error executes a throw, the runtime traverses each stack frame between the throw site and the catching protected call. During this traversal, the destructors of all automatic (stack-allocated) C++ objects are sequentially executed. This allows developers to use standard C++ idioms—such as std::unique_ptr, std::vector, and std::lock_guard—inside C++ functions exposed to the Lua runtime without worrying that a Lua error will bypass cleanup routines.

Exception Boundary Considerations

While compiling Lua as C++ facilitates RAII compliance, it alters how exceptions must be managed at boundaries:

  • Catching Lua Errors as Exceptions: Lua errors thrown via the C++ mechanism can inadvertently be caught by overly broad user code containing catch (...). If user code swallows a Lua error exception without rethrowing it, Lua's internal state machine can become desynchronized or corrupted.
  • Foreign C++ Exceptions: Standard C++ exceptions thrown inside custom functions are not automatically converted into Lua error messages unless explicitly caught and translated via lua_pushstring and lua_error. If an unhandled standard exception escapes across a Lua boundary that is compiled as C, the process typically aborts; when compiled as C++, it will unwind straight through the Lua frames up to the nearest C++ handler, bypassing Lua's error reporting.

Performance Implications

In standard C, setjmp incurs a slight setup overhead at every protected call, but longjmp execution is essentially a single register restoration.

When compiled as C++, modern platforms typically use zero-cost exception tables (such as DWARF or Windows Structured Exception Handling). In this model, entering a try block incurs virtually zero runtime overhead during normal execution. However, when an error occurs, the stack unwinding process is substantially more computationally expensive than a raw longjmp, as it must consult exception handling tables and run destruction logic for every stack frame.
