How Lua Tables Dynamically Resize Array and Hash Parts

Lua tables are hybrid data structures composed of a contiguous array section and a chained hash map section. As programs insert keys, Lua does not statically lock elements into one storage mechanism; instead, it dynamically shifts elements between the array and hash parts using an internal rehashing algorithm. This dynamic balancing ensures that dense sequences of integer keys enjoy \(O(1)\) direct indexing and lower memory overhead, while arbitrary or sparse keys fall back onto the hash table without requiring manual developer intervention.

The Dual Architecture of Lua Tables

Internally, Lua represents a table through the Table struct (defined in ltable.h). This struct maintains two distinct storage segments:

  • The Array Part (TValue *array): A contiguous C array sized to a power of two (\(2^n\)). It stores values corresponding to 1-based sequential integer keys from \(1\) up to sizearray. Accessing keys in this segment requires no hashing and operates via direct pointer offset.
  • The Hash Part (Node *node): A hash table sized to a power of two, resolving collisions using a hybrid of open addressing and separate chaining (often referred to as Brent's variation or coalesce chaining with a "last free" pointer). It holds non-integer keys, negative or fractional numbers, and integer keys outside the current array boundary.

The Trigger: Detecting Exhaustion

Elements do not shift continuously on every individual insertion. Instead, shifts occur when an insertion fails to find space in the hash part.

When a new key cannot be placed into the array (either because it is not an integer, it is \(\le 0\), or it exceeds the current sizearray), Lua attempts to insert it into the hash part. If the hash part has no free nodes remaining (meaning the internal lastfree cursor has reached the beginning of the node array), Lua invokes the internal luaH_newkey function, which triggers the table's rehash routine.

The Rehashing Algorithm

The core of Lua’s reallocation strategy lies in the rehash function. The primary goal of rehash is to determine a new size for the array part, \(N\), where \(N\) is a power of two, such that at least half of the slots between \(1\) and \(N\) are populated. This condition—often called the 50% utilization rule—prevents memory fragmentation from overly sparse arrays.

The algorithm executes the following sequence:

  1. Bucket Counting: Lua initializes an array of counters, where each counter \(i\) corresponds to the number of existing integer keys in the range \((2^{i-1}, 2^i]\).
  2. Scanning the Array Part: Lua iterates over the existing array part and increments the corresponding power-of-two range counters for every non-nil value present.
  3. Scanning the Hash Part: Lua iterates over the hash part, checks for keys that are valid positive integers, and increments the range counters for those keys as well.
  4. Finding Optimal Array Size: Lua iterates through the cumulative sums of these counters to find the largest power-of-two size \(N\) such that the number of valid keys from \(1\) to \(N\) is greater than \(N / 2\).
  5. Assigning Remaining Keys: All non-integer keys, non-positive integer keys, and integer keys greater than the newly computed \(N\) are allocated to the hash part.

Shifting Elements Between Segments

Once the new sizes for the array part and the hash part are computed, Lua allocates new memory buffers for both segments and re-distributes every existing key-value pair:

  • Hash to Array: Any integer key between \(1\) and \(N\) that previously resided in the hash part is written directly to index key - 1 in the new array allocation. The corresponding hash node is freed.
  • Array to Hash: If the table shrank its array segment (which occurs if dense sequences were deleted prior to rehash), keys that used to sit in the array part at indices \(> N\) are extracted, hashed, and inserted into the new hash table nodes.
  • Hash to Hash: Non-integer keys and integers outside the array boundary are re-hashed and linked into the newly sized hash table.
  • Array to Array: Keys remaining within the new boundary \(1 \dots N\) are copied to the new contiguous memory block.

Finally, the old memory blocks are released, the table's metadata pointers are updated, and the pending insertion that initially triggered the rehash completes.

Performance Considerations

Because rehashing visits all existing elements in both the array and hash parts, it runs in \(O(n)\) time relative to table size. However, because both parts double in capacity when expanding, the cost of reallocation is amortized over many insertions, resulting in an amortized \(O(1)\) insertion time.

Sparse insertions—such as assigning to index t[1] and then t[1000000]—will keep t[1] in the array part (size 1) and place t[1000000] into the hash part to satisfy the 50% density threshold without wasting memory on one million empty slots.
