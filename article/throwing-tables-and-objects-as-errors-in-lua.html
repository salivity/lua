Throwing Tables and Objects as Errors in Lua

In the Lua programming language, error handling is not limited to text-based messages. Lua natively supports throwing any data type as an error object, including tables and complex objects with metatables. This article explains how to throw structured error objects using the error() function, how to catch and handle them with pcall and xpcall, and the key caveats regarding stack trace preservation.

How Lua Handles Non-String Errors

The built-in error() function in Lua accepts any value as its primary argument:

error(message [, level])

While developers frequently pass strings, message can be a number, a boolean, a function, a userdata value, or a table. When you pass a table or an object, Lua preserves the reference to that data structure when propagating the failure.

Throwing and Catching Table Errors with pcall

When using pcall (protected call), the returned error value is the exact object passed to error():

local function performTask()
    local errObj = {
        code = 404,
        message = "Resource not found",
        timestamp = os.time(),
        details = { resourceId = "usr_1024" }
    }
    error(errObj)
end

local success, err = pcall(performTask)

if not success then
    if type(err) == "table" then
        print("Error Code: " .. err.code)
        print("Message: " .. err.message)
        print("Resource: " .. err.details.resourceId)
    else
        print("Generic Error: " .. tostring(err))
    end
end

Because err retains its table type, you can implement structured exception patterns, categorical error types, and contextual debugging payloads.

Using xpcall and Custom Error Handlers

The xpcall function allows you to define an error handler that executes before the stack unwinds. The handler receives the original error object directly:

local function errorHandler(err)
    if type(err) == "table" and err.code then
        return {
            formatted = string.format("[%d] %s", err.code, err.message),
            raw = err
        }
    end
    return { formatted = tostring(err), raw = err }
end

local success, result = xpcall(performTask, errorHandler)

if not success then
    print(result.formatted)
end

Adding Metatables for Printable Objects

If external code or standard output attempts to convert an error object into a string, a raw table will print as a memory address (e.g., table: 0x...). You can attach a metatable with a __tostring metamethod to make complex objects readable while retaining their structured properties:

local ErrorMeta = {
    __tostring = function(self)
        return string.format("Error %d: %s", self.code, self.message)
    end
}

local function raiseCustomError(code, message)
    local err = setmetatable({ code = code, message = message }, ErrorMeta)
    error(err)
end

local ok, err = pcall(raiseCustomError, 500, "Internal Server Failure")
if not ok then
    print(err) -- Calls __tostring: "Error 500: Internal Server Failure"
    print(err.code) -- Accesses table property: 500
end

Important Caveats

  1. Stack Trace Information (level parameter): When passing a string, Lua uses the level parameter to prepend file and line number information to the message. When passing a table or non-string object, Lua ignores the level argument and does not append source position data, since doing so would mutate or change the type of your error object. If file and line numbers are required, you must capture them manually using debug.getinfo() or debug.traceback() before throwing the table.
  2. Third-Party Compatibility: Some third-party Lua libraries assume all caught errors are strings and attempt string operations like string.match(err, ...) directly. If your code interfaces with libraries that do not handle arbitrary error types safely, provide a __tostring metamethod or verify library expectations.
