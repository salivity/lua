Lua Object Pooling: Avoid GC in Game Loops

In Lua-based game development, dynamic table allocation within inner game loops frequently triggers automatic garbage collection (GC) cycles, leading to visible stutter and frame rate drops. Object pooling circumvents this issue by pre-allocating and recycling tables rather than abandoning them for the collector to sweep. This guide outlines the essential architectural patterns and best practices for creating high-performance table and object pools in Lua, ensuring stable frame times in performance-critical environments like Love2D, Defold, or Roblox.

The GC Problem in Lua Game Loops

Lua manages memory automatically using an incremental or generational garbage collector. Every time a table or closure is instantiated (local v = { x = 0, y = 0 }), memory is allocated on the heap. In a 60 FPS loop running physics, AI, or particle updates, generating hundreds of short-lived tables per frame forces Lua's GC to run aggressively. When the GC pause kicks in, frame rendering stalls. The solution is zero-allocation loops achieved through pooling.

Implement a Fast Stack-Based Pool

A minimal, performant pool operates as a Last-In, First-Out (LIFO) stack. Using a simple array with an integer pointer is significantly faster than using standard library functions like table.insert and table.remove, which incur overhead from dynamic resizing and boundary checks.

local Pool = {}
Pool.__index = Pool

function Pool.new(constructor, initial_size)
    local self = setmetatable({}, Pool)
    self.constructor = constructor
    self.free_objects = {}
    self.size = 0
    
    for _ = 1, (initial_size or 32) do
        self.size = self.size + 1
        self.free_objects[self.size] = self.constructor()
    end
    
    return self
end

function Pool:obtain(...)
    local obj
    if self.size > 0 then
        obj = self.free_objects[self.size]
        self.free_objects[self.size] = nil
        self.size = self.size - 1
    else
        obj = self.constructor()
    end
    
    if obj.init then
        obj:init(...)
    end
    return obj
end

function Pool:free(obj)
    if obj.reset then
        obj:reset()
    end
    self.size = self.size + 1
    self.free_objects[self.size] = obj
end

Pre-warm Pools During Initialization

Never allow a pool to allocate memory during gameplay. Allocate the maximum expected capacity of objects during level loading, scene transitions, or engine initialization. If a game scenario requires a maximum of 500 active bullets, pre-warm the pool to 500 or 600 items. Growing a pool at runtime triggers both table creation and hash/array re-hashing inside the Lua runtime.

Clean Object States Without Deleting Keys

When resetting a recycled object, avoid setting keys to nil if those keys will simply be assigned again on the next acquisition. In Lua, toggling keys between nil and a value causes table re-hashes and internal reallocation.

  • Scalar Values: Reset numeric, boolean, or string flags back to default values (e.g., self.x = 0, self.alive = false).
  • Nested Tables: If an object contains sub-tables (like a vector or bounding box), pool those sub-tables or clean their inner scalar fields instead of recreating them.
  • External References: Explicitly set references to other game entities or assets to nil upon returning the object to the pool to prevent memory leaks from retained references.

Separate Array and Hash Elements

Lua optimizes tables internally into an array part and a hash (dictionary) part. Mixed tables that alternate between sequential integers and string keys can trigger reallocation.

For pooled objects representing vectors, transforms, or components, prioritize consistent keys. If performance is paramount, structure pooled data as flat arrays with numeric indices (e.g., obj[1] for X, obj[2] for Y) or ensure the hash structure remains static throughout the application lifecycle.

Avoid Accidental Hidden Allocations

A robust object pool can still be undermined by hidden allocations inside the loop:

  • Closures: Avoid defining local functions or anonymous callbacks inside pooled methods or loop updates. Each declaration allocates a new closure object.
  • String Manipulation: String concatenation (..) allocates new memory because Lua strings are immutable and interned. Use predefined IDs, booleans, or enums (numbers) to represent states instead of dynamic strings.
  • Varargs (...): In standard Lua versions (prior to LuaJIT optimizations or Lua 5.3+ improvements), passing or capturing ... into a table ({...}) instantiates a new table. Pass explicit parameters to init and reset methods.

Keep Pools Homogeneous

Do not create a single "generic" table pool for entirely different data structures. A bullet table requires different internal sizing than an enemy AI state machine table. Keeping pools homogeneous ensures that the internal memory footprint of the tables matches their usage pattern, preventing Lua from continually expanding the capacity of small tables that accidentally inherited larger fields from previous use.
