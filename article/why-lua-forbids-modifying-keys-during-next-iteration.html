Why Lua Forbids Modifying Keys During Next Iteration

In Lua, assigning a value to a non-existent key while traversing a table with next—including the generic pairs loop—results in undefined behavior. This restriction exists because Lua tables rely on a compact, highly optimized internal hash table structure. Inserting new keys alters this underlying structure, which breaks the internal indexing that next depends on to locate subsequent elements.

How next Works Under the Hood

A Lua table is implemented internally as a combination of a contiguous array part and a hash map part. When you call next(table, key), Lua does not keep an external cursor or an iterator object stored in memory. Instead, it relies on the provided key as a reference point.

To find the subsequent entry, Lua performs an internal search:

  1. It hashes the provided key to locate its position inside the table's node array.
  2. It advances to the immediately following physical slot in the internal storage.
  3. It returns the key and value found at that next non-empty slot.

Because the state of the iteration is entirely reconstructed on each step using only the table and the current key, the iteration order is strictly bound to the physical memory layout of the table's internal array of hash nodes.

The Problem with Adding New Keys

When you assign a value to a key that does not already exist in the table during iteration, several internal changes occur:

  • Rehashing and Resizing: If the hash part of the table is full, inserting a new key forces Lua to reallocate and resize the node array. During a rehash, Lua recalculates the positions of all existing keys to maintain optimal lookup times. As a result, the physical positions of both visited and unvisited keys change. The original reference key passed to next may end up at a completely different offset or collision chain, causing the iterator to skip unvisited entries or cycle back over previously processed ones.
  • Collision Chain Realignment: Even when an insertion does not trigger a full reallocation, Lua resolves collisions using a variation of Brent's algorithm (last-free-node approach). Inserting a key can cause existing collision chains to be reorganized or displaced. If the key passed into next is part of a modified chain, next may lose track of which keys have already been visited.

Because Lua cannot guarantee deterministic traversal once the internal node array has been reshuffled, the language specification explicitly defines key insertion during traversal as undefined behavior.

Modifying Values vs. Modifying Keys

Lua makes a strict distinction between changing values and changing keys:

  • Allowed: Modifying existing keys (changing t[k] to a different non-nil value) or clearing existing keys (setting t[k] = nil) is explicitly safe. Lua handles nil assignments by removing the value while keeping the key node intact during traversal, avoiding a structural reorganization that would break next.
  • Forbidden: Creating new keys (setting t[new_key] = value) introduces new entries into the internal structure, triggering the structural instability described above.

Safe Alternatives

To safely introduce new keys based on iteration results, you must decouple the read phase from the write phase:

  1. Collect Changes in a Separate Buffer: Store the new keys and their intended values in a separate temporary table during the iteration, then merge the temporary table into the main table once traversal completes.
  2. Iterate Over a Key Snapshot: Copy all existing keys into a temporary array and iterate over that array using ipairs. You can then freely add new keys to the original table, as ipairs tracks a numeric counter rather than the hash table layout.
