Optimize Lua Performance by Pre-Allocating Tables

Pre-allocating table capacities in Lua is one of the most effective techniques for reducing CPU overhead and memory fragmentation in performance-critical applications. In Lua, tables serve as the sole data structure for arrays, dictionaries, and objects. When a table grows dynamically without a predefined size, the Lua runtime repeatedly reallocates internal memory and rehashes keys, introducing significant latency and triggering frequent garbage collection cycles. By defining table dimensions in advance, developers eliminate dynamic resizing costs, resulting in faster execution loops and a predictable memory footprint.

How Lua Tables Manage Memory

Internally, a Lua table consists of two separate segments: an array part and a hash part. The array part stores values associated with sequential integer keys starting from 1, while the hash part stores all other keys, including strings, objects, and non-sequential numbers.

When you instantiate an empty table with {} and sequentially append elements, Lua initially allocates minimal or zero capacity. As new elements exceed the current threshold, the runtime executes a resize operation. This involves:

  1. Allocating a new, larger memory block (typically doubling the previous capacity).
  2. Copying or rehashing existing elements into the new block.
  3. Freeing the obsolete memory block, which increases garbage collector (GC) workload.

In loops that process thousands or millions of elements, these repeated reallocation and rehashing steps consume substantial CPU cycles.

Methods for Pre-Allocating Tables

Standard Lua and LuaJIT provide different mechanisms to declare table capacities upfront for both the array and hash segments.

1. LuaJIT: table.new

In LuaJIT, the table.new(narr, nrec) function allows you to pre-allocate memory directly from Lua code. The parameter narr specifies the number of expected array slots, and nrec specifies the number of key-value (hash) slots.

local table_new = require("table.new")

-- Pre-allocate an array with 10,000 slots and 0 hash slots
local list = table_new(10000, 0)
for i = 1, 10000 do
    list[i] = i * 2
end

Using table.new completely bypasses resize checks during the loop, allowing the Just-In-Time (JIT) compiler to generate highly optimized native machine instructions.

2. The Lua C API: lua_createtable

When interacting with Lua through its C API, the lua_createtable function provides native support for pre-allocation:

// Creates a table with 1,000 array elements and 50 hash elements
lua_createtable(L, 1000, 50);

Using lua_createtable instead of lua_newtable (which is equivalent to lua_createtable(L, 0, 0)) prevents internal reallocations when populating data from C extensions, such as database drivers or network deserializers.

3. Standard Lua Table Constructors

In pure Lua 5.1–5.4 without external modules or C extensions, table.new is not built-in. However, initializing a table with literal values sizes the table correctly at creation:

-- Lua sizes the array to 3 immediately
local point = {0, 0, 0}

-- Lua sizes the hash part to 2 immediately
local config = { host = "localhost", port = 8080 }

For large arrays where manual declaration is impractical in standard Lua, developers often reuse existing tables (clearing values via table.clear in supported runtimes or setting keys to nil) rather than repeatedly constructing empty tables in tight loops.

Performance Benefits

  • Elimination of Rehashing: Rehashing the dictionary portion requires recalculating hash functions and resolving bucket collisions. Setting nrec avoids this entirely.
  • Minimized Memory Churn: Allocating the exact memory block once reduces the allocation rate, directly lowering the frequency and duration of garbage collection pauses.
  • Cache Locality: Contiguous, properly sized array buffers benefit from better CPU cache utilization, accelerating traversal and index access.

Pre-allocating table capacities should be prioritized inside game loops, real-time networking stacks, and data serialization routines where tables are frequently created and populated with predictable numbers of elements.
