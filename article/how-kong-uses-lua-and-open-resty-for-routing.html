How Kong Uses Lua and OpenResty for Routing

Kong API Gateway achieves high-performance microservice routing by using the Lua programming language within the OpenResty web platform to dynamically intercept, process, and forward HTTP requests. By executing Lua code inside the asynchronous, non-blocking Nginx event loop, Kong can evaluate incoming traffic, execute plugin logic, resolve upstream microservice destinations, and manipulate payloads in memory with sub-millisecond latency.

The Foundation: Nginx and OpenResty

At its core, Kong is built on OpenResty, a software bundle that integrates Nginx core with the Just-In-Time (JIT) Lua compiler (LuaJIT). OpenResty exposes the internal processing phases of Nginx to Lua through a series of directives, such as access_by_lua_block, rewrite_by_lua_block, and content_by_lua_block.

Instead of relying on standard static Nginx configuration files that require server reloads (nginx -s reload) to apply changes, Kong runs entirely as a dynamic Lua application on top of this environment. It manages routing configurations inside an external database (PostgreSQL) or a declarative YAML file, loading these rules directly into shared memory.

The Routing Mechanism: Lua in Nginx Phases

When a client sends a request to Kong, it traverses the standard Nginx request-processing lifecycle. Kong hooks its Lua codebase into these phases to handle routing:

  1. rewrite phase: Kong normalizes URLs, strips prefixes, or applies basic path modifications defined in route rules.
  2. access phase: This is where the core routing decisions occur. Kong's Lua router inspects the incoming HTTP method, URI path, headers, and hostnames. It evaluates these values against an in-memory data structure (typically a Radix tree implemented in Lua) to find a matching Route and associated Service entity.
  3. Upstream resolution: Once a Service is matched, Kong's Lua balancer resolves the target microservice address. If the target is an Upstream object containing multiple microservice instances, Kong applies Lua-based load-balancing algorithms (such as round-robin, least-connections, or hash-based routing) and performs passive or active health checks.
  4. Dynamic proxying: OpenResty sets internal Nginx variables ($upstream_host, $upstream_uri) based on the Lua router’s decision, directing Nginx to forward the connection to the determined microservice instance without leaving the event loop.

In-Memory Configuration and Shared Dictionaries

To route microservices without introducing database bottlenecks, Kong utilizes OpenResty's shared memory zones (lua_shared_dict).

Routing tables, upstream definitions, and target health statuses are cached in shared memory across all Nginx worker processes. When routing changes are made via Kong’s Admin API, event workers propagate invalidation messages across the system, prompting the Lua runtime to re-build its in-memory routing tree without dropping existing network connections.

Plugin Execution During Routing

The integration of Lua and OpenResty allows Kong to inject microservice policies directly into the routing path. Between the moment a route is matched and the request is proxied, Kong executes configured Lua plugins in a deterministic sequence based on defined priorities:

  • Authentication: Plugins (e.g., Key Authentication, JWT, OAuth2) validate incoming credentials against cached credentials in Lua memory.
  • Traffic Control: Plugins enforce rate limits via OpenResty memory dictionaries or Redis before the proxy phase is reached.
  • Transformations: Lua scripts can mutate headers, query parameters, or body contents on the fly using header_filter_by_lua and body_filter_by_lua before the upstream microservice receives the request.

By executing all routing, balancing, and policy enforcement within the embedded LuaJIT engine, Kong eliminates process switching and preserves the native high-concurrency architecture of Nginx.
