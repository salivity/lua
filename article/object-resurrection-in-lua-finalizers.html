Object Resurrection in Lua Finalizers

Object resurrection in Lua is a phenomenon where a garbage-collected object is restored to life during the execution of its own finalizer. When Lua's garbage collector identifies an unreachable object that defines a __gc metamethod, it must run this finalizer before reclaiming the memory. Because the object itself is passed as an argument to the finalizer, it can be re-anchored to an active, reachable reference, preventing the collector from deallocating it. This article explores how object resurrection occurs, how the Lua runtime manages resurrected objects across subsequent garbage collection cycles, and the potential pitfalls associated with this behavior.

How Lua Triggers Finalizers

In Lua, objects such as userdata and tables (from Lua 5.2 onwards) can register a finalizer by defining the __gc field in their metatable.

The garbage collection (GC) process operates in phases:

  1. Marking: The GC traverses all reachable objects starting from root references (such as the global table _G and the Lua registry).
  2. Separation: Objects identified as unreachable that possess a __gc metamethod are placed into a separate list for finalization.
  3. Finalization: The collector iterates through the finalization list and executes each object's __gc method.
  4. Sweeping: Unreachable objects without finalizers are collected and their memory is freed.

The Mechanism of Resurrection

To execute the finalizer, the runtime must pass the object to the __gc function as its primary parameter (self). At this precise moment, the object is temporarily accessible within the scope of the finalizer.

If the finalizer assigns self to a globally accessible table, an upvalue, or any other live structure, the object regains a strong reference from the active environment. This action resurrects the object:

local graveyard = {}

local obj = { name = "Resurrected Object" }
local mt = {
    __gc = function(self)
        print("Finalizing:", self.name)
        -- Resurrection occurs here:
        table.insert(graveyard, self)
    end
}

setmetatable(obj, mt)

-- Remove the only external reference
obj = nil

-- Force garbage collection
collectgarbage("collect")

-- The object is alive again and accessible in 'graveyard'
print(#graveyard) -- Outputs: 1
print(graveyard[1].name) -- Outputs: Resurrected Object

Because graveyard is reachable, the collector detects that the object is no longer dead during subsequent mark-and-sweep phases.

Lifecycle After Resurrection

Lua accommodates object resurrection without corrupting its internal memory allocator, but it imposes a strict lifecycle constraint to avoid infinite finalization loops:

  • Single Finalization Rule: In standard Lua, once an object's __gc metamethod has run, the runtime removes the object from the finalization pipeline. The object continues to exist as normal data.
  • Secondary Collection: If the resurrected object later loses its new reference (e.g., it is removed from graveyard) and becomes unreachable a second time, the garbage collector will reclaim its memory immediately without running the __gc metamethod again.

Because the finalizer is not re-invoked automatically, any cleanup logic that was supposed to occur right before absolute memory release must have either completed during the initial execution or be handled manually.

Risks and Side Effects

  1. Zombie States: An object whose finalizer closed internal OS handles, sockets, or native C pointers will be restored in an invalid or half-closed state, leading to runtime errors if application code attempts to reuse it.
  2. Memory Leaks: Accidental resurrection—often caused by logging functions or event listeners retaining references to the object during cleanup—prevents memory from ever being freed.
  3. Destructor Inconsistencies in C Modules: For native C userdata, resurrecting the userdata after calling free() on its internal pointer inside the __gc callback can cause use-after-free vulnerabilities or segmentation faults if Lua code subsequently accesses the userdata methods.

To prevent resurrection issues, finalizers should avoid storing references to self in outside scopes and should solely focus on releasing non-memory resources.
