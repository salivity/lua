Lua Userdata: Exposing C Memory Blocks to Lua

This article explains how Lua's userdata data type acts as a bridge between C and Lua, enabling C programs to expose arbitrary blocks of memory and native data structures directly to the Lua runtime. By leveraging full and light userdata alongside metatables and garbage collection hooks, developers can pass complex C state, structs, and pointers to Lua scripts while maintaining memory safety, encapsulation, and seamless integration with the host environment.

The Concept of Userdata in Lua

In Lua, basic types such as numbers, strings, and tables are managed entirely by the Lua runtime. However, when extending Lua with C, applications often need to manipulate native structs, file descriptors, network sockets, or raw memory buffers. Lua cannot interpret arbitrary C structs directly because it is an untyped, garbage-collected language.

The userdata type solves this by acting as an opaque container for raw C memory inside Lua. To the Lua interpreter, a userdata is just a value representing an address block. To C code, it is a typed pointer to data that C can freely read, modify, and manage.

Full Userdata: Lua-Managed Memory

Full userdata represents a block of raw memory allocated directly by Lua on behalf of C code. It is created using the C API function lua_newuserdata() (or lua_newuserdatauv() in Lua 5.4):

struct CustomResource *res = (struct CustomResource *)lua_newuserdata(L, sizeof(struct CustomResource));

When this function is called:

  1. Lua allocates a memory block of the specified size directly inside its own memory pool.
  2. A reference to this new userdata object is pushed onto the Lua stack.
  3. The function returns a raw pointer (void*) to the allocated block to the C program.

Because the memory is allocated by Lua, the Lua garbage collector fully tracks its lifecycle. When no more references to the userdata exist in Lua, the garbage collector reclaims the memory block automatically.

Light Userdata: Host-Managed Pointers

Lua also provides "light userdata," created using lua_pushlightuserdata(). Unlike full userdata, light userdata does not allocate any memory within Lua. It simply wraps an existing C pointer (void*) as a Lua value:

lua_pushlightuserdata(L, external_pointer);

Light userdata has significant trade-offs:

  • No Garbage Collection: Lua does not manage the underlying memory. The C code must ensure the memory remains valid while Lua holds the pointer.
  • No Individual Metatables: All light userdata values share a single metatable, making it impractical to attach object-oriented behaviors or custom type-checking to specific pointer types.

Light userdata is typically used for transient pointers, passing callbacks, or storing references to long-lived singleton instances maintained by the host application.

Exposing Functionality via Metatables

Because Lua treats a userdata as an opaque block of bytes, Lua scripts cannot inherently read fields from or write fields to the memory block using syntax like object.field. To allow scripts to interact with the data, C assigns a metatable to the userdata using lua_setmetatable().

Metatables provide control over how Lua interacts with the exposed memory:

  • __index: Intercepts read operations. C code can implement an __index metamethod or table to map Lua member access (e.g., res:process() or res.width) to corresponding C functions or field offsets.
  • __newindex: Intercepts write operations, allowing C code to validate and write values directly into the native struct memory when Lua sets a field (e.g., res.width = 10).
  • __tostring: Defines how the memory block is printed when inspected in Lua.

Managing Lifecycles with the __gc Metamethod

While Lua's garbage collector automatically frees the memory block of a full userdata, the C struct itself may own external resources, such as system handles, network connections, or memory allocated via malloc.

To handle cleanup before the memory block is released, C code registers a __gc metamethod in the userdata's metatable. When the garbage collector marks the userdata for deletion, it executes the __gc function first, allowing C to release dependent resources, close files, or execute custom destructors before Lua frees the primary memory block.

Type Safety and Validation

Exposing raw memory introduces the risk that a script might pass an invalid userdata type to a C function, causing memory corruption or segmentation faults. Lua avoids this through type tagging via the registry.

C libraries use luaL_newmetatable() to create a uniquely named metatable in the Lua registry. Before casting a userdata pointer, C functions call luaL_checkudata():

struct CustomResource *res = (struct CustomResource *)luaL_checkudata(L, 1, "CustomResourceMeta");

This verifies that the value at the given stack index is a full userdata and possesses the exact metatable associated with "CustomResourceMeta". If the validation fails, Lua generates a runtime error instead of allowing undefined memory access.
