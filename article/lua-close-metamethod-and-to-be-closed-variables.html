Lua __close Metamethod and To-Be-Closed Variables

This article explains how the __close metamethod functions in Lua to automate resource management and cleanup. Introduced in Lua 5.4, to-be-closed variables use the <close> attribute to guarantee that cleanup code runs deterministically whenever a variable leaves its declaring block. The following sections explore how to define these variables, the mechanics of when and how __close executes, how errors affect execution, and the order in which multiple resources are freed.

Declaring To-Be-Closed Variables

A to-be-closed variable is declared by appending the <close> annotation to a local variable declaration:

local resource <close> = create_resource()

For this declaration to be valid, the value assigned to resource must either be nil, false, or possess a metatable containing a __close metamethod. If a non-nil, non-false value lacks a valid __close metamethod at the moment of assignment, Lua immediately raises a runtime error.

How and When __close Executes

The __close metamethod acts like a destructor or a finally block in other languages. It executes automatically as soon as the lexical scope containing the variable terminates.

Scope exit occurs in several scenarios:

  • Natural completion: Reaching the end of a function, loop, do...end block, or then/else branch.
  • Explicit jumps: Exiting via statements such as return, break, or goto.
  • Runtime errors: An unhandled error raised within the block via error() or a standard runtime failure.

When the block ends, Lua automatically calls the metamethod in a protected environment equivalent to pcall, ensuring that pending cleanup operations are not skipped even during unexpected failure states.

Arguments Passed to __close

The __close function receives two arguments:

function mt:__close(err)
    -- cleanup logic
end
  1. self: The object being closed.
  2. err: The error value that caused the scope to exit. If the scope exited normally (via completion, return, break, or goto), err is nil. If the block terminated due to an error, err contains the error object.

This design allows the cleanup logic to adapt depending on whether the block succeeded or failed (e.g., committing a database transaction on normal exit or rolling it back if err is present).

Execution Order (LIFO)

When multiple <close> variables are defined within the same block, their __close metamethods execute in reverse order of declaration (Last In, First Out). This ensures that dependencies between resources are respected:

do
    local a <close> = make_resource("A")
    local b <close> = make_resource("B")
    -- Execution finishes here
end
-- Output order:
-- Closing B
-- Closing A

Error Handling During Cleanup

If an error occurs inside a __close metamethod itself, Lua continues executing the __close methods for any remaining to-be-closed variables higher up in the scope stack. Once all methods finish executing, the new error replaces any previous error unless an original error was already in progress, in which case the original error is preserved or converted into an error object reflecting the failure chain.
