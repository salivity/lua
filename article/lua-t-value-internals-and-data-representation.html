Lua TValue Internals and Data Representation

In the Lua virtual machine, the TValue (Tagged Value) structure serves as the fundamental container for all dynamic runtime values. This article explores how the standard PUC-Rio Lua virtual machine implements TValue as a tagged union, how it separates primitive immediate types from heap-allocated objects, the structural changes introduced to support distinct integer and floating-point representations, and how implementations like LuaJIT diverge from PUC-Rio by utilizing NaN-tagging.

The Tagged Union Architecture

PUC-Rio Lua avoids expensive dynamic allocations for every single variable by wrapping values inside a tagged union known as TValue. In the C source code, this structure typically consists of two main fields:

struct TValue {
  Value value_;
  lu_byte tt_;
};

The tt_ field is an integer tag defining the data type (such as LUA_TNIL, LUA_TBOOLEAN, LUA_TNUMBER, or LUA_TSTRING), while the value_ field is a C union capable of holding different representations in the same shared memory space:

union Value {
  GCObject *gc;    /* Collectible objects */
  void *p;         /* Light userdata */
  lua_CFunction f; /* Light C functions */
  lua_Integer i;   /* Integer numbers */
  lua_Number n;    /* Floating-point numbers */
};

On a 64-bit architecture, Value requires 8 bytes. Although tt_ only requires 1 byte (or an int depending on compiler options and Lua version), memory alignment rules typically pad struct TValue to 16 bytes.

Immediate Values vs. Garbage-Collected References

The primary structural divide inside TValue is between types that store their payloads inline and types that point to dynamically allocated memory tracked by Lua's garbage collector.

  1. Immediate (Inline) Types:
    • Nil and Booleans: Nil requires no payload; its existence is completely defined by its type tag. Booleans store their state either directly in an integer field in the union or, in newer Lua versions, directly within variant bits of the tt_ tag itself to save operations.
    • Numbers: Both floating-point and integer types fit directly into the union (lua_Number n or lua_Integer i).
    • Light Userdata: This represents raw C pointers (void *p) managed outside Lua’s runtime. Because Lua does not manage the memory behind these pointers, they are stored directly in the union without garbage collection overhead.
  2. Collectable (Pointer) Types:
    • Strings, Tables, Functions, Threads, and Full Userdata: These data structures cannot fit inside an 8-byte scalar. Instead, their TValue stores a pointer (GCObject *gc). The object itself lives on the heap and begins with a common header (CommonHeader) that contains the pointers and color bits required by the incremental mark-and-sweep garbage collector.

Number Subtyping in Lua 5.3+

Prior to Lua 5.3, all numbers were represented uniformly using a single double-precision floating-point type (lua_Number). Lua 5.3 introduced an internal distinction between integers and floats without breaking dynamic typing at the language level.

Within TValue, this distinction is managed through sub-tags encoded in tt_:

  • LUA_VNUMINT: Designates that value_.i holds a signed 64-bit integer (lua_Integer). Bitwise operations and integer arithmetic read and write directly to this field.
  • LUA_VNUMFLT: Designates that value_.n holds an IEEE 754 double-precision float (lua_Number).

The VM checks the sub-type tag before execution to dispatch the appropriate hardware instructions (integer ALU instructions versus floating-point FPU/SIMD instructions), preventing truncation errors and improving execution speed for integer indexing.

Short Strings vs. Long Strings

Lua divides strings into two distinct internal categories, which are reflected in the type tag and underlying object:

  • Short Strings (LUA_VSHRSTR): Strings up to a specific length (typically 40 bytes) are internalized via hash-consing. The VM ensures that only one copy of any unique short string exists in a global string table. Equality comparisons between short strings evaluate in \(O(1)\) time by simply checking if their pointer values in value_.gc are identical.
  • Long Strings (LUA_VLNGSTR): Longer strings are not automatically internalized upon creation to prevent high hashing overhead for large payloads. They compute their hash lazily only when used as table keys, and equality comparisons require a full byte-by-byte comparison if their pointers differ.

PUC-Rio Lua vs. LuaJIT: Tagged Union vs. NaN-Tagging

While PUC-Rio Lua uses the traditional tagged union that expands to 16 bytes on 64-bit platforms, LuaJIT utilizes an optimization known as NaN-tagging to reduce the size of TValue down to 8 bytes.

An IEEE 754 double-precision float uses 64 bits: 1 sign bit, 11 exponent bits, and 52 mantissa bits. When all exponent bits are set to 1, the value represents a Not-a-Number (NaN). The remaining 52 mantissa bits are essentially unused by standard hardware calculations.

LuaJIT takes advantage of this unused space:

  • Any valid floating-point number is stored directly as its native 64-bit representation.
  • If the bits match a specific quiet NaN pattern, the upper bits encode the dynamic type tag (such as string, table, boolean, or integer), while the lower 48 bits store the pointer or integer payload.

Because 64-bit pointers on modern architectures only use the lower 48 bits of the address space, an entire pointer and its type tag fit comfortably inside a single 64-bit double. This halves the memory footprint of Lua tables and the VM register stack compared to PUC-Rio, significantly improving CPU cache utilization.
