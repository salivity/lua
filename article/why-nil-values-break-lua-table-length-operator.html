Why Nil Values Break Lua Table Length Operator

In the Lua programming language, using the length operator (#) on a table assumes that the table represents a proper sequence—a contiguous list of positive integer keys starting from index 1. When you store nil values inside such a table, you create "holes," which breaks the formal definition of a sequence. Because Lua's length operator is designed to locate any valid boundary between a non-nil value and a nil value rather than scanning the entire table, presence of internal nil values leads to undefined, unstable, and unpredictable length results.

The Formal Definition of a Sequence

In Lua, a sequence is defined as a table where the set of positive numeric keys is equal to {1..n} for some non-negative integer n. In a proper sequence, every integer index from 1 to n holds a non-nil value, and the key n + 1 holds nil.

When a table conforms to this rule, #t reliably returns n. However, if any key within the range 1 to n contains nil, the table ceases to be a valid sequence.

How the Length Operator Works

Lua does not store an internal counter for the number of elements in a table. Instead, the length operator # uses an \(O(\log n)\) binary search algorithm to find an index \(i\) such that:

t[i] ~= nil and t[i + 1] == nil

Alternatively, if t[1] == nil, the operator simply returns 0.

When a table contains holes (such as {10, nil, 30}), multiple indices satisfy this boundary condition:

  • At index 1: t[1] is 10 (not nil), and t[2] is nil.
  • At index 3: t[3] is 30 (not nil), and t[4] is nil.

Because both indices meet the specification's definition of a border, Lua is free to return either 1 or 3. The language specification explicitly states that if a table has holes, #t may produce any index that immediately precedes a nil value.

Internal Table Representation

Lua tables are internally divided into two segments: an array part and a hash part. Lua dynamically redistributes keys between these parts during table resizing to optimize memory and speed.

When you insert nil values or delete items using t[k] = nil, keys may shift between the array and hash parts during subsequent reallocations. As a result, the exact index returned by #t on a table with holes can change based on:

  • The order in which keys were inserted.
  • Table reallocations triggered by adding other keys.
  • The specific Lua implementation (e.g., standard PUC-Rio Lua vs. LuaJIT).

For example, initializing a table as t = {1, nil, 3} might yield #t as 3, but adding more elements and deleting them could cause #t to return 1 for the exact same set of remaining keys.

Practical Implications and Common Pitfalls

  1. Broken Iteration: Traditional numeric for loops relying on #t (e.g., for i = 1, #t do) will silently terminate early if #t resolves to an internal boundary, skipping valid data located after the hole.
  2. Improper Deletion: Setting an array index to nil (t[index] = nil) instead of shifting elements leaves a hole. If the intent is to remove an element and maintain the sequence, table.remove(t, index) must be used instead.
  3. Data Loss in Serialization: Functions or libraries that serialize sequences based on #t will truncate payloads prematurely when encountering an internal nil.

Safe Alternatives for Handling Nil Values

To avoid unpredictable behavior when working with sparse arrays or data that must preserve nil:

  • Use table.pack: Calling table.pack(...) returns a new table containing all arguments, along with an explicit n field (accessible via t.n) that records the true argument count regardless of nil entries.
  • Track Length Manually: Maintain a separate counter variable or a metadata key within the table (e.g., t.size) that updates whenever items are inserted or removed.
  • Use Sentinel Values: Replace nil with a unique sentinel object, such as a custom empty table (local NULL = {}) or a boolean flag, so every intended position contains a non-nil value.
