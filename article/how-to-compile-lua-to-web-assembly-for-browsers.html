How to Compile Lua to WebAssembly for Browsers

This article explains how to compile the Lua programming language into WebAssembly (Wasm) to execute it securely within modern web browsers. It covers the prerequisites, the step-by-step compilation process using Emscripten on the official Lua C source, the mechanism for interacting between JavaScript and Lua, and the security benefits provided by WebAssembly's native sandbox architecture.

Prerequisites

To compile Lua to WebAssembly, you need the following:

  • Emscripten SDK (emsdk): The standard toolchain for compiling C and C++ projects into WebAssembly.
  • Lua Source Code: The standard ANSI C distribution of Lua (such as Lua 5.4), downloadable from the official Lua website.
  • A modern web browser: Chrome, Firefox, Safari, or Edge with WebAssembly support.

Step 1: Install and Configure Emscripten

Clone and activate the Emscripten toolchain:

git clone https://github.com/emscripten-core/emsdk.git
cd emsdk
./emsdk install latest
./emsdk activate latest
source ./emsdk_env.sh

Step 2: Download and Prepare Lua Source

Download and extract the Lua source archive:

curl -R -O http://www.lua.org/ftp/lua-5.4.6.tar.gz
tar zxf lua-5.4.6.tar.gz
cd lua-5.4.6/src

Lua is written in clean, portable C, making it an ideal candidate for Emscripten without needing source-level modifications.

Step 3: Compile Lua Core to WebAssembly

To compile Lua into a WebAssembly module that can be loaded by JavaScript, use emcc. Instead of compiling the standalone command-line executable (lua.c), compile the core library files along with a lightweight wrapper or export the essential Lua C API functions directly.

Run the following command in the src directory to compile the core engine into lua.js and lua.wasm:

emcc -O3 \
  lapi.c lcode.c lctype.c ldebug.c ldo.c ldump.c lfunc.c lgc.c llex.c \
  lmem.c lobject.c lopcodes.c lparser.c lstate.c lstring.c ltable.c \
  ltm.c lundump.c lvm.c lzio.c \
  lauxlib.c lbaselib.c lcorolib.c ldblib.c liolib.c lmathlib.c loslib.c \
  ltablib.c lstrlib.c lutf8lib.c loadlib.c linit.c \
  -s WASM=1 \
  -s EXPORTED_FUNCTIONS="['_luaL_newstate', '_luaL_openlibs', '_luaL_loadstring', '_lua_pcallk', '_lua_close', '_lua_tolstring']" \
  -s EXPORTED_RUNTIME_METHODS="['ccall', 'cwrap', 'UTF8ToString', 'stringToUTF8']" \
  -s MODULARIZE=1 \
  -s EXPORT_NAME="createLuaModule" \
  -o lua.js

This generates:

  • lua.wasm: The compiled binary WebAssembly module.
  • lua.js: The Emscripten glue code handling memory initialization and the JavaScript bridge.

Step 4: Execute Lua in the Browser

You can now instantiate the module in an HTML page and execute Lua scripts directly via JavaScript:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>Lua in WebAssembly</title>
  <script src="lua.js"></script>
</head>
<body>
  <script>
    createLuaModule().then(Module => {
      // Create a new Lua state
      const L = Module._luaL_newstate();
      Module._luaL_openlibs(L);

      // Function to run Lua code strings
      function runLua(code) {
        const stackTop = Module._luaL_loadstring(L, allocateUTF8(code));
        if (stackTop === 0) {
          // Protected call: lua_pcall(L, nargs, nresults, errfunc)
          Module._lua_pcallk(L, 0, 0, 0, 0, null);
        } else {
          const err = Module.UTF8ToString(Module._lua_tolstring(L, -1, 0));
          console.error("Lua compilation error:", err);
        }
      }

      function allocateUTF8(str) {
        const length = Module.lengthBytesUTF8(str) + 1;
        const ptr = Module._malloc(length);
        Module.stringToUTF8(str, ptr, length);
        return ptr;
      }

      // Execute a Lua command
      runLua("print('Hello from Lua running inside WebAssembly!')");

      // Clean up
      Module._lua_close(L);
    });
  </script>
</body>
</html>

Security Considerations

Running user-defined Lua inside a browser poses significantly lower risk when compiled to WebAssembly:

  1. Memory Isolation: WebAssembly runs within a sandboxed virtual machine with its own separate, linear memory space. A crash, buffer overflow, or memory corruption inside Lua cannot access or corrupt the browser's DOM, JavaScript memory, or the host operating system.
  2. Restricted OS APIs: Standard C libraries functions for direct hardware, filesystem, and network access (such as fopen or standard sockets) are either stubbed or mapped to Emscripten's virtual in-memory filesystem. Host system files cannot be modified or read.
  3. Controlled Capabilities: The browser environment grants Lua only the capabilities explicitly exposed to it through JavaScript bindings. Untrusted Lua scripts can be executed safely for game logic, mathematical evaluation, or plugin architectures without compromising client security.
