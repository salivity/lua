How lua.c Implements the Lua Interactive REPL

The lua.c source file provides the frontend entry point for the standalone Lua interpreter, decoupling the execution environment from the core language engine. Rather than containing parser or virtual machine internals, lua.c serves as an embedding client that uses the public Lua C API to parse CLI flags, run scripts, manage OS signals, and implement an interactive Read-Eval-Print Loop (REPL). It manages dynamic user inputs, evaluates expressions versus statements, and coordinates multi-line code accumulation when inputs are syntactically incomplete.

The Role of lua.c

In the Lua source distribution, the core virtual machine and standard libraries compile into a standalone library (often liblua.a). The lua.c file exists independently to compile into the lua executable. It acts as an example of how an external host application embeds Lua via headers like lua.h, lauxlib.h, and lualib.h.

Its responsibilities include:

  • Parsing command-line arguments (such as -e, -l, -i, and -v).
  • Initializing and tearing down the Lua state (lua_State).
  • Trapping OS signals like SIGINT (Ctrl+C) to interrupt long-running operations cleanly.
  • Running the interactive REPL when invoked with -i or without script arguments.

Initialization and Protected Execution

Execution begins in main(), which immediately delegates to lua_pcall to run pmain() in protected mode. This ensures that any initialization failure, memory allocation error, or uncaught exception prints cleanly to stderr rather than triggering an unhandled C crash.

Within pmain():

  1. luaL_newstate() allocates the primary lua_State.
  2. luaL_openlibs() loads the standard Lua libraries (math, string, table, io, etc.).
  3. Command-line flags are processed sequentially.
  4. If no script is provided or the -i flag is passed, the program calls doREPL().

The REPL Architecture (doREPL)

The REPL function runs a continuous loop that collects user input, compiles it as a Lua chunk, executes it, and displays any returned values or errors.

1. Prompt Resolution and Reading Input

The REPL first displays a prompt retrieved via get_prompt(). Lua checks global variables _PROMPT (defaulting to >) for new statements and _PROMPT2 (defaulting to >>) for continuation lines.

Input collection relies on lua_readline(), which dynamically maps to GNU Readline or POSIX editline if enabled during compilation, enabling history navigation and line editing. Otherwise, it falls back to standard C fgets().

2. Differentiating Expressions from Statements

When a user enters a line like x + 1, a standard compiler expects a statement and raises a syntax error. To deliver a user-friendly REPL, lua.c implements addreturn():

  • It prepends return to the entered buffer (turning x + 1 into return x + 1).
  • It attempts to compile the modified buffer using luaL_loadbuffer().
  • If compilation succeeds, the buffer was a valid expression. The generated bytecode is pushed onto the Lua stack, and execution proceeds.
  • If compilation fails, the code discards the modified buffer and re-attempts compilation on the raw user input as a standard statement.

3. Handling Multi-Line Input

If compilation of the raw statement fails, lua.c analyzes the error message via incomplete().

The function inspects the compiler output for an unexpected end-of-file error (specifically looking for the <eof> token at the end of the syntax error string). When an incomplete statement (such as an unclosed if, function, or for block) is detected:

  • The REPL does not display an error.
  • It switches to the secondary prompt (_PROMPT2).
  • It reads subsequent lines and appends them to the current buffer using luaL_Buffer.
  • It repeats compilation until the syntax is complete or an unrecoverable syntax error occurs.

4. Code Execution and Error Handling (docall)

Once a chunk compiles successfully, lua.c runs it via docall():

  • A message handler is pushed onto the stack to generate stack traces via debug.traceback if runtime errors occur.
  • The compiled chunk runs inside lua_pcall().
  • If execution returns values, lua.c iterates through the returned items on the Lua stack and calls the global print() function on them, outputting results directly to standard out.

Signal Handling and Interruption

To prevent the REPL from exiting when an interrupted program enters an infinite loop, lua.c registers a signal handler for SIGINT. When triggered, the handler registers a C debug hook via lua_sethook().

The hook runs on the next instruction cycle of the Lua VM and throws a Lua runtime error ("interrupted!"). This safely unwinds the Lua execution stack back to pmain() or doREPL() without terminating the interpreter process or leaking memory.
