lua_pushlightuserdata vs lua_newuserdatauv in Lua

In modern Lua (versions 5.4 and later), managing external C data requires choosing between light userdata and full userdata. While lua_pushlightuserdata pushes a plain, unmanaged C pointer into the Lua stack with zero allocation cost, lua_newuserdatauv allocates a full memory block directly within Lua’s garbage-collected heap, complete with support for custom metatables and multiple associated Lua values. This guide explains how each function works, their core architectural differences, and when to use each approach in modern Lua C APIs.

What Is lua_pushlightuserdata?

lua_pushlightuserdata simply pushes a raw C pointer (void*) onto the Lua stack as a value:

void lua_pushlightuserdata(lua_State *L, void *p);

Light userdata is treated as a primitive value, similar to a number or a boolean:

  • No Garbage Collection: Lua does not manage, track, or free the memory pointed to by a light userdata. The host C application is entirely responsible for allocating, maintaining, and freeing this memory.
  • Shared Metatable: Light userdata instances cannot have individual metatables. All light userdata share a single, global metatable (which is nil by default), preventing instance-specific object-oriented behaviors or individual type validation.
  • Value Equality: Two light userdata values in Lua are considered equal (==) if and only if their underlying memory addresses match.
  • Zero Overhead: Pushing a light userdata does not trigger Lua memory allocation, making it extremely fast.

What Is lua_newuserdatauv?

Introduced in Lua 5.4 to replace lua_newuserdata, lua_newuserdatauv creates a full userdata object managed entirely by the Lua runtime:

void *lua_newuserdatauv(lua_State *L, size_t size, int nuvalue);

This function allocates a block of memory of size bytes on Lua's heap and associates it with nuvalue number of user values (Lua values tied to the userdata lifecycle):

  • Garbage-Collected Lifecycle: The allocated block is subject to Lua's garbage collector. When the userdata is collected, Lua automatically reclaims the memory and invokes any __gc metamethod assigned to it, allowing C-side resources (such as file handles or socket descriptors) to be cleaned up safely.
  • Individual Metatables: Each full userdata can have its own metatable. This enables type tagging via the registry, custom indexing (__index), arithmetic operators, and proper object-oriented encapsulation.
  • Multiple Uservalues (nuvalue): Unlike older Lua versions that allowed only a single user value, Lua 5.4 permits multiple associated Lua values. These user values prevent referenced Lua objects from being prematurely garbage collected while the host userdata remains alive.

Core Architectural Differences

Feature lua_pushlightuserdata lua_newuserdatauv
Memory Allocation Allocated and managed in C Allocated inside Lua's heap
Garbage Collection Ignored by GC; no __gc Managed by GC; supports __gc
Metatables Global, shared metatable only Dedicated, per-object metatables
User Values None supported Supports 0 to 65,535 user values
Equality Check Strict pointer comparison Identity comparison (or __eq metamethod)
Performance Cost Negligible; no allocation Allocation and GC tracking overhead

Choosing Between the Two

Use lua_pushlightuserdata when:

  • Passing transient pointers or raw handles to Lua where lifetime management is strictly confined to C.
  • Using pointers as table keys for mapping C objects to Lua state.
  • Maximum performance is required and Lua code does not need to inspect, manipulate, or finalize the underlying structure.

Use lua_newuserdatauv when:

  • Exposing C/C++ objects or libraries to Lua where the object should behave like a native Lua object.
  • Resources require deterministic cleanup via the __gc metamethod.
  • Type safety is critical, requiring verification through luaL_checkudata.
  • The C structure needs to hold references to other Lua values (such as callbacks or configuration tables) using the nuvalue slots to prevent them from being garbage-collected.
