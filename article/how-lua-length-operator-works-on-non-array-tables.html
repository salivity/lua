How Lua Length Operator Works on Non-Array Tables

The length operator (#) in Lua is specifically optimized for sequences—tables with contiguous positive integer keys starting at 1. When applied to a table containing "holes" (nil values between non-nil keys) or non-numeric keys, the # operator does not calculate a true total count of elements. Instead, Lua’s language specification only guarantees that the operator will return a "border"—an index where a non-nil value is immediately followed by a nil value—due to the underlying binary search algorithm used for performance.

What is a Border in Lua?

In Lua, a border in a table t is defined as any non-negative integer i that satisfies the condition:

(i == 0 or t[i] ~= nil) and t[i + 1] == nil

For a proper sequence (like {10, 20, 30}), there is only one border: index 3 (t[3] == 30 and t[4] == nil). Therefore, #t reliably returns 3.

However, if a table contains internal nil values, multiple indices can satisfy the definition of a border. Consider the following table:

local t = { [1] = "a", [2] = nil, [3] = "c" }

In this table, both i = 1 and i = 3 are valid borders:

  • t[1] ~= nil and t[2] == nil
  • t[3] ~= nil and t[4] == nil

Because both fit the specification, Lua can return either 1 or 3 as the result of #t.

Why Lua Implements Borders Instead of True Counts

The primary reason for this behavior is computational efficiency.

Lua tables are implemented internally as hybrid data structures consisting of an array part and a hash part. Determining the exact count of arbitrary keys or identifying all non-nil elements across both parts would require an \(O(n)\) linear traversal of the entire table every time # is called.

To make the length operation virtually instantaneous, Lua specifies # to run in \(O(\log n)\) time. It achieves this by using a binary search to find a boundary:

  1. Check the Array Boundary: Lua checks if the end of its internal array buffer is a border.
  2. Binary Search: If keys extend beyond the array buffer into the hash part, Lua performs a binary search between known bounds to locate an index followed by nil.

Because binary search requires monotonic data to guarantee a specific target, using it on an array with arbitrary gaps produces non-deterministic results. The algorithm simply stops at the first border it converges upon, which can change depending on how the table was allocated or resized in memory.

Handling Non-Array Elements

The # operator completely ignores keys that are not positive integers, including:

  • Negative numbers and 0
  • Floating-point numbers
  • Strings, booleans, and other table references

Because these keys are stored exclusively in the hash part and cannot form part of a contiguous integer sequence starting at 1, they are not factored into the border search.

How to Get a True Count of Non-Array Tables

To find the true count of elements in a table that contains holes or non-integer keys, avoid using # and use one of the following approaches:

1. Linear Traversal with pairs Iterate through the table using pairs and increment a counter to get an exact \(O(n)\) count of all keys:

local function countElements(t)
    local count = 0
    for _ in pairs(t) do
        count = count + 1
    end
    return count
end

2. Maintain an Explicit Counter If frequent lookups are required, maintain a dedicated counter variable that tracks additions and removals alongside table modifications, preserving \(O(1)\) read access without relying on #.
