How Lua Stores Line Number Mapping Tables

In the Lua programming language, runtime error reporting relies on mapping bytecode instructions back to their corresponding source code lines via metadata stored within function prototypes (Proto). Lua implements this by maintaining internal arrays alongside the generated bytecode: older versions (Lua 5.1 through 5.3) utilize a straightforward one-to-one mapping array, whereas Lua 5.4 introduces a hybrid, delta-compressed structure with absolute checkpoints to minimize memory usage. When a runtime error occurs, the virtual machine resolves the active instruction pointer against these tables to identify the exact line number for stack traces and debug output.

The Function Prototype (Proto) Context

In Lua's C internals, compiled functions (chunks) are represented by the Proto struct (defined in lobject.h). A prototype encapsulates everything required to execute a function, including:

  • The array of bytecode instructions (Instruction *code).
  • Constants (TValue *k).
  • Nested prototypes (Proto **p).
  • Debug information, including the source chunk name (TString *source) and line mapping arrays (lineinfo and, in Lua 5.4, abslineinfo).

When code compiles, the parser generates bytecode and concurrently populates the line mapping data structures.

Direct Mapping (Lua 5.1 to Lua 5.3)

In Lua 5.1 through Lua 5.3, the line mapping scheme is direct and uncompressed:

  • Data Structure: The Proto structure contains a pointer int *lineinfo and an integer sizelineinfo.
  • Storage: For every instruction in the code array, there is a matching integer in lineinfo. If a function contains \(N\) instructions, lineinfo is allocated as an array of \(N\) integers.
  • Resolution: Finding the line number corresponding to program counter pc requires a simple \(O(1)\) array lookup: proto->lineinfo[pc].

While this model provides constant-time access, it incurs a substantial memory footprint: 4 bytes (or 8 bytes on 64-bit platforms where int might vary or require padding) per bytecode instruction, even when hundreds of instructions originate from the same line or increment sequentially.

Compressed Delta Mapping (Lua 5.4)

Lua 5.4 reworked line information storage to reduce the memory overhead of the debug tables. Because line numbers generally advance sequentially or remain unchanged across multiple instructions, storing a full 32-bit integer per instruction is redundant.

Lua 5.4 splits line mapping across two fields in Proto:

  1. ls_byte *lineinfo: An array of signed bytes (signed char), sized to match the number of instructions. Each entry represents a relative delta from the previous instruction's line.
  2. AbsLineInfo *abslineinfo: A sparsely populated array of absolute checkpoints. Each AbsLineInfo entry contains a program counter offset (pc) and an absolute line number (line).

Delta Encoding Rules

During compilation:

  • If the difference between the current instruction's line and the previous instruction's line falls between -128 and 127, Lua stores this delta directly in lineinfo[pc].
  • If the line delta exceeds the range of a signed byte, or if the compiler reaches a fixed instruction interval (defined by MAXIWTHABS, typically 128 instructions), an entry is added to abslineinfo. The corresponding lineinfo[pc] is marked with a special sentinel value (ABSLINEINFO, defined as -128), signifying that the engine must look up an absolute value rather than applying a delta.

Resolving Line Numbers in Lua 5.4

To resolve the line number for an instruction pc, Lua uses the internal function luaG_getfuncline:

  1. If proto->lineinfo is NULL (debug information was stripped), the engine falls back to proto->linedefined.
  2. If the table is present, the engine performs a binary search or reverse scan over proto->abslineinfo to find the closest absolute checkpoint where checkpoint.pc <= pc.
  3. Starting from that absolute line number and instruction offset, the engine steps forward to pc, accumulating the signed byte deltas stored in lineinfo.

This approach reduces line table memory consumption by roughly 75% for typical code while maintaining near-instant line resolution.

The Runtime Error Reporting Flow

When an execution error occurs inside the Lua virtual machine:

  1. Instruction Identification: The virtual machine references the current execution state via the active call frame (CallInfo *ci). The frame retains ci->u.l.savedpc, which points directly to the failing instruction in the prototype's code array.
  2. Offset Calculation: The program counter index is computed via pointer arithmetic: int pc = pcRel(ci->u.l.savedpc, proto).
  3. Line Lookup: The runtime calls luaG_getfuncline(proto, pc) to query the line mapping table.
  4. Error Construction: Functions such as luaG_runerror and luaG_addinfo read the proto->source string, format it alongside the resolved line number (e.g., [string "chunk"]:line:), and prepend this prefix to the runtime error description before raising an error via longjmp or invoking the configured error handler.
