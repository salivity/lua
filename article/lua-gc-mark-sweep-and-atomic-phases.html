Lua GC: Mark, Sweep, and Atomic Phases

This article provides an overview of the incremental garbage collector (GC) in the Lua programming language, focusing on its core execution cycle. Lua employs a tri-color incremental mark-and-sweep collector designed to interleave garbage collection steps with program execution to minimize latency. Below is a detailed breakdown of the three primary phases of this cycle: the mark phase, the atomic phase, and the sweep phase.

Tri-Color Marking Basics

To understand Lua's GC phases, it helps to understand its tri-color abstraction:

  • White: Unvisited objects that are candidates for collection. Lua distinguishes between "current white" and "other white" to track object generations across cycles.
  • Gray: Objects visited by the collector, but whose referenced objects (children) have not yet been examined.
  • Black: Reachable objects whose references have all been fully traversed. Black objects cannot point directly to white objects without triggering a barrier.

1. The Mark Phase

The mark phase identifies all live objects reachable by the program. Because Lua's collector is incremental, this phase runs in small steps interleaved with regular program execution.

  • Root Initialization: The phase begins by marking the root set—including the global table, the registry, and active coroutine stacks—turning them gray.
  • Incremental Propagation: In successive steps, the collector pops an object from the gray list, traverses its references (such as table keys and values), marks those referenced objects as gray (if they were white), and transitions the original object to black.
  • Write Barriers: Because user code runs concurrently between mark steps, the running program might link a white (unmarked) object to a black (fully visited) object. To preserve the invariant that black objects never point to white objects, Lua uses write barriers. A write barrier either reverts the black object back to gray (barrier back) or immediately marks the white object as gray (barrier forward).

2. The Atomic Phase

The atomic phase is an uninterruptible, stop-the-world transition point between marking and sweeping. It handles state that cannot safely or efficiently be processed incrementally.

  • Finishing the Mark: The collector processes any remaining gray objects, including tables that were pushed back to the gray list by write barriers.
  • Weak Tables Handling: Lua clears references inside weak-keyed or weak-valued tables if the associated key or value is about to be collected.
  • Finalization (__gc Metamethods): Objects with finalizers that are marked for collection are identified. Lua rescues these objects for the duration of finalization by marking them and moving them to a separate finalization list so their __gc metamethods can run safely later.
  • Color Flip: The collector flips the internal definition of "white." Objects currently marked white are definitively garbage, while surviving black objects will be prepared for the next cycle.

3. The Sweep Phase

The sweep phase reclaims memory from dead objects and resets the remaining live objects for future GC cycles. Like the mark phase, sweeping is performed incrementally across multiple engine ticks.

  • Dead Object Deallocation: The collector traverses Lua’s global linked list of all allocated objects. Any object that remains white (not reached during marking) is unlinked and deallocated, freeing its memory back to the system.
  • State Reset for Survivors: Surviving objects (marked black) are reset back to the current white state so they can be evaluated afresh in the subsequent garbage collection cycle.
  • String Table Sweeping: Unused, unreferenced strings in the internal string pool are freed during this phase.

Once the sweep phase finishes traversing the global object list, the cycle concludes, and the collector enters a pause state until memory allocation thresholds trigger the next mark phase.
