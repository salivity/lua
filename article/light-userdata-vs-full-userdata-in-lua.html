Light Userdata vs Full Userdata in Lua

In the Lua programming language, userdata is the primary mechanism used to bind arbitrary C/C++ data to Lua scripts. Lua divides this mechanism into two distinct types: full userdata and light userdata. While both represent external C memory, they fundamentally differ in memory management, garbage collection behavior, metatable support, and equality semantics. This article breaks down the operational differences between these two types to help you choose the right approach when extending Lua with C.

Memory Management and Ownership

The most critical functional distinction is how memory is allocated and freed.

  • Full Userdata: Represents a block of raw memory allocated directly by the Lua runtime via the C API function lua_newuserdata (or lua_newuserdatauv in Lua 5.4). Because Lua allocates this memory, it is a fully managed Lua value and is subject to Lua's garbage collector (GC).
  • Light Userdata: Represents a plain C pointer (void*) pushed into the Lua stack using lua_pushlightuserdata. Lua does not allocate, manage, or free the memory address the pointer references. The host application or external C library retains full responsibility for the allocation and deallocation of that memory.

Metatables and Metamethods

Metatables define how values behave in Lua, such as operator overloading and object-oriented syntax.

  • Full Userdata: Each full userdata instance can have its own individual metatable. This allows you to define custom behavior, implement object-oriented method dispatch (via the __index metamethod), and attach a finalizer. The __gc metamethod is particularly important, as it enables C cleanup code to run automatically when Lua collects the object.
  • Light Userdata: Light userdata instances cannot have individual metatables. Instead, all light userdata values share a single, global metatable across the entire Lua state. Consequently, you cannot give distinct behavior or method sets to different types of C pointers. Furthermore, light userdata does not support the __gc metamethod because Lua has no lifecycle awareness of the underlying resource.

Equality and Identity

The two types evaluate equality (==) using different criteria.

  • Full Userdata: A full userdata is evaluated by identity. Two full userdata objects are equal only if they refer to the exact same Lua-allocated memory block, unless an __eq metamethod is provided to redefine equality.
  • Light Userdata: A light userdata is evaluated purely by the value of the pointer it holds. Any two light userdata values wrapping the exact same void* memory address are always strictly equal (==), regardless of where or when they were pushed to the stack.

Practical Use Cases

  • Use Full Userdata when:
    • You are exposing complex C structs or C++ objects to Lua scripts.
    • You need the resource to automatically free itself (e.g., closing file descriptors, releasing sockets, freeing database handles) via the __gc metamethod.
    • You want to provide an object-oriented API in Lua using metatables and methods.
  • Use Light Userdata when:
    • The memory lifecycle is already strictly managed by C or an external framework.
    • You need to pass an identifier, handle, or callback context into Lua with zero memory allocation overhead.
    • You want to use raw C pointers as fast, unique keys in Lua tables.
