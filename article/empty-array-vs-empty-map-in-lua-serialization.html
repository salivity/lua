Empty Array vs Empty Map in Lua Serialization

In the Lua programming language, tables are the sole data structure used to represent both sequential arrays (lists) and associative maps (dictionaries). Because an empty table {} contains neither numeric indices nor key-value pairs, custom serialization schemes—such as JSON, MessagePack, or custom binary encoders—cannot infer intent from table contents alone. This article examines the core strategies used to differentiate between empty arrays and empty maps during serialization, including metatables, sentinel values, and schema-driven definitions.

The Ambiguity of Lua Tables

A populated Lua table easily reveals its structure: a table with contiguous integer keys starting at 1 functions as an array, while a table with string or non-contiguous keys acts as a map. However, when a table is empty, inspection functions like next() return nil, and the length operator # returns 0. Consequently, an empty table provides no inherent structural clues to indicate whether it should serialize as an empty array ([]) or an empty object/map ({}).

Strategy 1: Metatables and Type Tagging

The most common approach in Lua libraries is attaching metadata directly to the table using metatables. A serialization library can inspect the metatable of an empty table to read a dedicated type tag.

  • Boolean Metatags: The metatable can include a boolean field, such as __is_array = true or __is_map = true.
  • String Type Identifiers: A generic field like __type = "array" or __type = "map" can be evaluated by the serializer's dispatch loop.

When the serializer encounters an empty table, it checks getmetatable(t). If the specific array or map tag is present, it emits the corresponding serialized token. Libraries like lua-cjson use this concept by providing explicit metatables, such as cjson.empty_array_mt, allowing developers to set setmetatable(data, cjson.empty_array_mt).

Strategy 2: Dedicated Sentinel Objects

Rather than tagging existing tables, serialization schemes can provide immutable sentinel singletons. These unique object references represent empty types explicitly.

  • serial.empty_array = newproxy(true) or serial.empty_array = {}
  • serial.empty_map = newproxy(true) or serial.empty_map = {}

When constructing data, developers use these singletons instead of standard {} literals. During serialization, the encoder performs identity comparison:

if value == serial.empty_array then
    write_empty_array()
elseif value == serial.empty_map then
    write_empty_map()
end

Because these sentinels rely on reference equality (rawequal), checks are fast and avoid metatable lookups.

Strategy 3: Wrapper/Boxed Data Structures

For object-oriented architectures, custom serializers often use wrapper objects or classes. Instead of working with raw Lua tables, collections are instantiated via constructors:

local my_list = Array()
local my_dict = Map()

These objects wrap an underlying table and expose specific methods (push, set, etc.) along with explicit type signatures. The serializer inspects the instance's class or internal type identifier, ensuring that an empty Array instance is always distinguished from an empty Map instance.

Strategy 4: Schema-Driven Serialization

When the target output format has a rigid structure (such as Protocol Buffers, Avro, or predefined JSON Schemas), the serializer does not rely on Lua runtime clues.

Instead, the serialization function accepts both the Lua data and a schema definition. When the serializer encounters {} at a specific key, it consults the schema for that key. If the field is defined as repeated or array, it serializes []; if the field is defined as an object or map, it serializes {}. This removes all ambiguity without requiring metatable modifications or custom Lua data types.

Strategy 5: Default Heuristics with Override Directives

When metadata cannot be embedded in every table, serializers frequently adopt a global default rule—usually treating all ambiguous empty tables as either empty maps or empty arrays by default.

To handle exceptions, the serializer supports out-of-band hints. For example, a configuration flag can specify:

  • Treat all empty tables as maps ({}) by default.
  • Check a secondary "hints" registry (a weak table mapping specific table references to type strings) to selectively override the default for designated arrays.
