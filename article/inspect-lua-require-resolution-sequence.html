Inspect Lua require Resolution Sequence

When managing dependencies in Lua, understanding how the require function locates files is essential for troubleshooting missing module errors and path conflicts. This guide outlines the core mechanisms behind Lua module resolution and details the most effective techniques to inspect the complete sequence of paths and loaders Lua evaluates when importing a module.

How Lua Resolves Modules

When require("module_name") is invoked, Lua evaluates loaders defined in the package.searchers table (named package.loaders in Lua 5.1). By default, Lua executes the following sequence:

  1. Preload Table: Checks if the module is already defined in package.preload.
  2. Lua Loader: Searches for standard .lua files using templates in package.path.
  3. C Loader: Searches for compiled shared libraries (.so, .dll) using templates in package.cpath.
  4. All-in-One Loader: Searches for C libraries containing combined submodules.

Method 1: Triggering an Intentional Error via pcall

The simplest and most complete way to view the exact search sequence evaluated by require is to deliberately fail a module load using pcall. When a module cannot be found, Lua raises an error containing every attempted path across all default searchers.

local module_name = "target_module"
local success, err = pcall(require, module_name)

if not success then
    print("Resolution sequence attempted by require:")
    print(err)
end

If the module does not exist, Lua outputs the formatted trace showing the exact paths checked:

module 'target_module' not found:
    no field package.preload['target_module']
    no file './target_module.lua'
    no file '/usr/local/share/lua/5.4/target_module.lua'
    no file '/usr/local/share/lua/5.4/target_module/init.lua'
    no file './target_module.so'
    no file '/usr/local/lib/lua/5.4/target_module.so'

Method 2: Inspecting Path Strings Directly

The search templates evaluated by the second and third searchers are stored directly in package.path and package.cpath. These strings contain semicolon-separated path templates where ? represents the module name (with dots converted to directory separators).

You can print and iterate over them directly:

print("--- Lua Search Path (package.path) ---")
for template in string.gmatch(package.path, "[^;]+") do
    print(template)
end

print("\n--- C Library Search Path (package.cpath) ---")
for template in string.gmatch(package.cpath, "[^;]+") do
    print(template)
end

Method 3: Using package.searchpath (Lua 5.2+)

In Lua 5.2 and later, package.searchpath exposes the underlying template-expansion algorithm used by require. It takes the module name and a template string, attempting to locate the file without loading it. If the file is not found, it returns nil followed by an error message listing every generated file path.

local modname = "my.module"

-- Check Lua paths
local file, err = package.searchpath(modname, package.path)
if file then
    print("Resolved to: " .. file)
else
    print("Failed to resolve in package.path. Paths checked:\n" .. err)
end

-- Check C paths
local cfile, cerr = package.searchpath(modname, package.cpath)
if not cfile then
    print("\nPaths checked in package.cpath:\n" .. cerr)
end

Method 4: Hooking package.searchers

For programmatic observation or logging during runtime, you can wrap each function in the package.searchers array. This reveals which searchers execute and what arguments they receive.

local searchers = package.searchers or package.loaders

for index, searcher in ipairs(searchers) do
    searchers[index] = function(modname)
        print(string.format("Searcher #%d testing: %s", index, modname))
        local result = searcher(modname)
        if type(result) == "function" then
            print(string.format("Searcher #%d matched %s", index, modname))
        end
        return result
    end
end
