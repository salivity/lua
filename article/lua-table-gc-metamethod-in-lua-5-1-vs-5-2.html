Lua Table __gc Metamethod in Lua 5.1 vs 5.2

This article explains the critical differences in how the Lua programming language handles the __gc (garbage collection) metamethod on standard tables between versions 5.1 and 5.2. While Lua 5.1 restricted finalizers strictly to userdata objects, Lua 5.2 introduced native support for table finalizers, altering resource management and cleanup patterns for developers.

The Behavior in Lua 5.1

In Lua 5.1, the __gc metamethod is completely ignored on standard Lua tables. The garbage collector only checks for and invokes the __gc metamethod on full userdata types created via the C API.

Because standard tables could not use __gc, developers had to rely on workarounds to run cleanup code when a table went out of scope. The standard workaround involved using the undocumented newproxy function:

-- Lua 5.1 workaround using newproxy
local function set_table_finalizer(tbl, finalizer)
    local proxy = newproxy(true)
    getmetatable(proxy).__gc = function()
        finalizer(tbl)
    end
    tbl.__proxy = proxy
    return tbl
end

In this pattern, the finalizer was bound to a proxy userdata stored inside the table, triggering the cleanup function only when the table (and its proxy) were collected.

The Behavior in Lua 5.2

Lua 5.2 added native support for the __gc metamethod on regular tables. You no longer need newproxy (which was deprecated and removed in 5.2) to detect table destruction. Instead, you can define __gc directly inside the table's metatable:

-- Lua 5.2 native implementation
local mt = {
    __gc = function(t)
        print("Cleaning up table: " .. tostring(t))
    end
}

local my_table = setmetatable({}, mt)
my_table = nil
collectgarbage() -- Output: Cleaning up table: table: 0x...

The Registration Caveat in Lua 5.2

Although Lua 5.2 enables __gc on tables, it introduced a specific registration rule: a table is only marked for finalization if its metatable contains the __gc field at the exact moment setmetatable is called.

If you attach a metatable first and define the __gc metamethod later, Lua 5.2 will not finalize the table:

-- This will NOT trigger the finalizer in Lua 5.2:
local mt = {}
local t = setmetatable({}, mt)

-- Defining __gc after attachment fails to mark the table
mt.__gc = function(self)
    print("Collected")
end

t = nil
collectgarbage() -- No output

To ensure a table is queued for finalization in Lua 5.2, __gc must be present in the metatable beforehand, or you must re-invoke setmetatable(t, mt) after defining the method.

Object Resurrection Rules

In Lua 5.2, if a finalizer stores a reference to the table being collected into a global variable or an active scope, the table is "resurrected" and will not be collected in that cycle. Unlike userdata in earlier implementations, once a table's __gc method runs in Lua 5.2, it will not run again during subsequent garbage collection cycles unless the metatable is explicitly re-bound to the object.
