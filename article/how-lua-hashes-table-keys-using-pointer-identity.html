How Lua Hashes Table Keys Using Pointer Identity

In the Lua programming language, tables are associative arrays capable of storing values using almost any data type as a key, with the exceptions of nil and NaN. When non-primitive reference types—specifically tables and functions—are used as table keys, Lua determines their hash values and equality based entirely on their internal memory addresses, also known as pointer identities. This article details how the Lua runtime utilizes pointer addresses to index tables and functions, the internal distinction between identity and structural equality, and the practical ramifications this has on data lookup and garbage collection.

Reference Types vs. Value Types in Lua

Lua distinguishes between primitive value types and reference types:

  • Value Types: Booleans, numbers, and strings. Strings are internalized (interned) in Lua, meaning only one copy of any given string exists in memory, allowing them to be compared and hashed predictably by their contents.
  • Reference Types: Tables, functions (closures), userdata, and threads (coroutines).

When a reference type is created, Lua allocates a corresponding C data structure on the heap—such as Table for tables or Closure for functions. Operations on these objects, including passing them as arguments or assigning them to variables, pass a pointer to the existing allocation rather than copying the object's contents.

The Mechanism of Pointer-Based Hashing

Internally, Lua's table implementation (ltable.c) stores key-value pairs in an array of nodes (a hybrid hash table and array structure). When a key is inserted or queried:

  1. Hash Calculation: Lua checks the type tag of the key. If the key is a table (LUA_TTABLE) or a function (LUA_TFUNCTION), the runtime does not inspect the contents of the table or the bytecode of the function. Instead, Lua passes the pointer address of the underlying C struct directly to a pointer-hashing macro (typically point2uint or l_hashpointer). This macro converts the memory address into an integer hash value that determines the target hash bucket.
  2. Key Collision and Resolution: If two different pointers resolve to the same hash bucket, Lua resolves the collision using a main-position chain (an open-addressing variation with coalesced chaining).
  3. Equality Checks: When traversing the chain to locate a matching key, Lua verifies key equality using strict raw equality (rawequal). For reference types, two keys match if and only if their memory pointers are identical.

Behavior of Tables as Keys

Because hashing and equality rely on pointer identity, two separate tables are never interchangeable as keys, regardless of whether their contents are identical:

local registry = {}

local keyA = { id = 1 }
local keyB = { id = 1 }

registry[keyA] = "Profile A"

print(registry[keyA]) -- Outputs: "Profile A"
print(registry[keyB]) -- Outputs: nil

Even though keyA and keyB share the same structural schema and values, they reside at different memory addresses. Consequently:

  • Their computed hash indices can differ.
  • Even if they land in the same bucket via hash collision, keyA == keyB evaluates to false at the pointer level.

Furthermore, defining an __eq metamethod on a table does not affect key lookup in standard Lua. Built-in table indexing bypasses metamethods for internal key matching to preserve execution speed and prevent cyclic metamethod calls.

Behavior of Functions as Keys

Functions in Lua are first-class closures. How a function behaves as a table key depends on where and how that function was instantiated:

Static Function References

If a function is defined in a global or module scope, its closure is instantiated once. Using that function as a key yields consistent lookups throughout its lifetime:

local lookup = {}

local function handler()
    -- logic
end

lookup[handler] = "Active"
print(lookup[handler]) -- Outputs: "Active"

Dynamically Generated Closures

If a function is declared inside a factory or a loop, a new closure instance is allocated on the heap whenever the declaration executes, especially if it captures upvalues:

local handlers = {}

local function createHandler()
    return function() end
end

local h1 = createHandler()
local h2 = createHandler()

handlers[h1] = "Handler 1"
print(handlers[h2]) -- Outputs: nil

Because h1 and h2 are distinct closure objects in memory, their pointer hashes differ, preventing cross-lookup.

Garbage Collection and Weak Tables

Using pointers as keys directly ties hash map operations to Lua's garbage collector (GC).

Under default table behavior, using a table or function as a key creates a strong reference to that object. Even if no other variable references the object, it cannot be garbage collected because the hosting table maintains an active reference to its pointer.

To prevent memory leaks when mapping metadata to pointer identities, Lua provides weak tables via the __mode metamethod:

local metadata = setmetatable({}, { __mode = "k" })

do
    local tempKey = {}
    metadata[tempKey] = "Temporary Data"
end

-- Force a garbage collection cycle
collectgarbage()

-- tempKey is collected, and its entry is automatically removed from metadata

In a table with weak keys (__mode = "k"), entries whose keys are only reachable via their table slot are cleared during garbage collection cycles, regardless of their pointer identity.
