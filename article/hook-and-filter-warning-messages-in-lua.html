Hook and Filter Warning Messages in Lua

This article demonstrates how to intercept, filter, and control warning messages in the Lua programming language. Lua 5.4 introduced a native warning system governed by the global warn function and the C API function lua_setwarnf. By intercepting warning calls in pure Lua or attaching a custom warning handler in C, you can detect control messages prefixed with @, filter unwanted output, and implement custom routing for your application's logging pipeline.

Understanding the Lua 5.4 Warning System

The standard Lua warn function accepts one or more string arguments and outputs them to standard error. Control messages in Lua begin with the @ symbol. By default, Lua recognizes two standard control messages:

  • @off: Disables the emission of future warnings.
  • @on: Enables the emission of future warnings.

Any other message beginning with @ is treated as an unrecognized control message and is silently ignored by the default handler. This design allows developers to define custom control messages (such as @filter:category or @level:error) and handle them via custom warning hooks.

Method 1: Intercepting Warnings in Pure Lua

If you are running in a pure Lua environment without access to C host code, you can intercept and filter warnings by monkey-patching the global warn function.

local original_warn = warn
local filter_rules = {
    suppress_deprecated = false
}

function warn(...)
    local args = {...}
    if #args == 0 then return end

    local first_arg = tostring(args[1])

    -- Check for control messages starting with '@'
    if first_arg:sub(1, 1) == "@" then
        if first_arg == "@suppress_deprecated:on" then
            filter_rules.suppress_deprecated = true
            return
        elseif first_arg == "@suppress_deprecated:off" then
            filter_rules.suppress_deprecated = false
            return
        end
        -- Pass standard control messages through to the original handler
        original_warn(...)
        return
    end

    -- Filter logic based on active rules
    local full_message = table.concat(args, "")
    if filter_rules.suppress_deprecated and full_message:find("deprecated") then
        return -- Drop the warning
    end

    -- Forward allowed warnings to the original function
    original_warn(...)
end

-- Usage:
warn("@on") -- Native control
warn("This is a standard warning.")

warn("@suppress_deprecated:on") -- Custom control message
warn("This is a deprecated feature warning.") -- Filtered out

warn("@suppress_deprecated:off")
warn("This deprecated warning will now show.")

Method 2: Hooking Warnings via the C API

The robust and native approach to warning management is implemented at the host level using lua_setwarnf. This function attaches a callback of type lua_WarnFunction that receives warning messages and control commands directly from the Lua state.

Callback Signature

typedef void (*lua_WarnFunction) (void *ud, const char *msg, int tocont);
  • ud: A pointer to user data passed to lua_setwarnf.
  • msg: The current warning string fragment.
  • tocont: A boolean flag (1 or 0) indicating whether this message continues into the next call.

Implementing the Custom C Handler

A complete warning hook must manage message fragmentation (indicated by tocont) and check for control directives.

#include <lua.h>
#include <lauxlib.h>
#include <stdio.h>
#include <string.h>

typedef struct {
    int enabled;
    int filter_custom;
} WarningState;

void custom_warning_handler(void *ud, const char *msg, int tocont) {
    WarningState *state = (WarningState *)ud;

    // Handle control messages
    if (msg[0] == '@') {
        if (strcmp(msg, "@on") == 0) {
            state->enabled = 1;
        } else if (strcmp(msg, "@off") == 0) {
            state->enabled = 0;
        } else if (strcmp(msg, "@filter_custom:enable") == 0) {
            state->filter_custom = 1;
        } else if (strcmp(msg, "@filter_custom:disable") == 0) {
            state->filter_custom = 0;
        }
        return;
    }

    // Skip output if warnings are disabled globally
    if (!state->enabled) {
        return;
    }

    // Apply custom filtering
    if (state->filter_custom && strstr(msg, "[DROP]") != NULL) {
        return;
    }

    // Output the warning message
    fprintf(stderr, "Lua Warning: %s", msg);
    if (!tocont) {
        fprintf(stderr, "\n");
    }
}

int main(void) {
    lua_State *L = luaL_newstate();
    luaL_openlibs(L);

    WarningState state = {1, 0}; // Warnings enabled, filtering disabled

    // Register the custom warning hook
    lua_setwarnf(L, custom_warning_handler, &state);

    // Send control message and warnings
    luaL_dostring(L, "warn('@filter_custom:enable')");
    luaL_dostring(L, "warn('[DROP] This message will be ignored.')");
    luaL_dostring(L, "warn('This message will be displayed.')");

    lua_close(L);
    return 0;
}

Best Practices for Custom Control Messages

  1. Prefixing: Use a structured namespace for custom control commands (such as @app_name:command) to prevent collisions with potential future keywords in the Lua core.
  2. Handling Fragmentation: In the C API, messages sent via warn("part1", "part2") result in multiple consecutive calls where tocont is true until the final fragment. Maintain an internal string buffer in your user data structure if your custom filter requires parsing the entire message string.
  3. Fallback to Standard Behaviors: Always retain support for @on and @off so that standard library behaviors and third-party modules behave predictably.
