Can Lua _G Table Hold a Reference to Itself?

In the Lua programming language, the global environment table, known as _G, not only can hold a reference to itself, but it actually does so by default during runtime. This article examines how the _G table operates, demonstrates how self-referencing works in Lua's runtime environment, explains the underlying memory management handling circular references, and details the impact of modifying this reference.

The Default Self-Reference in Lua

When the Lua runtime initializes, it sets up the global environment inside a standard table assigned to the global variable _G. Within this table, Lua creates a key named "_G" that maps directly back to the table itself.

You can verify this self-reference with a simple check:

print(_G == _G._G) -- Outputs: true
print(_G == _G._G._G._G) -- Outputs: true

Because tables in Lua are reference types rather than value types, assigning _G._G = _G does not duplicate the environment in memory. It simply creates an internal pointer where the key "_G" points to the same underlying table structure.

How Circular References Work in Lua Tables

The ability of _G to reference itself is not a special case reserved solely for the global scope; it is a fundamental property of Lua tables. Any table in Lua can hold references to itself or form circular reference chains with other tables:

local myTable = {}
myTable.self = myTable

print(myTable == myTable.self) -- Outputs: true

Lua’s runtime seamlessly handles cyclic data structures. The runtime uses a mark-and-sweep garbage collector, which traverses accessible object graphs rather than using simple reference counting. As a result, circular references—including _G pointing to itself—do not cause memory leaks when an isolated cycle becomes unreachable. Because _G is anchored to the global state, it remains active for the duration of the program unless explicitly detached.

Modifying or Removing _G._G

Because _G is an ordinary Lua table, the self-reference is mutable. A script can reassign or remove it at runtime:

_G._G = nil
print(_G) -- Outputs: nil (when evaluated in global context)

Unsetting _G._G removes the variable name _G from the global namespace, but it does not immediately destroy the global environment. Functions and C code that already hold a reference to the global environment table can still access it. However, any code relying explicitly on the _G identifier to access global variables will fail with a nil lookup error.

Environments in Modern Lua (_ENV)

Starting with Lua 5.2, variable scoping introduced lexical environments using _ENV. In these versions, global access is syntactic sugar for indexing the current _ENV table (variable compiles to _ENV.variable).

In the root scope of a chunk:

  • _ENV is set to the global environment table.
  • _ENV._G still points back to that same global table by default.

Consequently, _ENV._G == _ENV evaluates to true, preserving the traditional self-referencing behavior while allowing sandbox implementations to isolate or redefine environments as needed.
