Lua String Comparison: ASCII vs Localized Collation

In the Lua programming language, string comparison behaves fundamentally differently depending on whether you rely on native byte-by-byte ordering or localized collation. By default, Lua compares strings using raw ASCII and byte values via standard relational operators, ensuring blazing-fast, deterministic results across all platforms. Conversely, localized collation accounts for cultural rules, character accents, and linguistic case-folding, which are necessary for human-facing sorting but require specialized handling or external libraries. This article explains the technical mechanics, behavioral differences, and practical trade-offs between both comparison strategies in Lua.

Default String Comparison: ASCII Byte Ordering

Lua's native relational operators (<, <=, >, >=, ==, ~=) compare strings lexicographically by their underlying byte values. Internally, standard Lua uses the C function memcmp to evaluate strings byte by byte until a difference is found or the end of a string is reached.

Key Characteristics of Lua's Native Comparison

  • Case Precedence: In ASCII, uppercase letters have lower numerical values (65–90) than lowercase letters (97–122). Consequently, uppercase strings always evaluate as smaller than lowercase ones.

    print("Zebra" < "apple") -- Evaluates to true (ASCII 90 < 97)

  • UTF-8 Naivety: Lua treats strings as arbitrary sequences of 8-bit bytes. While Lua 5.3 introduced a utf8 library for length and pattern handling, relational operators do not decode UTF-8 code points. A multi-byte accented character (such as é, encoded as bytes 0xC3 0xA9) is evaluated purely by its byte values, placing it after standard ASCII characters like z (0x7A).

    print("z" < "é") -- Evaluates to true (0x7A < 0xC3)

  • Performance: Byte comparison operates directly in memory with minimal overhead. It executes in \(O(n)\) time relative to string length and requires no external lookups or system state.

  • Portability: Because the byte values of strings do not change between operating systems, a sort order generated with default Lua operators is completely reproducible across platforms.

Localized Collation in Lua

Localized collation sorts characters based on the linguistic conventions of a specific human language. In natural languages:

  • Uppercase and lowercase equivalents are grouped together (e.g., a, A, b, B).
  • Accents and diacritics are sorted alongside their base characters (e.g., é is sorted alongside e, rather than at the end of the alphabet).
  • Multi-character sequences may be treated as single entities depending on the locale (e.g., historically ch in Spanish, or cs in Hungarian).

Because standard Lua operators never use the system locale for string comparisons, localized sorting cannot be performed using native < or > operators directly. Instead, localized collation must be implemented via C extensions, the LuaJIT FFI (Foreign Function Interface), or third-party ICU (International Components for Unicode) bindings.

Implementing Localized Collation via C strcoll

The standard C library provides strcoll, which compares two strings using the current system locale defined by setlocale. Using LuaJIT's FFI or a C module, strcoll can be invoked inside table.sort:

local ffi = require("ffi")
ffi.cdef[[
    int strcoll(const char *s1, const char *s2);
    char *setlocale(int category, const char *locale);
]]

-- Set locale to system default or specific language
ffi.C.setlocale(0, "") -- LC_ALL = 0

local function locale_sort(a, b)
    return ffi.C.strcoll(a, b) < 0
end

local words = {"zebra", "Apple", "äpfel", "banana"}
table.sort(words, locale_sort)

Summary of Differences

Feature ASCII Byte Ordering (Native) Localized Collation (strcoll / ICU)
Sorting Rule Raw byte values (0–255) Cultural/linguistic rules
Case Behavior Uppercase precedes lowercase ("Z" < "a") Letters grouped naturally ("a" < "B")
Diacritics Accented characters pushed to end Accents grouped near base glyphs
Performance Extremely fast, hardware-native Slower due to locale tables and rule checks
Determinism 100% consistent across machines Varies depending on OS and installed locales
Implementation Built into <, >, <=, >= Requires FFI, C libraries, or ICU bindings

When to Use Each Approach

  • Use ASCII Byte Ordering for internal data structures, hash table keys, database identifiers, protocol parsing, and programmatic configuration keys. In these contexts, deterministic behavior and maximum execution speed are essential.
  • Use Localized Collation whenever sorting data that will be presented directly to end users in a user interface, such as lists of names, file browsers, or localized search results.
