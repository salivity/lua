Why Cache Global Functions as Locals in Lua

Caching global functions into local variables is a standard performance optimization technique in Lua that significantly reduces runtime overhead. Because Lua stores global variables in a regular hash table, accessing a global function requires repeated, relatively expensive table lookups. Storing these functions in local variables allows Lua’s virtual machine to access them directly from fast, internal registers using index-based bytecode instructions, dramatically speeding up execution in performance-critical sections such as loops.

How Lua Accesses Globals

In Lua, the global environment is not a separate low-level memory space; it is simply a standard Lua table, historically referred to as _G and handled via the _ENV upvalue in modern Lua versions (5.2+).

When code calls a global function like math.floor(x), the Lua virtual machine (VM) must perform a dynamic hash-table lookup at runtime to resolve the key "math", and then perform a second lookup inside that table for the key "floor". Even single-level global calls like print() require a hash lookup into _ENV every time the statement executes.

Hash table lookups involve hashing the string key, finding the corresponding bucket, and resolving potential hash collisions. While Lua's hash table implementation is highly optimized, the CPU cost is non-zero.

How Lua Accesses Locals

Local variables in Lua are resolved at compile time rather than runtime. When a script is compiled into bytecode, local variables are assigned specific virtual machine register indices or stack slots.

Accessing a local variable requires no table lookup or string hashing. Instead, the VM simply reads from an indexed array slot using direct, single-cycle register operations.

Bytecode Comparison

The performance difference is evident when inspecting Lua bytecode:

Using a global function:

local y = math.sin(x)

The VM produces instructions similar to:

  1. GETTABUP (Lookup "math" in _ENV)
  2. GETTABLE (Lookup "sin" in math)
  3. CALL

Using a cached local function:

local sin = math.sin
-- later in execution:
local y = sin(x)

The VM produces:

  1. GETLOCAL (Read from the local register slot)
  2. CALL

The localized version completely bypasses two dynamic hash lookups at runtime.

Cumulative Impact in Loops

In isolated, infrequently called code paths, the performance overhead of a global lookup is negligible. However, in tight loops or functions invoked thousands of times per second (such as game loops, rendering routines, or data processing pipelines), repeated table lookups compound quickly.

Caching frequently used library functions (like string.sub, table.insert, or math.sqrt) at the top of a file or module can yield measurable execution time reductions, often between 10% to 30% in standard PUC-Rio Lua.

Consideration for LuaJIT

In LuaJIT, the Just-In-Time compiler can optimize global table accesses by hoisting invariant lookups out of traces. However, caching globals locally remains a recommended practice even in LuaJIT. It guarantees that accesses outside compiled traces remain fast, aids the trace compiler in generating cleaner machine code, and ensures code remains maximally performant across both standard Lua interpreters and JIT-enabled runtimes.
