Compiling Lua for Embedded POSIX vs Non-POSIX

This article outlines the configuration, build system, and source-level modifications required to compile the Lua programming language for embedded environments, contrasting POSIX-compliant systems with non-POSIX targets such as bare-metal microcontrollers and real-time operating systems (RTOS). It covers necessary adjustments in luaconf.h, Makefile modifications, handling standard library dependencies, and tailoring memory management to constrained hardware.

Build System and Target Definitions

Lua is written in clean, standard ANSI C (C89/C99), allowing it to compile on virtually any platform. However, the build system differentiates between targets that provide POSIX interfaces and those that do not.

POSIX Targets

For embedded Linux, QNX, or other embedded POSIX environments, the build system utilizes POSIX-specific APIs for dynamic module loading, high-resolution timers, and terminal handling.

  • Makefile Target: Typically built using make posix or platform-specific targets like make linux.
  • Compiler Flags: Compiles with -DLUA_USE_POSIX. If dynamic loading is required, it includes -DLUA_USE_DLOPEN.
  • Linker Flags: Requires linking against system libraries, typically -ldl for dynamic library loading and optionally -lreadline (often stripped for embedded systems to reduce binary size).

Non-POSIX Targets

Bare-metal microcontrollers (e.g., ARM Cortex-M, RISC-V) and RTOS platforms (e.g., FreeRTOS, Zephyr) lack POSIX system calls and standard dynamic linkers.

  • Makefile Target: Built using make generic or by directly invoking the cross-compiler toolchain (e.g., arm-none-eabi-gcc) on the core source files.
  • Compiler Flags: Omit -DLUA_USE_POSIX and -DLUA_USE_DLOPEN. Define -DLUA_USE_C89 to ensure strict standard C compliance without assuming external POSIX abstractions.
  • Linker Flags: Remove -ldl, -lm (if soft-float or custom math is integrated elsewhere), and any terminal libraries.

Modifying luaconf.h

The src/luaconf.h file contains Lua's platform configuration options. Adjusting this header is the primary method for adapting the engine to different target architectures.

POSIX Configurations

On an embedded POSIX system, luaconf.h enables features that rely on the underlying OS:

  • Dynamic Loading: LUA_USE_DLOPEN is enabled, allowing package.loadlib and the loading of shared objects (.so).
  • Path Separation: Directory separators are set to /, with system paths such as /usr/local/share/lua/ configured for package.path.
  • Pipes and System Commands: lua_popen and lua_pclose are mapped directly to the POSIX popen and pclose.

Non-POSIX Configurations

For non-POSIX and bare-metal environments, OS dependencies must be disabled or redirected:

  • Disable Dynamic Loading: Ensure LUA_USE_DLOPEN is undefined. Lua will rely strictly on statically linked C modules registered via luaL_requiref.
  • Path Management: Disable default file system search paths in LUA_PATH_DEFAULT and LUA_CPATH_DEFAULT if no underlying file system exists.
  • Remove Shell Access: Undefine or stub lua_popen and lua_pclose, as shells and process forks do not exist.
  • Numeric Representation: For microcontrollers without a Hardware Floating Point Unit (FPU), configure Lua to use 32-bit integers or single-precision floats:
    • Define LUA_32BITS to reduce memory consumption and map lua_Integer to 32 bits.
    • Define LUA_FLOAT_TYPE as LUA_FLOAT_FLOAT instead of the default LUA_FLOAT_DOUBLE.

Handling the Standard Libraries and linit.c

The default Lua distribution opens several standard libraries during initialization via luaL_openlibs.

/* Standard library array in linit.c */
static const luaL_Reg loadedlibs[] = {
    {LUA_GNAME, luaopen_base},
    {LUA_LOADLIBNAME, luaopen_package},
    {LUA_COLIBNAME, luaopen_coroutine},
    {LUA_TABLIBNAME, luaopen_table},
    {LUA_IOLIBNAME, luaopen_io},
    {LUA_OSLIBNAME, luaopen_os},
    {LUA_STRLIBNAME, luaopen_string},
    {LUA_MATHLIBNAME, luaopen_math},
    {LUA_UTF8LIBNAME, luaopen_utf8},
    {LUA_DBLIBNAME, luaopen_debug},
    {NULL, NULL}
};

POSIX Strategy

In POSIX environments, all standard libraries can generally remain enabled. luaopen_io handles standard streams and file access through regular POSIX file descriptors, and luaopen_os maps cleanly to standard system calls (time, system, getenv, rename, remove).

Non-POSIX Strategy

In bare-metal or RTOS environments, standard C runtime implementations of file and system operations may crash, hang, or result in unresolved linker errors.

  • Modify linit.c: Remove {LUA_IOLIBNAME, luaopen_io} and {LUA_OSLIBNAME, luaopen_os} to eliminate references to unavailable system calls.
  • Selective Implementation in loslib.c: If basic timing is required, retain luaopen_os but manually edit src/loslib.c to stub out os.execute, os.remove, os.rename, and os.tmpname, while preserving os.clock and os.difftime mapped to an RTOS tick counter.
  • Package Library: If files cannot be loaded from disk, remove luaopen_package or replace the package searchers with a custom in-memory table lookup.

Memory Allocation Configuration

POSIX Targets

POSIX systems utilize standard virtual memory management. Initializing Lua using luaL_newstate() safely routes allocation requests to the standard C library's malloc, realloc, and free.

Non-POSIX Targets

Bare-metal devices often feature limited static RAM (SRAM) and lack robust heap implementations.

  • Avoid luaL_newstate(): Do not call luaL_newstate(), as it defaults directly to standard malloc.
  • Use lua_newstate(): Provide a custom allocator function lua_Alloc that restricts Lua to a statically allocated buffer or an RTOS-managed memory pool (e.g., pvPortMalloc in FreeRTOS):
void *custom_allocator(void *ud, void *ptr, size_t osize, size_t nsize) {
    (void)ud; (void)osize; /* Unused parameters */
    if (nsize == 0) {
        embedded_free(ptr);
        return NULL;
    } else {
        return embedded_realloc(ptr, nsize);
    }
}

/* Initialization */
lua_State *L = lua_newstate(custom_allocator, NULL);

Using this approach prevents memory fragmentation across the global system heap and guarantees that Lua operates strictly within its designated physical memory footprint.
