Using Lua in Tarantool for Application Logic

This article explores how the Tarantool in-memory database natively embeds the Lua programming language to execute application logic and stored procedures. By integrating a Just-In-Time (JIT) Lua compiler directly into its core runtime, Tarantool eliminates traditional database network latency, allowing developers to execute complex data manipulation, background routines, and complete microservice logic in the same memory space as the data itself.

The Embedded Lua Architecture

Unlike traditional databases that expose external drivers or rely on slow, isolated procedural languages, Tarantool includes an embedded LuaJIT runtime directly inside its single-threaded, cooperative-multitasking core. This tight coupling turns Tarantool into a hybrid database and application server.

Because LuaJIT executes within the same process space as the database engine, data access bypasses TCP/IP sockets, serialization, and inter-process communication overhead. Operations that would otherwise require multiple round-trip network calls in a conventional architecture execute locally at native memory speeds.

Writing Stored Procedures in Lua

In Tarantool, stored procedures are standard Lua functions declared in the global namespace or encapsulated within modules. These procedures interact directly with stored data via the built-in box package.

A typical stored procedure accesses spaces (Tarantool's equivalent of tables), searches indexes, and modifies tuples directly:

local function transfer_funds(from_id, to_id, amount)
    box.atomic(function()
        local sender = box.space.accounts:get(from_id)
        local receiver = box.space.accounts:get(to_id)

        if not sender or sender.balance < amount then
            error("Insufficient funds or invalid sender")
        end

        box.space.accounts:update(from_id, {{'-', 2, amount}})
        box.space.accounts:update(to_id, {{'+', 2, amount}})
    end)
    return true
end

rawset(_G, 'transfer_funds', transfer_funds)

Clients connect to Tarantool and call transfer_funds via remote procedure calls (RPC). Using box.atomic, the entire Lua function runs inside a single transaction, guaranteeing ACID compliance while maintaining microsecond-level execution times.

Developing Full Application Logic

Tarantool's use of Lua extends beyond isolated queries to encompass complete application backends:

  • Microservices and HTTP APIs: Using ecosystem modules like http.server, developers can expose REST or JSON APIs directly from Tarantool, handling HTTP requests, business validation, and persistence in one place.
  • Fiber-Based Concurrency: Tarantool employs a cooperative multitasking model based on "fibers." Lua scripts can spawn background fibers for tasks such as data polling, periodic batch processing, or cache invalidation without blocking the primary event loop.
  • Queue and Job Management: Built-in Lua modules allow Tarantool to act as an in-memory priority queue engine (such as the queue module), managing task distribution across worker pools.
  • Replication and Sharding Automation: Tarantool modules like vshard leverage Lua to manage cluster topologies, horizontal partitioning, and automatic data rebalancing across multiple nodes.

Performance and Safety Considerations

While LuaJIT provides near-native C execution speeds, cooperative multitasking requires developers to avoid long-running, blocking CPU tasks in a single function. In Tarantool's execution model, a CPU-intensive Lua script that does not yield or invoke an I/O operation can stall other concurrent operations. To maintain high throughput, long iterations must explicitly yield execution back to the event loop using Tarantool's fiber.yield() function.
