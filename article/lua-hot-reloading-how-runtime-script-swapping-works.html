Lua Hot Reloading: How Runtime Script Swapping Works

Hot-reloading in Lua allows developers to swap modified script files at runtime without restarting the host application, preserving active application state while replacing execution logic. This article breaks down the mechanics of the hot-reloading pattern in Lua, detailing how Lua caches modules, how to safely recompile modified files, and how to transfer existing state and references to updated functions.

The Role of package.loaded

In standard Lua, the require function manages module loading. When a file is required for the first time, Lua executes the file, returns the module (usually a table of functions), and caches it inside the global table package.loaded[modname]. Subsequent calls to require(modname) return this cached table rather than reading the file from disk again.

To swap a script, the host system must bypass or invalidate this cache:

-- Invalidate the cached module
package.loaded["my_module"] = nil

-- Force Lua to re-read and execute the file from disk
local my_module = require("my_module")

While setting package.loaded[modname] = nil reloads the file, it creates a new table in memory. Any other system holding an existing reference to the old module table will continue using the old code.

In-Place Table Patching

To ensure external references to the module remain valid, robust hot-reloading patterns patch the existing table rather than replacing it entirely.

  1. Read and Compile Safely: Use loadfile() or load() instead of require(). This compiles the file into a function chunk without executing it immediately, allowing syntax errors to be caught without crashing the application.
  2. Execute in Isolation: Run the newly compiled chunk to generate the updated module table.
  3. Copy Members: Iterate over the new module and copy its fields into the old module table.
local function reload_module(modname, filepath)
    local chunk, err = loadfile(filepath)
    if not chunk then
        print("Syntax error while reloading:", err)
        return false
    end

    local success, new_module = pcall(chunk)
    if not success then
        print("Runtime error during module execution:", new_module)
        return false
    end

    local old_module = package.loaded[modname]
    if type(old_module) == "table" and type(new_module) == "table" then
        -- Update functions and new fields in the existing table
        for k, v in pairs(new_module) do
            old_module[k] = v
        end
    else
        package.loaded[modname] = new_module
    end

    return true
end

By mutating old_module in place, any external script referencing that table instantly accesses the updated function definitions.

State Preservation and Closures

Functions in Lua frequently capture local variables outside their scope, known as upvalues. If a module stores internal state inside local variables rather than inside the returned module table, reloading the file will reinitialize that state to default values.

To solve this, reloaders employ two primary strategies:

1. Separation of State and Logic

The cleanest architecture isolates state into dedicated data containers or passes state explicitly into module functions. If state is stored globally or inside an external registry table that is not reloaded, the logic can be swapped freely without resetting data.

2. Upvalue Migration via the Debug Library

Advanced reloaders use Lua's debug library (debug.getupvalue, debug.setupvalue, and debug.upvaluejoin) to migrate state from old closures to new closures.

local function migrate_upvalues(old_func, new_func)
    local i = 1
    while true do
        local name, val = debug.getupvalue(old_func, i)
        if not name then break end
        
        -- Find matching upvalue in the new function and apply the old value
        local j = 1
        while true do
            local new_name = debug.getupvalue(new_func, j)
            if not new_name then break end
            if name == new_name then
                debug.setupvalue(new_func, j, val)
                break
            end
            j = j + 1
        end
        i = i + 1
    end
end

Change Detection and Execution Loop

The trigger mechanism for hot-reloading operates outside of Lua's core execution:

  • Filesystem Monitoring: The host environment (often written in C, C++, or Go) uses OS-level file system notifications (such as inotify on Linux, kqueue on macOS, or ReadDirectoryChangesW on Windows) or periodically polls file modification timestamps (mtime).
  • Safe Injection Point: Swapping code mid-frame can lead to inconsistent state. File modifications are queued and processed at a deterministic phase in the main loop, such as the beginning of a tick or frame, ensuring no functions from the target module are currently active on the call stack when the reload occurs.
  • Lifecycle Hooks: Well-architected reloaders check for lifecycle callbacks (such as module:on_reload()) to allow newly loaded scripts to migrate schemas, rebind event listeners, or rebuild derived state immediately after the swap completes.
