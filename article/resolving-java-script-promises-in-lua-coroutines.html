Resolving JavaScript Promises in Lua Coroutines

Interfacing modern JavaScript with the Lua programming language requires bridging two distinct asynchronous models: JavaScript’s event-loop-driven Promises and Lua’s cooperative coroutines. Because Lua lacks a built-in event loop, resolving a JavaScript Promise within Lua is achieved by yielding the current Lua coroutine when an asynchronous operation begins, attaching resolution handlers to the Promise in JavaScript, and resuming the paused coroutine with the resolved data once the event loop fulfills the Promise.

The Architectural Mismatch

JavaScript handles asynchronous operations natively through an event loop and the microtask queue, returning Promise objects that resolve or reject asynchronously. In contrast, Lua relies on coroutines (threads) for non-preemptive concurrency. A Lua coroutine executes synchronously until it explicitly calls coroutine.yield(), transferring execution back to the caller until manually re-awakened via coroutine.resume().

When running Lua embedded inside a JavaScript runtime—such as via WebAssembly runtimes (e.g., Wasmoon) or JavaScript-based interpreters (e.g., Fengari)—Lua cannot natively block execution to wait for a JavaScript Promise without freezing the entire JavaScript thread.

The Yield-and-Resume Bridge

To make JavaScript Promises behave like synchronous calls inside Lua, bridge libraries implement an await-style wrapper using the yield-and-resume pattern:

  1. Detection and Yielding: When Lua invokes an asynchronous JavaScript function, the bridge receives a JavaScript Promise. Instead of returning the unsettled Promise directly to Lua, a bridge function captures the running Lua thread using coroutine.running() and immediately yields execution using coroutine.yield(). This suspends the Lua execution context.
  2. Attaching Callbacks: On the JavaScript side, handlers are registered to the Promise using .then() and .catch(). Because Lua has yielded control back to JavaScript, the main JavaScript thread remains unblocked and can continue processing its event loop and microtask queues.
  3. Resuming on Resolution: Once the asynchronous operation completes, the Promise settles:
    • If the Promise resolves, the .then() handler invokes coroutine.resume(thread, resolvedValue). This re-enters the Lua state exactly where it yielded, passing the JavaScript result back as the return value of the yield call.
    • If the Promise rejects, the .catch() handler captures the error. It either resumes the coroutine with an error flag or triggers an error in Lua using coroutine.resume(thread, nil, error) or the bridge's internal error mechanism, allowing the failure to be caught via Lua's pcall or xpcall.

Conceptual Implementation Flow

In a typical implementation, an await utility function in Lua or the foreign function interface (FFI) operates like this:

-- Conceptual Lua await implementation
function await(promise)
    local current_thread = coroutine.running()
    assert(current_thread, "await must be called inside a coroutine")

    promise:next(
        function(result)
            -- JavaScript fulfilled the Promise
            local success, err = coroutine.resume(current_thread, result)
            if not success then
                error(err)
            end
        end,
        function(err)
            -- JavaScript rejected the Promise
            coroutine.resume(current_thread, nil, err)
        end
    )

    -- Suspend Lua until one of the callbacks executes
    local result, err = coroutine.yield()
    if err then
        error(err)
    end
    return result
end

Context and State Management

For this pattern to work robustly, bridge runtimes must manage thread lifecycles and garbage collection:

  • Reference Preservation: The Lua thread object must be protected from garbage collection while yielded. If Lua’s garbage collector sweeps the suspended coroutine before the JavaScript Promise resolves, the subsequent coroutine.resume() attempt will fail. Bridge interfaces typically store a reference to the yielding thread in the Lua registry until the Promise settles.
  • Data Marshalling: Resolved values must cross the language boundary. Primitives (numbers, strings, booleans) convert directly, while complex JavaScript objects and arrays are usually wrapped in Lua userdata or proxy tables with appropriate metatables to allow field access from Lua.
  • Top-Level Execution: Because yielding is only permitted inside an active coroutine, top-level Lua scripts that interact with asynchronous JavaScript APIs must either be automatically wrapped in an outer coroutine by the environment or restrict Promise resolution to designated asynchronous task runners.
