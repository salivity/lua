Lua String Interning: Short vs Long Strings

In the Lua programming language, string handling differs significantly depending on string size, a design choice formalized in Lua 5.2 and refined in subsequent releases. Short strings are globally interned into a central hash table to ensure instant pointer-based equality checks and rapid table lookups, whereas long strings bypass global interning to avoid severe performance penalties, memory churn, and denial-of-service vulnerabilities. This article explores the architectural reasons behind this bifurcation, examining how short strings optimize Lua’s core runtime while long strings maintain performance when processing large data payloads.

The Role and Mechanism of Short Strings

By default, any string shorter than a compile-time threshold—typically 40 bytes (LUAI_MAXSHORTSTR)—is classified as a short string. When a short string is created, Lua checks a global hash table stored inside the global state (global_State). If the string already exists, the runtime returns a pointer to the existing string object; otherwise, a new string is allocated and inserted into the table.

This approach provides two primary benefits:

  1. Instant Comparisons: Because duplicate short strings share identical memory addresses, equality checks (a == b) operate in \(O(1)\) time via simple pointer comparison, avoiding byte-by-byte traversal.
  2. Optimized Table Access: Lua relies heavily on tables for records, modules, and object-oriented programming. Identifiers and method names are typically short strings. Interning ensures that table lookups use precomputed hash values and pointer equality, keeping property accesses consistently fast.

The Problem with Interning Long Strings

Prior to Lua 5.2, all strings were interned regardless of length. While this guaranteed universal pointer equality, it introduced substantial bottlenecks when handling large blocks of text, such as file contents, network buffers, or serialized JSON payloads:

  • Expensive Hash Calculation: Interning requires computing the hash of every incoming string upfront. Computing hashes for large data buffers requires reading through megabytes of memory, severely bottlenecking operations like concatenation and file I/O.
  • Hash Collisions and Table Overhead: Constantly inserting and removing large, transient strings causes churn in Lua's internal string table. Reallocating and rehashing the global string table degrades performance across the entire runtime.
  • Denial of Service (Hash-DoS): Global interning of arbitrary-length strings created a vulnerability where an attacker could provide tailored payloads that trigger hash collisions, forcing the internal hash table into worst-case lookup times.

How Modern Lua Handles Long Strings

In recent Lua versions, strings exceeding the threshold are created as independent heap-allocated objects rather than tracked within the global string cache.

Long strings use the following design patterns:

  • Lazy Hashing: A long string does not compute its hash value upon creation. Instead, hashing is deferred until the string is explicitly used as a key in a table. If a long string is merely created, manipulated, and discarded, no hash computation ever takes place.
  • Direct Equality Checks: Comparing two long strings first compares their lengths and pointers. If both pointers differ, Lua performs a standard byte-wise memory comparison (memcmp). While byte comparison takes \(O(N)\) time in the worst case, long strings are rarely compared for equality repeatedly in typical scripting workloads.
  • Independent Lifecycles: Long strings are collected independently by Lua’s garbage collector without the overhead of unlinking them from the global string registry, reducing garbage collection sweep times.

Summary

The separation between short and long strings balances execution speed and scalability. Lua interns short strings globally because their primary usage lies in table keys, identifiers, and frequent comparisons, where deduplication and \(O(1)\) checks yield massive performance gains. Conversely, long strings bypass global interning to eliminate unnecessary hashing costs, protect against hash collisions, and ensure efficient handling of large-scale data.
