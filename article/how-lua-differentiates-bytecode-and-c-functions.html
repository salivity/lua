How Lua Differentiates Bytecode and C Functions

This article explores how the Lua Virtual Machine (VM) distinguishes between running its own compiled bytecode and calling native host C functions. By examining Lua's internal tagged union structures, the call stack management mechanism, and the function dispatch pipeline, this guide clarifies how the runtime seamlessly switches between the bytecode interpreter loop and direct native execution.

The Unified Function Abstraction

In Lua, every callable entity exposed to the runtime is treated uniformly as a function object represented by the basic type tag LUA_TFUNCTION. Internally, however, the Lua engine differentiates functions by splitting them into distinct subtypes within a tagged union:

  • Lua Closures (LClosure): Contain a pointer to a Proto (prototype) structure that holds the compiled bytecode instructions, constants, debug information, and a list of upvalues.
  • C Closures (CClosure): Contain a direct native C function pointer (lua_CFunction) along with an array of Lua values serving as upvalues bound to the C environment.
  • Light C Functions: Lightweight function representations stored directly inside Lua's general value container (TValue) as raw function pointers without upvalue allocation overhead.

When a function is pushed onto the stack, the VM assigns it a specific subtype tag—such as LUA_VLCL for Lua closures, LUA_VCCL for C closures, and LUA_VLCF for light C functions.

Call Dispatch and Stack Frames

The differentiation occurs during the call preparation phase, primarily handled by the internal core function luaD_precall. When the interpreter encounters a call instruction (such as the OP_CALL bytecode or an explicit invocation via the C API like lua_pcall), it executes the following steps:

  1. Tag Checking: The VM inspects the target object's type tag at the base of the call frame. If the object is not a function, Lua checks for a __call metamethod. If it is a function, the VM reads the subtype tag to decide the execution branch.
  2. CallInfo Allocation: The VM pushes a new CallInfo struct onto its execution call stack. This structure tracks the state of the active call, including the base register index, expected number of return values, and status flags.

Executing C Callbacks

If luaD_precall identifies a CClosure or a light C function, the VM bypasses the bytecode interpreter entirely:

  • The runtime sets the call frame status flag to mark it as a C call.

  • The VM invokes the stored lua_CFunction pointer directly via standard machine-code calling conventions, passing the current execution thread (lua_State* L) as the single argument:

    int n = (*f)(L);

  • The C callback performs its tasks using the Lua C API, manipulating the virtual stack relative to its own stack window.

  • Once the C function returns an integer indicating the number of results placed on the stack, luaD_poscall executes immediately to adjust the stack, copy the return values to the caller's frame, and pop the CallInfo record.

Executing Native Bytecode

If the target object is an LClosure, the VM remains within the interpreter context:

  • The runtime initializes the execution frame using the metadata stored in the closure's Proto block.
  • It sets the VM’s program counter (pc) to the first bytecode instruction of the prototype.
  • It verifies stack space, ensures that all expected parameters are mapped into registers, and initializes any missing arguments to nil.
  • Control is transferred to the main virtual machine loop (luaV_execute), which fetches, decodes, and executes bytecode instructions sequentially.

Through this dual-path dispatching system, the Lua VM maintains a clean separation between high-level interpreted instructions and native C host boundaries while presenting a unified calling interface to the programmer.
