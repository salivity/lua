Can 64-Bit Lua Bytecode Run on 32-Bit Systems?

Standard binary bytecode compiled on a 64-bit architecture cannot run on a 32-bit architecture in the standard Lua programming language. Lua precompiled chunks are not designed to be fully portable across differing architectures. When a 32-bit Lua virtual machine attempts to load bytecode generated by a 64-bit Lua compiler, the VM detects incompatible data type sizes in the bytecode header and rejects the file.

The Lua Bytecode Header

When Lua code is compiled using luac or dumped via string.dump(), the resulting binary output begins with a signature followed by a architecture-specific header. This header acts as a safeguard to ensure that the environment executing the bytecode matches the environment that generated it.

The header explicitly verifies several architecture parameters:

  • Size of int: Typically 4 bytes on both architectures.
  • Size of size_t: 8 bytes on 64-bit systems, but 4 bytes on 32-bit systems.
  • Size of Instruction: The internal instruction size used by the Lua VM.
  • Size of lua_Integer: Often defaults to 8 bytes on 64-bit systems and 4 or 8 bytes on 32-bit systems, depending on the Lua version and compilation flags.
  • Size of lua_Number: The floating-point type used by the VM.
  • Endianness: The byte order (little-endian vs. big-endian) of the host system.

Because a 64-bit machine uses 8-byte pointers and size_t values, the bytecode layout reflects these larger structures. When a 32-bit Lua runtime reads these header fields, it encounters values that do not match its own internal memory configuration. Consequently, functions like load() or loadfile() throw a runtime error indicating a corrupted or incompatible binary chunk (such as bad binary format).

Lua Version Variations

  • Lua 5.1 and 5.2: Bytecode portability is strictly restricted. Any mismatch in size_t or integer definitions causes an immediate failure during the binary header validation check.
  • Lua 5.3 and 5.4: These versions introduced a unified 64-bit integer type by default, even on many 32-bit platforms, but the fundamental structure of size_t and pointer representations in compiled bytecode still breaks cross-compatibility between 32-bit and 64-bit builds.
  • LuaJIT: LuaJIT features its own bytecode format separate from the official PUC-Rio Lua. LuaJIT 2.0 bytecode can be portable across architectures of the same word size and endianness, but LuaJIT 2.1 introduces GC64 mode on 64-bit systems, which breaks bytecode compatibility with standard 32-bit targets.

Solutions for Cross-Platform Deployment

If software must support both 32-bit and 64-bit client environments, the following approaches resolve the compatibility problem:

  1. Distribute Plain Source Code: Lua's source parser is fast and memory-efficient. Distributing original .lua files eliminates architecture restrictions entirely, allowing the target machine's native interpreter to compile the source at runtime.
  2. Build Architecture-Specific Binaries: If precompilation is required to protect source code or reduce startup latency, compile separate bytecode binaries for 32-bit and 64-bit targets. A 32-bit version of luac can be executed on a 64-bit host system to produce 32-bit-compatible bytecode.
