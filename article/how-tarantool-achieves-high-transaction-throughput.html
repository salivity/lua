How Tarantool Achieves High Transaction Throughput

Tarantool achieves extreme transaction throughput by operating primarily as an in-memory data store combined with an embedded LuaJIT application server driven by an asynchronous event loop. By executing application logic directly in the memory space where data resides, Tarantool completely eliminates the latency of inter-process communication and network round-trips. Furthermore, its cooperative multitasking architecture uses lightweight coroutines (fibers) scheduled across a non-blocking event loop, enabling a single operating system thread to handle hundreds of thousands of concurrent operations per second without the overhead of locks, context switching, or thread contention.

The In-Memory Foundation and Lock-Free Execution

At its core, Tarantool stores primary data sets directly in RAM using optimized data structures such as lock-free skiplists and tree indexes. Persistence is maintained asynchronously through write-ahead logging (WAL) and periodic snapshots, meaning disk operations do not sit on the critical path of read and write transactions.

Because data modification is confined to a single execution thread, the database does not require mutexes, read-write locks, or latching mechanisms to preserve memory consistency. This eliminates lock contention—one of the primary bottlenecks in traditional multi-threaded relational database management systems (RDBMS). Transactions execute strictly in sequence, enabling predictable, sub-millisecond execution times.

The Event Loop and Cooperative Multitasking

To handle thousands of concurrent client connections without spawning OS-level threads, Tarantool relies on an event loop built upon libev. Concurrency is managed via cooperative multitasking using lightweight execution threads called fibers.

  • Minimal Overhead: Fibers are user-space coroutines that consume only a few kilobytes of memory, contrasting sharply with OS threads that require megabytes of dedicated stack space.
  • Cooperative Scheduling: A running fiber yields control voluntarily only when performing an asynchronous operation (such as waiting for network I/O or waiting for a WAL disk flush).
  • Zero Locking Overhead: While a fiber computes logic and updates in-memory tuples, it cannot be preempted by another fiber. This guarantees that transactions running within that fiber observe consistent state without needing explicit record locking.

When a fiber initiates an I/O request, it suspends itself and registers a callback with the event loop. The event loop then seamlessly switches execution to the next ready fiber, ensuring the CPU remains saturated with useful computation.

Co-Locating Compute and Storage with LuaJIT

Traditional client-server database architectures require an application to query data over a socket, serialize/deserialize payloads, process business logic, and send updates back. This architecture multiplies network latency and CPU cycles spent on I/O.

Tarantool acts as both an in-memory database and an application server by embedding LuaJIT—a highly optimized, Just-In-Time compiler for the Lua language. Developers write business logic, stored procedures, and APIs directly in Lua:

  1. Zero-Copy Access: Lua code accesses C-level database tuples directly via a C-Lua bridge, bypassing serialization formats like JSON or Protocol Buffers.
  2. Near-Native Execution Speed: LuaJIT compiles Lua bytecode into machine code at runtime, often matching the execution performance of compiled C.
  3. Complex Transactions in a Single Trip: Instead of issuing multiple SQL commands over a network, a client calls a single Lua function stored on the server. The entire sequence of reads, computations, and updates occurs locally inside memory in one atomic-like pass.

Synthesizing Lua and the Event Loop for Maximum I/O

The real synergy occurs where Lua meets the fiber-driven event loop. Tarantool exposes non-blocking socket and file operations through standard, synchronous-looking Lua interfaces. When a developer calls a network or database read in Lua, the underlying runtime transparently yields the fiber to the C-level event loop without blocking the main execution thread.

By eliminating thread context switches, abolishing memory locks, executing compiled application logic directly in the data space, and utilizing a non-blocking event loop for concurrency, Tarantool extracts maximum possible throughput from modern multicore processors and memory hierarchies.
