How to Use Custom Comparators in Lua table.sort

The table.sort function in Lua provides an in-place sorting mechanism for sequence-like tables, sorting elements in ascending order by default using the standard less-than (<) operator. Developers can override this behavior by passing a custom comparator function as the second argument to table.sort. This article explains the technical mechanics behind Lua's custom comparators, the strict mathematical ordering rules they must follow, and practical implementations for sorting complex data structures.

The Comparator Mechanism

When calling table.sort(my_table, comp), Lua's internal sorting algorithm—typically an introsort or quicksort variant—relies on the provided comp function to determine the relative order of pairs of elements.

The custom comparator must accept two arguments, a and b, representing two elements from the table:

local function custom_comp(a, b)
    -- Returns true if 'a' must come before 'b'
end

The function must return a boolean value:

  • true: Indicates that a must precede b in the sorted result.
  • false: Indicates that a does not precede b (meaning a is either greater than or equivalent to b).

If no comparator is provided, Lua uses an internal default equivalent to:

local function default_comp(a, b)
    return a < b
end

The Strict Weak Ordering Requirement

Lua mandates that any custom comparator function must implement a strict weak ordering equivalent to the mathematical < operator. Violating these rules can cause the sorting algorithm to malfunction, resulting in incorrect sorting order, infinite loops, or segmentation faults in certain Lua runtimes.

A valid comparator must satisfy three core conditions:

  1. Irreflexivity: comp(a, a) must always be false. An element cannot be strictly less than itself.
  2. Asymmetry: If comp(a, b) returns true, then comp(b, a) must return false.
  3. Transitivity: If comp(a, b) is true and comp(b, c) is true, then comp(a, c) must also be true.

The Common <= Mistake

The most frequent error in Lua sorting is using <= instead of <. Consider the following flawed descending comparator:

-- INCORRECT: Violates irreflexivity
table.sort(numbers, function(a, b)
    return a >= b 
end)

When a and b are equal, a >= b returns true. This breaks the rule comp(a, a) == false. The correct implementation requires a strict greater-than comparison:

-- CORRECT
table.sort(numbers, function(a, b)
    return a > b
end)

Practical Implementation Examples

1. Sorting Complex Records

When dealing with tables of dictionaries, the comparator accesses specific keys to determine the order.

local users = {
    { name = "Alice", age = 30 },
    { name = "Bob", age = 22 },
    { name = "Charlie", age = 25 }
}

-- Sort users by age in ascending order
table.sort(users, function(a, b)
    return a.age < b.age
end)

2. Multi-Tier Sorting (Tie-Breaking)

When elements have identical values on a primary metric, a comparator can fall back to secondary or tertiary metrics.

local players = {
    { name = "PlayerA", score = 100, ping = 45 },
    { name = "PlayerB", score = 150, ping = 60 },
    { name = "PlayerC", score = 100, ping = 20 }
}

-- Sort by highest score first; tie-break with lowest ping
table.sort(players, function(a, b)
    if a.score ~= b.score then
        return a.score > b.score
    end
    return a.ping < b.ping
end)

3. Case-Insensitive String Sorting

By default, Lua sorts strings using standard ASCII byte values, causing uppercase letters to appear before lowercase letters. A comparator can normalize the casing during comparison:

local words = { "banana", "Apple", "cherry", "Date" }

table.sort(words, function(a, b)
    return a:lower() < b:lower()
end)

Performance Considerations

Because table.sort invokes the comparator function repeatedly during execution (approximately \(O(N \log N)\) times), the comparator code should remain as lightweight as possible. Avoid expensive calculations, allocations, or complex pattern matching inside the comparator body. If sorting requires an expensive transformation—such as resolving a file path or computing an expensive hash—precompute the values and store them directly in the table before executing the sort.
