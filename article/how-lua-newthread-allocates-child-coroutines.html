How lua_newthread Allocates Child Coroutines

This article examines how the lua_newthread C API function allocates and initializes child coroutines in the Lua programming language. It breaks down the distinction between thread-specific execution data and shared runtime resources, explaining the internal memory management and architectural mechanisms Lua uses to let a child coroutine execute independently while maintaining access to the shared global state.

The Architecture of Lua States

To understand lua_newthread, it is essential to distinguish between the two core structs Lua uses for its execution environment: lua_State and global_State.

  • lua_State: Represents an individual execution thread (coroutine). It contains the private execution context: the evaluation data stack (StkId), the call frame list (CallInfo), the program counter, hook functions, and error handling status.
  • global_State: Represents the entire Lua instance. It is shared across all coroutines and contains the garbage collector state, the global string intern table, the registry table, memory allocation functions, and basic type metatables.

When you initialize a Lua runtime using luaL_newstate, Lua allocates both a global_State and the primary lua_State (the main thread).

How lua_newthread Allocates a Coroutine

When lua_newthread(L) is called with an existing lua_State *L, it creates a new coroutine through the following internal sequence:

1. Memory Allocation via the Shared Allocator

Lua invokes its internal thread factory (typically luaE_newthread in the source code). The memory allocator configured in L->l_G is called to allocate a new lua_State structure on the heap. Because memory is allocated through the existing global_State allocator, the memory footprint of the new thread is accounted for in the runtime's total memory metrics.

2. Linking to the Shared Global State

The newly allocated lua_State sets its internal global pointer (l_G) to point directly to the parent's L->l_G. By sharing this single pointer, the new thread gains immediate access to:

  • The shared environment tables (_G).
  • The registry (LUA_REGISTRYINDEX).
  • The central string interning cache.
  • Global garbage collection cycles.

No duplication of standard libraries, globals, or string pools takes place, making thread creation lightweight.

3. Initializing Independent Execution Contexts

The new lua_State creates its own dedicated execution stack. Lua allocates an initial stack array (typically sized to BASIC_STACK_SIZE, around 40 slots) and a base CallInfo structure for the coroutine.

The child's call chain, stack top (top), stack base (func), and execution status are set to zero/clean states. As a result, pushing values, calling functions, or encountering errors inside the child coroutine will not corrupt or alter the stack frame of the parent coroutine.

4. Garbage Collection Registration and Anchoring

Because coroutines are first-class values in Lua, the new thread is registered as a collectable object (GCObject) marked with the type LUA_TTHREAD. It is linked into the global garbage collector list managed by global_State.

To prevent the newly allocated thread from being immediately collected by the garbage collector during an allocation phase, lua_newthread automatically pushes the newly created lua_State onto the parent thread's stack (L) as a thread object value before returning. The function then returns a raw lua_State* pointer to the caller, allowing the C host to configure, populate, or resume the child coroutine.
