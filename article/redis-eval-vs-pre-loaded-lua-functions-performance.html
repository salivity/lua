Redis EVAL vs Pre-Loaded Lua Functions Performance

Executing Lua scripts inside Redis can be accomplished either by passing raw script bodies using the EVAL command or by invoking pre-loaded scripts and routines via EVALSHA or Redis 7 Functions (FCALL). While the execution speed of the Lua code itself remains identical once the script is running inside the Redis Lua engine, pre-loaded functions provide substantial performance gains over raw EVAL in production environments. These advantages stem primarily from drastically reduced network overhead, lower serialization costs, and eliminated script parsing overhead on the server.

Network Bandwidth and Latency

The most significant performance bottleneck with raw EVAL is network payload size. With EVAL, the client sends the entire Lua script text over the network for every single execution. For complex logic, this payload can range from hundreds of bytes to several kilobytes per call.

In contrast, calling pre-loaded code via EVALSHA requires only a 40-character SHA1 digest, and Redis Functions (FCALL) use a brief user-defined function name. At high throughput—such as tens of thousands of requests per second—the redundant transmission of script bodies under EVAL consumes significant network bandwidth, saturates network interfaces, and increases round-trip latency.

Parsing and Compilation Overhead

When Redis receives an EVAL command, it must read the script string, compute its SHA1 hash internally, check whether the script already exists in the script cache, and compile it if it does not. Even though Redis maintains an internal cache of compiled scripts to mitigate recompilation, evaluating the incoming command string and hashing it on every call wastes CPU cycles.

With pre-loaded functions:

  • SCRIPT LOAD with EVALSHA: The script is compiled once during the load phase. Subsequent executions bypass the transmission and hashing steps entirely.
  • Redis Functions (FCALL): Introduced in Redis 7.0, functions are loaded once as modules/libraries. Redis resolves function references directly by name from an internal lookup table, avoiding script cache lookups and hashing altogether.

Client and Server CPU Utilization

Raw EVAL commands increase CPU utilization on both sides of the connection:

  • Client Overhead: Clients must allocate memory and format command buffers containing large script strings repeatedly.
  • Server Overhead: The Redis single-threaded event loop spends more time reading larger packets from the socket buffer and parsing command arguments before execution can even begin.

By shrinking the command size to an identifier and its arguments, pre-loaded functions allow the Redis event loop to process requests faster, leading to higher overall operations per second (OPS).

Script Eviction and Execution Guarantees

The transient script cache used by EVAL and EVALSHA is volatile. If SCRIPT FLUSH is executed or Redis restarts, cached scripts are wiped. When using EVALSHA, if a script is missing from the cache, the server returns a NOSCRIPT error, forcing the client to fall back to EVAL and re-upload the script.

Redis Functions resolve this limitation. Functions loaded with FUNCTION LOAD are treated as first-class database artifacts. They are persisted inside the RDB and AOF files and automatically replicated to replicas. This architecture eliminates cache misses and fallback latency spikes entirely.

Summary Comparison

Metric / Feature Raw EVAL EVALSHA Redis Functions (FCALL)
Network Payload High (full script text) Minimal (40-char SHA1) Minimal (function name)
Parsing Overhead Per-request string parsing & hashing Direct cache lookup Direct lookup table resolution
In-Engine Speed Identical Identical Identical
Persistence Volatile cache only Volatile cache only Persisted in RDB/AOF and replicated
Throughput Ceiling Lower (bandwidth-bound) High High

For optimal performance and reliability, pre-loaded Redis Functions or EVALSHA should be used instead of raw EVAL for any workload requiring regular script invocation.
