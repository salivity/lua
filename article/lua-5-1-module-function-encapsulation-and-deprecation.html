Lua 5.1 module Function: Encapsulation and Deprecation

In Lua 5.1, the built-in module() function was introduced to standardize how packages defined namespaces and encapsulated their internal state. By manipulating the calling function’s environment, it aimed to eliminate boilerplate and prevent unintended leakage of variables into the global scope. However, this mechanism introduced significant side effects, including global namespace pollution, broken access to standard libraries, and structural conflicts with Lua's runtime design. As a result, module() was deprecated in Lua 5.2 and completely removed in subsequent versions in favor of a simpler, table-return pattern.

How module Handled Environment Encapsulation

Prior to Lua 5.1, authors manually created tables and assigned them to global variables to serve as modules. This often led to accidental global variable declarations within the module file.

To solve this, Lua 5.1 introduced module(name, ...). When called, module() performed several automated tasks:

  1. Table Creation and Registration: It checked if a table named name already existed. If not, it created a new table, registered it in package.loaded[name], and assigned it to the global variable name.
  2. Environment Replacement: Using Lua 5.1’s setfenv() function, module() changed the environment of the current chunk so that the new module table became the chunk's global environment.

Because the environment was swapped to the module table itself, any variable or function declared without the local keyword was automatically assigned directly to the module table:

module("mymodule")

-- Automatically exported as mymodule.greet
function greet()
    return "Hello"
end

This effectively encapsulated the module's functions and internal declarations without requiring developers to prefix every export with a table name.

Why module Was Deprecated

Despite simplifying basic module definitions, the mechanics behind module() proved problematic in real-world applications for several reasons.

1. Inability to Access Standard Globals

Once module() replaced the function's environment with the newly created table, standard global functions and libraries—such as print(), tostring(), math, and table—were no longer visible. A developer had to explicitly alias every needed global locally before calling module():

local print = print
local math = math

module("mymodule")

2. The Flaws of package.seeall

To remedy the loss of standard globals, Lua provided the package.seeall option:

module("mymodule", package.seeall)

This assigned a metatable to the module where __index pointed to the global table _G. While this restored access to standard functions, it broke true encapsulation and introduced security concerns. Any consumer of mymodule could access the entire global environment through the module's metatable (e.g., mymodule.os.execute()), and modifying fields on the module could inadvertently overwrite or expose sensitive globals.

3. Automatic Global Namespace Pollution

The module() function forcefully set a global variable with the module's name. This prevented users from cleanly renaming modules upon import, complicated sandboxing, and conflicted with systems that preferred unpolluted global environments.

4. The Removal of setfenv and the Shift to _ENV

In Lua 5.2, the runtime model shifted from dynamic function environments (getfenv/setfenv) to lexical environments controlled by the _ENV variable. Because module() relied directly on dynamic stack manipulation via setfenv, it was fundamentally incompatible with this cleaner, compiler-driven scoping model.

The Modern Replacement

Modern Lua completely bypasses module() in favor of returning a plain local table:

local mymodule = {}

function mymodule.greet()
    return "Hello"
end

return mymodule

This standard idiom retains natural access to standard globals, eliminates unwanted modifications to _G, and allows the importing file to assign the module to any local variable name via require.
