Suricata Lua Scripting for Deep Packet Inspection

Suricata integrates the Lua programming language to provide security analysts with flexible, programmable deep packet inspection capabilities that extend beyond static signature-based rules. By embedding a Lua runtime directly into its multi-threaded architecture, Suricata allows custom scripts to access normalized protocol buffers, evaluate complex payload logic, and perform custom logging. This article explains the technical mechanics of how Suricata embeds Lua, exposes packet and stream data to the runtime, and executes scripts during packet analysis.

Embedding Architecture and the Lua C API

Suricata embeds Lua using standard C API bindings, typically leveraging LuaJIT for just-in-time compilation and high-throughput performance. When compiled with Lua support (via the --enable-lua flag), Suricata links the Lua virtual machine directly into its core binary.

To maintain scalability across multi-core systems, Suricata uses a multi-threaded architecture where worker threads process packets independently. Rather than sharing a single global Lua state—which would cause heavy lock contention—Suricata initializes an independent lua_State instance for each processing thread. Each worker thread runs its own isolated Lua environment, ensuring thread safety and lock-free script execution during high-volume packet processing.

The Lua Rule Keyword Interface

Lua scripts integrate into Suricata's detection engine primarily through the lua (or luajit) rule option within standard Suricata signatures. A rule references an external script:

alert tcp any any -> any any (msg:"Custom Lua Inspection"; lua:custom_inspect.lua; sid:1000001; rev:1;)

When Suricata loads the signature, it registers the script and calls an initialization function within the Lua file. For each packet or flow that reaches the evaluation stage of that rule, Suricata invokes the script's matching entry point.

A standard Suricata Lua inspection script implements three core functions:

  • init (args): Sets up required protocol buffers and registers dependencies.
  • match (args): Evaluates the packet or flow data and returns 1 (match) or 0 (no match).
  • deinit (): Cleans up allocated states or outputs summary metrics when Suricata shuts down.

Data Exposure: Passing Packets and Streams to Lua

Suricata exposes internal C structures to Lua by pushing C functions and userdata into the Lua execution stack. Through Suricata's Lua API, scripts can access several layers of network data:

  1. Raw Packet Data: Scripts can directly inspect raw layer 2 through layer 4 packet headers and payload slices.
  2. Reassembled Stream Buffers: For TCP traffic, Suricata's stream reassembly engine provides Lua with access to continuous data streams, avoiding the need for scripts to handle out-of-order packets or TCP fragmentation.
  3. Application Layer Protocol Contexts: Suricata’s protocol decoders parse protocols such as HTTP, TLS, DNS, SSH, and SMTP. The parsed metadata is exposed to Lua through helper functions (e.g., Http.get_uri(), Tls.get_sni()). This allows scripts to evaluate normalized data fields rather than parsing complex protocols manually.

Execution Flow in the Detection Pipeline

During packet processing, Suricata applies pre-filters such as IP addresses, ports, and fast-pattern matches before running computationally intensive checks. If a packet satisfies the preliminary conditions of a rule containing a Lua keyword, Suricata pauses native rule evaluation and transfers execution context to the embedded Lua interpreter.

The worker thread pushes a reference to the current packet context onto the thread's Lua stack and calls the Lua match() function. The script executes its logic using the provided API functions to query payloads or flow variables. Once the script finishes, it leaves a boolean integer on the stack, which Suricata reads to determine whether to trigger an alert or proceed down the rule evaluation tree.

Custom Logging and Output Scripting

Beyond signature matching, Suricata embeds Lua into its output sub-system. Users can replace or supplement standard EVE-JSON logging with Lua scripts specified in the suricata.yaml configuration file.

In this mode, Suricata invokes Lua callback functions whenever an event—such as a flow timeout, an alert, or an application transaction—is finalized. The script extracts relevant fields from the Suricata data structures and formats them into custom outputs, such as direct database writes, filtered JSON files, or external API calls, without requiring modifications to Suricata's core C codebase.
