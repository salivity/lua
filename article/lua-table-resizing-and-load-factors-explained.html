Lua Table Resizing and Load Factors Explained

This article explores the internal mechanics of table resizing and load factor management in the Lua programming language. Lua tables serve as the language’s sole data structuring mechanism, implemented internally as a hybrid combination of an array slice and a hash map. By examining how Lua tracks occupancy, triggers the rehash routine, and enforces capacity thresholds, this guide breaks down how Lua achieves memory efficiency and high performance during dynamic table growth.

The Dual Structure of Lua Tables

In the Lua C source code, a table (Table struct) consists of two distinct components:

  1. The Array Part: A contiguous array allocated to hold integer keys from 1 up to \(n\).
  2. The Hash Part: A node-based hash table designed to hold non-integer keys, negative or out-of-bounds integers, and strings.

Both segments are dynamically sized, and their capacities are almost always powers of two. Rather than managing independent resize cycles for each part, Lua synchronizes array and hash resizing inside a single centralized function named luaH_resize, which is triggered by rehash.

Hash Part Load Factor and Resize Threshold

Unlike runtimes such as Java (which defaults to a 0.75 load factor) or Python (which resizes around a 0.66 load factor), Lua uses an aggressive load factor threshold of 1.0 (100%) for its hash part.

Lua’s hash table implementation uses a variation of open addressing combined with chained scatter hashing:

  • Hash buckets and collision nodes share the same contiguous block of memory (Node array).
  • Each node contains a key, a value, and a next offset linking collided keys.
  • A dedicated internal pointer, lastfree, starts at the end of the node array and steps backward searching for empty slots whenever a collision occurs at a key’s primary hash position.

Because of this layout, the hash part does not resize when collisions occur; it only triggers a reallocation when an insertion requires an empty slot and lastfree has walked all the way to the base of the node array without finding one. Consequently, Lua delays resizing until the hash part is entirely full, minimizing unused allocated memory.

The Rehash Algorithm and the 50% Array Rule

When an insertion fails due to a saturated hash part, Lua does not simply double the hash capacity. Instead, it initiates a full count of all existing keys across both the array and hash parts to redistribute them optimally.

The algorithm counts the distribution of integer keys to find the optimal size for the array part. Lua evaluates integer keys bucketed into powers of two (\([1, 1], [2, 2], [3, 4], [5, 8], \dots, [2^{i-1}+1, 2^i]\)) and enforces the 50% density rule:

  • The array size is chosen as the largest power of two \(2^m\) such that more than half of the slots from \(1\) to \(2^m\) are occupied by valid keys.
  • Any integer key greater than \(2^m\), non-integer keys, or sparse integers that fail the density condition are directed to the hash part.

Once the optimal array size is determined, Lua counts the remaining keys that do not fit into the array. It computes the smallest power of two that can accommodate these remaining keys and sets that as the new size of the hash part.

Execution of luaH_resize

After computing the target sizes:

  1. Lua allocates a new array buffer and a new node buffer of the calculated power-of-two dimensions.
  2. It re-inserts all existing elements from the old structures into the new segments.
  3. Because the array capacity may have grown or shrunk, keys migrate dynamically between the array slice and the hash slice.
  4. The old memory blocks are freed.

Performance and Memory Trade-offs

Lua's aggressive 100% hash load factor makes tables exceptionally lightweight in terms of memory footprint, which aligns with the language’s primary design goal of embedded execution. However, this high load factor increases the length of collision chains as the table approaches capacity, causing a slight degradation in lookup times immediately before a resize.

Additionally, because recomputing the optimal split between array and hash parts requires scanning all keys, frequent reallocations can introduce computational overhead. To mitigate this during table creation, Lua provides standard functions such as table.create (in LuaJIT and Luau) to pre-allocate array and hash capacities, bypassing the incremental resize and rehashing cycle entirely.
