Lua assert vs error: What Is the Difference?

In the Lua programming language, error handling typically relies on two built-in mechanisms: assert() and error(). While assert() acts as a conditional wrapper that raises a runtime exception only when a given condition evaluates to false or nil, error() halts execution immediately and unconditionally. Understanding the differences between them—such as how arguments are evaluated, stack level customization, and handling of complex error objects—is essential for writing clean, performant, and robust Lua code.

Conditional vs. Unconditional Execution

The most visible difference between the two functions is their execution control:

  • assert(v [, message]) tests its first argument, v. If v is truthy (anything other than nil or false), assert returns all passed arguments. If v is falsy, it automatically raises an error using message (defaulting to "assertion failed!").
  • error(message [, level]) unconditionally raises an error the moment it is called. It does not evaluate a condition; execution terminates immediately unless caught by a protected call such as pcall or xpcall.
-- assert evaluates the condition inline:
local file = assert(io.open("config.lua", "r"), "Unable to open config file")

-- error requires a conditional block:
local file, err = io.open("config.lua", "r")
if not file then
    error("Unable to open config file: " .. tostring(err))
end

Argument Evaluation and Performance

Because assert() is a standard Lua function, all arguments passed to it are evaluated before the function executes. If an error message involves expensive string concatenation or function calls, that work occurs even when the assertion succeeds:

-- String concatenation happens on EVERY pass, degrading performance:
assert(user ~= nil, "User " .. tostring(id) .. " not found in database")

With error(), the error message is placed inside an explicit conditional block (like an if statement). The string formatting or table creation executes only during the failure path, keeping the happy path fast and efficient.

Stack Trace Levels

When a function in a module or library fails due to bad input from the caller, you often want the error message to point to the caller's line of code rather than internal library code.

  • assert() raises errors from the point of the assert call itself (stack level 1). It does not provide a native parameter to adjust the error stack level.
  • error() accepts a second argument, level:
    • level = 1 (default): Points to where error() was called.
    • level = 2: Points to the line where the enclosing function was called, effectively attributing the error to the caller.
    • level = 0: Omits file and line number information from the error message entirely.
local function set_age(age)
    if type(age) ~= "number" then
        -- Blames the caller who invoked set_age, not this line:
        error("Age must be a number", 2)
    end
end

Throwing Structured Error Objects

While both functions can accept non-string values as error objects, error() is typically favored when implementing structured exception handling.

Lua allows throwing tables, custom objects, or error codes instead of plain strings:

local function fetch_data(id)
    if not id then
        error({ code = 400, message = "Missing ID parameter" }, 2)
    end
end

local success, err = pcall(fetch_data, nil)
if not success then
    -- err is the table thrown by error()
    print("Error code: " .. err.code)
end

Summary of When to Use Each

  • Use assert() for concise idioms like file and network operations that return result, err on failure (e.g., assert(file:read())), or for internal invariants and debugging checks where performance is not critical.
  • Use error() when developing public APIs, when constructing the error message requires computation, when you need custom error stack levels (level = 2), or when passing structured error tables to a pcall handler.
