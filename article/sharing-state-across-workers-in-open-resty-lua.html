Sharing State Across Workers in OpenResty Lua

Sharing state across worker processes in the OpenResty framework is essential for caching, rate limiting, and synchronizing configuration. Because OpenResty utilizes Nginx’s single-threaded, multi-process architecture rather than OS-level multi-threading, each worker operates within its own isolated Lua VM. Consequently, standard Lua global variables are not shared between workers. To coordinate data across the entire instance, OpenResty provides built-in shared memory zones (lua_shared_dict), non-blocking external datastores, inter-process communication libraries, and copy-on-write memory initialized during startup.

The OpenResty Worker Model

In OpenResty, Nginx spawns multiple independent OS processes (workers) to handle network events asynchronously. Because memory is isolated per process, modifying a global variable in one worker does not affect the others. Modifying global variables in Lua handlers can also lead to race conditions within a single worker across coroutines. Managing global or cross-worker state therefore requires external synchronization or dedicated shared memory structures.

1. Built-in Shared Memory Dictionaries (lua_shared_dict)

The most common and highest-performing method for sharing state across workers is lua_shared_dict. This directive allocates an in-memory key-value store in the Nginx master process before workers are forked, making the allocated block accessible to all worker processes.

Configuration

Define the dictionary in the http block of nginx.conf:

http {
    lua_shared_dict app_cache 10m;
}

Access in Lua

Access the dictionary within any Lua phase using the ngx.shared API:

local cache = ngx.shared.app_cache

-- Set a key with an optional expiration time (in seconds)
local success, err = cache:set("key", "value", 60)

-- Read a key
local val, flags = cache:get("key")

-- Atomic operations
local new_val, err = cache:incr("counter", 1, 0)

Key Characteristics

  • Concurrency Safe: Read and write operations use internal mutexes to ensure atomicity across workers.
  • Primitive Types: Supported data types are strings, numbers, and booleans. Complex types like Lua tables must be serialized (e.g., using JSON) before storage.
  • LRU Eviction: If the allocated memory zone runs out of space, the store automatically purges the least-recently used items unless using safe_set.

2. Synchronization and Locking (lua-resty-lock)

When multiple workers attempt to update a shared value simultaneously (such as fetching data on a cache miss), dog-piling or race conditions can occur. The lua-resty-lock library uses lua_shared_dict to build a non-blocking, cross-process mutex.

local resty_lock = require "resty.lock"
local lock, err = resty_lock:new("app_cache")

local elapsed, err = lock:lock("resource_key")
if not elapsed then
    ngx.log(ngx.ERR, "Failed to acquire lock: ", err)
    return
end

-- Perform critical update or database fetch here

local ok, err = lock:unlock()

3. Copy-on-Write via init_by_lua_block

If your state is static or read-only (such as static configuration files, routing tables, or predefined lookup lists), you can load it in the init_by_lua or init_by_lua_block phase.

http {
    init_by_lua_block {
        _G.CONFIG = {
            timeout = 5000,
            api_endpoint = "https://api.example.com"
        }
    }
}

Because Nginx calls init_by_lua in the master process before forking worker processes, the operating system uses Copy-on-Write (COW) memory. All workers share this memory space with zero runtime locking overhead, provided the data is never modified after initialization.

4. Inter-Process Communication (lua-resty-ipc)

When one worker needs to notify other workers about an event (such as clearing local in-memory caches or updating a runtime setting), polling a shared dictionary can become inefficient. Third-party modules like lua-resty-ipc use Unix domain sockets to broadcast messages directly across worker processes, allowing pub/sub messaging patterns inside a single Nginx instance.

5. External Non-Blocking Datastores

When state needs to persist across server restarts or be shared across a multi-server OpenResty cluster, external storage engines are required. OpenResty provides non-blocking cosocket-based drivers for this purpose:

  • Redis (lua-resty-redis): Ideal for distributed counters, session stores, and pub/sub messaging across multiple nodes.
  • Memcached (lua-resty-memcached): Suitable for high-throughput distributed caching.

Using these external drivers preserves OpenResty's non-blocking event loop while synchronizing state beyond the boundaries of a single host.
