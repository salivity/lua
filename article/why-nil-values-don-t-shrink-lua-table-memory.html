Why Nil Values Don't Shrink Lua Table Memory

In the Lua programming language, setting a table key's value to nil logically removes the entry, but it does not immediately release or shrink the table's allocated memory buffer. This behavior is rooted in Lua's internal table implementation, which balances memory usage against CPU performance by delaying resizing operations. This article explains how Lua tables are structured, why removing values fails to trigger memory shrinkage, and how you can reclaim that memory when necessary.

The Dual Structure of Lua Tables

To understand memory retention, it is essential to understand how Lua represents tables in memory. Internally, a Lua table is split into two components:

  1. The Array Part: A contiguous block of memory optimized for dense, 1-based integer keys.
  2. The Hash Part: A hash table composed of fixed-size nodes used for non-integer keys, sparse integers, or integers outside the array range.

Both parts are allocated in chunks, typically in powers of two (e.g., 2, 4, 8, 16 slots). Allocating and reallocating these blocks is an expensive operation that requires interacting with the memory allocator.

Setting Values to Nil Is Only a Logical Deletion

When you assign nil to a table entry—such as t[5] = nil or t["key"] = nil—Lua does not reallocate the underlying storage. Instead:

  • In the array part, Lua simply overwrites the memory slot with a nil value.
  • In the hash part, Lua marks the node's value as nil, but the node structure itself remains part of the hash bucket array.

The physical capacity of the table remains unchanged. Lua avoids shrinking the table immediately to prevent "allocation thrashing." If an application frequently inserts and removes keys, constantly reallocating and resizing the memory buffer would cause massive CPU overhead and memory fragmentation.

Rehashing Only Occurs on Insertion

Lua resizes a table using an internal routine called luaH_resize. This routine evaluates the keys present in the table, recalculates the optimal size for both the array and hash parts, and allocates fresh memory blocks.

Crucially, Lua only triggers a rehash during an insertion of a new key when there are no free slots left. Deletions (assigning nil) never trigger a rehash. Consequently, even if you clear every single key by assigning them to nil, the table retains its maximum allocated capacity indefinitely until it is either destroyed or forces a resize upon future insertions.

The Role of the Garbage Collector

There is a distinct difference between the table's internal capacity and the objects stored inside it:

  • Setting an element to nil removes the reference to the underlying data (such as a string, function, or another table). If no other references exist, the garbage collector (GC) will eventually reclaim the memory occupied by that data.
  • However, the table container itself—the array slots and node arrays—remains allocated and is not shrunk by the garbage collector.

How to Force Memory Reallocation

If you must reclaim the memory held by an oversized table, you have two primary options:

  1. Create a New Table: Discard the old table entirely and allow the garbage collector to reclaim it.

    t = nil -- The old table and its buffer will be garbage collected
t = {}  -- Allocate a fresh, minimal table

  2. Rebuild the Table: Copy the active keys into a new table so the new table only allocates what it actually needs.

    local new_table = {}
for k, v in pairs(old_table) do
    new_table[k] = v
end
old_table = new_table
