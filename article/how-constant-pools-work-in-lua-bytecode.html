How Constant Pools Work in Lua Bytecode

This article explores the mechanics of constant pools within the compiled bytecode prototypes of the Lua programming language. In Lua, every function is compiled into an internal prototype structure that encapsulates its executable instructions, debugging metadata, sub-prototypes, and a dedicated constant pool. The constant pool serves as an indexed storage array for literal values encountered at compile time, enabling the Lua virtual machine to execute fixed-width instructions efficiently without embedding variable-length data directly into the bytecode stream.

The Role of Function Prototypes

When the Lua compiler parses source code, it organizes each lexical scope—such as the top-level script or nested function definitions—into a function prototype, represented internally in the C source code as the Proto struct. A Proto contains the blueprint necessary to instantiate function closures at runtime.

Because Lua utilizes a register-based virtual machine with fixed-width (typically 32-bit) instructions, it cannot fit arbitrarily sized data like long strings, 64-bit floating-point numbers, or 64-bit integers directly into an instruction's operand fields. To resolve this, the compiler extracts literals from the source text and places them into an array within the Proto, commonly designated as k. This array is the function's constant pool.

Structure and Value Storage

The constant pool is an array of TValue structures, Lua’s universal tagged-union representation for values. Elements in the constant pool can include:

  • Strings: Stored as pointers to interned Lua string objects (TString).
  • Numbers: Integers and floating-point values (lua_Integer and lua_Number).
  • Booleans and Nil: Stored directly as tagged types when needed for explicit initialization or comparison.

During the parsing phase, the compiler performs literal deduplication. If a string or number appears multiple times within the same function scope, the compiler reuses the existing index in the constant pool rather than allocating duplicate entries. This minimizes memory usage and optimizes cache locality during bytecode execution.

Bytecode Operand Addressing

Lua bytecode instructions reference constants using indices pointing into the k array. Depending on the Lua version and the specific instruction format, addressing occurs in a few primary ways:

  1. Dedicated Load Instructions: Opcodes such as LOADK specify a destination register and a constant table index Bx. The virtual machine reads the TValue at k[Bx] and copies it into the designated register. When a function has more constants than the standard Bx field can address (often exceeding 18 bits or 262,143 entries), Lua employs an extended instruction like LOADKX followed immediately by EXTRAARG to supply a wider index.
  2. Embedded Register/Constant Flags (RK operands): Many arithmetic, relational, and table-access instructions (such as ADD, EQ, or GETTABLE) allow their operands to be either a register or a constant. In architectures like Lua 5.1 through 5.3, this is achieved by partitioning the operand bitfield; an index greater than a specific threshold (often using the highest bit as a flag) indicates an offset into the constant pool rather than a register index. In Lua 5.4, separate opcodes or distinct bit allocations differentiate constant and register operands directly.

Execution and Memory Management

At runtime, the constant pool is read-only. Instantiated closures derived from a Proto share the prototype's constant array, ensuring that multiple closures of the same function do not duplicate constant storage.

Because the elements within the pool are tracked as TValue objects, the Lua Garbage Collector (GC) traverses the k array of all active Proto structures during the mark phase. Any interned strings referenced by the constant pool are marked as reachable, preventing them from being swept while the prototype remains in use. When a prototype is eventually deallocated, its constant array is freed alongside the rest of the bytecode structures.
