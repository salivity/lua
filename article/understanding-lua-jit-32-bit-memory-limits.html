Understanding LuaJIT 32-Bit Memory Limits

This article examines the historical 32-bit memory address space limitations encountered when deploying LuaJIT, explaining the architectural reasons behind the 1 GB to 2 GB memory ceilings on 64-bit systems, the practical issues these constraints caused in production, and how the Lua ecosystem addressed them.

The Architectural Root: NaN Tagging and GC32

LuaJIT achieves much of its performance by utilizing an optimization technique known as NaN tagging to represent its dynamic values (TValue). On 32-bit architectures, this allows standard values—including numbers, booleans, and pointers to garbage-collected objects—to fit into a compact 64-bit slot.

When targeting 64-bit architectures, LuaJIT historically preserved this compact 64-bit TValue representation through an engine mode known as GC32. Under GC32, object references were stored as 32-bit pointers. Because the runtime relied on 32-bit pointers for garbage-collected objects, all Lua-managed objects (such as tables, strings, functions, and coroutines) had to be allocated within the lowest memory addresses of the host process's virtual address space.

The Resulting Address Space Ceilings

Although running on 64-bit operating systems, LuaJIT instances were hard-capped by the availability of low virtual memory addresses:

  • The 2 GB Boundary (Linux): On Linux, user-space virtual addresses start at zero. However, signed pointer arithmetic within the JIT compiler and standard address space partitions limited the usable allocation range for the garbage collector to the lowest 2 GB (0x00000000 to 0x7FFFFFFF) of virtual memory.
  • The 1 GB Boundary (macOS and Windows): On platforms like macOS and Windows, system libraries, thread stacks, or address space layout randomization (ASLR) frequently occupied chunks of the lowest virtual memory ranges. As a result, LuaJIT was often unable to allocate more than 1 GB—and sometimes significantly less—before running out of contiguous address space for the GC heap.

Production Consequences

In production environments, these constraints created specific operational hazards:

  1. Premature "Out of Memory" Errors: Applications would trigger not enough memory errors even when the physical machine had hundreds of gigabytes of free RAM, simply because the process exhausted low virtual addresses.
  2. Address Space Fragmentation: Allocations by host applications (such as embedding C/C++ runtimes) or external dynamic libraries could claim memory in the low address space prior to LuaJIT initializing, further starving the Lua VM.
  3. Multi-Tenant Inefficiency: Running multiple LuaJIT instances in a single process proved challenging, as every instance competed directly for the same scarce pool of memory addresses below 2 GB.

Workarounds and the Transition to GC64

Developers initially mitigated these limits by moving bulk data out of the Lua garbage collector:

  • FFI Allocation: Using LuaJIT's Foreign Function Interface (FFI) allowed developers to allocate buffers directly on the system heap via standard malloc. These allocations could reside anywhere in the full 64-bit address space, reserving the limited 32-bit GC pool strictly for application logic.
  • The GC64 Mode: To permanently resolve the issue, LuaJIT introduced the GC64 execution mode. GC64 redesigns the TValue layout to support 47-bit (or full 64-bit) pointers, allowing the garbage collector to allocate memory across the entire 64-bit virtual address space. While GC64 introduces a slight performance overhead due to larger pointer operations and changed register usage, it eliminates the hard 32-bit memory ceiling.
