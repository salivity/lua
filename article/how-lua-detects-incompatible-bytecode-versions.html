How Lua Detects Incompatible Bytecode Versions

When loading precompiled code, the Lua Virtual Machine (VM) detects incompatible bytecode versions by inspecting a standardized binary header prefixed to every compiled chunk. Through internal routines in the chunk loader (traditionally implemented in lundump.c), the runtime systematically evaluates signature bytes, version specifiers, format identifiers, data type sizes, and endianness markers. If any byte in this header fails to match the exact specifications expected by the host VM, loading immediately aborts, preventing memory corruption or runtime crashes caused by mismatched instruction sets or architecture differences.

The Lua Binary Header

When Lua compiles source code using tools like luac or the string.dump function, it prepends a fixed-size header to the generated bytecode. When lua_load or load processes a binary stream, the VM calls luaU_undump, which immediately parses this header before reading any opcodes, constants, or debug data.

The header verification sequence checks several specific components:

1. The Magic Signature

The first four bytes of any compiled Lua chunk constitute a magic number known as LUA_SIGNATURE. In standard Lua distributions, this sequence is defined as \x1bLua (0x1B, 0x4C, 0x75, 0x61):

  • The escape character (0x1B) ensures the file is identified as binary and cannot be confused with human-readable text code.
  • The trailing characters "Lua" serve as the human-readable identifier.

If these four bytes do not match, the VM treats the input as plain text source code. If text compilation is disallowed or the input contains garbage, the parser rejects it as a syntax error.

2. The Lua Version Number

Immediately following the signature is a single byte indicating the exact Lua version used to compile the chunk.

Lua calculates this byte as:

(major_version * 16) + minor_version

For example:

  • Lua 5.3 stores 0x53 (83 in decimal).
  • Lua 5.4 stores 0x54 (84 in decimal).

Lua bytecode is deliberately not backward- or forward-compatible across minor versions. If the version byte does not equal the VM’s internal LUAC_VERSION constant, the runtime terminates the operation immediately with an error indicating an incompatible version.

3. The Format Identifier

Following the version byte is the format byte (LUAC_FORMAT). The official Lua release sets this value to 0, representing the official bytecode format. Custom distributions, forks, or modified VMs often alter this byte to signify custom instruction sets or non-standard optimizations. If the incoming chunk's format byte does not match the host VM's LUAC_FORMAT, the loader halts.

4. Data Type Sizing and Architecture Checks

Even within the same Lua version, different systems can compile Lua with distinct configurations (e.g., 32-bit vs. 64-bit systems, or systems configured for integer-only processing). To verify host environment compatibility, the header contains type-size indicators and conversion tests:

  • Size Values: The header records the exact size in bytes of core C and Lua types, including sizeof(int), sizeof(size_t), sizeof(Instruction), sizeof(lua_Integer), and sizeof(lua_Number). The VM checks that every incoming size matches the compiled sizes of the current runtime.
  • Endianness and Conversion Tests: Older versions of Lua used dedicated endianness bytes, while modern versions (Lua 5.3+) serialize specific test values into the header. A standard integer value (such as 0x5678) and a standard floating-point value (such as 370.5) are written to the stream. The VM reads these numbers; if the resulting values do not equal the expected constants, the host recognizes an endianness mismatch or differing floating-point representation (e.g., IEEE 754 vs. fixed-point).

Failure and Error Handling

If any comparison in the header fails, luaU_undump triggers luaD_throw with a syntax error status (LUA_ERRSYNTAX). The loader refuses to allocate or map instructions from the chunk, safely returning an error message to the user—such as "cannot load precompiled chunk in incompatible code" or a version mismatch warning—without executing corrupt memory or invalid instructions.
