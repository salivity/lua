Redis Lua Script Restrictions for Replication

To guarantee data consistency across replicas and the Append Only File (AOF), Redis executes Lua scripts within a sandboxed, deterministic environment. This article details the core state restrictions Redis enforces on Lua scripts—including global variable lockdowns, random number seed management, lexical sorting of unordered collections, and write-after-read limitations—ensuring that identical script executions produce identical state transitions on every node.

Global Variable Lockdown

Redis reuses the same Lua execution context to avoid the overhead of re-initializing the Lua state machine on every EVAL invocation. Because state could leak from one execution to another, Redis strictly forbids scripts from creating global variables or modifying the global environment.

  • Sandboxed Environment: The global environment table (_G) is protected. Attempting to define a global variable via my_var = 1 or modifying pre-existing global libraries (such as string or math) raises a runtime error: Script attempted to create global variable '...'.
  • Explicit Local Scope: All variables, helper functions, and imported modules must be declared with the local keyword. This ensures that every script runs as an isolated, stateless transaction without leaving artifacts that could alter the behavior of subsequent scripts.

Deterministic Randomness and PRNG Control

In standard Lua, functions like math.random and math.randomseed can produce varying outputs depending on system state and execution timing. Because identical calls must yield identical outputs across the primary instance and all replicas:

  • Redis resets the internal Lua pseudorandom number generator (PRNG) before every script execution.
  • The PRNG is initialized with the exact same default seed every time a script starts. Unless explicitly seeded inside the script, successive runs of identical scripts will generate the exact same sequence of pseudorandom numbers.

Forced Ordering of Non-Deterministic Data

Certain Redis commands return sets or collections whose internal memory layout does not guarantee a predictable order. For example, hash keys (HKEYS) or sets (SMEMBERS) rely on internal hash table bucketing, which can vary between Redis instances with different memory architectures or hash seeds.

  • When a Lua script invokes commands like SMEMBERS, HKEYS, HGETALL, SUNION, or SDIFF, Redis intercepts the output before passing it to the Lua runtime.
  • Redis automatically applies a lexicographical sort to the elements. This guarantees that iterations through retrieved collections execute in the exact same sequence on both the primary node and the replicas.

Non-Deterministic Command and Write Limitations

In Redis's original script-based replication model (the default prior to Redis 5.0), the entire Lua script text was sent to replicas and written to the AOF. To prevent the script from producing different writes across nodes, Redis placed strict limits on non-deterministic commands:

  • Non-Deterministic Command Flagging: Commands like TIME, SRANDMEMBER, and RANDOMKEY are flagged as non-deterministic because their output depends on the clock or internal node state.
  • Write Blocking After Non-Deterministic Calls: Once a script executes a non-deterministic read command, Redis marks the script execution state as "dirty" with non-determinism. Any subsequent call to a write command (such as SET, HSET, or DEL) is aborted with a runtime error: Write commands not allowed after non-deterministic commands.

Script Replication vs. Command Effects Replication

To reduce the friction caused by strict determinism rules, Redis 3.2 introduced—and Redis 5.0 made default—effects replication (command-based replication).

  • Instead of sending the full Lua script to replicas and the AOF, Redis records only the actual mutating commands resulting from the script execution.
  • Under effects replication, scripts can safely execute non-deterministic commands (like TIME) followed by write commands, because the replicas receive the resulting values directly rather than re-executing the logic.
  • Even with effects replication enabled, the sandbox and global variable protections remain enforced to preserve internal engine stability and prevent cross-execution state contamination.
