Profiling Lua Memory with collectgarbage("count")

In Lua, tracking memory consumption is critical for optimizing performance and preventing memory leaks, and the built-in collectgarbage("count") function serves as the primary diagnostic utility for this purpose. This article examines how collectgarbage("count") functions, its role in benchmarking and differential memory profiling, best practices for obtaining accurate allocation metrics, and the limitations developers must consider when analyzing Lua heaps.

Understanding collectgarbage("count")

Lua manages memory automatically using an internal garbage collector. The collectgarbage() function provides an interface to control and inspect this subsystem. When invoked with the "count" argument:

local memory_in_kb = collectgarbage("count")

The function returns a single floating-point number representing the total memory currently in use by the Lua state, measured in kilobytes. The integer portion represents whole kilobytes, while the fractional portion corresponds to the remaining bytes (calculated as fraction * 1024).

Key Roles in Memory Profiling

1. Differential Allocation Tracking

The most common use of collectgarbage("count") is measuring the memory footprint of specific code blocks or functions. By capturing the count before and after executing a routine, developers can determine the gross or net allocations caused by that routine.

collectgarbage("collect") -- Force a full cycle for a clean baseline
local before = collectgarbage("count")

-- Code under test
local t = {}
for i = 1, 10000 do
    t[i] = i
end

local after = collectgarbage("count")
print(string.format("Memory allocated: %.2f KB", after - before))

2. Identifying Memory Leaks

Unintended references (such as values left in global tables, improperly managed registries, or long-lived closures) prevent the garbage collector from reclaiming memory. By logging collectgarbage("count") periodically—specifically immediately after a forced collection cycle (collectgarbage("collect"))—developers can observe whether baseline memory usage continually grows over time, which signals a memory leak.

3. Churn and Temporary Allocation Monitoring

High allocation rates can degrade performance by triggering frequent garbage collection pauses. Profilers can use collectgarbage("count") to evaluate high-frequency functions (such as render loops or per-tick game updates). If the count rises dramatically between iterations, it indicates temporary table creations, string concatenations, or closure instantiations that should be pooled or cached.

Best Practices for Accurate Profiling

  • Stabilize the Collector: Because Lua's incremental garbage collector runs concurrently with execution, automatic collection can occur between your start and end measurements, leading to negative or misleading deltas. To measure raw allocation volume accurately, temporarily stop the collector:

    collectgarbage("stop")
local start_mem = collectgarbage("count")

run_workload()

local end_mem = collectgarbage("count")
collectgarbage("restart")

  • Distinguish Between Retained and Temporary Memory: To measure retained memory (objects that survived), run a full collection (collectgarbage("collect")) both before and after the target routine. To measure total memory churn (including temporary objects), disable the collector as shown above.

Limitations

While collectgarbage("count") is an essential first-line diagnostic tool, it has notable limitations:

  • Scope of Tracking: It only measures memory allocated through Lua's standard memory allocator. Memory allocated directly by third-party C libraries or native extensions via standard malloc calls remains invisible to this function unless explicitly routed through Lua’s allocation function (lua_Alloc).
  • Coarse Visibility: The call only returns aggregate memory usage for the entire Lua state. It does not provide object-level attribution, type breakdowns, or allocation call stacks. Pinpointing the exact source of an allocation spike requires combining collectgarbage("count") with custom table crawlers, the Lua Debug library, or external profilers.
