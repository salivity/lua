How LUA_PATH Overrides package.path in Lua

This article explains how the LUA_PATH environment variable controls module resolution in the Lua programming language by modifying or replacing the default package.path string. When Lua boots, it queries the environment to set up its module search templates, allowing developers to extend, alter, or completely override where the require function searches for source files. Understanding the substitution rules—specifically the double semicolon syntax—is critical for managing dependencies across different development environments.

Default Initialization of package.path

When you load a module in Lua using require("module_name"), Lua traverses a series of file path templates stored in the global variable package.path.

By default, package.path is initialized from a compile-time default configured in Lua's luaconf.h header file. This standard path usually includes common system directories such as /usr/local/share/lua/5.x/?.lua on Unix-like systems or relative paths to the Lua binary.

Environment Variable Lookup Order

Before falling back to the hardcoded defaults, the Lua interpreter checks the host operating system's environment variables. Lua checks for version-specific variables first, followed by the generic variable:

  1. LUA_PATH_X_Y (where X_Y matches the running version, such as LUA_PATH_5_4)
  2. LUA_PATH
  3. Compiled-in default path (if neither variable is set)

If a version-specific variable like LUA_PATH_5_4 is defined, it takes precedence and completely ignores LUA_PATH. If only LUA_PATH is defined, it applies across all Lua versions that do not have their version-specific variable set.

Override Mechanics: Complete Replacement vs. Appending

The replacement behavior depends strictly on whether the value of the environment variable includes two consecutive semicolons (;;).

1. Complete Replacement

If LUA_PATH contains path templates separated only by single semicolons, the default compiled-in search paths are discarded entirely.

export LUA_PATH="./src/?.lua;./modules/?.lua"

In this case, package.path becomes exactly:

./src/?.lua;./modules/?.lua

Lua will only search those two locations. System-wide installed modules will no longer be found unless explicitly defined in the variable.

2. Splicing with the Double Semicolon (;;)

Lua uses ;; as a placeholder token representing the default package.path. When Lua detects ;; within the environment variable, it expands that token into the compiled-in default string.

  • Prepending custom directories:

    export LUA_PATH="./custom/?.lua;;"

    Lua searches ./custom/?.lua first. If the file is not found, it continues searching the standard system paths.

  • Appending custom directories:

    export LUA_PATH=";;./fallback/?.lua"

    Lua searches all default system paths first, only checking ./fallback/?.lua if standard locations fail.

  • Sandwiching default paths:

    export LUA_PATH="./override/?.lua;;./fallback/?.lua"

    Lua checks ./override/?.lua, followed by all default system paths, followed finally by ./fallback/?.lua.

Path Template Syntax

package.path strings adhere to these formatting rules:

  • Templates: Semicolons (;) delimit individual search templates.
  • Wildcards: The question mark (?) is replaced by the module name passed to require().
  • Submodules: Periods in module names denote subdirectories. Calling require("a.b") causes Lua to transform the query into a/b and substitute it for ?, checking paths like ./src/a/b.lua.

Inspecting the Active Path

You can verify how LUA_PATH affects your runtime environment by running Lua directly from the command line:

lua -e 'print(package.path)'

This prints the finalized template string that Lua constructed after reading and evaluating the environment variables.
