Using LuaJIT FFI with External C Data Structures

The Foreign Function Interface (FFI) library in LuaJIT enables Lua programs to declare, instantiate, and manipulate native C data structures directly with near-native execution speed. This article explains how the FFI library parses standard C declarations, maps C structures to specialized Lua cdata objects, handles memory allocation and layout, and optimizes member access through Just-In-Time (JIT) compilation.

Parsing C Declarations with ffi.cdef

The bridge between Lua and C begins with the ffi.cdef function. It accepts a string containing standard C-syntax type declarations, such as struct, union, enum, and typedef.

local ffi = require("ffi")

ffi.cdef[[
    typedef struct {
        double x, y;
    } Point;

    typedef struct {
        int id;
        Point position;
        char name[32];
    } Entity;
]]

When ffi.cdef is called, LuaJIT parses the types using an internal C parser and registers them in an internal type registry. It uses the host platform's Application Binary Interface (ABI) rules, automatically calculating member offsets, alignments, and padding to match the target architecture exactly.

Instantiation and Memory Allocation with ffi.new

Once a type is registered, Lua code creates instances of the structure using ffi.new:

local p = ffi.new("Point", { x = 10.5, y = 20.2 })
local e = ffi.new("Entity")

The returned object has the Lua type cdata. By default, memory allocated through ffi.new is managed by LuaJIT's garbage collector. When the cdata reference leaves Lua scope, LuaJIT automatically reclaims the allocated memory without requiring an explicit free() call.

For manual or non-garbage-collected allocations, you can declare standard C memory functions (such as malloc and free) in ffi.cdef and assign pointers manually.

Direct Field Access and Array Indexing

LuaJIT exposes C structure fields through conventional Lua dot-notation and pointer dereferencing:

e.id = 101
e.position.x = 5.0
e.position.y = 12.0

Unlike traditional Lua tables, access to cdata structures does not invoke Lua hash lookups. Instead, LuaJIT performs direct byte-offset memory operations identical to compiled C code.

When interacting with C arrays inside structures, indexing follows standard C semantics rather than Lua semantics:

  • C arrays are 0-indexed (e.g., e.name[0]), unlike native Lua tables, which are 1-indexed.
  • Boundary checking is omitted in optimized code, matching raw C memory behavior.

Extending Structures with ffi.metatype

LuaJIT allows you to bind Lua metamethods directly to C types using ffi.metatype. This permits object-oriented syntax and operator overloading on low-level structs:

local Point = ffi.metatype("Point", {
    __add = function(a, b)
        return ffi.new("Point", { a.x + b.x, a.y + b.y })
    end,
    __tostring = function(p)
        return string.format("Point(%.1f, %.1f)", p.x, p.y)
    end
})

local p1 = Point(1, 2)
local p2 = Point(3, 4)
local p3 = p1 + p2

The resulting cdata maintains the compact memory layout of a native C struct while executing Lua-defined methods.

Pointers, Buffers, and Type Casting

To interact with external memory buffers or foreign APIs, the FFI provides explicit casting via ffi.cast:

local raw_ptr = ffi.cast("uint8_t*", external_memory_address)
local byte = raw_ptr[0]

ffi.cast interprets raw memory addresses as typed C pointers without copying the underlying data, making it straightforward to parse network packets, process hardware buffers, or decode binary file formats in place.

JIT Compiler Optimization

The primary advantage of LuaJIT's FFI is its deep integration with the trace compiler. When code manipulating cdata is compiled by the JIT:

  1. Elimination of Marshaling: Data is not converted into intermediate Lua types (numbers, strings, tables). The machine code reads and writes directly to native CPU registers and memory locations.
  2. Allocation Sinking: Temporary cdata allocations that do not escape a compiled trace can be eliminated completely by the compiler, placing structure values directly into CPU registers.
  3. Inlined Pointer Arithmetic: Struct field lookups and array accesses are compiled into single-instruction memory loads (MOV) using base-plus-displacement addressing modes.
