Where Lua Relocates Closed Upvalues on the Heap

In the Lua programming language, when a function frame exits, any local variables captured by inner closures must survive beyond the lifetime of the call stack. Lua transitions these captured variables from "open" upvalues to "closed" upvalues. Rather than allocating a brand-new chunk of memory elsewhere on the heap, Lua relocates the variable directly into an internal storage field inside the already heap-allocated UpVal structure itself, updating internal pointers so the closure can seamlessly access the variable without referencing the deactivated stack.

The Structure of an Upvalue

To understand the relocation process, it is necessary to examine how Lua structures upvalues in its C implementation. An upvalue in the Lua virtual machine is represented by the UpVal object (struct UpVal), which is managed by the Lua garbage collector:

  • When a closure captures a local variable from an active function, Lua creates or reuses an UpVal object on the GC heap.
  • While the enclosing function's stack frame is active, the upvalue is open. Its internal pointer (uv->v) points directly to the corresponding memory address on the Lua execution stack (TValue *).
  • All open upvalues belonging to a thread (lua_State) are linked in a sorted, singly linked list (L->openupval) to ensure that multiple closures capturing the same local variable share the exact same UpVal reference.

What Happens When a Function Exits

When a function returns, executes an OP_CLOSE instruction, or terminates due to a scope exit, its local variables on the register stack are designated for invalidation. The runtime invokes the internal C function luaF_close.

luaF_close iterates through the thread's openupval list for all upvalues that point to stack slots at or above the exiting function's stack level:

  1. Copying to the Heap Buffer: Each UpVal structure contains an embedded storage slot—specifically a TValue union field (often named u.value in the source code). When an upvalue is closed, Lua copies the TValue from the execution stack directly into this internal u.value field inside the UpVal struct.
  2. Redirecting the Pointer: The upvalue's reference pointer uv->v is updated to point directly to its own embedded u.value field (uv->v = &uv->u.value).
  3. Unlinking from the Stack List: The upvalue is decoupled from the L->openupval linked list.

Where the Data Resides

Because the UpVal container was already allocated as a garbage-collected object (GCObject) on the heap when the closure was first instantiated, no secondary memory allocation takes place.

The closed variable resides permanently within the contiguous memory block of the UpVal struct on the general Lua heap. Once closed, the value's lifetime is no longer tied to the execution stack; it is instead governed entirely by standard garbage collection reachability via whichever closures retain a reference to that UpVal.
