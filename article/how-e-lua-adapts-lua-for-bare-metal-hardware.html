How eLua Adapts Lua for Bare-Metal Hardware

The eLua (Embedded Lua) project adapts the standard Lua programming language runtime to run directly on microcontrollers without the support of an underlying operating system. This article examines the core modifications and architectural enhancements introduced by eLua, focusing on memory footprint reduction, hardware peripheral integration, integer-based execution, and bare-metal system initialization.

Bare-Metal Initialization and System Startup

Standard Lua relies on a host operating system and a full C runtime library to initialize the environment, manage I/O, and allocate resources. In contrast, eLua acts as both the runtime and the operating system. It provides minimal startup files, interrupt vector tables, and clock initialization code tailored to specific processor architectures (such as ARM7, ARM9, Cortex-M, and AVR32). Upon boot, the microcontroller configures system clocks, initializes the stack and heap, and directly launches the Lua virtual machine or drops the user into an interactive Read-Eval-Print Loop (REPL).

Memory Optimization: Lua Tiny RAM (LTR)

Microcontrollers typically feature far less RAM than Flash memory—often as little as 32 KB to 64 KB of RAM alongside several hundred kilobytes of Flash. Standard Lua duplicates core libraries, string tables, and function references into RAM at startup, consuming tens of kilobytes before running user code.

To solve this, eLua introduced the Lua Tiny RAM (LTR) patch. LTR alters the Lua runtime to allow read-only data structures—such as standard library tables, C functions, and constant strings—to remain in Flash (ROM) memory rather than being loaded into RAM. By treating these structures as statically mapped Flash entities, eLua reduces baseline RAM usage to just a few kilobytes, leaving the vast majority of memory free for user applications.

The Emergency Garbage Collector (EGC)

In desktop environments, Lua invokes its garbage collector periodically based on memory allocation metrics. On bare-metal targets with limited memory, an allocation request can easily fail if a garbage collection cycle has not run recently.

The eLua project addresses this by implementing an Emergency Garbage Collector. If a memory allocation request (malloc or equivalent) fails, the runtime forces a full garbage collection cycle immediately and retries the allocation. Only if the second attempt fails does eLua raise an "out of memory" error. This prevents unnecessary allocation aborts on systems operating close to their physical memory limits.

Floating-Point vs. Integer Numerical Representation

Standard Lua traditionally defined its primary numeric type (lua_Number) as a double-precision floating-point number. Many low-power microcontrollers lack a hardware Floating-Point Unit (FPU), making software-emulated floating-point arithmetic slow and memory-intensive.

eLua allows developers to configure the runtime build for integer-only operation. By redefining lua_Number as a 32-bit signed integer, the runtime avoids software floating-point emulation libraries, significantly reducing binary size and accelerating mathematical operations on integer-only processor cores.

Hardware Abstraction Layer (HAL)

To bridge high-level Lua scripts with low-level chip registers, eLua introduces a standardized Platform Hardware Abstraction Layer. The HAL defines a consistent C interface for common microcontroller peripherals, including:

  • General-Purpose Input/Output (GPIO)
  • Universal Asynchronous Receiver-Transmitter (UART)
  • Serial Peripheral Interface (SPI)
  • Inter-Integrated Circuit (I2C)
  • Analog-to-Digital Converters (ADC)
  • Pulse-Width Modulation (PWM)
  • Timers and Pulse Counters

The runtime exposes these HAL functions directly to Lua through dedicated native modules (e.g., pio, uart, spi). When a Lua script toggles a pin or configures a baud rate, the runtime executes the underlying C driver mapped specifically to the active processor architecture.

Filesystem and Standard I/O Redirection

Standard Lua assumes access to a POSIX or Windows filesystem and standard I/O streams (stdin, stdout, stderr). eLua integrates a lightweight virtual filesystem layer that redirects standard input and output to physical communication ports, typically a serial UART interface or USB-CDC. This enables an interactive console over a terminal emulator.

For code and data storage, eLua provides RomFS, a read-only filesystem compiled directly into the microcontroller's Flash memory alongside the firmware. It can also interface with external SPI Flash chips or SD cards running FAT filesystems via integrated libraries like FatFS, allowing scripts to be executed without reflashing the device.
