Lua package.loadlib Platform Requirements

The package.loadlib function provides low-level dynamic linking in the Lua programming language, enabling scripts to load and bind functions directly from native shared libraries. This article outlines the essential system, compilation, and architectural requirements needed for package.loadlib to function correctly across Windows, Linux, and macOS.

Universal Requirements

Regardless of the operating system, several fundamental conditions must be met:

  • Architecture Matching: The target compiled shared library must match the architecture of the Lua executable (e.g., a 64-bit Lua runtime requires a 64-bit library; a 32-bit library will fail to load).
  • ABI and Linkage: Exported C functions must use standard C calling conventions (cdecl). If using C++, the target function must be wrapped in extern "C" to prevent name mangling.
  • Function Signature: The target entry point function must match the Lua C API function prototype: int func(lua_State *L).
  • Dynamic Linking Support in Lua: The Lua interpreter itself must be built with support for dynamic loading enabled (standard in prebuilt distributions, but requires LUA_USE_DLOPEN or equivalent during manual source builds).

Windows Requirements

On Windows, package.loadlib interfaces with the Win32 API functions LoadLibraryEx and GetProcAddress.

  • Binary Format: The binary must be a standard Dynamic Link Library (.dll).
  • Symbol Exporting: The entry point function must be explicitly exported. This is typically achieved using __declspec(dllexport) in the source code or by defining the symbol in a Module-Definition (.def) file.
  • Runtime Dependencies: All dependent DLLs must be located in standard Windows search paths (the application directory, System32, or directories defined in the system PATH variable).
  • C Runtime Compatibility: While not strictly fatal for symbol loading, mismatched C Runtime (CRT) versions between Lua and the DLL can cause memory crashes if resources allocated by one CRT are freed by another.

Linux Requirements

On Linux, package.loadlib relies on the POSIX dlopen and dlsym APIs provided by libdl.

  • Binary Format: The target file must be an ELF Shared Object (.so).
  • Compilation Flags: The library source must be compiled with the -fPIC (Position Independent Code) compiler flag and linked with the -shared linker flag.
  • Dynamic Symbol Resolution: The main Lua executable must be linked with the -Wl,-E (or -rdynamic) flag if the shared library relies on symbols exported by the host Lua process. Alternatively, the library must be explicitly linked against a shared liblua.so.
  • Library Paths: If the shared object has external dependencies, they must be resolvable via standard linker paths, LD_LIBRARY_PATH, or an embedded rpath.

macOS Requirements

On macOS, dynamic loading is also implemented via dlopen and dlsym, targeting the Darwin Mach-O binary format.

  • Binary Format: The binary can be either a Mach-O dynamic library (.dylib) or a Mach-O bundle (.so). Lua convention typically favors .so.
  • Linker Flags: When compiling a plugin intended specifically for Lua, use the -bundle flag along with -undefined dynamic_lookup. The dynamic_lookup flag allows the dynamic linker to resolve Lua API symbols from the host executable at runtime without requiring direct linkage to a Lua library at build time.
  • System Integrity Protection (SIP): Libraries must adhere to Apple's code-signing requirements if running under a hardened runtime environment. Unsigned or improperly signed binaries may be blocked from dynamic loading by the OS.
