How package.preload Intercepts Module Loading in Lua

In the Lua programming language, the require function manages module loading through an extensible pipeline of searchers. At the very front of this pipeline sits the package.preload table, an in-memory registry of module loader functions. By evaluating this table before querying the filesystem or native dynamic libraries, Lua provides a built-in mechanism to intercept, mock, or bundle modules directly in memory without triggering expensive disk lookups.

The Lua Module Resolution Pipeline

When code executes require(modname), Lua does not immediately scan the disk. Instead, it follows a strict sequence of steps:

  1. Check Loaded Cache: Lua checks package.loaded[modname] to determine if the module has already been loaded. If present and not false, it returns that value immediately.
  2. Iterate Searchers: If the module is not yet loaded, Lua iterates sequentially through the functions defined in the package.searchers array (named package.loaders in Lua 5.1).
  3. Execute Loader: The first searcher function that successfully finds a loader returns that loader function, which Lua then executes to initialize the module.

How package.preload Preempts the Filesystem

The default configuration of package.searchers determines the priority of module resolution:

  • Searcher 1 (Preload Searcher): Queries package.preload[modname].
  • Searcher 2 (Lua Loader): Searches the paths in package.path for matching .lua source files.
  • Searcher 3 (C Loader): Searches the paths in package.cpath for compiled dynamic libraries (.so, .dll).
  • Searcher 4 (All-in-one C Loader): Searches for C libraries capable of exporting submodules.

Because Searcher 1 is the first entry in the array, Lua evaluates package.preload before any subsequent searcher can execute. If package.preload[modname] contains a function, Searcher 1 returns this function directly to require.

Lua treats this as a successful resolution, executes the returned function, assigns the result to package.loaded[modname], and halts the searcher pipeline. Consequently, Searcher 2 and Searcher 3 are never called, entirely bypassing filesystem lookups against package.path and package.cpath.

Implementation Example

To intercept a module, you assign a loader function directly to the package.preload table matching the desired module name:

-- Define an in-memory loader for "database"
package.preload["database"] = function(modname)
    local db = {}
    function db.connect()
        return "Connected to in-memory database"
    end
    return db
end

-- 'require' resolves immediately via package.preload
local db = require("database")
print(db.connect()) -- Output: Connected to in-memory database

Even if a file named database.lua exists in the working directory or anywhere on package.path, Lua ignores it because the preload searcher successfully resolves the request first.

Common Use Cases

  • Embedded Executables: Bundling multiple Lua source files into a single binary by compiling them into bytecode arrays and registering them in package.preload during host application initialization.
  • Unit Testing and Mocking: Overriding hardware, network, or file-dependent modules with stubbed implementations during test execution without altering source code.
  • Performance Optimization: Eliminating file system overhead for core libraries by keeping their loading routines pre-compiled in memory.
