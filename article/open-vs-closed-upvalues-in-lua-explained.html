Open vs Closed Upvalues in Lua Explained

In the Lua programming language, closures capture external local variables through a mechanism known as upvalues. During execution, Lua distinguishes between open upvalues—which refer directly to variables still living on the execution stack—and closed upvalues—which have been migrated to heap-allocated memory once their defining scope exits. This distinction allows Lua to maintain shared state among multiple closures efficiently without keeping expired stack frames alive.

What Is an Upvalue?

When an inner function in Lua accesses a local variable defined in an enclosing outer function, that variable is called an upvalue. Because functions are first-class values that can escape their defining scope (for instance, being returned or passed as callbacks), Lua must guarantee that the captured variable remains accessible and mutable even after the outer function finishes executing.

Open Upvalues

An upvalue is open as long as the variable it references is currently active on the Lua execution stack.

  • Stack Reference: An open upvalue does not hold its own copy of the data. Instead, it contains a pointer that directly references the slot on the stack where the local variable resides.
  • Shared State: If multiple inner closures reference the same local variable while it is active on the stack, the Lua Virtual Machine (VM) ensures they all point to the identical open upvalue structure.
  • The Open Upvalue List: The Lua execution state (lua_State) maintains a linked list of all active open upvalues, ordered by their position on the stack. This list allows the runtime to quickly find existing upvalues and coordinate their lifecycle.

Because the variable is read and written directly on the stack, operations on open upvalues are fast and incur minimal memory overhead.

Closed Upvalues

An upvalue becomes closed when the scope containing the target local variable terminates.

  • Triggering Closure: When an execution frame exits (such as when an outer function returns) or a lexical block terminates, the Lua VM executes instructions like OP_CLOSE or handles closure cleanup during OP_RETURN.
  • Value Migration: The VM traverses the open upvalue list for any upvalues pointing to stack positions that are about to be destroyed. For each matching upvalue, Lua copies the variable's value from the stack directly into dedicated internal storage inside the upvalue struct itself.
  • Pointer Redirection: The internal pointer within the upvalue is updated to point to its own internal storage rather than the stack slot.
  • Removal from the List: Once converted, the upvalue is unlinked from the state's list of open upvalues.

From this point forward, the upvalue is managed independently by Lua's garbage collector. It persists as long as at least one closure maintains a reference to it.

Comparison Summary

Characteristic Open Upvalue Closed Upvalue
Storage Location Stack frame of the enclosing function Internal storage inside the upvalue object
Lifecycle Bound to the active scope of the local variable Bound to the lifetime of the closures referencing it
VM Tracking Tracked in the lua_State linked list Untracked by the stack list; managed by the Garbage Collector
Transition Initial state upon closure instantiation Triggered by OP_CLOSE or function exit (OP_RETURN)

This dual-state mechanism provides optimal performance: variables remain on the cache-friendly execution stack for as long as possible, shifting to heap storage only when the function finishes and persistent closure semantics demand it.
