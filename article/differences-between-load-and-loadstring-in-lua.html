Differences Between load and loadstring in Lua

In Lua, dynamically compiling and executing code chunks at runtime has evolved significantly across major releases. This article explains the functional differences between loadstring and load, tracing their distinct roles in Lua 5.1, the consolidation and feature expansion introduced in Lua 5.2, and the complete removal of loadstring in Lua 5.3 and 5.4.

Lua 5.1: Separation of Input Types

In Lua 5.1, loadstring and load served mutually exclusive purposes based entirely on the data type of the code being compiled:

  • loadstring(string [, chunkname]): Specifically designed to parse code supplied as an in-memory string. It compiles the chunk and returns it as a function. If compilation fails, it returns nil plus the error message.
  • load(func [, chunkname]): Designed to load chunks piece-by-piece via a reader function. Each time Lua needed more data, it invoked func. The function was expected to return successive string pieces until returning nil or an empty string to signal the end of the stream. Passing a raw string directly to load in Lua 5.1 caused an error.

In this version, neither function supported sandboxing parameters natively. Scoping code to an isolated environment required modifying the resulting function using setfenv.

Lua 5.2: Unification and Sandboxing Improvements

Lua 5.2 fundamentally changed this dynamic by expanding load to handle both strings and reader functions, rendering loadstring redundant.

The signature of load was updated to:

load(ld [, source [, mode [, env]]])

The functional changes introduced in Lua 5.2 include:

  • Dual Input Support: The ld parameter accepts either a string or a reader function. If ld is a string, load operates identically to the legacy loadstring.
  • Execution Environment (env): Lua 5.2 removed setfenv in favor of lexical environments (_ENV). The fourth parameter of load allows developers to directly assign an environment table to the compiled chunk's global scope, making secure sandboxing significantly easier.
  • Safety Modes (mode): The third parameter controls the binary format of the code. It accepts "b" (binary bytecode only), "t" (text source code only), or "bt" (both, which is the default). This prevents arbitrary bytecode injection attacks by allowing applications to reject precompiled bytecode.
  • Deprecation of loadstring: While retained solely for backward compatibility, loadstring was implemented merely as an alias calling load(string).

Lua 5.3 and Lua 5.4: Removal of loadstring

In Lua 5.3 and Lua 5.4, loadstring was completely removed from the standard library. Codebases running on modern Lua versions must use load for all dynamic code compilation tasks.

If legacy code containing loadstring must be run on Lua 5.3+, developers must either enable backward-compatibility flags during Lua compilation (LUA_COMPAT_5_2 or LUA_COMPAT_5_1) or define a polyfill in Lua code:

loadstring = load
