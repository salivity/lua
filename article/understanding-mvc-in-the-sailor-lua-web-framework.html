Understanding MVC in the Sailor Lua Web Framework

Sailor is an open-source, lightweight MVC (Model-View-Controller) web framework written in Lua that structures web applications into distinct, maintainable layers. This article explains how Sailor implements the MVC architectural pattern, detailing how requests are routed, how controllers process application logic, how models manage data schema and validation, and how dynamic Lua Pages render the user interface.

Request Routing and Application Structure

Sailor projects follow an organized directory convention separating models, views, and controllers. Incoming HTTP requests are intercepted by the framework's core dispatcher, which translates the URL path into a controller and action name using the conventional /controller/action format. If not explicitly specified, requests default to the main controller and index action. The router initializes a page context table that is passed along to the designated controller.

Controllers: The Orchestration Layer

Controllers in Sailor are Lua modules placed inside the /controllers directory. A controller file returns a table containing functions that represent distinct actions available to users.

Each action receives a page object representing the current HTTP transaction. The controller handles incoming user input via page.GET and page.POST, interacts with the data models, sets layout variables, and specifies which view to display using the page:render() method.

local sailor = require "sailor"
local user_controller = {}

function user_controller.view(page)
    local User = sailor.model("user")
    local user_record = User:find_by_id(page.GET.id)

    page:render("view", {
        user = user_record
    })
end

return user_controller

Models: Data and Validation

Models reside in the /models directory and represent the data layer. Sailor provides an object-relational mapping (ORM) layer that connects Lua tables to relational databases, such as MySQL, SQLite, or PostgreSQL.

A Sailor model defines attributes, relations, and validation rules using the valua validation library. This centralizes business logic and data integrity checks, ensuring that invalid data cannot be persisted to the database.

local user_model = {
    attributes = {
        { id = "number" },
        { username = "string" },
        { email = "string" }
    },
    rules = {
        { "username", "presence" },
        { "email", "email" }
    }
}

return user_model

When instantiated in a controller, models provide built-in methods such as :find(), :save(), and :validate() to interact with the underlying database storage without writing raw SQL queries.

Views: Lua Pages (LP)

Views represent the presentation tier and are located under the /views/<controller_name>/ path. Sailor uses Lua Pages (.lp) for templating, allowing developers to embed standard Lua code within HTML documents using template tags similar to PHP or ERB:

  • <% ... %>: Executes Lua logic (such as loops and conditionals) without outputting values.
  • <%= ... %>: Evaluates a Lua expression and outputs the result into the HTML markup.

Variables passed into page:render() by the controller are made globally accessible within the view template:

<h1>User Profile</h1>
<% if user then %>
    <p>Username: <%= user.username %></p>
    <p>Email: <%= user.email %></p>
<% else %>
    <p>User not found.</p>
<% end %>

The Request Lifecycle

  1. Dispatch: An incoming request arrives, and Sailor routes it to the corresponding controller and action.
  2. Execution: The controller action evaluates input, queries the model for necessary data, and enforces application logic.
  3. Data Retrieval: The model validates schemas and interacts with the database driver to return plain Lua tables or model instances.
  4. Rendering: The controller invokes page:render(), which merges the retrieved data with the corresponding .lp view and project layout.
  5. Response: The completed HTML markup is transmitted back to the client as an HTTP response.
