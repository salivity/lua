Assign Environments in Lua Using load

This article provides a concise guide on using the fourth argument of the load function in modern Lua (5.2 and later) to set custom execution environments for dynamically loaded code. By supplying an environment table directly during the compilation step, developers can isolate execution contexts, create secure sandboxes, and supply custom globals without resorting to legacy functions like setfenv.

The Syntax of load

Starting with Lua 5.2, the unified load function replaced older mechanisms for parsing code strings and streams. The function signature is:

load(chunk [, chunkname [, mode [, env]]])
  • chunk: A string or a reader function providing the Lua source or bytecode.
  • chunkname: A label for the chunk used in error messages and debug information.
  • mode: A string controlling chunk type: "b" for binary bytecode only, "t" for text source only, or "bt" for both (the default).
  • env: The target environment table assigned to the first upvalue of the loaded chunk (_ENV).

If the fourth argument is omitted, Lua automatically assigns the current global environment (_G) as the chunk's _ENV.

Assigning a Custom Environment

To assign a custom environment, you must provide values for the second and third arguments (chunkname and mode) so that the environment falls into the correct fourth parameter position.

-- Define a restricted environment
local sandboxed_env = {
    x = 10,
    y = 20,
    print = print -- explicitly grant access to print
}

local code = "print(x + y)"

-- Compile the code with the custom environment
local fn, err = load(code, "dynamic_chunk", "t", sandboxed_env)

if not fn then
    error("Compilation error: " .. err)
end

-- Execute the loaded function
fn() -- Outputs: 30

Inside dynamic_chunk, free variable lookups resolve through sandboxed_env. Standard global functions, such as os.execute or io.open, are inaccessible unless deliberately included in sandboxed_env.

Inheriting from the Global Environment

Often, an environment needs custom variables or sandboxed overrides while still maintaining read access to the rest of Lua's standard library. This is achieved by attaching a metatable with an __index metamethod pointing to _G:

local custom_env = {
    custom_val = 42
}

-- Fallback to _G for standard library access
setmetatable(custom_env, { __index = _G })

local code = "print('Value:', custom_val, 'Math Pi:', math.pi)"
local fn = assert(load(code, "inherited_env_chunk", "t", custom_env))

fn() -- Outputs: Value: 42    Math Pi: 3.1415926535898

Any new global variables defined inside the evaluated chunk are stored exclusively inside custom_env, keeping the root _G unmodified.
