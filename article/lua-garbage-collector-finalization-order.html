Lua Garbage Collector Finalization Order

In the Lua programming language, when multiple dead objects are collected during the same garbage collection cycle, their finalizers are executed in the reverse order of their creation. This Last-In, First-Out (LIFO) order ensures that objects created later—which often depend on objects created earlier—can safely access their dependencies during cleanup. Understanding this execution order is essential for managing resources such as file handles, memory allocations, and network sockets without running into dangling references.

The Finalization Sequence: Reverse Order of Creation

Lua executes finalizers (the __gc metamethod) in the exact reverse order that the objects were marked for finalization.

When a program creates a table or userdata with a valid __gc metamethod, Lua places that object onto an internal finalization list. Because Lua adds newly registered objects to the head of this list, traversing the list during the sweep phase processes the most recently added objects first.

As a result:

  • If Object A is created first, and Object B is created second, Object B's finalizer will execute before Object A's finalizer.
  • This LIFO behavior applies to all objects that become unreachable and are scheduled for finalization in the same collection cycle.

Dependency Management and Safety

The reverse-order mechanism is deliberately designed to solve dependency issues in software architecture.

In typical application flows, dependent objects are initialized after their prerequisites. For example, a buffered stream wrapper is created after the underlying file descriptor is opened. Because Lua finalizes objects in reverse order, the stream wrapper's finalizer runs first, allowing it to flush buffered data safely to the underlying file descriptor. The file descriptor's finalizer runs afterward, closing the handle only after all dependent wrappers have finished their cleanup.

If two objects hold circular references to each other, Lua cannot infer a logical dependency based on hierarchy. In this scenario, Lua still strictly adheres to the creation order rule, finalizing whichever object was created last, followed by the earlier one.

Internal Collection and Resurrection

The full lifecycle of finalization in Lua proceeds through specific phases:

  1. Detection: During the mark phase, the collector identifies unreachable objects that possess a __gc metamethod.
  2. Transfer: These unreachable objects are moved from the main finalization list to a separate "to-be-finalized" list (tobefnz), preserving their relative reverse creation order.
  3. Resurrection: To run the __gc metamethod safely, Lua temporarily resurrects each object, making it accessible again during the execution of its finalizer.
  4. Execution: The collector iterates through the list, invoking each __gc function with the object passed as its parameter.
  5. Re-collection: Once the finalizer completes, the object loses its finalizer flag. It is collected permanently and its memory is reclaimed during the subsequent garbage collection cycle, provided it was not permanently stored back into a global or reachable scope during finalization.
