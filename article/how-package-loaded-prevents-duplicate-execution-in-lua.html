How package.loaded Prevents Duplicate Execution in Lua

In the Lua programming language, the require function relies on an internal registry table named package.loaded to implement module caching and prevent the redundant execution of scripts. When a file or module is requested, Lua checks this table before searching the filesystem or running any code. If an entry for the specified module already exists, Lua immediately returns the cached value rather than loading and executing the file again. This article explains the internal mechanics of package.loaded, the step-by-step execution lifecycle of the require function, and how this caching strategy maintains state and performance.

The Lifecycle of a require Call

When you invoke require("module_name"), Lua follows a strict sequence to locate and load the requested code:

  1. Cache Inspection: Lua queries package.loaded["module_name"]. If the key exists and its value is anything other than false or nil, require halts further operations and immediately returns that value.
  2. Search Phase: If the value is not present, Lua iterates through searchers (defined in package.searchers in Lua 5.2+ or package.loaders in Lua 5.1) to locate the file on disk or identify a C library.
  3. Execution Phase: Once the loader finds the file, it compiles the chunk and executes it as a function.
  4. Cache Population: Lua assigns the return value of that executed chunk directly to package.loaded["module_name"]. If the chunk does not explicitly return a value, Lua assigns true to that key instead.
  5. Return: The assigned value in package.loaded["module_name"] is returned to the caller.

Preventing Duplicate Execution and Side Effects

Because Lua populates package.loaded during the initial load, any subsequent calls to require("module_name") in any file within the same Lua state will trigger step 1 and exit early.

This mechanism provides two primary benefits:

  • Elimination of Redundant Overhead: Parsing and compiling source files, performing filesystem I/O, and evaluating top-level code chunks are computationally expensive. Checking an in-memory hash table eliminates this overhead on subsequent imports.
  • Preservation of Module State (Singletons): Top-level variables and local state within a required file are executed only once. Every subsequent file that imports the module receives a reference to the exact same table or object, enabling shared state across disparate parts of an application.

Handling Circular Dependencies

The package.loaded table also acts as a safeguard against infinite loops caused by circular dependencies. When a module execution begins, Lua temporarily sets package.loaded["module_name"] to a sentinel boolean value (typically true) before the file finishes executing. If module A requires module B, and module B requires module A, module B will receive this sentinel value from package.loaded rather than causing an infinite recursion of file executions.

Manual Cache Invalidation

Because package.loaded is a standard Lua table exposed globally, developers can manipulate it directly. Setting package.loaded["module_name"] = nil purges the cached entry. The next time require("module_name") is called, Lua will be forced to search the filesystem, recompile, and execute the file from scratch, confirming that package.loaded is the sole gatekeeper controlling execution prevention.
