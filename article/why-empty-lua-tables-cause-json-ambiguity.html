Why Empty Lua Tables Cause JSON Ambiguity

In the Lua programming language, a single data structure called a table serves as both an associative map and an ordered list. When serializing Lua data into JSON, this unified design creates a fundamental ambiguity: an empty table {} contains no keys, values, or metadata to indicate whether it represents a JSON object ({}) or a JSON array ([]). Because JSON strictly distinguishes between these two structures, serializers must guess the programmer's intent, frequently resulting in type mismatches, broken API contracts, and schema validation failures in downstream applications.

The Unified Design of Lua Tables

Unlike most programming languages, Lua does not provide distinct native types for arrays and hash maps. Instead, it provides only the table type.

  • To represent an array, Lua uses a table with sequential integer keys starting at index 1 (e.g., { "apple", "banana" }, which internally maps 1 -> "apple" and 2 -> "banana").
  • To represent an object or dictionary, Lua uses a table with string or non-numeric keys (e.g., { name = "Alice", role = "admin" }).

Because these implementations share the same underlying structure, the categorization of a table depends entirely on the keys it holds at runtime.

JSON's Strict Structural Separation

JSON enforces a clear boundary between collections:

  • An Array ([...]) is an ordered list of values accessed by zero-based sequential indices.
  • An Object ({...}) is an unordered collection of key-value pairs where keys must be strings.

Strict parsers and schema validators in receiving environments (such as TypeScript, Python, or relational databases using JSON columns) treat [] and {} as incompatible types. Receiving an object where an array was expected—or vice versa—often produces runtime exceptions.

The Source of the Ambiguity

When a Lua table contains data, a JSON serializer can inspect its keys to deduce the correct JSON representation:

  • If the keys are consecutive integers starting at 1, the library serializes the table to a JSON array.
  • If the keys are strings or non-sequential integers, the library serializes the table to a JSON object.

However, an empty table {} contains zero keys. The serializer cannot inspect key types or sequences because none exist. A table defined as local data = {} could represent an empty list of users intended to become [], or it could represent an empty profile object intended to become {}. Because the Lua runtime treats both intentions identically, the serializer lacks the context required to make a deterministic decision.

How Lua JSON Libraries Resolve the Issue

Because the language offers no built-in distinction, JSON libraries in the Lua ecosystem adopt different strategies to handle empty tables:

  1. Defaulting to One Type: Many libraries default to encoding all empty tables as either objects ({}) or arrays ([]). This frequently requires developers to fix anomalies when the chosen default does not match the target schema.
  2. Sentinel Values and Metatables: Advanced libraries (such as lua-cjson) provide explicit sentinels or metatable markers. For example, assigning a special metatable—like setmetatable({}, cjson.empty_array_mt)—explicitly instructs the encoder to produce [] instead of {}.
  3. Schema-Driven Encoding: Some serializers allow developers to pass a predefined schema alongside the data, enforcing the intended target type regardless of whether the table currently contains elements.

Without these explicit workarounds, the architectural difference between Lua's flexible single-table design and JSON's dual-type system makes ambiguous serialization inevitable.
