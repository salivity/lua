Lua Rockspec Dependencies and Build Rules Guide

A .rockspec file is a Lua-based manifest used by LuaRocks, the package manager for the Lua programming language, to distribute and install modules. This article provides a focused breakdown of how a .rockspec defines project dependencies, external libraries, and build mechanisms, explaining the syntax and execution models that govern module installation.

Defining Dependencies

Dependencies in a .rockspec file are declared within the dependencies table as an array of strings. Each entry specifies a required rock name followed by optional version constraints.

dependencies = {
   "lua >= 5.1, < 5.5",
   "luafilesystem >= 1.8.0",
   "dkjson ~> 2.5"
}

Version constraints support comparison operators such as ==, ~=, >, <, >=, <=, and ~> (compatible release).

Lua itself must be listed as a dependency if your project targets specific interpreter versions.

External System Dependencies

When a module relies on C libraries or header files provided by the host operating system rather than LuaRocks, they are declared in the external_dependencies table.

external_dependencies = {
   OPENSSL = {
      header = "openssl/ssl.h",
      library = "ssl"
   }
}

LuaRocks verifies that these files exist before attempting to build. During the build process, the locations are exposed via variables (e.g., $(OPENSSL_INCDIR) and $(OPENSSL_LIBDIR)).

Defining Build Rules

The build table governs how LuaRocks compiles and installs files. It requires a type field that determines the build driver to use.

The builtin Build Type

The builtin type is the default and most portable build method. It handles both pure-Lua projects and simple C extensions without requiring an external build tool like Make or CMake.

Files and compilation targets are defined inside the modules sub-table:

build = {
   type = "builtin",
   modules = {
      -- Pure Lua module: maps require path to file path
      ["mymodule"] = "src/mymodule.lua",
      ["mymodule.helper"] = "src/helper.lua",

      -- C extension: compiles source files into a shared library
      ["mymodule.core"] = {
         sources = { "src/core.c", "src/util.c" },
         libraries = { "ssl" },
         incdirs = { "$(OPENSSL_INCDIR)" },
         libdirs = { "$(OPENSSL_LIBDIR)" }
      }
   },
   copy_directories = { "doc", "samples" }
}

In the builtin model:

  • Pure Lua keys map the module's require() name to the local .lua file path.
  • C modules specify arrays of source files, header search paths (incdirs), library search paths (libdirs), and link libraries (libraries).

External Build Systems (make, cmake, and command)

For projects with advanced build setups, LuaRocks can delegate compilation to external tools:

  • make: Invokes a Makefile. You can supply build_variables and install_variables to pass compiler flags and install targets.
  • cmake: Invokes CMake to generate platform-native build files and compile them, passing LuaRocks paths automatically.
  • command: Runs arbitrary shell commands for building and installing.

Example using cmake:

build = {
   type = "cmake",
   cmake = "CMakeLists.txt",
   variables = {
      LUA_INCDIR = "$(LUA_INCDIR)",
      CMAKE_INSTALL_PREFIX = "$(PREFIX)"
   }
}

Platform-Specific Overrides

A .rockspec can conditionally override dependencies and build rules for specific operating systems (such as windows, linux, macosx, or posix) using the platforms table:

platforms = {
   windows = {
      dependencies = {
         "luawinapi >= 1.0"
      },
      build = {
         modules = {
            ["mymodule.platform"] = "src/windows.c"
         }
      }
   }
}

When LuaRocks processes the file, values defined inside a matching platform block merge into and overwrite the top-level definitions.
