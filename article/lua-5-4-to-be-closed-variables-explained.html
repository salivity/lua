Lua 5.4 To-be-closed Variables Explained

Lua 5.4 introduced to-be-closed variables to provide deterministic resource management, functioning similarly to the using statement in C# or Python's with blocks. This article breaks down how to declare to-be-closed variables using the <close> attribute, how the underlying __close metamethod works, how Lua handles errors during scope termination, and how to implement custom cleanup logic in your code.

What Are To-be-closed Variables?

In Lua versions prior to 5.4, cleanup tasks—such as closing file descriptors, releasing locks, or terminating database connections—relied heavily on garbage collection finalizers (__gc) or verbose pcall/xpcall wrappers. Garbage collection is non-deterministic, meaning resources could linger in memory long after they were no longer needed.

To-be-closed variables solve this by tying resource cleanup directly to lexical scope. When a block containing a to-be-closed variable exits, Lua immediately and automatically executes the cleanup routine, regardless of whether the block finished normally, executed a break or return, or encountered a runtime error.

Syntax and Basic Usage

A to-be-closed variable is declared using the <close> attribute immediately following the variable name during a local declaration:

local function readFile(path)
    local file <close> = io.open(path, "r")
    if not file then return nil end
    return file:read("*a")
end

In this example, standard file handles in Lua 5.4 come with built-in support for closing. Even if file:read("*a") raises an error or the function returns early, Lua guarantees that file:close() is invoked the moment execution leaves the function's scope.

The __close Metamethod

The cleanup behavior of a to-be-closed variable is governed by the __close metamethod. When a <close> variable exits its scope, Lua checks its metatable for this method and calls it.

The __close method receives two arguments:

  1. The value bound to the to-be-closed variable.
  2. An error object, if the scope exited due to a raised error, or nil if the scope exited normally.

Here is an example of creating a custom resource with deterministic cleanup:

local function createLock(name)
    local lock = { name = name }
    
    local mt = {
        __close = function(self, err)
            if err then
                print(string.format("Releasing lock '%s' after error: %s", self.name, tostring(err)))
            else
                print(string.format("Releasing lock '%s' normally.", self.name))
            end
        end
    }
    
    return setmetatable(lock, mt)
end

do
    local myLock <close> = createLock("DatabaseLock")
    print("Performing protected operations...")
end
-- Output:
-- Performing protected operations...
-- Releasing lock 'DatabaseLock' normally.

Execution Order and Error Handling

When using multiple to-be-closed variables within the same scope, Lua finalizes them in the reverse order of their declaration (last-in, first-out):

do
    local first <close> = createLock("First")
    local second <close> = createLock("Second")
end
-- "Second" is closed before "First"

If an error occurs inside a block, Lua runs the __close methods of all active to-be-closed variables before propagating the error upward. If an error also occurs inside a __close metamethod itself, Lua replaces the original error with the new one, but still guarantees that the remaining to-be-closed variables in the scope are executed.

Requirements and Limitations

  • Local Variables Only: The <close> attribute can only be applied to local declarations. Global variables and table fields cannot be declared as to-be-closed.
  • Metamethod Requirement: The assigned value must have a valid __close metamethod attached to its metatable at the time it goes out of scope, unless the value is nil or false. If a variable with a <close> attribute evaluates to nil or false, the cleanup step is silently skipped.
