How to Run Lua Close Handlers with os.exit

In Lua 5.4 and later, to-be-closed variables allow developers to define cleanup logic that automatically triggers when a variable goes out of scope. However, terminating a script prematurely with os.exit normally bypasses these handlers by default. This article explains how to properly configure the second argument of os.exit to guarantee that all active <close> metamethods run before the process terminates.

Understanding the os.exit Function

The standard os.exit function accepts two optional parameters:

os.exit([code [, close]])
  1. code: A boolean or integer representing the exit status returned to the host environment (default is true, representing success).
  2. close: A boolean indicating whether to close the primary Lua state before exiting (default is false).

When os.exit is called with only an exit code, or with close set to false, the Lua runtime immediately calls the host system's exit function. This halts execution instantly without unwinding the call stack, preventing any pending to-be-closed variables (<close>) or garbage collector finalizers (__gc) from executing.

Enabling Close Handlers

To force Lua to invoke active close handlers upon termination, you must explicitly pass true as the second argument:

os.exit(0, true)

Setting close to true directs Lua to call lua_close on the main Lua state prior to process termination. This process closes all active to-be-closed variables on the call stack and triggers their corresponding __close metamethods in reverse order of declaration.

Implementation Example

The following code illustrates how to define a to-be-closed resource and exit cleanly:

-- Define a closable resource
local function create_resource(name)
    return setmetatable({ name = name }, {
        __close = function(self, err)
            print("Cleaning up resource: " .. self.name)
        end
    })
end

local function main()
    -- Declare to-be-closed variables
    local res1 <close> = create_resource("DatabaseConnection")
    local res2 <close> = create_resource("FileHandle")

    print("Working with resources...")

    -- Terminate execution while ensuring cleanup occurs
    os.exit(0, true)
end

main()

Output:

Working with resources...
Cleaning up resource: FileHandle
Cleaning up resource: DatabaseConnection

If os.exit(0) or os.exit(0, false) had been used instead, the output would simply read Working with resources..., skipping the cleanup phase entirely.

Key Considerations

  • Scope Coverage: Only to-be-closed variables currently in active scopes on the main thread will be executed when the state closes.
  • Coroutines: Pending to-be-closed variables inside suspended coroutines are not automatically closed unless the coroutines themselves are explicitly closed using coroutine.close.
  • Error Handling: The __close metamethod receives the error object as its second argument if the scope exited due to an error; when exited via os.exit(code, true), this error parameter is nil.
