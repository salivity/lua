Lua __pairs Metamethod: Custom Table Iteration

The __pairs metamethod in modern Lua allows developers to override default table traversal, providing full control over how for ... in pairs(t) loops inspect and return data. Introduced in Lua 5.2, this metamethod intercepts the standard pairs() call to return custom iterator functions, enabling developers to iterate over encapsulated proxy tables, filter internal properties, or output keys in a predetermined order.

Default Iteration vs. Custom Metamethods

In standard Lua operations without metamethods, calling pairs(t) returns three values: the built-in traversal function next, the table t itself, and an initial nil state. The generic for loop then repeatedly calls next(t, key) until the iterator returns nil.

When working with abstract data types, proxy tables, or encapsulated objects, standard iteration often fails or exposes internal implementation details. The __pairs metamethod bridges this gap by acting as an interceptor. When pairs(t) is called, Lua checks the table's metatable for the __pairs key. If present, Lua invokes that metamethod and returns its results directly to the generic for loop, bypassing the default next mechanism.

The Structure of the __pairs Return Value

To satisfy the contract of a Lua generic for loop, a __pairs function must return three components:

  1. Iterator Function: A function that receives the state and the current key, returning the next key and value.
  2. State: An invariant state passed back to the iterator on every step (often the table itself, or an internal data store).
  3. Initial Key: The starting index or key, typically nil.

If __pairs does not return an iterator function, Lua raises a runtime error when the for loop attempts to execute.

Implementing __pairs

Consider a proxy table pattern where data is stored in a private sub-table, preventing direct key access while still permitting iteration:

local function make_proxy(data)
    local proxy = {}
    local mt = {
        -- Redirect normal lookups to the internal store
        __index = data,
        
        -- Override iteration to traverse the private data store
        __pairs = function(_)
            -- Return custom iterator, state, and initial key
            return next, data, nil
        end
    }
    return setmetatable(proxy, mt)
end

local internal_data = { alpha = 1, beta = 2, gamma = 3 }
local secure_table = make_proxy(internal_data)

for k, v in pairs(secure_table) do
    print(k, v)
end

In this implementation, iterating over secure_table behaves identically to iterating over internal_data, even though secure_table itself contains no keys.

Modifying Traversal Order

The __pairs metamethod can also enforce sorted key iteration, which is impossible with the unordered nature of default hash tables:

local function sorted_pairs(tbl)
    local keys = {}
    for k in next, tbl do
        table.insert(keys, k)
    end
    table.sort(keys)

    local i = 0
    -- The custom iterator function
    local function iterator()
        i = i + 1
        local key = keys[i]
        if key ~= nil then
            return key, tbl[key]
        end
    end

    return iterator, tbl, nil
end

local ordered_table = setmetatable({ z = 26, a = 1, m = 13 }, {
    __pairs = sorted_pairs
})

for k, v in pairs(ordered_table) do
    print(k, v) -- Always outputs in alphabetical order: a, m, z
end

Version Considerations

  • Lua 5.1 and LuaJIT: Lua 5.1 does not support __pairs. LuaJIT supports __pairs only when compiled with the 5.2 compat flag enabled.
  • Lua 5.2 and 5.3: Fully support __pairs for pairs(). Lua 5.2 also supported __ipairs, but __ipairs was deprecated in 5.3 in favor of relying on standard indexing (__index) within ipairs().
  • Lua 5.4: Maintains native support for __pairs, allowing seamless custom iteration alongside features like to-be-closed variables and generational garbage collection.
