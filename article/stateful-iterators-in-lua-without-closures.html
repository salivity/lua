Stateful Iterators in Lua Without Closures

This article examines how to implement stateful iterators in the Lua programming language without relying on closure factories. While closures are the default convention for holding transient state across iterations, Lua's generic for loop inherently supports state preservation via explicit invariant states and control variables. By utilizing mutable tables, metamethods, and the built-in semantics of generic for loops, developers can efficiently maintain complex traversal state—such as tree branching, graph traversals, or parsing context—while minimizing memory allocations and avoiding closure overhead.

The Mechanism of Lua's Generic for

A generic for loop in Lua operates using three components returned by an iterator construction expression:

  1. An iterator function: Called at each step with two arguments (the invariant state and the control variable).
  2. An invariant state: A value passed unchanged to every invocation of the iterator function.
  3. An initial value for the first variable: The initial control variable passed to the first iteration.

The syntax for var_1, ..., var_n in explist do internally executes a loop equivalent to:

local f, s, var = explist
while true do
    local var_1, ..., var_n = f(s, var)
    var = var_1
    if var == nil then break end
    -- loop body
end

By supplying a mutable reference—such as a table—as the invariant state s, the iterator function f can read and modify arbitrary tracking variables without capturing an upvalue.

Using a Mutable Table as Invariant State

When traversing complex structures like trees or graphs, you often need a stack or a queue to keep track of unvisited nodes. Instead of capturing this stack inside a closure, place the stack inside a dedicated state table passed as the invariant state. The iterator function itself remains a single, static function that can be allocated once and shared globally.

Here is an example implementing a depth-first binary tree traversal:

-- Static iterator function (no closure, allocated once)
local function tree_iterator(state, _)
    local stack = state.stack
    if #stack == 0 then
        return nil
    end

    -- Pop the current node
    local node = table.remove(stack)

    -- Push children to stack (right child first for left-to-right order)
    if node.right then
        table.insert(stack, node.right)
    end
    if node.left then
        table.insert(stack, node.left)
    end

    return node.value, node
end

-- Constructor returning the static function, mutable state, and initial key
local function traverse_tree(root)
    if not root then
        return function() return nil end
    end
    
    local state = {
        stack = { root }
    }
    
    return tree_iterator, state, nil
end

To run the loop:

local tree = {
    value = "root",
    left = { value = "left_child" },
    right = { value = "right_child" }
}

for value, node in traverse_tree(tree) do
    print(value)
end

In this pattern:

  • tree_iterator is a standalone function with zero upvalues.
  • The state table acts as the invariant state and stores the navigation stack.
  • Each iteration modifies state.stack, maintaining traversal context directly across calls.

Callable State Objects via the __call Metamethod

Another approach to managing complex iteration state is to make the state table itself callable. By assigning a metatable with a __call metamethod to the state object, the object serves as both the iterator function and the state container.

local ComplexIterator = {}
ComplexIterator.__index = ComplexIterator

function ComplexIterator:new(data_source)
    local instance = {
        source = data_source,
        index = 1,
        history = {}
    }
    return setmetatable(instance, self)
end

function ComplexIterator:__call()
    if self.index > #self.source then
        return nil
    end

    local current_item = self.source[self.index]
    table.insert(self.history, current_item)
    self.index = self.index + 1

    return current_item, self.index - 1
end

local function iterate(data)
    local state_obj = ComplexIterator:new(data)
    -- Returns the callable object itself; state and control are handled internally
    return state_obj
end

Used in a loop:

for item, index in iterate({"alpha", "beta", "gamma"}) do
    print(index, item)
end

When Lua invokes a table as a function, it passes the table itself as the first parameter to __call, allowing the object to modify its internal properties (self.index, self.history) seamlessly.

Benefits Over Closures

  • Memory Efficiency: Static iterator functions can be declared once at file scope. Only the state table is allocated per loop invocation, eliminating closure allocations and garbage collection pressure in tight loops.
  • Serialization and Resumption: Because all traversal context resides in standard table fields rather than internal Lua upvalues, the iteration state can be inspected, serialized, paused, or cloned at any arbitrary point in the traversal.
  • Testability: The iterator logic is decoupled from state instantiation, allowing the step function to be unit-tested directly by providing mock state tables.
