How Lua require Searches package.path

In the Lua programming language, the require function is the standard mechanism for loading external code modules. When given a module name, require consults the package.path string to locate pure Lua source files by substituting the requested module name into a series of predefined path templates. This article explains how Lua formats module identifiers, iterates through package.path templates, checks for matching files, and handles cache and fallback mechanisms.

The Structure of package.path

The package.path variable is a standard global string containing a semicolon-delimited list of file path templates. Each template represents a potential file location on the host file system and contains a question mark (?) placeholder.

A typical package.path configuration on a Unix-like system looks like this:

./?.lua;/usr/local/share/lua/5.4/?.lua;/usr/local/share/lua/5.4/?/init.lua

In this string, semicolons (;) act strictly as separators between distinct search templates.

Module Name Translation

Before testing paths, require normalizes the module name provided as an argument. If the module name contains dots (.), Lua interprets them as hierarchical directory separators:

  1. Dots (.) are replaced with the system-specific directory separator (/ on POSIX systems or \ on Windows). For example, require("utils.parser") transforms the module name into utils/parser.
  2. Any question mark placeholder (?) in the path templates is then substituted with this transformed string.

Applying utils.parser to the template ./?.lua results in ./utils/parser.lua. Applying it to /?/init.lua results in /utils/parser/init.lua.

The Search Procedure

When require(modname) is invoked, Lua performs the search through the following sequential steps:

  1. Check the Cache: Lua first checks package.loaded[modname]. If the module has already been loaded, require immediately returns the cached value, bypassing the file system search entirely.
  2. Consult Searchers: Lua delegates the lookup to the loader functions in the package.searchers table (called package.loaders in Lua 5.1). The second searcher in this table handles standard Lua files via package.path.
  3. Template Iteration: The Lua file searcher parses package.path from left to right, splitting the string by semicolons.
  4. File Probing: For each template, Lua substitutes the formatted module name for the ? character and attempts to open the file in read mode.
  5. Loading the Chunk: As soon as a file is successfully opened, the search terminates. Lua loads the file contents as a chunk using loadfile and executes it, passing the module name as an argument.
  6. Caching the Result: If the chunk returns a non-nil value, that value is stored in package.loaded[modname]. If no value is returned, Lua stores true in the cache to mark the module as loaded.

Error Reporting and Fallbacks

If no template in package.path yields an accessible file, the Lua loader fails and yields an error trace detailing every evaluated file path. The require function then proceeds down the package.searchers chain to check for C shared libraries using package.cpath. If all searchers fail, Lua raises an error containing the full list of examined paths across both package.path and package.cpath.
