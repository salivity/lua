Lua Weak Tables for Automatic Memoization Cleanup

Memoization optimizes performance by caching the results of expensive function calls, but standard implementations can cause memory leaks because standard Lua tables hold strong references to their entries. In Lua, you can prevent these unbounded memory leaks by using weak tables configured with the __mode metamethod. This approach allows the Lua garbage collector to automatically discard cached inputs and outputs when they are no longer referenced elsewhere in the application.

The Memory Problem with Standard Memoization

In a typical Lua memoization implementation, a cache table stores results keyed by the arguments passed to the function:

local function memoize(fn)
    local cache = {}
    return function(arg)
        if cache[arg] == nil then
            cache[arg] = fn(arg)
        end
        return cache[arg]
    end
end

Because ordinary tables hold strong references to both keys and values, any object passed as arg or returned as fn(arg) remains in memory indefinitely. Even if the rest of the application finishes using the object, Lua cannot reclaim it because the cache table keeps a reference alive. Over time, long-running applications accumulate obsolete data and experience memory bloat.

Using Weak Tables for Garbage Collection

Lua solves reference retention through weak tables. Weak tables instruct the garbage collector not to count references stored inside the table as preventing an object from being reclaimed.

Weakness is controlled through the __mode field in a table's metatable. The __mode string can contain:

  • "k": The table has weak keys.
  • "v": The table has weak values.
  • "kv": The table has both weak keys and weak values.

When an object used as a weak key or value loses all strong references outside of weak tables, the garbage collector reclaims the object and automatically removes its corresponding key-value pair from the table.

Implementing Weak Memoization

The choice between weak keys, weak values, or both depends on whether the function's inputs, outputs, or both are collectable objects (tables, functions, threads, or userdata).

If function arguments are collectable objects, configure the cache with weak keys:

local function memoize_weak_keys(fn)
    local cache = setmetatable({}, { __mode = "k" })
    return function(arg)
        local result = cache[arg]
        if result == nil then
            result = fn(arg)
            cache[arg] = result
        end
        return result
    end
end

In this implementation, as soon as the caller drops all references to arg, the garbage collector frees arg on its next cycle and removes the entry from cache, freeing result as well if nothing else references it.

If results are objects that should only stay cached as long as the caller holds onto them, configure weak values (__mode = "v"). If both the arguments and results are objects, use fully weak tables (__mode = "kv"):

local function memoize_weak_all(fn)
    local cache = setmetatable({}, { __mode = "kv" })
    return function(arg)
        local result = cache[arg]
        if result == nil then
            result = fn(arg)
            cache[arg] = result
        end
        return result
    end
end

Limitations with Value Types

Weak tables only discard collectable objects. Primitive types such as numbers and booleans are not garbage collected and will never be cleared from a weak table. Strings in Lua are subject to garbage collection, but they are interned; a string will not be collected if it matches any literal or active string in the runtime. As a result, automatic garbage collection of memoization tables via weak references is effective primarily for functions that accept or return objects, tables, or userdata.
