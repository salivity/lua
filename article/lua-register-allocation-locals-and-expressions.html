Lua Register Allocation: Locals and Expressions

The Lua virtual machine uses a fast, single-pass register allocator that assigns virtual registers directly to stack slots within a function's activation frame. Rather than utilizing complex algorithms like graph coloring or linear scan, the Lua compiler relies on lexical scoping and the inherently nested structure of expressions to manage registers as an internal stack. Local variables are assigned dedicated, persistent register slots for the duration of their lexical scope, while intermediate temporary expressions dynamically borrow and release registers directly above the active local variables.

The Virtual Register Model

Lua 5.0 and later versions implement a register-based virtual machine where instructions operate on virtual registers. These registers do not map to physical CPU registers; instead, they correspond directly to consecutive slots within the current Lua call frame on the execution stack.

Because an instruction uses an 8-bit field to address a register, a single function can access up to 255 registers simultaneously. The compiler (lcode.c and lparser.c) tracks register usage using two primary counters inside the function's compile-time state (FuncState):

  • nactvar: The number of currently active local variables.
  • freereg: The index of the first unallocated register available for new locals or temporaries.

Allocation of Local Variables

When a local variable is declared, the compiler assigns it a permanent register slot for the entirety of its lexical scope:

  1. Reservation: The variable receives the register index pointed to by freereg.
  2. Advancing the Counter: The compiler increments freereg by one (or by the number of declared locals), effectively locking that slot.
  3. Activation: The variable is marked active once its initialization expression is fully evaluated, updating nactvar. This prevents the variable's initialization code from mistakenly referencing its own uninitialized slot.
  4. Scope Exit: When a lexical block ends (such as exiting an if block, loop, or function body), the compiler decrements nactvar and resets freereg back to the slot of the first variable that went out of scope. These slots immediately become available for reuse by subsequent local variables or expressions.

Allocation of Temporary Expressions

Temporary values generated during expression evaluation (such as intermediate arithmetic results or table accesses) are allocated strictly above the currently active local variables:

  1. Expression Descriptors (expdesc): During parsing, the compiler does not immediately emit code to allocate a register for an expression. Instead, it maintains a descriptor holding the expression’s state (such as a constant value, a boolean, or an existing local variable register).
  2. Discharge to Register: If an expression must be placed into a register (for example, to serve as an operand in an opcode that requires a register source), the compiler "discharges" it. It assigns the value to freereg and then increments freereg. If the expression is already a local variable, no temporary register is allocated; the instruction directly targets the variable's existing register.
  3. Deallocation: Because expression trees evaluate in a strictly nested order, temporary registers have lifecycles that follow a strict Last-In, First-Out (LIFO) pattern. As soon as an instruction (such as an arithmetic ADD or logic operation) consumes its source operands, any temporary registers used by those operands are immediately freed by winding freereg back down to the position of the earliest consumed temporary register.

Register Reuse in Practice

Consider the statement: local x = (a + b) * c.

  1. Assuming a, b, and c are local variables located in registers 0, 1, and 2, freereg starts at 3.
  2. Evaluating a + b emits an ADD instruction. The result is placed into the first free register, R(3), and freereg becomes 4.
  3. Evaluating the multiplication between R(3) and c (R(2)) outputs a MUL instruction.
  4. The local variable x is assigned to R(3). The compiler optimizes the target destination so the multiplication stores its final result directly into R(3), avoiding an unnecessary register copy.
  5. x is then registered as an active variable, permanently setting the base of freereg to 4 for subsequent statements in that scope.

By handling register allocation via a top-of-stack bump allocator driven by freereg, the Lua compiler achieves high-speed compilation in a single pass without needing to build an intermediate control-flow graph.
