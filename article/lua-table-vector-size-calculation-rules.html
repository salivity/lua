Lua Table Vector Size Calculation Rules

In the Lua programming language, tables are implemented as hybrid data structures containing an array (vector) part and a hash part. When a table runs out of space during an insertion, it triggers an internal reallocation process known as rehash. During this growth phase, Lua uses a specific mathematical optimization rule to recompute the sizes of both parts: the vector part is set to the largest power of two such that more than half of the vector slots are occupied by existing integer keys (achieving at least 50% utilization), while any remaining keys are allocated to a hash table sized to the smallest power of two that can hold them.

The Trigger Condition

Lua does not resize the array segment dynamically on every append. Instead, a reallocation occurs when an insertion fails because the hash part is full, or when Lua detects that resizing will improve efficiency. When triggered, the engine executes luaH_resizearray or the internal rehash routine found in ltable.c.

The Array (Vector) Optimization Rule

To balance fast index lookups with memory overhead, Lua enforces a strict 50% density rule for its vector component. The size of the array part is determined by the following mathematical algorithm:

  1. Bucket Counting: Lua inspects all integer keys present in the table (both in the current array and the hash parts). It categorizes them into power-of-two intervals \(I_i = (2^{i-1}, 2^i]\) for \(i \ge 0\).
  2. Cumulative Density Check: Lua calculates the cumulative number of integer keys \(a_i\) present in the range \([1, 2^i]\): \[a_i = \sum_{j=0}^{i} \text{count}(I_j)\]
  3. Array Size Selection: The allocated array size \(S_{\text{array}}\) is chosen as the largest power of two (\(2^i\)) that satisfies the condition that strictly more than half of the slots up to that boundary are populated: \[S_{\text{array}} = \max \left\{ 2^i \;\middle|\; a_i > \frac{2^i}{2} \right\} = \max \left\{ 2^i \;\middle|\; a_i > 2^{i-1} \right\}\]

If no power of two satisfies this condition (for example, if all integer keys are sparse and non-consecutive), \(S_{\text{array}}\) is set to \(0\).

The Hash Part Calculation

Any keys not accommodated by the newly sized array vector are relegated to the hash part. This includes all non-integer keys, negative integer keys, float keys, and any positive integer keys greater than \(S_{\text{array}}\).

The required size for the hash part \(S_{\text{hash}}\) is computed as:

  1. Compute the number of remaining elements: \[N_{\text{hash}} = N_{\text{total}} - a_{S}\] where \(N_{\text{total}}\) is the total number of keys in the table, and \(a_{S}\) is the number of integer keys allocated to the array segment.
  2. If \(N_{\text{hash}} = 0\), \(S_{\text{hash}} = 0\).
  3. If \(N_{\text{hash}} > 0\), \(S_{\text{hash}}\) is the smallest power of two greater than or equal to \(N_{\text{hash}}\): \[S_{\text{hash}} = 2^{\lceil \log_2(N_{\text{hash}}) \rceil}\]

Practical Example

Consider a table populated with integer keys \(1, 2, 3, 4, 5, 6, 7\) and \(100\):

  • At \(2^0 = 1\): \(a_0 = 1 > 0\) (Valid candidate: 1)
  • At \(2^1 = 2\): \(a_1 = 2 > 1\) (Valid candidate: 2)
  • At \(2^2 = 4\): \(a_2 = 4 > 2\) (Valid candidate: 4)
  • At \(2^3 = 8\): \(a_3 = 7 > 4\) (Valid candidate: 8)
  • At \(2^4 = 16\): \(a_4 = 7 \ngtr 8\) (Fails density requirement)
  • At \(2^6 = 64\): \(a_6 = 7 \ngtr 32\) (Fails)
  • At \(2^7 = 128\): \(a_7 = 8 \ngtr 64\) (Fails)

The optimal array size chosen is \(8\), holding keys \(1\) through \(7\). Key \(100\) fails the 50% density cutoff for sizes 16 through 128, so it is routed to the hash part. Because there is only \(1\) remaining key, the hash part is allocated with a size of \(2^{\lceil \log_2(1) \rceil} = 2^0 = 1\) node.
