Lua Error Handling: longjmp vs C++ Exceptions

When integrating Lua with C++, handling errors during stack unwinding requires choosing between Lua’s native setjmp/longjmp mechanism and C++ exceptions. The fundamental risk of using longjmp is that it bypasses the C++ runtime, completely skipping destructors for stack-allocated objects and causing resource leaks or undefined behavior. Conversely, using C++ exceptions restores RAII compliance but introduces risks related to ABI mismatches, binary bloat, and improper handling of non-C++ frames.

How Lua Handles Errors by Default

In standard ANSI C builds, Lua handles errors and flow control using the standard C library functions setjmp and longjmp. When a protected call (such as lua_pcall) is initiated, Lua saves the execution context using setjmp. If a runtime error occurs, lua_error calls longjmp, instantly resetting the stack pointer and instruction pointer back to the saved jump buffer.

While this mechanism is fast and portable in pure C environments, it is entirely unaware of C++ object lifecycles.

Critical Risks of Using longjmp in C++

1. RAII Destruction Failure

The primary hazard of longjmp in C++ code is that it executes a low-level register and stack restore. It does not invoke destructors for automatic (stack-allocated) objects residing in intermediate frames between the setjmp call and the longjmp call.

If a C++ function calls into a Lua function that triggers an error:

  • Heap allocations managed by smart pointers (std::unique_ptr, std::shared_ptr) are leaked.
  • Mutex guards (std::lock_guard, std::unique_lock) fail to unlock, causing immediate deadlocks.
  • File descriptors, database connections, and OS handles remain open indefinitely.

2. Undefined Behavior

Under the ISO C++ standard, using longjmp to bypass the destruction of non-trivial objects (objects with non-trivial destructors) is explicitly undefined behavior. Even if an application appears to run without immediate crashes, the compiler's optimizer assumes destructors run at their normal scope exits, which can lead to unpredictable memory corruption and state inconsistency.

Risks and Trade-offs of C++ Exceptions

To solve the RAII problem, Lua can be compiled as C++ (often by compiling the source with a C++ compiler rather than a C compiler). In this configuration, Lua defines internal error macros (LUAI_THROW, LUAI_TRY) using throw and try ... catch rather than longjmp and setjmp. While this preserves destructors, it introduces its own set of technical risks:

1. ABI and Compiler Mismatches

If the Lua runtime is compiled as C (using longjmp) but linked against a C++ host or C++ extension modules, throwing an exception across Lua frames will cause a crash. A C++ exception traversing a C-compiled Lua frame often results in std::terminate because the C frames lack the unwind tables required by the C++ personality routine. Every binary component interacting with the Lua state must strictly agree on the unwinding ABI.

2. Uncaught Foreign Exceptions

If native C++ code throws an exception inside a C function exposed to Lua, Lua cannot handle it natively unless the runtime was explicitly compiled with C++ exception support. In a standard C Lua build, an uncaught C++ exception escaping into Lua’s core will immediately abort the process rather than converting into a recoverable Lua runtime error.

3. Performance and Memory Overhead

C++ exception implementations (typically table-based unwinding like DWARF or Windows Structured Exception Handling) impose virtually zero runtime overhead during standard execution. However, when an error occurs, the unwinding process is substantially slower than a raw longjmp register restore. Additionally, the unwind tables required for stack tracing increase the final binary footprint.

Choosing the Right Strategy

  • Use C++ Exceptions (Compile Lua as C++): Required if your Lua-exposed C++ functions instantiate non-trivial objects, use RAII wrappers, or call standard library containers. Ensure the entire toolchain compiles Lua using the C++ compiler.
  • Use longjmp (Standard C Build): Acceptable only if your integration layer strictly isolates C++ objects from Lua frames using manual cleanup idioms, or if Lua communicates solely through pure C boundary wrappers where no C++ destructors exist between pcall boundaries.
