OpenResty ngx.shared.DICT Shared Memory Cache Guide

This article explores the core purpose, functionality, and advantages of ngx.shared.DICT within the OpenResty ecosystem. OpenResty integrates the Lua programming language into NGINX, relying on NGINX’s multi-process architecture. This guide explains how ngx.shared.DICT bridges the gap between isolated worker processes by providing an ultra-fast, thread-safe shared memory storage zone for high-performance caching and cross-worker data coordination.

The Architecture Problem in OpenResty

NGINX handles concurrency using a master-worker multi-process architecture. In OpenResty, every NGINX worker process maintains its own independent Lua Virtual Machine (VM) instance.

Because worker processes are strictly isolated operating system processes, standard Lua variables, tables, and modules instantiated in one worker cannot be accessed or modified by another. Without a shared storage mechanism, each worker would have to fetch and maintain duplicate copies of cached data or rely on external network services like Redis or Memcached, introducing unwanted network overhead, serialization costs, and latency.

The Purpose of ngx.shared.DICT

ngx.shared.DICT provides an in-memory key-value dictionary that is allocated directly in the NGINX core memory space and shared across all NGINX worker processes. Its primary purposes are:

  • Cross-Worker State Sharing: It serves as a unified central registry where all worker instances can read and write application state, configuration, and data simultaneously.
  • Low-Latency In-Memory Caching: Because data resides in the local system RAM, access speeds are measured in nanoseconds. It avoids network round trips, TCP handshakes, and inter-process communication (IPC) overhead.
  • Process-Safe Concurrency: The dictionary handles concurrent read and write operations from multiple worker processes natively using internal spinlocks and mutexes. This guarantees data consistency without requiring application-level locking logic in Lua.
  • Atomic Operations: It natively supports atomic operations, such as integer incrementing (incr), making it ideal for distributed counters, rate-limiting algorithms, and connection tracking.

Core Features and Lifecycle

To use ngx.shared.DICT, the memory zone must be predefined in the http block of the nginx.conf file using the lua_shared_dict directive with a designated name and size (e.g., lua_shared_dict my_cache 10m;).

Once declared, the dictionary exposes standard key-value operations through the Lua API:

  • TTL and Expiration: Entries can be assigned a Time-To-Live (TTL) in seconds, after which they automatically expire.
  • LRU Eviction: If the allocated shared memory runs out of space, ngx.shared.DICT automatically evicts the least recently used (LRU) non-expired items when new data is inserted using methods like set.
  • Safe Operations: The safe_set and safe_add methods allow developers to strictly control memory limits by returning an error instead of automatically evicting existing entries when memory is exhausted.

Common Use Cases

  • Rate Limiting: Tracking IP requests or API key usage counters across all worker processes using atomic increments.
  • Dynamic Configuration: Storing feature flags, upstream lists, or routing tables fetched at runtime and accessed universally.
  • Upstream Response Caching: Storing micro-cached backend responses, tokens, or JWT public keys locally to minimize upstream database load.
