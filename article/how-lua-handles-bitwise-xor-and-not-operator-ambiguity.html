How Lua Handles Bitwise XOR and NOT Operator Ambiguity

Lua uses the tilde symbol (~) for both the binary bitwise XOR operator and the unary bitwise NOT operator. This article explains how Lua's syntactic grammar, operator positioning, and single-pass recursive descent parser distinguish between these two operations without encountering ambiguity or requiring lookahead backtracking.

Positional Context: Prefix vs. Infix

The primary mechanism Lua uses to avoid ambiguity is positional context within the grammar of expressions. An expression alternates predictably between operands and operators:

  • Unary Bitwise NOT (~x) is a prefix operator. It can only appear where an operand or the start of a subexpression is expected, such as at the beginning of an expression, immediately after an assignment operator, or directly following another operator (e.g., y = ~x or a & ~b).
  • Binary Bitwise XOR (x ~ y) is an infix operator. It can only appear where a binary operator is expected, which occurs strictly after a complete operand or subexpression has already been resolved (e.g., x ~ y).

Because the parser always knows whether it is waiting for an operand or a binary operator, the token ~ is never ambiguous. If an operand has just been parsed, ~ must be XOR. If the parser is awaiting an operand, ~ must be NOT.

Precedence and Associativity Resolution

Operator precedence reinforces this separation when both operations appear close together:

  • Unary NOT has high precedence, evaluated at the same level as unary minus (-), unary length (#), and logical not.
  • Binary XOR has lower precedence, evaluated at the same level as binary OR (|) and binary AND (&).

Consider the expression ~a ~ b. The parser interprets the first ~ in a prefix position (unary NOT on a). Once a is consumed, the parser expects an infix operator, identifying the second ~ as binary XOR. The expression resolves unambiguously to (~a) ~ b.

Conversely, in a ~ ~b, the first ~ occurs after operand a (making it binary XOR), and the second ~ occurs after an operator where a new operand is required (making it unary NOT). This evaluates strictly as a ~ (~b).

Implementation in the Lua Parser

Under the hood, Lua's parser (lparser.c) implements expression parsing via a precedence-climbing algorithm within the internal subexpr function.

When entering an expression, Lua checks for prefix unary operators (~, -, #, not). If it matches ~, it registers a unary bitwise operation and immediately recurses to parse the following subexpression with unary precedence.

Only after a valid primary expression or operand is constructed does the parser enter its binary operator loop. Inside this loop, encountering ~ maps directly to the binary OPR_BXOR enum. Because the state machine strictly distinguishes between parsing a primary subexpression and evaluating intermediate binary operators, the token ~ is handled by two completely separate execution paths.
