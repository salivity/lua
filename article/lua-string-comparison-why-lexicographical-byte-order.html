Lua String Comparison: Why Lexicographical Byte Order?

In the Lua programming language, the relational less-than operator (<) compares strings using a standard lexicographical comparison based on raw byte values. This design choice guarantees maximum execution speed, zero external dependencies, consistent deterministic results across platforms, and full compatibility with binary data. By relying on native byte-level comparison, Lua avoids the performance penalties, memory overhead, and platform variability inherent in locale-dependent and Unicode-aware collation algorithms.

1. Minimal Footprint and Embedded Design

Lua is primarily designed as a lightweight, embeddable scripting language. A central design principle of Lua is to keep its memory footprint minimal, with the entire interpreter typically compiling to just a few hundred kilobytes. Advanced string comparison algorithms, such as the Unicode Collation Algorithm (UCA), require massive weight tables and normalization data that exceed the size of the Lua core itself. Using standard byte comparison allows Lua to remain tiny and easily embeddable in memory-constrained environments.

2. Implementation Simplicity and ANSI C Portability

Lua is written in strict, portable ANSI C. The language implements string comparison via the standard C library function memcmp (or direct byte-loop equivalents). Standardizing on raw byte comparisons ensures that Lua does not require external third-party libraries (such as ICU) to perform fundamental operations, thereby maintaining high portability across any compiler and operating system.

3. Execution Speed

Comparing strings byte-by-byte is one of the fastest operations a CPU can perform. Because modern C standard libraries heavily optimize memcmp using SIMD and vectorized CPU instructions, byte-wise comparison resolves differences between strings in just a few CPU cycles. Locale-aware and Unicode-normalized comparisons introduce computational overhead, involving multi-pass character decoding, normalization checks, and multi-level weight assignments.

4. Binary Safety and Agnostic Encodings

In Lua, strings are not restricted to human-readable text; they are immutable sequences of arbitrary bytes that can contain null bytes (\0) and arbitrary binary payloads. Because the Lua runtime does not enforce UTF-8, ASCII, or any specific text encoding on strings, it cannot make assumptions about character boundaries or alphabetical rules. Treating strings strictly as byte sequences ensures that binary buffers and raw network packets can be sorted and compared reliably without corrupting data or throwing decoding errors.

5. Determinism and Reproducibility

Locale-dependent string comparison functions (such as C's strcoll) depend on the host operating system's active locale settings. Relying on system locales means the same comparison expression could evaluate to true on one machine and false on another, introducing non-deterministic bugs in cross-platform applications and multiplayer game state logic. Standard lexicographical byte-order comparison ensures identical behavior across all architectures and environments.
