How Lua Optimizes Table Array Lookups

The Lua programming language achieves high-performance data access by implementing its universal table structure as a hybrid container composed of an array slice and a hash table. When tables utilize consecutive positive integer keys starting at index 1, Lua automatically places these elements into a contiguous C array, allowing lookups to bypass hash computations entirely and execute via direct memory offset calculations in constant \(O(1)\) time.

The Dual-Structure Architecture of Tables

Internally, every Lua table is represented by a C structure (defined as Table in the Lua source code, primarily ltable.c and ltable.h). This structure splits storage into two distinct segments:

  1. The Hash Part (Node *node): A conventional hash table that handles arbitrary keys, including strings, floating-point numbers, functions, objects, and non-consecutive or out-of-range integers.
  2. The Array Part (TValue *array): A contiguous block of raw TValue objects allocated in memory, specifically reserved for consecutive positive integer keys starting from 1 up to an internally tracked limit (sizearray or alimit in modern Lua releases).

Direct Pointer Arithmetic and Bounds Checking

When a program accesses a key using the syntax t[k], Lua first checks whether k is a positive integer within the bounds of the array slice:

  1. Lua verifies that k is an integer type (or a float convertible to an exact integer without loss).
  2. It evaluates whether 1 <= k <= alimit.

If this condition is met, Lua skips hashing, modulus arithmetic, and hash collision traversal. Instead, the runtime accesses the element using raw C pointer indexing:

TValue *val = &t->array[k - 1];

Because C utilizes zero-based indexing while Lua uses one-based indexing, the runtime simply subtracts 1 from the key k. The CPU calculates the physical memory address with a single base-plus-offset calculation:

\[\text{Address} = \text{base\_address} + ((k - 1) \times \text{sizeof}(TValue))\]

This provides true \(O(1)\) random-access performance equivalent to native arrays in compiled languages such as C or Rust.

Memory Locality and Cache Performance

Placing consecutive integer keys in a contiguous C array provides significant hardware-level optimizations via CPU cache lines:

  • Spatial Locality: Successive elements are stored immediately adjacent to one another. Iterating over an array slice sequentially (for example, with ipairs or a numeric for loop) causes the CPU cache prefetcher to load adjacent values into L1/L2 caches ahead of execution, minimizing memory latency.
  • No Pointer Indirection: Unlike languages that box all primitive values or store arrays as collections of references, Lua's TValue stores primitive types (like booleans, numbers, and pointers) directly inside the array slot, eliminating an extra dereference step during lookups.

The 50% Density Threshold for Array Allocation

To balance memory usage against access speed, Lua does not allocate an array slice of arbitrary size if the keys are sparse. When a table triggers a resize (rehash), the runtime computes the optimal size for the array part using a power-of-two allocation rule:

  • Lua scans all integer keys present in the table and counts how many fall into intervals \([2^{i-1} + 1, 2^i]\).
  • It selects the largest power of two \(2^n\) such that at least 50% of the slots between 1 and \(2^n\) will be populated by non-nil values.

If integer keys are consecutive (such as indices 1 through 1,000), the density is 100%, well above the 50% threshold. The entire sequence stays inside the array slice. If the keys are sparse (e.g., indices 1 and 1,000,000), allocating a million-element array would waste memory; in that case, Lua routes the sparse high-integer keys to the hash part, ensuring the array slice is only deployed when it yields compact, cache-friendly lookups.
