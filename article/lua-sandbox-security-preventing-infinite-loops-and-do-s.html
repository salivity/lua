Lua Sandbox Security: Preventing Infinite Loops and DoS

Securing a Lua sandbox against denial of service (DoS) and infinite execution requires eliminating dangerous standard library functions and enforcing strict runtime resource limits. While native loop constructs like while true do are part of the language syntax rather than built-in functions, several standard library functions can be exploited to cause unbounded memory allocation, extreme CPU consumption, or host process termination. This guide covers the specific built-in functions to eliminate or restrict, along with the complementary mechanisms needed to reliably prevent execution deadlocks.

String Library Functions to Remove or Restrict

The string library contains functions capable of causing memory exhaustion or severe CPU degradation with minimal code:

  • string.rep: Allows users to repeat a string a specified number of times. Executing string.rep("a", 2^30) can instantly exhaust host memory, triggering an out-of-memory crash. It should either be completely excluded from the sandbox or wrapped with strict length caps.
  • string.gsub and string.match: Lua's pattern matching engine does not implement a full regular expression engine, but pathological patterns paired with large inputs can still cause significant CPU lockup. Exclude them if string manipulation is not required, or run them under strict instruction quotas.
  • string.dump: Allows exporting functions as binary bytecode. If users can manipulate or re-import bytecode, it can lead to memory corruption or sandbox escapes in standard Lua runtimes.

Code Loading and Compilation Functions

Dynamically compiling and evaluating Lua code inside a sandbox introduces severe security risks:

  • load and loadstring: These functions compile arbitrary code strings into executable chunks. Malicious users can supply massive, deeply nested syntax trees to exhaust parser memory or inject bytecode that bypasses standard safety invariants. Bytecode loading in particular (permitted by default in Lua 5.1 and earlier) must be strictly forbidden.
  • dofile and loadfile: These load and execute files from the host filesystem. They should be stripped completely to prevent both arbitrary file disclosure and blocking I/O operations.

OS and I/O Functions

Blocking operations can permanently stall a host thread, leading to application-level denial of service:

  • The entire io library (io.read, io.open, etc.): Must be entirely excluded. Reading from special devices (like /dev/zero or /dev/random on Unix systems) or reading from hanging standard input streams will block execution indefinitely.
  • The entire os library (os.execute, os.exit, os.remove, etc.): Functions like os.exit allow a sandboxed script to kill the entire host process. os.execute spawns arbitrary shell processes, causing system-wide resource contention.
  • package.loadlib and require: These functions allow loading external dynamic libraries (.so, .dll), which immediately bypasses any Lua-level restrictions.

Debug Library Functions

  • The entire debug library: While the host can use the C debug API internally to enforce timeouts, exposing the debug table to the sandboxed script breaks all isolation. Sandboxed scripts can use debug.getupvalue, debug.setmetatable, or debug.upvaluejoin to inspect parent environments, overwrite metatables, and alter runtime state to cause crashes or disable resource monitors.

Handling Algorithmic Complexity

  • table.sort: This built-in function accepts a custom comparator callback. A script can pass a comparator that deliberately runs an infinite loop, throws controlled errors to disrupt execution flow, or behaves inconsistently to force worst-case time complexity.

Halting Infinite Loops via Execution Hooks

Removing built-in functions alone cannot stop basic syntax-level loops such as:

while true do end

Because native loops are not function calls, they bypass function-level overrides. To prevent CPU starvation from these loops:

  1. Instruction Count Hooks (debug.sethook): From the host C application, attach a hook using lua_sethook configured to trigger after a specific count of VM instructions. When the count threshold is exceeded, the hook must invoke lua_error() to abort the script.
  2. Custom Memory Allocators: Pass a custom allocator to lua_newstate to enforce a hard ceiling on the total bytes a script can allocate, neutralizing memory-based DoS payloads that bypass standard function checks.
  3. OS-Level Process Isolation: For complete security against CPU exhaustion, run the Lua state inside a separate worker process managed by OS-level resource limits (such as ulimit or cgroups) and terminate non-responsive processes with a watchdog timer.
