Native Lua Code Profiling Using debug.sethook

Profiling Lua code natively allows developers to diagnose performance bottlenecks without compiling external C extensions or deploying heavyweight third-party tools. By leveraging Lua's built-in debug.sethook function, the runtime can intercept function calls and returns to track execution duration, invocation frequency, and call hierarchy directly within pure Lua. This article demonstrates how debug.sethook works, provides a complete implementation of a functional profiler, and details techniques for managing profiling overhead.

Understanding debug.sethook

The debug.sethook function registers a callback that Lua invokes whenever specific runtime events occur. Its signature is:

debug.sethook([thread,] hook_function, mask [, count])

The mask string dictates which execution events trigger the hook:

  • "c": Invoked every time Lua enters a function call.
  • "r": Invoked every time Lua exits a function via return.
  • "l": Invoked every time Lua switches execution to a new line of code.
  • count: An optional integer specifying that the hook should run after executing every N virtual machine instructions.

For standard function-level profiling (measuring execution times and call counts), setting the mask to "cr" (call and return) is the most efficient choice, avoiding the substantial overhead generated by "l".

Architecture of a Native Profiler

A native profiler requires three primary components:

  1. A Data Store: A table aggregating performance metrics per function (call count, total execution time, and exclusive/self time).
  2. A Call Stack: A LIFO (last-in, first-out) data structure tracking timestamps and function references during nested calls to calculate elapsed intervals upon return.
  3. The Hook Callback: A dispatcher that updates the call stack on "call" events and tallies elapsed times into the data store on "return" events using os.clock().

Implementation

The following complete script defines, runs, and reports on a self-contained Lua profiler:

local Profiler = {}
local records = {}
local call_stack = {}

local function get_func_id(level)
    local info = debug.getinfo(level, "nS")
    if not info then return "unknown" end
    
    local source = info.short_src or info.source or "?"
    local line = info.linedefined or -1
    local name = info.name or "(anonymous)"
    
    return string.format("%s:%d [%s]", source, line, name)
end

local function hook(event)
    local now = os.clock()

    if event == "call" or event == "tail call" then
        -- debug.getinfo level 2 points to the function being called
        local func_id = get_func_id(2)
        
        if not records[func_id] then
            records[func_id] = { count = 0, total_time = 0, self_time = 0 }
        end
        records[func_id].count = records[func_id].count + 1

        table.insert(call_stack, {
            id = func_id,
            start_time = now,
            child_time = 0
        })

    elseif event == "return" then
        local frame = table.remove(call_stack)
        if not frame then return end

        local elapsed = now - frame.start_time
        local self_time = elapsed - frame.child_time
        
        -- Guard against negative delta due to system clock resolution
        if self_time < 0 then self_time = 0 end

        records[frame.id].total_time = records[frame.id].total_time + elapsed
        records[frame.id].self_time = records[frame.id].self_time + self_time

        -- Propagate child time to the caller frame if one exists
        if #call_stack > 0 then
            call_stack[#call_stack].child_time = call_stack[#call_stack].child_time + elapsed
        end
    end
end

function Profiler.start()
    records = {}
    call_stack = {}
    debug.sethook(hook, "cr")
end

function Profiler.stop()
    debug.sethook()
end

function Profiler.report()
    local sorted = {}
    for id, data in pairs(records) do
        table.insert(sorted, {
            id = id,
            count = data.count,
            total = data.total_time,
            self_time = data.self_time
        })
    end

    table.sort(sorted, function(a, b) return a.self_time > b.self_time end)

    print(string.format("%-45s | %-8s | %-10s | %-10s", "Function", "Calls", "Total (s)", "Self (s)"))
    print(string.rep("-", 80))
    for _, row in ipairs(sorted) do
        print(string.format("%-45s | %-8d | %-10.4f | %-10.4f", 
            row.id:sub(1, 45), row.count, row.total, row.self_time))
    end
end

return Profiler

Usage Example

To profile a target block of code, wrap the execution between Profiler.start() and Profiler.stop():

local Profiler = require("profiler")

local function heavy_work()
    local sum = 0
    for i = 1, 1e6 do
        sum = sum + math.sqrt(i)
    end
    return sum
end

local function compute()
    heavy_work()
    heavy_work()
end

Profiler.start()
compute()
Profiler.stop()

Profiler.report()

Key Considerations and Limitations

The Observer Effect

Executing Lua code within the hook alters the performance characteristics of the host program. Running debug.getinfo incurs substantial VM overhead on every call. In high-frequency, low-latency loops, the measurement overhead can exceed the execution time of the functions being measured. To mitigate this:

  • Cache metadata: Use the function pointer itself (retrieved via debug.getinfo(2, "f").func) as a key in a lookup cache to avoid repeating string formatting on every call.
  • Avoid inspecting unused fields: Always constrain debug.getinfo using the string specifier argument (such as "nS") rather than calling it with no flags.

Clock Resolution

The standard os.clock() returns CPU time in seconds. Depending on the operating system and C runtime implementation, its resolution may be coarse (typically between 1 millisecond and 1 microsecond). Leaf functions that execute in sub-microsecond intervals may register as zero seconds unless invoked thousands of times.

Tail Calls

Lua optimizes tail calls by reusing the current stack frame. When a tail call occurs, the runtime emits a "tail call" event without a corresponding standard "return" event for the calling function. Profiler implementations must account for this behavior by matching stack depths correctly or capturing the "tail call" event to avoid stack imbalance.
