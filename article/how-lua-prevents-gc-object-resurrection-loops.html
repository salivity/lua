How Lua Prevents GC Object Resurrection Loops

In the Lua programming language, objects with finalizers can inadvertently or intentionally be "resurrected" if their cleanup routines restore references to them in the active environment. To prevent infinite loops where an object repeatedly finalizes, resurrects, and stalls garbage collection cycles, Lua's garbage collector enforces a strict single-finalization rule. By executing an object's finalizer only once during its lifecycle, Lua ensures that any resurrected object is permanently reclaimed on its next collection cycle without re-triggering cleanup routines.

When an object containing a __gc metamethod becomes unreachable, the garbage collector cannot immediately free its memory. The object must remain accessible long enough to execute its finalizer, as the __gc function receives the object itself as a parameter. During this execution, the finalizer might assign the object to a global variable or store it in an active table, restoring its reachability—a phenomenon known as object resurrection.

Lua prevents infinite cycles caused by this behavior through state tracking in its internal finalization lists:

  • Separation of Finalization Queues: When an object with a __gc metamethod is instantiated, Lua registers it in an internal list of objects awaiting finalization. When the garbage collector detects that such an object has become unreachable, it removes the object from this list and moves it to a separate "to-be-finalized" queue (tobefnz).
  • One-Time Execution Flag: Once an object is dequeued from the finalization list, its finalizer is executed. At this point, the garbage collector considers the object's finalization process complete. Lua does not re-register the object for finalization automatically, even if the object becomes reachable again during the __gc call.
  • Direct Deallocation on Subsequent Cycles: If an object is resurrected, it survives the current garbage collection pass because it is once again reachable from root references. However, because it is no longer registered on the finalization queue, it behaves like an ordinary object without a __gc metamethod in subsequent collection cycles. When it eventually loses all references and becomes unreachable a second time, the garbage collector immediately deallocates its memory without invoking the finalizer.

An application can only re-enable finalization on a resurrected object by explicitly calling setmetatable on it again with a metatable containing a __gc field. Without this deliberate manual intervention, Lua's runtime design guarantees that an object can only be resurrected once, preventing automatic and unbounded garbage collection loops.
