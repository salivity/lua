How Lua utf8.len Counts Characters vs Bytes

In the Lua programming language, string measurement differs significantly depending on whether you are evaluating raw storage size or visible text. The standard string.len function calculates length strictly in terms of bytes, which works reliably for single-byte ASCII characters but fails when handling multi-byte UTF-8 sequences. To accurately count human-readable characters, Lua 5.3 introduced the utf8.len function, which decodes the underlying byte stream to return the total number of Unicode code points while validating the structural integrity of the encoding.

Bytes vs. Characters in Standard Lua

Lua strings are inherently 8-bit clean byte arrays. By default, functions in the standard string library operate directly on bytes rather than character representations:

  • string.len(s) (or #s): Counts the total number of bytes in the string.
  • ASCII Characters: Require exactly 1 byte per character, meaning byte count matches character count.
  • UTF-8 Characters: Can occupy anywhere from 1 to 4 bytes per character. Accented letters, non-Latin scripts, and emojis use multiple bytes.

When multi-byte characters are measured using # or string.len, Lua reports a number higher than the visible character count.

How utf8.len Measures Characters

The utf8.len function parses the string according to the UTF-8 specification. UTF-8 uses specific prefix bits in each byte to indicate whether a byte is a standalone character (ASCII) or part of a multi-byte sequence:

  1. Single-byte (ASCII): 0xxxxxxx
  2. Two-byte leading byte: 110xxxxx followed by one continuation byte (10xxxxxx)
  3. Three-byte leading byte: 1110xxxx followed by two continuation bytes
  4. Four-byte leading byte: 11110xxx followed by three continuation bytes

Instead of incrementing for every byte encountered, utf8.len steps through the byte stream, recognizes complete code point sequences, and increments the count once per decoded code point.

Comparative Example

Consider a string containing an English word, a non-ASCII letter, and an emoji:

local text = "café ☕"

print(#text)            -- Output: 9 (bytes)
print(string.len(text)) -- Output: 9 (bytes)
print(utf8.len(text))   -- Output: 6 (characters/codepoints)

In this string:

  • c, a, f, and the space are each 1 byte (4 bytes total).
  • é occupies 2 bytes (0xC3 0xA9).
  • ☕ occupies 3 bytes (0xE2 0x98 0x95).
  • Total bytes: 4 + 2 + 3 = 9.
  • Total UTF-8 code points: 4 + 1 + 1 = 6.

Validation and Error Handling

A fundamental difference between byte counting and utf8.len is error detection. While string.len always succeeds on any sequence of bytes, utf8.len acts as a validator.

If utf8.len encounters an invalid UTF-8 byte sequence (such as a malformed leading byte or a missing continuation byte), it does not return a count. Instead, it returns:

  1. nil as the first return value.
  2. The byte position of the first invalid byte as the second return value.
local invalid_utf8 = "hello\xFFworld"
local len, err_pos = utf8.len(invalid_utf8)

print(len)     -- Output: nil
print(err_pos) -- Output: 6

Positional Range Parameters

utf8.len accepts optional second and third arguments: utf8.len(s [, i [, j]]). These positions (i and j) are specified as byte indices, not character indices:

  • i defines the starting byte position (default is 1).
  • j defines the ending byte position (default is -1, representing the end of the string).

If i or j lands in the middle of a multi-byte UTF-8 sequence, the function identifies it as an invalid sequence and returns nil along with the failure position.
