How String Interning Works in the Lua VM

This article explores how the Lua virtual machine (VM) implements string interning, a core optimization technique where the runtime ensures that only a single immutable copy of any unique string exists in memory. By examining the underlying C source architecture, this guide breaks down the distinction between short and long strings, the role of the global string table, the creation and lookup process, and how this design impacts memory management and runtime execution speed.

The String Representation (TString)

In the Lua VM (specifically Lua 5.3 and 5.4), strings are represented internally by the TString structure. The header for a string contains metadata essential for VM operations, including:

  • marked: Flags used by the garbage collector.
  • tt: The type variant tag, distinguishing between short strings (LUA_VSHRSTR) and long strings (LUA_VLNGSTR).
  • hash: A precalculated 32-bit hash of the string contents.
  • u.hnext: A pointer to the next TString in the same hash bucket (used for hash collision chaining in short strings).
  • shrlen or lnglen: The length of the string, avoiding the need for strlen operations.

Directly following this metadata block in contiguous memory is the raw byte array containing the string data, terminated with a null byte for compatibility with C APIs.

Short Strings vs. Long Strings

Historically, Lua interned every string regardless of length. Starting in Lua 5.2 and refined in 5.3, Lua split strings into two categories based on a compile-time threshold, LUAI_MAXSHORTLEN (defaulting to 40 bytes):

  1. Short Strings (\(\le\) 40 bytes): Fully interned. Every short string is hashed upon creation and deduplicated via a VM-wide hash table.
  2. Long Strings (> 40 bytes): Not interned. Long strings allocate their own memory independently and bypass the global string table. This prevents performance degradation and potential denial-of-service (Hash DoS) vulnerabilities caused by feeding large, maliciously crafted strings into the hash function. Long strings compute their hash lazily only when used as keys in a table.

The Global String Table (stringtable)

Short strings reside in a centralized hash table within the global_State struct, represented by the stringtable type. The structure consists of:

  • hash: An array of pointers to TString nodes (the hash buckets).
  • nuse: The total count of elements currently stored in the table.
  • size: The total capacity (number of buckets), which is always a power of two.

Collisions in the table are resolved using separate chaining via singly linked lists using the u.hnext pointers embedded within each TString.

The Interning Workflow

When a short string is created via functions like luaS_new or luaS_newlstr, the VM performs the following steps:

  1. Hash Generation: The VM computes the string's hash using a randomized seed (global_State->seed) generated at VM initialization. The hashing algorithm processes the string bytes along with the seed to prevent external hash prediction.
  2. Bucket Lookup: The bucket index is calculated via a bitwise AND: hash & (size - 1).
  3. Linear Search: Lua traverses the linked list at the calculated bucket. It performs a quick check comparing lengths and precomputed hash values. If these match, it executes memcmp on the payload bytes.
  4. Reusing Existing Pointers: If a match is found, the existing TString pointer is immediately returned. The new string buffer is discarded, and no allocation occurs.
  5. Insertion and Allocation: If no match is found, Lua allocates a new TString object, initializes its fields, inserts it at the head of the bucket's linked list, and increments nuse.
  6. Resizing: If nuse exceeds size and size has not reached the maximum limit, the table triggers a resize operation (luaS_resize), doubling the bucket array and rehashing all existing short strings.

Garbage Collection and De-interning

Interned strings in Lua are subject to the incremental garbage collector. The global string table maintains weak references to interned strings in the context of GC liveness.

During the sweep phase, the garbage collector checks each bucket in the stringtable. If a TString is not marked as reachable by any active Lua variable, table, or closure, it is unlinked from the bucket's chain and its memory is freed. The nuse count is decremented accordingly, and if the table becomes too sparse, it shrinks to reclaim memory.

Performance Implications

String interning provides distinct performance characteristics inside the VM:

  • \(O(1)\) Equality Checks: Comparing two short strings (a == b) does not require comparing their contents. The VM simply checks pointer equality (ts1 == ts2), making string comparisons as fast as integer comparisons.
  • Fast Table Indexing: Table lookups with short string keys use the precalculated hash stored in the TString directly, bypassing hash calculations during table access.
  • Memory Efficiency: Repetitive identifiers, variable names, and common string values consume memory for their payload only once.
  • Allocation Overhead: Creating short strings incurs an upfront cost due to the mandatory hash calculation and hash table lookup.
