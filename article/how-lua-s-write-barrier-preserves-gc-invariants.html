How Lua's Write Barrier Preserves GC Invariants

In the Lua programming language, the incremental garbage collector (GC) relies on a write barrier to maintain tri-color marking invariants during execution. Because Lua mutates object references while the GC is actively running, an already-scanned object could inadvertently point to an unvisited object, risking premature memory deallocation. This article explains how Lua's tri-color marking abstraction operates, the specific invariants required to prevent dangling references, and how the forward and backward write barriers enforce these rules when linking objects.

The Tri-Color Abstraction and GC Invariants

Lua utilizes an incremental mark-and-sweep collector based on Dijkstra's tri-color marking algorithm. Objects in memory are categorized into three states:

  • White: Unvisited objects that are candidates for collection. During collection cycles, Lua differentiates between two shades of white to distinguish between newly allocated objects and those pending reclamation.
  • Gray: Objects that have been visited by the collector, but whose referenced objects (such as table keys, values, or closures) have not yet been fully inspected.
  • Black: Objects that have been fully visited along with all their immediate references. Black objects are considered reachable and cannot be collected in the current cycle.

The fundamental invariant required by the incremental collector is that a black object must never directly point to a white object without an intermediate gray object tracking the reference path. If a running program (the mutator) creates a link from a black object directly to a white object and removes any existing link from a gray object to that same white object, the collector will never traverse the white object. Consequently, the collector assumes the white object is garbage and frees it, leading to memory corruption.

The Mechanism of the Write Barrier

Because Lua executes user code concurrently with the incremental phases of collection, table assignments, upvalue updates, and object linking occur dynamically. Whenever a field assignment occurs (for instance, setting table[key] = value), the Lua runtime checks if the assignment violates the tri-color invariant. If a black parent object is assigned a reference to a white child object, a write barrier is executed.

The write barrier intervenes using one of two strategies: moving forward or moving backward.

1. Forward Barrier (luaC_barrier)

The forward barrier focuses on the child (the white object). When a black container links to a white object, the barrier immediately changes the color of the white object:

  • The white object is shifted to gray.
  • The object is added to the collector's gray list for future traversal.

By graying the child, the invariant is restored because the black object now points to a gray object instead of a white one. This ensures that the newly linked object and its downstream graph are preserved and scanned before the sweep phase begins.

2. Backward Barrier (luaC_barrierback)

Certain structures, notably tables, are modified frequently. If a forward barrier were used on every table modification, high-frequency writes would constantly push individual objects to the gray list, leading to high overhead and overhead in tracking.

To optimize for this access pattern, Lua employs a backward barrier on tables:

  • Instead of graying the white child object, the barrier resets the parent container from black to gray.
  • The parent object is placed back onto the gray list (grayagain list in the Lua C source).

By turning the black parent back into a gray object, the invariant is instantly satisfied—the link is now between gray and white, which is fully legal. The collector will re-scan the entire table later in an atomic traversal step before entering the sweep phase, capturing all newly added keys and values at once.

Preserving Memory Safety During Object Linking

When a program performs an operation such as a.b = c:

  1. Check: Lua evaluates the GC state. If the collector is in the mark phase, it evaluates whether object a is marked black and object c is marked white.
  2. Execution: If the condition evaluates to true, the relevant barrier function (luaC_barrier or luaC_barrierback) is triggered.
  3. State Transition: Depending on the parent object type, either c is promoted to gray or a is demoted to gray.

Through this conditional intervention, Lua's write barrier allows the mutator to execute with minimal overhead while strictly maintaining the tri-color invariant, ensuring that reachable objects are never reclaimed during incremental garbage collection cycles.
