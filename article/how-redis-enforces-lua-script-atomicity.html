How Redis Enforces Lua Script Atomicity

This article explores how Redis guarantees atomicity during the execution of Lua scripts. Redis relies on its single-threaded execution model to run Lua scripts non-preemptively, preventing any other client commands from executing concurrently. While this design ensures complete isolation and consistency without the need for traditional database locks, it also introduces specific constraints regarding script execution times and runtime error handling.

The Single-Threaded Execution Engine

At the core of Redis is an event-driven, single-threaded execution loop. While Redis uses background threads for specific tasks like asynchronous deletion and disk I/O, all client commands and data modifications are processed by a single main thread.

When a client executes a Lua script using the EVAL or EVALSHA commands (or via Redis Functions introduced in Redis 7.0), Redis hands complete control of the main thread to the embedded Lua interpreter. Because the thread is entirely dedicated to processing the script:

  • No interleaving occurs: No other client can inject a command while the script is running.
  • No race conditions exist: State changes made in the first line of a script are immediately visible to subsequent lines, and no external client can mutate the keys being evaluated.
  • Data isolation is absolute: The state of the database cannot be read or modified by other connections until the script runs to completion.

This mechanism provides serializable isolation, functioning like an automated, conditional transaction that surpasses standard MULTI/EXEC blocks by allowing read-then-write logic based on intermediate data.

Execution Isolation vs. Transactional Rollbacks

It is crucial to understand how Redis defines atomicity in the context of Lua scripts. In traditional ACID database terminology, atomicity implies that if an operation fails halfway through, all preceding operations are rolled back to the initial state.

Redis Lua scripts enforce atomicity in terms of isolation, not automatic rollback:

  1. Before Execution: If a script fails during the compilation or syntax-checking phase, it does not run at all.
  2. During Execution: If a runtime error occurs halfway through a script (for example, attempting an operation on a key holding the wrong data type), the script terminates immediately. However, any commands that executed successfully prior to the error are not rolled back.

Redis does not maintain an undo log for in-memory operations. Therefore, developers must ensure that scripts perform pre-validation checks on data types and parameters to avoid runtime failures.

Script Timeouts and the SCRIPT KILL Command

Because a running Lua script blocks all other operations on the Redis server, an infinite loop or heavy computation inside a script could make the instance unresponsive. To safeguard against this, Redis implements a execution watchdog configured by the lua-time-limit directive (defaulting to 5 seconds).

When a script exceeds this threshold:

  • Redis stops accepting normal commands and begins returning a BUSY error to other connected clients.
  • Clients can send a SCRIPT KILL command, which instructs Redis to terminate the script, but only if the script has not performed any write operations.
  • If the script has already modified the dataset, SCRIPT KILL is disabled to prevent partial data corruption. In this scenario, the only way to recover the instance is via the SHUTDOWN NOSAVE command, which stops the server without persisting the inconsistent state to disk.

By maintaining single-threaded script execution, avoiding interleaving, and disallowing concurrent data modification, Redis guarantees that Lua scripts operate as atomic, isolated units of work.
