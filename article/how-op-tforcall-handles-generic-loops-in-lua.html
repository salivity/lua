How OP_TFORCALL Handles Generic Loops in Lua

The OP_TFORCALL opcode in the Lua virtual machine manages the execution of iterator functions within generic for loops. It coordinates the transition of loop states by passing the invariant state and the primary control variable to an iterator function, capturing the newly returned values, and placing them into the appropriate stack registers so subsequent instructions can evaluate whether the loop should continue or terminate.

Generic Loop State Architecture

In Lua, a generic for loop is syntactically defined as:

for var_1, ..., var_n in explist do
    -- loop body
end

Before entering the iteration phase, the Lua compiler evaluates explist to produce three core values that govern the loop's lifecycle:

  1. Iterator Function (\(f\)): A callable entity that yields subsequent values on each iteration.
  2. Invariant State (\(s\)): A static context passed into every call to the iterator.
  3. Control Variable (\(var\)): The variable tracking the current iteration progress, initialized to the third result of explist.

These values are placed in consecutive internal registers in the virtual machine stack:

  • R(A): The iterator function (\(f\))
  • R(A+1): The invariant state (\(s\))
  • R(A+2): The control variable (\(var\))

The Mechanics of OP_TFORCALL

The OP_TFORCALL instruction executes the iterator invocation. Its format takes a base register A and a count parameter C, which specifies how many loop variables need to be extracted from the call.

When the virtual machine encounters OP_TFORCALL A C, it performs the following sequence:

  1. Argument Preparation: The VM sets up a function call using the iterator function located at R(A). It supplies exactly two arguments: the invariant state at R(A+1) and the current control variable at R(A+2).
  2. Function Invocation: The VM executes the function call equivalent to f(s, var).
  3. Return Value Capture: The returned values are written sequentially into target registers beginning directly after the internal loop state registers. The first returned value represents the next iteration's proposed control variable.

Because the invariant state R(A+1) never changes throughout the loop's execution, the state transition relies entirely on the progression of the control variable from one cycle to the next.

Transition Evaluation and OP_TFORLOOP

OP_TFORCALL does not handle conditional jumps or loop termination on its own. In Lua's bytecode architecture, OP_TFORCALL is immediately paired with OP_TFORLOOP.

Once OP_TFORCALL finishes writing the iterator's output to the stack:

  1. OP_TFORLOOP inspects the primary returned value (the candidate for the new control variable).
  2. Termination Check: If this value is nil, the iteration sequence has finished. The VM falls through to the instruction following OP_TFORLOOP, exiting the loop.
  3. State Update and Jump: If the value is not nil, the loop state transitions forward. OP_TFORLOOP copies the candidate control variable into R(A+2), updates the user-visible loop variables, and executes a backward jump to the start of the loop body.

Efficiency and Register Reuse

By separating the iterator invocation (OP_TFORCALL) from the branching logic (OP_TFORLOOP), Lua keeps virtual machine instructions simple and pipelined. This design updates the loop's variant state in-place on the stack without allocating heap memory or intermediate tables, allowing stateful traversal mechanisms like ipairs and stateless iterators like pairs to execute with minimal CPU overhead.
