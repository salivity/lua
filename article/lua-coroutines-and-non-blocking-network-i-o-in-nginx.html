Lua Coroutines and Non-Blocking Network I/O in Nginx

The lua-nginx-module integrates Lua coroutines with Nginx’s event-driven architecture to allow developers to write sequential, synchronous-looking code that executes in a 100% non-blocking manner. By mapping individual incoming HTTP requests or subtasks to Lua coroutines, the module intercepts blocking network I/O operations, suspends the coroutine, registers the underlying file descriptors with Nginx’s native event loop, and resumes execution only when the network event completes. This bridge between Lua’s lightweight user-space concurrency and Nginx’s C-level event loop enables massive concurrency without thread-scheduling overhead.

The Architectural Foundation

Nginx operates on an asynchronous, event-driven model using an event loop powered by OS-level multiplexing interfaces like epoll on Linux or kqueue on BSD/macOS. A single Nginx worker process handles thousands of connections simultaneously by never waiting for network I/O; operations that would block return immediately with an EAGAIN or EWOULDBLOCK status.

Lua coroutines are collaborative, non-preemptive threads of execution managed completely in user space. Unlike operating system threads, a coroutine can suspend its own execution via coroutine.yield() and be restarted later via coroutine.resume(), maintaining its complete execution stack and local variable state across suspensions.

The Request Lifecycle and Coroutine Creation

When a request arrives and enters a phase handled by lua-nginx-module (such as content_by_lua_* or access_by_lua_*), the module creates a new Lua coroutine (lua_State) derived from the main Lua state. The Lua code assigned to handle the request executes inside this coroutine context rather than the main thread.

Incoming Request -> Nginx Event Loop -> Spawn Lua Coroutine -> Execute Lua Handler

Because the request runs inside a coroutine, the module gains the power to pause and resume the execution of that specific request at any point in the C execution boundary.

The Cosocket Abstraction and Non-Blocking Suspension

Network communication inside the module relies on the "cosocket" (coroutine-based socket) API, which implements standard TCP, UDP, and Unix domain socket interfaces. When a Lua script performs an I/O operation—such as tcpsock:connect(), tcpsock:receive(), or tcpsock:send()—the following sequence occurs:

  1. Non-Blocking Execution Attempt: The module issues a standard non-blocking system call on the socket file descriptor. If the operation succeeds immediately (for instance, data is already available in the socket receive buffer), the function returns data to the Lua script without interruption.
  2. Handling Incomplete I/O: If the system call returns EAGAIN or EWOULDBLOCK, the operation cannot complete immediately.
  3. Event Registration: The module attaches the socket's file descriptor to Nginx's event loop (e.g., adding a read or write event watcher in epoll). Crucially, Nginx attaches the pointer to the currently suspended Lua coroutine (lua_State *) to the event's data context (ngx_event_t).
  4. Coroutine Yielding: The module invokes lua_yield() at the C level, returning execution control from Lua back to the C code of the module, and ultimately back to the Nginx core event loop.
  5. Worker Continues: The Nginx worker process is not blocked. It immediately processes other pending network events, timers, or requests.

Event Notification and Resumption

When the kernel detects that the monitored socket has become ready for reading or writing:

  1. Event Trigger: The OS multiplexer (epoll_wait) notifies Nginx, which invokes the read or write event handler associated with the socket descriptor.
  2. Context Retrieval: The module’s C callback function retrieves the reference to the suspended Lua coroutine from the event context.
  3. Data Transfer: The module reads available bytes from the socket into an internal buffer or writes outbound data to the socket.
  4. Coroutine Resumption: The module calls lua_resume(), passing the read data or operation status back up to the Lua stack.
  5. Execution Continues: The Lua coroutine resumes exactly where it yielded, receiving the return values of the socket call as if the operation had blocked synchronously.

Concurrency and Resource Management

This integration eliminates the traditional tradeoff between the simplicity of synchronous I/O and the scalability of asynchronous callbacks. Because coroutines are extremely lightweight (consuming only a few kilobytes of memory compared to megabytes for OS threads), a single Nginx worker can hold tens of thousands of paused Lua coroutines simultaneously.

Memory and cleanup safety are preserved through Nginx's pool allocators and Lua's garbage collector. If a client disconnects prematurely while a coroutine is suspended waiting for upstream I/O, Nginx invokes clean-up hooks that close the associated sockets, unregister the descriptors from the event loop, and allow the Lua garbage collector to reclaim the coroutine.
