How Lua Handles Gotos and Labels in Bytecode

This article explores how the Lua compiler processes goto statements and labels during its single-pass bytecode translation. It details the underlying data structures used to track identifiers, how forward and backward jumps are generated and patched, and the scope validation rules enforced to maintain the integrity of local variables and upvalues.

The Single-Pass Compilation Model

Lua compiles source code into bytecode in a single pass without constructing an explicit Abstract Syntax Tree (AST). Because of this design, the compiler encounters jumps to labels that may not yet have been defined (forward jumps) or jumps to labels that are already established in memory (backward jumps).

To manage these jumps, the parser tracks state using internal dynamically sized arrays stored in the Dyndata structure:

  • actvar: Active local variables in scope.
  • gt: A list of unresolved goto statements awaiting a target label.
  • label: A list of declared labels visible within the current function.

Each entry in these lists records the identifier's name, the program counter (pc) index of the associated instruction, the lexical block nesting level, and the count of active local variables at the point of declaration.

Backward Jumps

When the parser encounters a goto statement whose target label has already been defined within an accessible scope, the translation is straightforward:

  1. The compiler searches the existing labels in Dyndata.label from innermost to outermost scope.
  2. It verifies that the jump does not violate scoping rules (such as jumping into the scope of a local variable).
  3. The compiler emits an unconditional jump instruction (OP_JMP).
  4. Because the target label's bytecode offset is already known, the displacement offset of the OP_JMP is calculated immediately and written directly into the instruction.
  5. If the jump exits the scope of any local variables that have been captured as upvalues or marked with the <close> attribute, the compiler adjusts the instruction or emits an OP_CLOSE to ensure proper resource cleanup.

Forward Jumps and Backpatching

When a goto refers to a label that has not yet been declared, the compiler cannot immediately determine the destination address. Instead, it defers resolution:

  1. An OP_JMP instruction is emitted with an empty or placeholder jump offset.
  2. The compiler records a new pending jump entry in the Dyndata.gt list, capturing the label name, the instruction index of the placeholder OP_JMP, and the current local variable stack depth.
  3. Compilation continues sequentially.

When the target label ::name:: is eventually parsed, the compiler registers it in Dyndata.label and initiates a backpatching routine. It iterates over the pending gotos in Dyndata.gt:

  • For each unresolved jump matching the label's name, the compiler validates scoping boundaries.
  • The instruction offset between the forward OP_JMP and the newly declared label's pc is computed.
  • The offset field of the earlier OP_JMP instruction is updated (backpatched) in the function's bytecode array.
  • The resolved entries are removed from the pending jump list.

Scoping and Variable Lifecycles

Lua enforces strict rules regarding how goto interacts with local variables, preventing undefined states at runtime:

  • Jumping into variable scope: A program cannot jump from a point where a variable is not yet declared to a point where it is in scope. During label resolution, Lua compares the active variable count of the goto with that of the label. If the label requires more active variables than the goto had at its point of origin, the compiler halts and throws a syntax error.
  • Jumping out of variable scope: Jumping outward is valid, but leaving a scope may leave dangling upvalues or unclosed resources. When emitting the OP_JMP (or during backpatching), Lua inspects whether variables were closed between the source and target. Lua's OP_JMP instruction includes an operand indicating the register boundary above which all active upvalues must be closed, triggering automatic closure during the jump at runtime.

Block Finalization and Error Checking

Whenever a lexical block exits (such as the end of a do...end, loop, or function body), Lua cleans up labels defined inside that block. Any label defined within the closing block is discarded, as it is no longer visible to outer code.

At the close of a function body, the compiler checks the Dyndata.gt list for any remaining unresolved goto statements. If any entries persist, the compiler raises a compile-time syntax error stating that no visible label was found, ensuring no unlinked jump instructions ever reach the runtime virtual machine.
