How Lua Garbage Collection Handles Cyclical References

This article examines how the Lua programming language manages memory when tables reference each other in a closed loop. Because Lua employs a tracing mark-and-sweep garbage collector rather than a reference counting mechanism, cyclical table references are automatically detected and collected when they become unreachable from the root set. Below is a detailed breakdown of the internal mechanisms, the tri-color marking algorithm, and the specific behaviors governing these circular data structures.

The Problem of Cyclical References

A cyclical reference occurs when two or more objects reference each other, either directly or indirectly. For example, Table A contains a field pointing to Table B, and Table B contains a field pointing back to Table A. In programming environments that rely strictly on reference counting, each table maintains a reference count of at least one, even after all external references to them are discarded. Consequently, reference counting engines cannot free these isolated "islands" of memory without explicit cycle-breaking logic or auxiliary cycle detectors.

Lua’s Tracing Garbage Collector

Lua resolves this issue inherently by using a tracing garbage collector based on the mark-and-sweep algorithm (implemented as an incremental or generational collector depending on the Lua version). Instead of monitoring how many pointers target a given table, Lua periodically determines which objects are actually reachable by traversing the entire object graph starting from a base set known as the roots.

The root set includes:

  • The main thread and current coroutines.
  • The global environment table (_G).
  • The Lua registry.
  • Active stack frames, including local variables and upvalues.

The Tri-Color Marking Algorithm

To trace reachable objects incrementally without stopping execution for long periods, Lua uses a tri-color marking abstraction:

  1. White: Objects that are candidates for garbage collection. At the start of a collection cycle, all objects are white.
  2. Gray: Objects that have been visited by the collector, but their referenced objects (such as table keys and values) have not yet been traversed.
  3. Black: Objects that have been visited, along with all objects directly referenced by them. Black objects are guaranteed not to point directly to white objects without the collector's knowledge.

Handling Cycles During Traversal

When the garbage collector runs, it proceeds through the following phases:

  1. Root Scanning: All objects directly referenced by the root set are colored gray and pushed onto a traversal list.
  2. Propagation (Marking): The collector pops a gray object, inspects all tables and objects it references, turns those referenced white objects gray, and turns the original object black.
  3. Cycle Termination: If Table A points to Table B, and Table B points back to Table A, the collector marks Table A as gray, moves to Table B and marks it gray, and then inspects Table B's reference back to Table A. Because Table A is already gray (or black), the traversal stops following that path, naturally preventing an infinite loop.
  4. Sweep Phase: Once all reachable objects have turned black, any object that remains white is completely unreachable from the root set. The collector iterates through the master linked list of all allocated objects and deallocates every white object.

If a pair or group of cyclical tables is decoupled from the root set—meaning no variable in the active program holds a reference to any member of the cycle—none of the tables in the cycle will ever be colored gray during the propagation phase. As a result, the entire cycle remains white and is reclaimed during the sweep phase in a single collection cycle.

Weak Tables and Ephemerons

Cyclical structures can present challenges when combined with weak tables (tables whose keys or values have the __mode metamethod set to "k", "v", or "kv"). In older garbage collection models, a table whose key was held in a cycle within the table itself could prevent collection.

Starting in Lua 5.2, Lua implemented ephemeron tables. An ephemeron table is a table with weak keys and strong values where a value is considered reachable only if its corresponding key is reachable. Lua's collector iteratively marks ephemeron pairs, ensuring that self-referential or cyclical entries inside weak tables are collected properly once their external keys become unreachable.

Finalizers and Resurrection

If tables within a cycle define the __gc metamethod (finalizers), Lua still detects that the cycle is unreachable. However, the collector must run the finalizers before freeing the memory. During the cycle in which they are detected as dead, the tables are resurrected temporarily, their __gc metamethods are invoked, and their actual deallocation is deferred to the subsequent garbage collection cycle, provided they remain unreachable.
