Building ASTs in Lua with LPeg Captures

LPeg (Parsing Expression Grammars for Lua) provides an expressive framework that matches patterns and transforms raw text into structured data. By using LPeg captures, developers can extract tokens, attach structural metadata, group values, and construct hierarchical Abstract Syntax Trees (ASTs) in a single parsing pass. This article explains the core capture mechanisms in LPeg and demonstrates how to assemble them to build an AST for language parsers, compilers, and interpreters.

What Are LPeg Captures?

In standard LPeg, a pattern either succeeds or fails. When a match succeeds without captures, LPeg returns only the index following the last matched character.

Captures produce Lua values from matched text. When an LPeg pattern containing captures successfully matches an input, it yields those captured values directly to the caller. LPeg provides several capture operators suited for structural data representation:

  • Simple Capture (lpeg.C(p)): Captures the exact substring matched by pattern p.
  • Constant Capture (lpeg.Cc(val)): Injects an arbitrary Lua value (such as a string tag or boolean) into the capture list without consuming any input.
  • Table Capture (lpeg.Ct(p)): Collects all values captured within pattern p into a single Lua table array.
  • Group Capture (lpeg.Cg(p, [key])): Groups captures together, optionally associating them with a specific table key when placed inside a table capture.
  • Function/Replacement Capture (p / fn or p / table): Passes all captures produced by p as arguments to a function fn, or uses the first capture as a key to look up a value in table.
  • Fold Capture (lpeg.Cf(p, fn)): Iteratively folds captured values using an accumulator function, ideal for left-associative binary operations.

Building Individual AST Nodes

An AST is a tree structure composed of nodes, where each node typically contains a type tag, positional or metadata properties, and zero or more child nodes.

There are two primary patterns for constructing AST nodes using LPeg captures: using lpeg.Ct with lpeg.Cc, or using replacement captures (/) with constructor functions.

Approach 1: Table Captures with Constant Tags

Using lpeg.Ct combined with lpeg.Cc is a purely declarative way to build node tables:

local lpeg = require("lpeg")
local C, Cc, Ct, R, S = lpeg.C, lpeg.Cc, lpeg.Ct, lpeg.R, lpeg.S

local digits = R("09")^1
local number_node = Ct(
    Cc("tag") * lpeg.Cg(Cc("NumberLiteral"), "type") *
    Cc("value") * lpeg.Cg(digits / tonumber, "value")
)

Matching "42" against number_node outputs:

{ type = "NumberLiteral", value = 42 }

Approach 2: Constructor Functions via Replacement Capture

Using the division operator / allows constructor functions to standardize node shapes:

local function make_node(tag)
    return function(...)
        return { tag = tag, ... }
    end
end

local function make_binary_node(op, left, right)
    return { tag = "BinaryExpr", operator = op, left = left, right = right }
end

local identifier = lpeg.C(R("az", "AZ") * R("az", "AZ", "09")^0) / make_node("Identifier")

Whenever identifier matches, the matched substring is passed to make_node("Identifier"), producing { tag = "Identifier", [1] = "matched_name" }.

Managing Operator Precedence with Fold Captures

Expressions typically feature left-associativity and varying operator precedence (such as multiplication binding tighter than addition). LPeg's lpeg.Cf simplifies building nested binary AST nodes without requiring manual post-processing passes.

local lpeg = require("lpeg")
local P, S, R, C, Cf, Cg = lpeg.P, lpeg.S, lpeg.R, lpeg.C, lpeg.Cf, lpeg.Cg

local ws = S(" \t\n")^0
local function token(p) return p * ws end

local function fold_binary(left, op, right)
    return {
        tag = "BinaryExpr",
        operator = op,
        left = left,
        right = right
    }
end

-- Primary expressions
local number = token(R("09")^1) / function(v) 
    return { tag = "NumberLiteral", value = tonumber(v) } 
end

-- Factors: handles '*' and '/'
local mul_op = token(C(S("*/")))
local factor = Cf(number * Cg(mul_op * number)^0, fold_binary)

-- Terms: handles '+' and '-'
local add_op = token(C(S("+-")))
local expr = Cf(factor * Cg(add_op * factor)^0, fold_binary)

When evaluating the string "1 + 2 * 3", the grammar performs the following operations:

  1. factor matches 2 * 3, yielding:

    {
    tag = "BinaryExpr",
    operator = "*",
    left = { tag = "NumberLiteral", value = 2 },
    right = { tag = "NumberLiteral", value = 3 }
}

  2. expr encounters the + operator and folds the number 1 with the higher-precedence multiplication subtree, resulting in:

    {
    tag = "BinaryExpr",
    operator = "+",
    left = { tag = "NumberLiteral", value = 1 },
    right = {
        tag = "BinaryExpr",
        operator = "*",
        left = { tag = "NumberLiteral", value = 2 },
        right = { tag = "NumberLiteral", value = 3 }
    }
}

Complete Example: Expression Grammar to AST

Combining these techniques allows full grammars using lpeg.V (grammar variables) to output a complete AST:

local lpeg = require("lpeg")
local P, V, S, R, C, Ct, Cc, Cf, Cg = 
    lpeg.P, lpeg.V, lpeg.S, lpeg.R, lpeg.C, lpeg.Ct, lpeg.Cc, lpeg.Cf, lpeg.Cg

local ws = S(" \t\r\n")^0
local function tok(pat) return pat * ws end

local function binary_fold(left, op, right)
    return { tag = "Binary", op = op, left = left, right = right }
end

local grammar = P{
    "Program",
    Program = ws * V("Expr") * P(-1),
    
    Expr = Cf(V("Term") * Cg(tok(C(S("+-"))) * V("Term"))^0, binary_fold),
    
    Term = Cf(V("Factor") * Cg(tok(C(S("*/"))) * V("Factor"))^0, binary_fold),
    
    Factor = V("Number")
           + tok(P("(")) * V("Expr") * tok(P(")"))
           + V("Variable"),
           
    Number = tok(C(R("09")^1)) / function(n)
        return { tag = "Number", value = tonumber(n) }
    end,
    
    Variable = tok(C(R("az", "AZ") * R("az", "AZ", "09")^0)) / function(id)
        return { tag = "Variable", name = id }
    end
}

local ast = grammar:match("x + 10 * 5")

The resulting ast table accurately reflects the precedence rules and semantic hierarchy of the input program without requiring separate tokenization or tree-transformation phases.
