Understanding LClosure and CClosure in Lua Internals

In the Lua programming language, all functions are first-class values represented internally as closures rather than bare function pointers. To handle the execution of both interpreted script logic and native extensions efficiently, the Lua runtime bifurcates functions into two distinct data structures: LClosure (Lua closures) and CClosure (C closures). While both adhere to a shared closure header to facilitate unified garbage collection and runtime type inspection, they differ fundamentally in how they store executable logic, manage upvalues, and interact with the Lua virtual machine (VM).

The Common Closure Foundation

At the C implementation level (defined primarily in lobject.h), Lua unifies function instances through the Closure union. Both LClosure and CClosure embed a common header composed of garbage collection flags (GCObject), an internal type tag (LUA_VLCL or LUA_VCCL), and metadata such as the number of associated upvalues (nupvalues).

Because they share this foundation, the Lua runtime treats both variants uniformly as the basic type LUA_TFUNCTION from the perspective of user-facing scripts. However, when the VM invokes a closure, it inspects the internal subtype tag to route execution either through the bytecode interpreter loop or into native C code.

The Function of LClosure

An LClosure represents a function written in Lua and compiled down to Lua virtual machine bytecode. Its primary responsibility is to pair executable bytecode with the lexical environment in which the function was defined.

An LClosure contains two critical members:

  1. A Pointer to a Function Prototype (Proto* p): The Proto struct contains the immutable blueprint of the function, including the array of bytecode instructions, the constant table (k), debugging information, and descriptions of expected upvalues. Because multiple closure instances can share the same compiled code (such as functions generated inside a loop), the Proto is read-only and shared across all instances.
  2. An Array of Upvalue Pointers (UpVal* upvals[]): Unlike native languages that use stack-copying or full heap frames for closures, Lua manages closed-over local variables via UpVal objects. While an outer function is executing, an upvalue is "open" and points directly to a register on the execution stack. Once the outer function returns, the runtime "closes" the upvalue by copying the value into the UpVal struct itself. The LClosure holds an array of pointers to these shared UpVal structures, maintaining precise lexical scope across function boundaries.

Execution of an LClosure triggers the central VM loop (luaV_execute), which allocates a new activation frame (CallInfo) on the Lua thread stack and steps through the instructions defined in the underlying Proto.

The Function of CClosure

A CClosure represents a native function written in C that adheres to the lua_CFunction signature (int (*lua_CFunction) (lua_State *L)). It provides the bridge between the Lua runtime and native host code, allowing developers to extend the environment with native libraries and low-level system bindings.

Unlike its Lua counterpart, a CClosure has no Proto and contains no Lua bytecode. Instead, its structure consists of:

  1. A Native Function Pointer (lua_CFunction f): The direct memory address of the C function to be invoked.
  2. An Inline Value Array (TValue upvalue[]): Rather than referencing mutable, shared UpVal objects, a CClosure stores a contiguous array of TValue structs directly inside its memory allocation. When creating a C closure via lua_pushcclosure, any arguments passed on the stack are converted into persistent upvalues stored inside this array.

When the VM calls a CClosure, it bypasses the bytecode evaluation engine entirely. The runtime prepares a standard C call boundary, passes the active lua_State*, and immediately executes the function pointer. The C function accesses its stored upvalues using the pseudo-index API (lua_upvalueindex), which maps directly to the upvalue array embedded in the CClosure.

Key Differences and Architectural Purpose

The architectural separation between LClosure and CClosure serves specific runtime requirements:

  • Execution Pipeline: LClosure requires the interpreter dispatch loop, instruction decoding, and software register allocation. CClosure maps directly to host hardware instructions via an ABI-compliant native function call.
  • Upvalue Semantics: Upvalues in an LClosure are indirect and dynamic, supporting shared mutable state across multiple closures via the UpVal abstraction. Upvalues in a CClosure are static values owned exclusively by that closure instance, optimized for persistent state caching between native calls without garbage-collection tracking overhead for external stack frames.
  • Memory Layout: LClosure separates code (Proto) from state (UpVal pointers) to minimize memory usage across repeated function instantiations. CClosure combines the function pointer and upvalues into a single contiguous block of memory allocated dynamically on the Lua heap.
