How lua_pcallk Handles Coroutine Yields in Lua

In the Lua C API, running protected calls across yieldable coroutines historically presented a fundamental challenge due to C stack boundaries. The lua_pcallk function resolves this issue by introducing continuation functions, which decouple the state of a protected call from the native C call stack. This article explains how lua_pcallk operates, how it records execution contexts, and how it reliably preserves protected call semantics—such as error trapping and status reporting—when a coroutine yields and subsequently resumes.

The C-Call Boundary Limitation

In standard ANSI C, an application cannot pause a native function call mid-execution, preserve its stack frame, and resume it later from the exact point of interruption. In Lua 5.1 and earlier, invoking a Lua function from C using lua_pcall placed an inflexible C frame onto the stack. If the invoked code attempted to yield (coroutine.yield), Lua raised an "attempt to yield across a C-call boundary" error.

To circumvent this, Lua 5.2 introduced continuations via lua_pcallk. The k suffix denotes a continuation function (lua_KFunction), which supplies an explicit fallback path for execution to follow once a yielded thread resumes.

Anatomy of lua_pcallk

The signature of lua_pcallk introduces parameters designed to manage yield states:

int lua_pcallk (lua_State *L, 
                int nargs, 
                int nresults, 
                int errfunc, 
                lua_KContext ctx, 
                lua_KFunction k);

Alongside standard parameters for arguments, results, and error handler indices, lua_pcallk accepts:

  • ctx (lua_KContext): An integer or pointer-sized context value passed to the continuation function to maintain arbitrary application state.
  • k (lua_KFunction): A pointer to a C function that Lua invokes when the thread resumes after a yield.

State Storage Inside Lua Call Frames

When a protected call begins with lua_pcallk, Lua creates a CallInfo (ci) structure on its internal execution stack. Instead of storing the continuation inside native CPU registers or C stack frames, Lua records k, ctx, and the error handling state directly in the CallInfo record of the Lua thread (lua_State).

The internal call record sets the CIST_YPCALL (yieldable protected call) flag. This flag tracks:

  1. The expected number of return values.
  2. The index of the error handling function.
  3. The stack base offset where the function was called.
  4. The continuation function pointer (k) and its associated context (ctx).

Because this metadata lives on Lua's heap-allocated call stack rather than the operating system's native C thread stack, the native C function that initiated lua_pcallk is free to return and vacate the native stack when a yield occurs.

Execution Flow During a Yield

When a child coroutine calls coroutine.yield inside a lua_pcallk block:

  1. Lua gathers the yielded arguments and updates the coroutine’s program counter and top pointer.
  2. Lua unwinds its virtual stack frames up to the point of the yield. When it encounters the CallInfo frame created by lua_pcallk, it detects the CIST_YPCALL flag.
  3. Rather than rejecting the yield as an illegal cross-boundary operation, Lua preserves the call frame on the thread's call list, marks the frame as suspended, and propagates the yield status (LUA_YIELD) up to the nearest native caller.

Preserving Protected Semantics on Resumption

When the coroutine is resumed via lua_resume, Lua inspects the top suspended frame on the coroutine's stack:

  1. Successful Execution: Once the yielded function completes execution, Lua recognizes that the completed frame was protected by lua_pcallk. Lua restores the stack base according to the saved CallInfo, places the returned values onto the stack, and calls the continuation function k. The continuation receives the resumed lua_State, the status code LUA_YIELD, and the original ctx.
  2. Error Trapping: If an error occurs after resumption (either inside the resumed code or when raising a runtime error), Lua initiates longjmp or error propagation routines. Because the frame was marked as protected, the error search logic halts at the CallInfo frame containing CIST_YPCALL.
  3. Error Recovery: The registered error handler (referenced by errfunc) is executed if present. Lua then cleans up the stack frames between the error origin and the pcallk boundary, leaves the error object on the stack, and executes k with an error status code such as LUA_ERRRUN.

By attaching continuation pointers and execution metadata to Lua's managed virtual call structures, lua_pcallk ensures that coroutine suspensions bypass native C stack limitations without abandoning error boundaries or stack cleanup duties.
