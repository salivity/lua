Lua C API Bidirectional Embedding Guide

The Lua C API facilitates bidirectional host application embedding by establishing a standardized, stack-based communication bridge between compiled C code and the dynamic Lua runtime. This architecture enables a host program to instantiate isolated Lua states, run scripts, and extract return values, while simultaneously exposing native C functions, types, and memory structures to Lua. By decoupling the execution environments through a virtual stack, Lua achieves high-performance interoperability without compromising memory safety or host stability.

The Virtual Stack: The Core Interoperability Mechanism

At the heart of Lua's bidirectional communication is an abstract, dual-indexed virtual stack managed by the lua_State pointer. Because C uses manual memory management and static typing while Lua uses automatic garbage collection and dynamic typing, direct variable sharing is impractical. The stack solves this impedance mismatch:

  • Positive Indices: Represent elements relative to the bottom of the stack, starting at 1.
  • Negative Indices: Represent elements relative to the top of the stack, starting at -1.

Every operation—whether passing an argument, reading a return value, or altering a global variable—involves pushing or popping values via API functions such as lua_pushnumber, lua_tostring, or lua_getfield.

Direction 1: Host Calling Lua (C to Lua)

When a host application controls Lua, it initializes the runtime using luaL_newstate() and opens standard libraries using luaL_openlibs(). The host executes scripts and accesses Lua constructs through the following steps:

  1. Executing Code: Scripts are loaded and executed using luaL_dostring() or luaL_dofile(), which compile the source into bytecode and run it inside the protected state.
  2. Accessing Variables: Global Lua variables are retrieved via lua_getglobal(), which pushes the variable’s value onto the stack for C to read using inspection functions like lua_tointeger().
  3. Calling Functions: To execute a Lua function from C, the host pushes the function onto the stack, pushes the required arguments in order, and invokes lua_pcall(). The API runs the function in protected mode, pops the arguments, and leaves the results on top of the stack.

Direction 2: Lua Calling Host (Lua to C)

To allow Lua scripts to execute native operations, the host registers C functions within the Lua environment. Any C function callable from Lua must adhere to the lua_CFunction prototype:

typedef int (*lua_CFunction) (lua_State *L);

This interaction functions as follows:

  1. Parameter Extraction: When Lua invokes the registered C function, the function receives a private stack containing the parameters passed from Lua. The C function validates and extracts these using helpers like luaL_checkstring() or luaL_checknumber().
  2. Execution and Return: The C function executes its native logic, pushes any results onto the stack, and returns an integer specifying the exact count of return values pushed.
  3. Registration: The host registers the function in the Lua state using lua_pushcfunction() followed by lua_setglobal(), or by creating a module table using luaL_newlib().

Handling Custom Data: Full and Light Userdata

Bidirectional embedding often requires Lua to manipulate native C memory structures. The C API provides two mechanisms for this:

  • Light Userdata: Pointers (void*) managed by C. Lua stores the pointer as a primitive value, but does not manage its lifecycle.
  • Full Userdata: Blocks of raw memory allocated by Lua via lua_newuserdata(). Full userdata is subject to Lua's garbage collector. By assigning a metatable with a __gc metamethod to the userdata, the C API ensures that native resources (such as file handles or socket connections) are properly freed when Lua collects the object.

Error Handling and State Safety

The Lua C API enforces application stability using protected calls. Functions executed via lua_pcall() trap runtime errors, prevent host application crashes, and push an error message or trace object onto the stack. This defensive boundary allows the host application to recover gracefully from script errors, script timeouts, or malformed syntax during runtime.
