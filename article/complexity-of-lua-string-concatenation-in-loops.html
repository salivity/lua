Complexity of Lua String Concatenation in Loops

Repeatedly using the .. concatenation operator inside a loop in Lua has a quadratic algorithmic time complexity of \(O(N^2)\), where \(N\) represents the number of concatenations or the total length of the resulting string. Because strings in Lua are immutable, every iteration creates an entirely new string in memory by copying all previously accumulated characters. This article explains the underlying mechanics of this quadratic overhead, details the memory and garbage collection implications, and demonstrates the standard \(O(N)\) linear alternative using table.concat.

Why .. in Loops Has \(O(N^2)\) Complexity

Strings in Lua are immutable values. Once a string is created, its contents cannot be modified in place. When you write code such as:

local result = ""
for i = 1, n do
    result = result .. "a"
end

The Lua interpreter does not append the character to the existing buffer. Instead, on each iteration \(i\), it must:

  1. Allocate memory for a new string of length \(i\).
  2. Copy the \(i - 1\) characters from the previous result string into the new allocation.
  3. Copy the appended string.
  4. Intern and hash the newly generated string.

Over \(N\) iterations, the total number of characters copied follows the arithmetic progression:

\[1 + 2 + 3 + \dots + N = \frac{N(N + 1)}{2}\]

This formula yields an asymptotic time complexity of \(O(N^2)\). As the number of iterations grows, performance degrades significantly.

Memory and Garbage Collection Overhead

Beyond the \(O(N^2)\) CPU time complexity, repeated concatenation generates substantial memory overhead. Each step creates an intermediate string that immediately becomes garbage after the reassignment.

For a loop running \(N\) times, \(N\) distinct string objects are allocated. Because Lua maintains a global string table for string interning, each intermediate string must also be hashed and checked against existing strings before being registered. This puts intense pressure on Lua's garbage collector, causing frequent collection cycles and cache thrashing that further slow down execution.

The \(O(N)\) Alternative: table.concat

To achieve optimal performance, string accumulation should be handled using a table as an intermediate buffer, followed by table.concat.

local buffer = {}
for i = 1, n do
    buffer[i] = "a"
end
local result = table.concat(buffer)

Why table.concat Is Linear

  1. Pre-computation: table.concat determines the exact total size of the final string in a single preliminary pass over the table.
  2. Single Allocation: It allocates the exact required memory buffer once, eliminating redundant intermediate buffers.
  3. Single Copy: Each element is copied into the destination buffer exactly once.

This approach reduces the time complexity from \(O(N^2)\) to \(O(N)\), which is the optimal theoretical limit for constructing a string of length \(N\).
