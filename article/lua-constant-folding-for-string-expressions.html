Lua Constant Folding for String Expressions

In the Lua programming language, constant folding cannot optimize complex string expressions at compile time. While the standard Lua compiler evaluates basic numerical arithmetic during the compilation phase, string operations—including simple concatenation and library functions—are deliberately deferred to runtime. This article examines how Lua handles compile-time optimizations, why string expressions are excluded from constant folding, and how this impacts performance.

How Lua Implements Constant Folding

Constant folding is a compiler optimization technique that evaluates constant expressions at compile time rather than computing them at runtime. In the standard PUC-Rio Lua implementation, constant folding is handled directly inside the code generator (lcode.c).

When Lua parses code, it checks whether binary operations involve two known numeric constants. For example:

local seconds = 60 * 60 * 24

The Lua compiler recognizes that 60, 60, and 24 are numeric literals. It computes the result (86400) during bytecode generation and emits an instruction loading that single constant, completely eliminating runtime arithmetic.

String Concatenation and Compile-Time Limitations

Despite supporting numeric constant folding, Lua does not fold string expressions. Even a seemingly trivial concatenation of two string literals is not evaluated at compile time:

local message = "Hello, " .. "World!"

Rather than folding this expression into "Hello, World!", the compiler emits an explicit CONCAT opcode into the generated bytecode. The actual concatenation occurs only when the virtual machine executes that bytecode instruction.

There are key architectural reasons for this behavior:

  1. Compiler Simplicity and Size: Lua is designed with a lightweight, single-pass compiler intended to be fast and minimal. Adding complex compile-time evaluation routines increases binary size and parse-time overhead.
  2. String Interning and Garbage Collection: In Lua, strings are immutable and interned into a global hash table. Creating new strings at compile time forces the compiler to allocate memory and trigger garbage collector mechanisms within the parser, complicating memory management.
  3. Metamethod Semantics: Concatenation in Lua relies on the .. operator, which can be modified or hooked via metamethods (__concat) depending on how operands are resolved in dynamic contexts.

Complex String Expressions and the Standard Library

Complex string expressions typically rely on functions from Lua's string table, such as string.format, string.rep, or string.sub:

local tag = string.format("[%s]", "DEBUG")

The Lua compiler cannot fold expressions like this because Lua is an entirely dynamic language. At compile time, the compiler has no guarantee that the global string table or the string.format function has not been shadowed, replaced, or modified. Function execution cannot safely happen during parsing, meaning any complex expression involving function calls must be evaluated at runtime.

Behavior in LuaJIT

The LuaJIT bytecode compiler shares the same basic compile-time restrictions as PUC-Rio Lua and does not fold string concatenations into a single literal during the front-end parsing phase.

However, LuaJIT behaves differently during execution. Its Just-In-Time (JIT) tracing compiler monitors code as it runs. If a hot loop repeatedly performs string operations or allocations on invariant values, the trace optimizer can eliminate redundant allocations and hoist operations out of loops. While this achieves an effect similar to constant folding, it remains an adaptive runtime optimization rather than a compile-time pass.

Conclusion

Developers working in Lua should not rely on the compiler to optimize string expressions or concatenations ahead of time. To avoid unnecessary runtime overhead, especially in performance-critical code paths, string literals should be combined manually in the source code or pre-processed using external build tools before deployment.
