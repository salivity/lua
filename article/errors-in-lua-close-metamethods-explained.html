Errors in Lua __close Metamethods Explained

In Lua 5.4 and later, to-be-closed variables (<close>) rely on the __close metamethod for deterministic resource management and cleanup. When an error is raised inside a __close metamethod, Lua guarantees that other pending cleanup handlers still execute, after which the new error propagates outward, potentially superseding any previous error that triggered the scope's termination.

Execution of Remaining Cleanup Handlers

When a block exits, Lua processes to-be-closed variables in reverse order of their declaration. If an error occurs inside a __close metamethod, Lua catches it internally and continues calling the __close metamethods of any remaining to-be-closed variables in that scope. The failure of one resource cleanup does not abort the execution of the others.

Superseding Existing Errors

The consequence of an error in __close depends on whether the block was exiting normally or due to a prior runtime error:

  • Normal Exit: If the block was exiting normally (reaching the end of the block, a return, or a break), the error inside __close halts normal control flow and transforms the exit into an error state, propagating upward.
  • Error Exit: If the block was already unwinding due to an active runtime error, the error raised inside the __close metamethod supersedes (replaces) the original error. The original error object is discarded, and the new error continues propagating up the call stack.
  • Multiple __close Errors: If multiple __close metamethods throw errors during the same unwinding phase, each subsequent error replaces the previous one. The final error propagated outward is the one raised by the last __close method executed (which corresponds to the first to-be-closed variable declared in that scope).

Error Catching Limitations

An error generated by a __close metamethod cannot be caught within the same block where the variable is defined. Because the metamethod executes strictly when leaving the block, any internal pcall or xpcall constructs inside that block have already concluded. To handle an error originating from a __close metamethod, the protected call must wrap the entire outer block that defines the <close> variable.
