Generating Lua API Documentation Using LDoc

Documentation generators like LDoc streamline software development by automatically extracting structured comments from Lua source files and rendering them into navigable, formatted HTML web pages. This article explains how LDoc processes special comment annotations, maps them to code entities, parses project configuration files, and renders static API documentation for Lua projects.

Parsing Doc-Comments

LDoc operates by parsing Lua source code and looking for distinct doc-comment blocks. In Lua, standard single-line comments begin with -- and block comments begin with --[[ ... ]]. LDoc identifies documentation blocks when an extra dash is used (---) or within multiline comment blocks starting with --[[[.

Inside these blocks, LDoc recognizes Javadoc-style tags to extract metadata regarding variables, functions, classes, and modules. Common tags include:

  • @module: Defines the scope of a file or sub-module.
  • @param: Documents parameter names and descriptions.
  • @tparam: Specifies explicitly typed parameters (e.g., string, table, or custom types).
  • @return and @treturn: Define returned values and their associated types.
  • @field: Documents table fields.
  • @see: Creates references and cross-links to other functions or modules.

When a doc-comment immediately precedes a function or table definition, LDoc infers the name of the entity automatically from the code, reducing redundant annotations.

Source Analysis and Intermediate Data

Under the hood, LDoc uses Lua's internal parsing libraries or custom lexers to inspect the structure of the target files without executing the code. It scans the token stream to bind extracted comment blocks to the actual code constructs, such as local function, function M.method(), or returning module tables.

LDoc transforms this scanned data into an internal structured object model. This intermediate representation organizes the project into a hierarchy: the overall package contains modules, which contain sections (like exported functions, local routines, and tables), which in turn contain documented members with their parameters, types, and descriptions.

Configuration via config.ld

LDoc's behavior is managed through a central configuration file, typically named config.ld. Written in Lua, this file provides project-level settings to guide the build process, including:

  • project: The display name of the software or library.
  • file: The directory or array of source files to scan.
  • dir: The target output directory for the generated documentation.
  • format: The markdown dialect used inside descriptions (e.g., Markdown or Discount).
  • style: Paths to custom CSS stylesheets to alter the visual presentation.

Template Rendering and HTML Generation

Once the AST-like source analysis is complete and the metadata is structured, LDoc uses a templating engine (typically based on LuaPages or Lua templating patterns) to build the output.

LDoc loops over the intermediate data model and injects the extracted descriptions, type signatures, and cross-references into predefined HTML layouts. The result is a complete, static documentation website containing:

  1. An Index Page: Summarizing all modules, scripts, and topics.
  2. Navigation Sidebars: Allowing users to jump between files, modules, and individual functions.
  3. Cross-Linked Types: Converting documented types into hyperlinks that jump directly to their respective definitions.
  4. Markdown Support: Parsing inline markdown within comment descriptions into formatted HTML tables, lists, and code blocks.

The Build Workflow

The execution is straightforward. Once comments are added to Lua files and a config.ld file is defined in the root directory, developers run the command:

ldoc .

LDoc scans the files, generates the static assets (HTML, CSS, and search indices), and writes them to the designated output folder, ready to be hosted on static site platforms such as GitHub Pages or local servers.
