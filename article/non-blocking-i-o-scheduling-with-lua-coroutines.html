Non-Blocking I/O Scheduling with Lua Coroutines

This article explores how the coroutine-based fiber pattern enables non-blocking I/O operations within the Lua runtime. By combining first-class, stackful coroutines with an asynchronous event loop, Lua can suspend and resume lightweight execution contexts—often referred to as fibers—without blocking the operating system thread. You will learn the mechanics behind yielding on I/O boundaries, integrating kernel-level multiplexers, and achieving synchronous-looking code with asynchronous performance.

The Foundation: Stackful Coroutines as Fibers

Lua does not natively provide operating system threads. Instead, it offers asymmetric, stackful coroutines via the coroutine standard library. Unlike stackless coroutines found in languages like JavaScript or Python (which rely on state machines and async/await markers), Lua coroutines maintain their own execution stacks.

A fiber is essentially a coroutine wrapped with scheduler metadata (such as an identifier, priority, and wake-up conditions). Because switching between Lua coroutines only requires swapping pointers inside the Lua state (lua_State), the overhead is measured in nanoseconds, and memory usage per fiber is minimal—often just a few kilobytes compared to the megabytes typically reserved for OS thread stacks.

The Mechanics of Non-Blocking Yielding

To manage I/O without blocking the host process, all network sockets and file descriptors must be configured in non-blocking mode (e.g., using O_NONBLOCK via fcntl). The scheduling pattern operates as follows:

  1. Initiating I/O: A fiber requests an I/O operation, such as reading bytes from a TCP socket.
  2. Immediate Check: The fiber attempts a non-blocking system call. If data is immediately available in the kernel buffer, the operation completes synchronously without interruption.
  3. Yielding on EAGAIN or EWOULDBLOCK: If the system call returns an error indicating that data is not yet ready, the fiber does not poll in a tight loop. Instead, it yields control back to a central scheduler using coroutine.yield().
  4. Passing Context: During the yield, the fiber passes execution tokens—such as the file descriptor, the requested event type (read or write), and a reference to its own coroutine handle—to the scheduler.

The Event Loop and Demultiplexer

The central scheduler acts as the bridge between Lua fibers and operating system event notification mechanisms (such as Linux's epoll, BSD's kqueue, or cross-platform abstractions like libuv).

Once a fiber yields, the scheduler takes the file descriptor and registers interest with the event demultiplexer. The scheduler then evaluates its run queue:

  • If other fibers are marked as runnable, the scheduler immediately calls coroutine.resume() on the next fiber in line.
  • If all fibers are waiting on external events or timers, the scheduler delegates execution to the system demultiplexer (e.g., executing epoll_wait()), sleeping until the kernel signals that one or more descriptors are ready for transmission or receipt.

Resuming Execution

When the operating system signals that an I/O channel is ready:

  1. The event loop wakes up and retrieves the active file descriptors.
  2. The scheduler uses an internal lookup table to map the signaled descriptor back to the suspended coroutine.
  3. The scheduler removes the registration from the demultiplexer to prevent redundant triggers.
  4. The scheduler calls coroutine.resume(fiber, io_result), passing the acquired socket data or readiness state back into the coroutine.
  5. The fiber picks up execution directly after the point where it yielded, returning the data to the caller as if the operation had blocked normally.

Architectural Advantages

This pattern eliminates callback hell, deeply nested closures, and complex promise chains. Developers write sequential, imperative code:

-- The underlying framework transparently yields and resumes
local data = socket:read("*a")
process(data)

Because the entire scheduling cycle typically runs on a single OS thread, race conditions inherent to pre-emptive multithreading are avoided; execution is cooperatively deterministic. Frameworks like OpenResty (utilizing Nginx's event core) and Tarantool successfully scale to millions of concurrent connections using this exact model, proving that stackful coroutine scheduling remains one of the most resource-efficient paradigms for network-bound workloads.
