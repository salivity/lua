Efficient Lua ECS Architecture with Tables

This article outlines how to implement an efficient Entity-Component-System (ECS) architecture in Lua using its native table structure. It details the design of lightweight entity identifiers, optimal component storage techniques using contiguous array-backed tables, and decoupled systems. You will learn how to optimize memory access patterns, leverage Lua's internal array-versus-hash representation, and minimize Garbage Collection (GC) pauses to achieve high performance in real-time game loops.

Understanding the ECS Model in Lua

In an ECS architecture:

  • Entities are unique identifiers with no logic or data of their own.
  • Components are pure data containers without methods.
  • Systems are functions containing logic that operate across all entities possessing a specific set of components.

In Lua, the table is the sole data structure for arrays, hashes, and objects. An efficient Lua ECS leverages Lua's underlying C implementation of tables—specifically ensuring tables operate in their fast "array part" rather than their "hash part."

Entity Management: Numeric Identifiers

Entities should never be tables containing their own components. Instead, represent an entity as an integer ID. This avoids allocating a table per entity, keeping memory overhead to zero during entity creation and destruction.

Use an ID pool to reuse dead entity IDs to prevent integer overflow and maintain dense data sets:

local EntityManager = {
    next_id = 1,
    free_ids = {}
}

function EntityManager.create()
    if #EntityManager.free_ids > 0 then
        return table.remove(EntityManager.free_ids)
    end
    local id = EntityManager.next_id
    EntityManager.next_id = EntityManager.next_id + 1
    return id
end

function EntityManager.destroy(id)
    table.insert(EntityManager.free_ids, id)
end

Component Storage Strategies

The way components are stored directly dictates memory performance and cache behavior in Lua.

Approach 1: Table-per-Component Type (Sparse Array)

Allocate one master table per component type, indexed by the entity ID:

local Position = {} -- Position[entity_id] = {x = 0, y = 0}
local Velocity = {} -- Velocity[entity_id] = {dx = 0, dy = 0}

While idiomatic, allocating a small {x = 0, y = 0} table per entity introduces significant GC churn.

Approach 2: Flat Primitive Arrays (High Efficiency)

To eliminate GC allocations and maximize performance, decompose components into parallel flat arrays of primitive types:

local PositionX = {}
local PositionY = {}
local VelocityX = {}
local VelocityY = {}

function set_position(entity, x, y)
    PositionX[entity] = x
    PositionY[entity] = y
end

function set_velocity(entity, dx, dy)
    VelocityX[entity] = dx
    VelocityY[entity] = dy
end

Lua allocates contiguous memory for arrays indexed by consecutive positive integers. Storing primitives (number, boolean) directly in index-based tables uses the fast C-array segment of Lua tables, reducing pointer indirection and completely avoiding table allocations during runtime.

Approach 3: Packed Arrays with Dense Sets (Sparse-Dense Architecture)

Sparse arrays indexed directly by entity ID can leave gaps when entities are destroyed, degrading iteration speed. A sparse-dense approach maintains two tracking arrays:

  1. Dense Array: Contains consecutive entity IDs and their component data.
  2. Sparse Array: Maps an entity ID to its index in the dense array.
local DenseEntities = {}  -- [dense_idx] = entity_id
local SparseIndices = {}  -- [entity_id] = dense_idx
local Count = 0

function add_component(entity, x, y)
    Count = Count + 1
    DenseEntities[Count] = entity
    SparseIndices[entity] = Count
    PositionX[Count] = x
    PositionY[Count] = y
end

function remove_component(entity)
    local idx = SparseIndices[entity]
    if not idx then return end

    local last_entity = DenseEntities[Count]
    
    -- Swap with the last element to maintain contiguous memory
    DenseEntities[idx] = last_entity
    PositionX[idx] = PositionX[Count]
    PositionY[idx] = PositionY[Count]
    SparseIndices[last_entity] = idx

    -- Clear last entry
    DenseEntities[Count] = nil
    PositionX[Count] = nil
    PositionY[Count] = nil
    SparseIndices[entity] = nil
    Count = Count - 1
end

This guarantees that systems can iterate sequentially through 1 to Count with zero gaps.

Implementing Systems

Systems are pure functions that run once per frame. They do not maintain internal state; they loop directly through the component tables.

function MovementSystem(dt)
    -- Iterates through packed arrays sequentially
    for i = 1, Count do
        PositionX[i] = PositionX[i] + VelocityX[i] * dt
        PositionY[i] = PositionY[i] + VelocityY[i] * dt
    end
end

When systems require multiple component types, iterate over the component type with the smallest count (the driving query), and look up the secondary components via direct indexing.

Managing Signatures with Bitmasks

For fast component matching across multiple systems, assign each component type a bit flag using Lua 5.3+ native bitwise operators:

local COMPONENT_POSITION = 1 << 0
local COMPONENT_VELOCITY = 1 << 1
local COMPONENT_RENDER   = 1 << 2

local EntityMasks = {}

function add_entity_mask(entity, component_flag)
    EntityMasks[entity] = (EntityMasks[entity] or 0) | component_flag
end

function has_components(entity, required_mask)
    return (EntityMasks[entity] & required_mask) == required_mask
end

Bitmask checks allow systems to quickly filter non-qualifying entities before performing any data lookups.

Garbage Collection and Performance Optimization

  1. Avoid Temporary Tables in Systems: Never instantiate {} inside a loop. If a system must return complex data, pass a pre-allocated table as an out-parameter.

  2. Pre-allocate Tables: If using LuaJIT, use table.new(narr, nhash) to pre-allocate table storage, preventing dynamic resizing during gameplay.

  3. Localize Table References: Cache global tables and functions inside local variables before executing tight loops:

    local px, py = PositionX, PositionY
local vx, vy = VelocityX, VelocityY
for i = 1, Count do
    px[i] = px[i] + vx[i] * dt
    py[i] = py[i] + vy[i] * dt
end

  4. Use Sequential Integer Keys: Do not use string keys for component variables if performance is critical; string lookups force hash resolution, whereas sequential numeric keys map directly to C arrays in the Lua runtime.
