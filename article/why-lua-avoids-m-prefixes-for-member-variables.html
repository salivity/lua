Why Lua Avoids m_ Prefixes for Member Variables

In the Lua programming community, prefixing member variables with m_ or similar Hungarian-style markers is widely avoided in favor of clean, idiomatic naming conventions. This article explores why this practice is discouraged, detailing how Lua’s explicit table referencing, reliance on the self parameter, minimalist design philosophy, and established community idioms render scope-identifying prefixes both redundant and stylistically out of place.

The Explicit Nature of self

The primary reason Lua developers avoid m_ prefixes is that Lua already requires explicit scoping when accessing instance data. In languages like C++, member variables can often be referenced within class methods without an explicit this-> prefix, leading developers to use m_ to distinguish instance fields from local variables and function parameters.

Lua does not have native classes; object-oriented programming is simulated using tables and metatables. When defining a method using the colon syntax:

function Player:take_damage(amount)
    self.health = self.health - amount
end

The method implicitly receives self as its first parameter. Accessing any instance member requires writing self.field. Because the self. prefix is mandatory to access the table, writing self.m_health creates unnecessary syntactic redundancy. The context that the variable belongs to an instance is already made explicit by self.

Minimalist Philosophy and Aesthetic Cleanliness

Lua was designed from its inception to be a small, elegant, and readable language. Its design philosophy favors simplicity and readability over the ceremonial boilerplate common in older C++ and Win32 codebases, where Hungarian notation originated.

Prefixes like m_, s_, or type-denoting tags add visual noise to the codebase. In a dynamic language, adding structural metadata directly into variable identifiers contradicts the language's clean aesthetic. Lua programmers prefer plain identifiers using either snake_case or camelCase, keeping the code readable and lightweight.

Idiomatic Privacy via Closures or Leading Underscores

Prefixes like m_ are sometimes misused to signal access levels, such as private state. In Lua, if a developer wants to signal that a field is internal or private to a module, the accepted convention is to use a single leading underscore (such as self._health). This mirrors conventions found in languages like Python.

More importantly, Lua provides genuine data encapsulation through lexical scoping and closures. If true private variables are required, developers can define local variables inside an object factory function:

local function create_player(initial_health)
    local health = initial_health

    return {
        take_damage = function(amount)
            health = health - amount
        end,
        get_health = function()
            return health
        end
    }
end

In this pattern, health is completely hidden from external access. It is simply a local variable stored in an upvalue, making member-identifying prefixes entirely irrelevant.

Standard Library and Ecosystem Conventions

Conventions in Lua are heavily guided by the core language, the standard library, and the foundational reference book Programming in Lua by Roberto Ierusalimschy. Across the standard library and prominent ecosystem projects, member prefixing is consistently absent. Adhering to these established standards ensures that code remains idiomatic, maintainable, and instantly recognizable to other Lua developers.
