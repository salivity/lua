Understanding Activation Records and Lua CallInfo

This article explains the concept of activation records in computer systems and examines how the Lua virtual machine implements and manages them via its internal CallInfo data structure. You will learn the purpose of activation records, how Lua separates value storage from call control flow, the specific fields that make up a CallInfo node, and the step-by-step lifecycle of function calls, tail calls, and returns inside Lua's execution engine.

What Is an Activation Record?

An activation record, commonly referred to as a stack frame, is a control structure generated when a subroutine or function is invoked. In standard compiler theory, an activation record manages the state necessary to execute a function and safely return control to the caller.

Typically, an activation record stores:

  • Incoming Arguments: Values passed to the routine by the caller.
  • Local Variables: Storage allocated for variables scoped strictly to the function.
  • Temporaries: Scratchpad locations used by the compiler or interpreter during expression evaluation.
  • Return Address: The instruction pointer to resume execution in the calling procedure once the callee terminates.
  • Control Links: Pointers to the previous activation record (dynamic link) and lexical scopes (static link).

While native architectures (like x86-64) map activation records directly onto a contiguous native hardware stack using stack and frame registers (RSP and RBP), interpreted register-based virtual machines like Lua decouple this mechanism to support coroutines, dynamic stack resizing, and tail-call optimization.

Activation Records in Lua: Dual-Stack Architecture

The Lua runtime does not store complete activation records as single contiguous blocks. Instead, Lua uses a dual architecture within the thread state (lua_State):

  1. The Data Stack (TValue array): A contiguous array of tagged values containing function objects, passed arguments, local variables, and temporaries.
  2. The Call Stack (CallInfo list): A separate doubly-linked structure containing execution metadata that defines the boundaries and state of each active call.

Each activation record in Lua is represented by a CallInfo struct, and the current active frame is pointed to by L->ci. While the values used by the function reside on the data stack, the CallInfo structure points into that data stack, providing context on which slices of values belong to which function.

The Anatomy of the CallInfo Structure

Defined in lstate.h, the CallInfo struct acts as the dynamic frame controller for both Lua functions and C functions executed through the Lua C API. Key fields include:

  • StkId func: Points to the location on the data stack where the callable object (the LClosure or CClosure) resides. Arguments immediately follow this position.
  • StkId top: Marks the exclusive upper boundary of the stack space available to this invocation. It prevents a function from indexing outside its allocated virtual registers.
  • struct CallInfo *previous, *next: Pointers linking activation records into a doubly-linked list. Lua allocates CallInfo nodes in an array-backed pool, dynamically expanding it when recursion depth increases.
  • Function-Specific State Union (u):
    • For Lua Functions (u.l):
      • savedpc: The instruction pointer (program counter) storing the address of the next bytecode instruction to execute when this frame regains control.
      • trap: A flag signaling whether execution hooks or debuggers are monitoring this call.
      • nextraargs: Tracks variable arguments (...) when dealing with vararg functions.
    • For C Functions (u.c):
      • k: A continuation function used to resume execution after a yield across a C boundary.
      • old_errfunc: Preserves the previous error handler index.
      • ctx: Contextual data passed to the continuation function.
  • nresults: The number of values the caller expects this function to return.
  • callstatus: Bitmask flags tracking state such as whether the function is running a hook, executed as a tail call, or running inside a protected environment (pcall).

Maintaining CallInfo Across Function Lifecycles

Lua manages activation records across three main operations: invoking a function, executing a tail call, and returning results.

1. Function Invocation

When a function call instruction (OP_CALL) is executed:

  • Lua advances the current call pointer: L->ci = L->ci->next. If the preallocated CallInfo list is exhausted, luaD_growCI allocates more nodes.
  • ci->func is set to the stack index of the target function.
  • For Lua functions, ci->top is set to ci->func + 1 + maxstacksize, where maxstacksize is a statically determined register count computed by the bytecode compiler.
  • The instruction pointer ci->u.l.savedpc is pointed to the first opcode of the target prototype.
  • The previous frame's savedpc is preserved so execution can resume seamlessly later.

2. Tail-Call Optimization

Lua enforces proper tail calls (OP_TAILCALL). When a return statement directly invokes another function, Lua avoids unbounded stack growth by reusing the current activation record:

  • The arguments for the new function are shifted downward on the data stack to overwrite the current function's register window.
  • Instead of allocating a new CallInfo node via L->ci->next, Lua reuses the current L->ci.
  • The func and top pointers are updated, and savedpc is pointed to the new function’s entry point.
  • The caller link (ci->previous) remains unchanged, ensuring the new function eventually returns directly to the original caller.

3. Returning from Execution

When a function finishes via OP_RETURN:

  • Lua copies the return values down the data stack to the position expected by the caller, using ci->func as the reference anchor.
  • If ci->nresults specifies a fixed number of results, Lua adjusts the returned count by padding with nil or trimming excess values.
  • The virtual machine restores the caller’s context: L->ci = L->ci->previous.
  • Execution resumes at the instruction pointed to by the restored frame's u.l.savedpc.

By decoupling call bookkeeping (CallInfo) from data storage (the TValue stack), Lua manages coroutine yields, dynamically resizes register windows, and avoids C-stack overflow during deeply nested or tail-recursive execution.
